# F003 — GitHub issue / PR 报错溯源

**Status**: in-progress（当前验收仅以下表为准；排除大规模导入，真实模型未通过项不以工程测试替代）
**Created**: 2026-09-10

## Why

用户 2026-09-10 提的第二个需求：

> 比如我遇到一个报错，我们的 LLM-wiki 是否可以找到对应的 PR 或者 issue。

这类知识不在源码里，也不在文档里，只存在于社区讨论中。vllm-ascend 当前规模（2026-09-10 查 GitHub API）：

| 项 | 数 |
|---|---|
| PR 总数 | 12,074 |
| issue 总数 | 4,188 |
| 最新编号 | #16285 |

关键取舍先说清楚：**这 1.6 万条不做成 wiki 页**。按 2026-09-10 的试点单价估，全量转页要四万美元量级（当时的估价，是「不做成页」这个决策的依据；实际花费一律以 `pnpm wiki:budget status` 为准），且绝大多数 issue 没有沉淀价值。只有真正改动核心特性的 PR 才升级成 wiki 页（AC6）。

**2026-09-22 用户改了取证方式**（Codex 会话，原话）：

> 可以 然后我们限定个时间吧  近一年的 然后vllm仓库的我也想要 不仅仅是vllm 或者 我们不本地存储 我们做一套 贴出一个报错，找到相关 issue，读到解决办法，追到修复 PR，再判断自己的版本有没有修复。   这个机制 自动去github查 可行吗?? 哪个更好呢

随后用户同意「在线查 GitHub + 少量证据缓存」，并问「这个需要固化成一个skill吗？」。所以：不再做全库本地镜像；提问时在线搜 vllm-ascend 与 vllm 两个仓库、近一年；做成命令行与 skill，也接进网页聊天。

**2026-09-23 用户审视后逐条定的**（本会话原话）：「1 恢复 2、算 3、驳回 4、不需要 排错只是我们的一个功能 5、改」，即：

1. 09-22 被按实现改写的验收条文**恢复**：聊天层接入、调参样本另取、AC3 的非零退出与写 log、AC5 的 tag 列表放回来，状态按恢复后的条文重评（下表）。
2. **网页聊天接入算 F003 的验收项**。
3. 09-22 的 PR 11953 草稿**驳回**（整合一步是写死的，见 AC6）。
4. 在线排错**不写回知识库**：排错只是一个功能，查到的是社区线索，不升级成 Wiki 结论。

## What

用户能感知到的变化：

- 贴一段报错到聊天框，能得到「issue #1234 报过同样的错，PR #1300 修了，修复进了 v0.9.1，`v0.7.3-dev` 分支没有这个修复」。
- 问某个特性时，答案能带上相关的设计讨论与已知问题。
- ~~语料每天自动增量更新，不需要人操作~~——2026-09-22 起不做本地语料，改为提问时在线查、缓存已读证据（用户原话「我们不本地存储」）。

同一套在线查证有三个入口：网页聊天（贴报错自动触发）、命令行 `pnpm wiki:github-trace`、给 agent 用的 skill `.agents/skills/vllm-error-trace/`。搜索范围只在 [`wiki/github-trace.config.json`](../../wiki/github-trace.config.json) 定义一次。

- **AC1 · 有界在线搜索**（2026-09-22 按用户方向取代原「全量拉取」，原文见 `git show f4c55d3^:docs/features/F003-github-corpus.md`）：实际仓库、时间与查询可核对；候选数量不冒充全量计数。
- **AC2 · 按需取证与缓存**（2026-09-22 取代原「增量更新」）：正文、讨论、关联事件、PR diff 和评审有来源与时间，截断或缺失显式报告。缓存不自动成为正式页。
- **AC3 · 失败可见**：API 限额、网络失败、token 失效各自给出可区分的报错信息，非零退出，并在 `wiki/log.md` 写一条同步记录（时间、拉取数、失败数、原因）。验收：用无效 token 跑一次，报错指明是鉴权问题而不是笼统的网络错误。
- **AC4 · 报错检索**：聊天层通过 F001 AC10 的 `retrieve()` 接口接入语料（2026-09-22 起没有本地语料，聊天层接入的是在线搜索，与 `retrieve()` 在同一次问答里一起交给模型）。第一版实现：从用户贴的报错里抽取稳定片段（异常类名、错误信息主干、去掉路径与行号等易变部分）做精确 grep。验收：预先固定 10 条真实 issue traceback，Top-5 包含原 issue 的条数 ≥ 7，同时报告 Top-1；调参样本另取，检索输入不含 issue 编号、URL 或答案标注。另设无匹配对照，不得把词面相似呈现成已确认修复。不达标记录实测数据，按 F001 的约定评估是否给语料加向量检索。
- **AC5 · 溯源链路**：命中 issue 后顺着 `fixed by #NNNN` 找到 PR，再查 F002 的谱系得出修复进了哪些 tag 与分支。验收：给定一条已修复的 issue，输出链路完整（issue → PR → 合并提交 → 含该提交的 tag 列表）。
- **AC6 · 重要 PR 升级为 wiki 页**：PR 的 diff 若触及 seeds 里声明的入口文件或 F002 的参数定义文件，自动排进 ingest 队列生成草稿；社区不可信文本（PR 正文、评论）经 sanitize 模块处理后才进 prompt。作者不绑定一家模型（用户 09-22：「不需要定死claude」）。验收：挑一个真实的参数改动 PR，草稿生成且 diff 可读；构造一条含提示注入的评论，sanitize 后注入片段不出现在 prompt 里。
- **AC7 · 解析 issue 里引用的文档链接**：社区讨论大量引用官方文档 URL（`docs.vllm.ai/projects/ascend/en/<版本>/<路径>.html`）。抓取时把这类链接解析成结构化引用（版本 + 路径），并映射到本地 `docs/source/` 的对应文件，让「这条 issue 讲的是哪一页文档」可被检索与跳转。链接指向的版本与当前钉住的版本不同时要标出来。验收：取 10 条含文档链接的真实 issue，链接全部被解析出版本与路径，且能映射到本地文件（映射不到的要给出原因，例如该页已被删除）。

**Out of scope**：向量检索（先实测命中率，不达标再评估）；把全部 issue 转成 wiki 页（成本不成立，见 Why）；全库本地镜像（用户 09-22「我们不本地存储」）；GitHub webhook 实时推送；**把排错结论写回知识库**（用户 09-23「不需要 排错只是我们的一个功能」）。vllm 上游仓库原在此列，09-22 起按用户原话「vllm仓库的我也想要」纳入搜索范围。

## 使用与费用边界

```bash
pnpm -s wiki:github-trace plan --input <日志文件>
pnpm -s wiki:github-trace search --query "UnquantizedFusedMoEMethod is_monolithic"
pnpm -s wiki:github-trace inspect --url https://github.com/vllm-project/vllm-ascend/issues/15815
pnpm -s wiki:github-trace verify --repo vllm-project/vllm-ascend --fix 87c345c13d3b259fac8761d68381bd91df6906aa --target releases/v0.26.0rc
```

命令与聊天里的在线搜索都不调用模型、不写 GitHub；凭据只读环境变量 `GITHUB_TOKEN`，没有也能查公开资料，但限额低（匿名搜索每分钟 10 次、其余接口每小时 60 次），限额不足如实报告。只有清洗后的特征词发给 GitHub，原始日志、路径、token 不出本机。聊天里的回答本身仍由问答模型生成，费用按问答计。

## Dependencies

- **GitHub 访问**：凭据放本机环境变量 `GITHUB_TOKEN`，不进仓库、不输出值；按实际端点选择最低所需读取权限。
- **F001 AC10**：聊天层接入走同一次问答的检索步骤（`server/chat-route.ts`）。
- **F002 与本地克隆**：「修复进了哪些版本」用本地克隆判断，钉点只认 `wiki/seeds/vllm-ascend-code.yaml`（夜间任务与行号审计用的也是它）。
- **官方文档站与本地 `docs/source/`（AC7）**：解析 issue 里的文档链接需要两边的映射关系。
- **F004 共用编译与审阅管线（AC6）**：sanitize、队列、草稿和批准后的整合由 [F004 plan](../plans/knowledge-loop-plan.md) 定义一次。

## Design Decisions

| 决策 | 选项 | 结论 | 原因 |
|------|------|------|------|
| 1.6 万条的处置 | 全转 wiki 页 / 存为检索语料 | **不转页，选择性升级为页** | 按 2026-09-10 的估价全转要四万美元量级，且多数无沉淀价值 |
| 取证方式（09-22 改） | 全库本地镜像 / 提问时在线查 | **在线查 + 缓存已读证据** | 用户 09-22 原话「我们不本地存储」；全量首拉不现实，也不是排错的前置条件 |
| 语料是否进 git | 进 / 不进 | **不进**；在线缓存在 `tools/wiki-runtime/`（gitignore） | 与 `tools/repos/` 同样的处置方式 |
| 报错检索第一版 | 直接上向量 / 先精确匹配并实测 | **先精确匹配，实测命中率再决定**（用户 2026-09-10 拍板先不加向量）；09-22 起匹配交给 GitHub 搜索，本地只做清洗与抽特征词 | 向量要引入嵌入模型、向量库与重嵌入流程，且会成为第二个真相源 |
| PR 号与 issue 的关联 | 只给原文让模型自己找 / 程序先找 | **程序先找关联 PR，按依据排序**：主动引用 issue 的（cross-reference）在前，评论提及其次，正文提及最后（09-23） | 修复 PR 通常写着「Fixes #N」；正文里提到的多是背景。真实跑 #15815 时按出现顺序取，修复 #15981 被旧 PR 挤掉 |
| 修复进了哪个版本 | 在线 compare / 本地克隆 | **聊天路径用本地克隆**：按 `(#N)` 找合并提交，main 上没有就查发布分支；对钉点做祖先判断，列含该提交的 tag（09-23） | 不耗 GitHub 限额；钉点与 F002 同源。原提交不在祖先链上不等于没修（可能有回移），同号提交单独标出 |
| 网页聊天怎么接（09-23） | 给模型加工具 / 服务端先查再交给模型 | **服务端先查**，候选作为社区线索与知识库检索一起交给模型，同时显示给读者；只在有异常类名或 traceback 时触发 | 不给问答模型开新工具；普通提问不发网络请求 |
| 不可信文本 | 直接进 prompt / 先 sanitize | **先 sanitize，并限制问答与编译 agent 的工具与读取范围** | issue、PR 正文、评论都不能作为工具指令；文本清洗本身不是完整隔离 |
| 写不写回知识库（09-23） | 写成草稿待审 / 不写 | **不写** | 用户：「不需要 排错只是我们的一个功能」 |

各轮的历史实施证据在 [逐轮 review 归档](../plans/archive/README.md)，只作历史保留；当前状态一律以上方验收表为准。
