**glm-5-3-flash（22 分）**
懂了：45 层 = 34 层 KDA + 11 层稀疏 MLA；MLP = 前 3 层稠密 + 42 层 288 选 8 MoE；4 条 residual 流；一次前向的四步（查表 → 45 层 → logits → 采样）；3133 亿总参 / 174 亿激活，以及这些数从 config.json 哪个字段来。KDA 的「linear attention → DeltaNet → Gated DeltaNet → KDA」四步演进是全页最好的写法，我真的跟上了。

**glm-5-3-flash-two-node（16 分）**
懂了：TP/DP/EP/PP 各自切什么（本页 55–60 行才第一次说清）；为什么两台不是因为「单机放不下」，而是 KV 容量、每卡专家数、MC2 门槛三件事；每卡权重 20.58 GiB，86% 是路由专家；块 = 640 token = 7.969 MiB，一条 7 token 的新请求一进来就吃掉 15 块 119.5 MiB；启动七步。
模糊：3,855 块和 3,908 块哪个是「答案」；「块」的五种含义；索引器那份 FP32 副本为什么不算进 KV 预算。

**one-request（29 分，全线最长也最好）**
懂了：七站；prefill 与 decode 的区别落在哪一站；每张卡每层的形状怎么来；一次前向 218 次集合通信、只搬 7.3 MiB，所以慢在固定开销而不是带宽；MTP 草拟 3 个 + 下一步验证 + 按接受数回退计数；短请求块利用率 0.6%。「常见误解」8 条当场纠正了我三个错觉（以为 TP8 下 KV 也切 8 份、以为 MTP 让每步算得更少、以为拒绝的候选要还块）。
模糊：稀疏 MLA 那 11 行形状表里哪一维是头、哪一维是 token；`topk_indices [4, 2051]` 到底装了什么；MTP 「左移一格」的三路对齐。

**concurrent-requests（19 分）**
懂了：continuous batching；调度器没有 prefill / decode 之分，只看「还差几个位置」；8192 预算先给 running 再给 waiting；13 条请求拼成 6048 行 + query_start_loc；两次补齐（先自己的图尺寸、再两组最大值）；一条长 prefill 让两台机器一起退回 eager + All-Gather，DP1 的 28 行被拉到 6048 行；抢占在本部署特别贵（无 prefix caching + KDA 状态一起丢）。场景 M 走三步是全主线最有效的教学装置。
模糊：KV 块那条加法式里 `3 组 × 4 块` 的 4 是什么；20,000 / 60,000 / 67,983 / 68,000 四组数字分别属于哪个设定。

## 三、TP / EP / DP 专项跟踪

**第一次出现**：三个词同时出现在 `learning-guide.md:27` 的表格单元里——「TP8（tensor parallel，张量并行）、DP2（data parallel，数据并行）、EP16（expert parallel，专家并行）」。解释只有英文全称 + 中文译名，没有说切的是什么、为什么要切。紧接着 `learning-guide.md:30` 就在用「每台机器是一个 DP 执行组」。
**第一次真正解释**：`glm-5-3-flash-two-node.md:55-60` 的四行表。此后 `one-request.md:121-123`、`concurrent-requests.md:86`、`request-call-chain.md:100-101` 各重述一次，共四遍。
`glm-5-3-flash.md` 全页不用这三个词，干净。

**进入 tensor-parallel 页之前，我的理解**：
- **TP**：一台机器里的 8 张卡把同一层的同一个矩阵切开、各算一段，列切的直接拼、行切的算出部分和后用 All-Reduce 相加，每张卡都拿到完整结果；只在机内，不过机间链路。我还能说出哪些权重按 TP 切、哪些每卡各存一整份。——懂得比较实，但「为什么 `o_proj`、`down_proj` 必须 All-Reduce 而 `gate_up_proj` 不用」全线只讲过一次（one-request.md:298）。
- **EP**：288 个路由专家除以 16 张卡、每卡 18 个，合起来才是一份；token 被 router 选中的 8 个专家多半在别的卡甚至别的机器上，所以要 dispatch 过去、combine 回来；通信在 MC2 和 All-Gather 之间二选一，门槛是两组 token 数的最大值 128。——机制懂了，但 MC2 到底「融合」了什么、为什么不让每台机器各存一整套专家，说不出。
- **DP**：两台机器各是一个执行组，各有自己的 scheduler 和 KV 池，新请求按 `waiting×4 + running` 打分派给一组、之后不迁移；两组每步必须对齐 token 数和图模式，宽度由更忙的那组决定，空闲组也要陪跑。——三个词里我懂得最清楚的，因为场景 M 真的演了三步。但「DP 执行组」和「DP 通信组」的区别只在 two-node.md:130 说过一次，读到 concurrent-requests 时我已经忘了那 8 个跨机配对的两卡小组是干什么的。
