# 已有验收知识的回答使用复核

本轮处理“原页已有质量、延迟等要求，但回答没有把它们带入后续方案”的问题。只修改共用回答规则与试跑说明，没有增加或改写教学页、应用代码和图。新案例对照与实际产品调用分别保留，不能合并成一次有库/无库增益测试。

## 为什么没有继续补页面

独立复核旧题的输入、正文快照和原答后，结论分成三层：

1. **知识已经给到。** 相关页的完整文字在旧 A 输入中逐字存在，B 沿用同一 agent 上下文。没有发现所需段落缺失或截断；旧答长度也没有用满限制，不能把遗漏直接归因于字数上限。
2. **试读指令和产品指令不同。** 旧批使用“最小取证、按结果展开”的临时指令，没有带产品的手册查询规则。产品的两种 provider 已经消费该共用规则，没有发现规则传递代码缺陷。旧试读不能直接代表产品实际问答。
3. **回答边界和评分都要查。** S1/S2/S4 的现有记录解释基本成立；欠清楚的是未来改变配置或宣布服务可用时，启动阶段代价、完整交付及原输出约定怎样继续验。已经给定的条件不必重采，也不能因为没有重复某个词就判缺失。

特别纠正旧 T2 的解释：对其中关于最终成功率的追问，原答要求追踪剩余 15 条的最终结局，已经足够；额外要求追踪其质量和延迟目标是否满足，超出这项追问。题目另外涉及完成速率，原答已分别给出相应窗口口径。本轮保留原题、原答和原分，在[独立原因审查](../../../../tools/wiki-runtime/inference-answer-acceptance-2026-11-01/private/cause-audit.md)单列评分范围争议，不再将 T2 当作已证实的验收遗漏。

这些证据能定位维护职责，不能唯一证明模型内部为什么忽略了某段话。指令侧重、上下文位置与生成差异各占多少，仍未分离。

## 改在唯一维护处

- [手册查询规则](../../../../wiki/HANDBOOK.md#查询)的两条既有规则明确区分定位和验收：定位只取当前分支的必要证据；优化或恢复要在正常设置、目标负载下核对受影响的质量、延迟/吞吐、成功/失败/未完成与资源代价。改变启动或执行图还要纳入启动成功、准备耗时和峰值。
- 保留已知条件直接沿用、未知目标不编造、未发生异常仅作为条件分支、数值异常逐步缩小范围。局部计算与概念解释不套现场清单，指标门槛方向和全文时序一致要求继续保留。
- [试跑包说明](../../../superpowers/plans/inference-pilot-2026-10-31/README.md)要求模拟助手回答时直接提取并冻结同一份查询规则。纯学习者试读仍只给任务与正文；不另维护一套试跑答案指令，不追改旧实验。

修改后的查询片比旧片增加 22 字符。最初长稿触发既有提示长度测试，随后压缩并恢复独立审查发现弱化的两项旧约束，没有提高测试上限。原始 diff、各稿与失败日志均在本批附件保留。

## 四道未测题，十二份独立原答

出题者先核对旧题并冻结新题与依据；每题三种指令各运行一次，全新上下文、相同完整页面及长度要求，不择优重跑。A 为旧试读风格的中性指令，B 加改前手册查询片，C 加改后查询片。三组都使用知识库，比较的是回答组织指令。

| 新题 | 需要迁移的判断 | 复用正文 |
| --- | --- | --- |
| V1：量化提速但字段值出错 | JSON 可解析不等于质量通过；后处理要与模型作为整体重验，再比较真实负载下的完整交付 | 低精度格式、推理测量 |
| V2：长解释提速，能否全量切换并提额 | 长输出饱和吞吐不能代替短/长请求各自的延迟及质量约定；切换策略和提高接单上限分开验证 | DSpark、推理测量 |
| V3：按次启动的短批任务 | 把准备时间、运行时间和设备资源放回完整任务；不能拿预热后的步速代替冷启动交付 | 执行图、推理测量、容量恢复 |
| V4：同为两字节，范围和精度为什么不同 | 用相邻数间距解释局部分辨率，不扩展成部署验收 | 低精度格式 |

独立评分者只拿匿名原答、题目、冻结依据与正文，先评分再揭盲。原始初评为 11 份通过、1 份部分满足；164 处评分引文和 11 处歧义记录引文均已核对。分组结果如下：

| 题目 | A：中性指令初评 | B：改前规则初评 | C：改后规则初评 |
| --- | --- | --- | --- |
| V1 量化与业务质量 | 通过 | 通过 | 通过 |
| V2 混合业务与提额 | 通过 | 通过 | 通过 |
| V3 冷启动批任务 | 部分满足，有评分歧义 | 通过 | 通过 |
| V4 局部格式解释 | 通过 | 通过 | 通过 |

V3 的 R03 原判仅因没有单独写“结束释放设备”扣项。评分者在揭盲前已指出宽严不一致：三组都只改捕获表、沿用完整按需任务，另两答也没有独立的释放探针。本轮按冻结量表“未变条件可沿用”的通则裁决 R03 可以通过，原分不覆盖；详见[原始盲评](../../../../tools/wiki-runtime/inference-answer-acceptance-2026-11-01/private/blind-review.md)、[盲态歧义记录](../../../../tools/wiki-runtime/inference-answer-acceptance-2026-11-01/private/blind-review.ambiguities.md)及[范围复核](../../../../tools/wiki-runtime/inference-answer-acceptance-2026-11-01/private/adjudication.md)。这不证明真实设备已经释放。

**能确认什么：** 改后规则的四答能保留本题相关验收，概念题也没有被强塞现场清单。改前规则同样四题通过；按一致口径，三组全部满足本批要求。没有足够证据证明新规则优于旧规则，更不能用那一处有歧义的初评分差宣称提升。正文在三组里都能支持机制、完整交付与取舍，本批没有测无库状态下是否也能答好。各答的具体差异与等价表达见[揭盲比较](../../../../tools/wiki-runtime/inference-answer-acceptance-2026-11-01/private/unsealed-comparison.md)。

**方法限制。** 这是 4 题各 3 份、每格一次的探索对照，执行顺序为固定交错而非随机。主持人在最终文字压缩时已看到题型简报，最后恢复旧规则约束时已读题干；当时未读私有依据，也没有新答案生成，不声称改写对题型全盲。模型精确 ID、随机种子及 token 用量未提供；文件隔离依靠任务指令，不是安全沙箱。不能推统计显著性、总体正确率或正式十二题验收完成。

## 另做一次真实站内问答

向正在运行的 `POST /api/wiki/chat` 只发送 V2 原问题，由服务自己检索，未附指定页或评分条件。一次调用 HTTP 200，无错误事件；[原答](../../../../tools/wiki-runtime/inference-answer-acceptance-2026-11-01/product/answer.md)、完整事件和六个引用页正文均已保存。

原答暂缓全量切换和提额，先按真实 85% 短答案、15% 长解释及每秒 12 条做对照。明确保留短答案至少 95% 在 0.7 秒完整交付、长解释至少 95% 在 1 秒出现可见答案、有效文本间隔不超过 0.25 秒，以及原题库的答案和推理步骤质量要求；失败和未完成请求保留在报告中。之后才分开尝试提高接单上限，并按不达标的类别继续排查。

这说明本次实际产品回答把相关正文用进了可执行方案。[产品独立复核](../../../../tools/wiki-runtime/inference-answer-acceptance-2026-11-01/product/independent-review.md)确认上述条件已落实，未发现新实质问题；自动 `covered` 单独记录，五条自动审阅引文已核对在当次正文中存在。没有运行题设的模型负载或设备实验，不能写成方案上线有效。

本次请求未保存完整生成提示：十个检索候选、预算内注入页和六个引用页不是同一集合。两种 provider 的规则接入另以实际请求构造检查及测试验证，不把重建材料冒充当次模型输入。证据范围、requested 模型与实际版本未报告等限制见[调用说明](../../../../tools/wiki-runtime/inference-answer-acceptance-2026-11-01/product/provenance.md)。
