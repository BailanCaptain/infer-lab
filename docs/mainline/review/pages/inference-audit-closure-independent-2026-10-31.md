## 前两屏的独立复述

以下是审查代理依据页面开篇的概念、例子与图所做的复述，不是真人初学者试读，也不代表已经测得理解率。

| 页 | 我理解的“是什么” | 我理解的“代价在哪” |
|---|---|---|
| DyntraLB | 专做 decode 的同一实例里，各 DP 组互报请求历史占的块数，下一步在各自组内决定谁继续、谁暂停、谁接入；请求和 KV 不跨组迁移。它用块数挑候选计划，耗时收益要另看时间线。 | 暂停的短请求要等恢复才能继续输出，KV 仍占着；每步互报有通信和规划开销，预取候选也会占本组块。让长请求提前运行不自动等于整步变短。 |
| 请求调用链 | 一条请求的七站分布在 API server、EngineCore、worker；同进程是调用，跨进程要把请求/结果交给另一进程。日志必须同时对齐请求、批次、进程和步骤才能认站。 | 跨进程交接和集合通信需要等待；两组共享 MoE 专家，所以没有收到该请求的另一组仍要陪跑。异步重叠让调度与执行跨步交错，排障也需要把旧结果和旧清单配对。 |
| Scheduler | 每步按“应算减已算”分配本步位置数，先续 running，再接 waiting，同时满足 token 预算、请求数上限和 KV 容量。预算是计算位置，不是输出字数，也不是请求条数。 | 新请求会排队，长输入会被分成多步；KV 不足时抢占会丢掉已算进度并重算。完整序列准入检查会挡住第一段本来放得下的请求，但检查不等于立即预分配所有未来位置。 |

## 发现与关闭证据

### P2-1：DyntraLB 的“原等待时间”需要前后可比条件

- **位置：** `dyntra-lb.md:124`、`:130`、`:138`。
- **初稿问题与影响：** “DP0 仍最慢、DP1 仍先结束”不足以推出新增工作落在调整前的等待区间内；DP0 自身变慢时也会出现这个相对顺序。机制段还把读取历史最多直接等同于最晚完成，弱化了本轮要保留的“块数只是估计”。
- **依据：** `vllm-ascend@baa023ad` 官方 `dyntra_lb.md` L155–L157、L198–L207 说明块数是估计，并列出模型、草稿与算子成本；planner L201–L204 使用固定常数 20000 与 19.2，没有测量各组执行结束时间。
- **修法及结果：** 已加上“DP0 的耗时保持原水平”；机制段改成全注意力、执行条件相近时历史读取工作增加的趋势；等待图的解释明确是示意假设，现场须由时间记录确认瓶颈。复核关闭。

### P2-2：容量检查不触发全量预分配，但本步能恰好覆盖完整输入

- **位置：** `vllm-scheduler.md:148`、来源 40。
- **初稿问题与影响：** “既不当场分配全部输入块”过于绝对。若本步确实计算完整输入，就应分配它所需的块；准入检查与实际分配量不同，不表示实际分配绝不会覆盖完整输入。
- **依据：** `vllm@0fc695fc:vllm/v1/core/kv_cache_manager.py` L354–L368 仅执行容量判断；L370–L373 根据本步新增位置和 lookahead 求需槽位数；L385–L418 再检查并调用实际分配。容量判断没有替未知全部输出预留位置。
- **修法及结果：** 已改成“检查本身不触发全量预分配”，保留按本步与候选位置借块，并明示本步计算完整输入时会分相应块。来源 40 从 L354–L370 扩为 L354–L418，页末索引同步。复核关闭。

### P2-3：dummy 分支的精确引用遗漏了实际触发条件

- **位置：** `request-call-chain.md:87`、`:363`、`:382`。
- **初稿问题与影响：** 来源 57 原从 L2033 注释中段开始，未含 L2027–L2031 的零 token、external launcher 和 DP 大于 1 的实际判断。正文结论正确，但该精确引用无法独立展示触发条件。
- **依据：** `vllm-ascend@db701c1f:vllm_ascend/worker/model_runner_v1.py` L2027–L2042：先在整批零 token 分支检查 external launcher 与多 DP，做 dummy，再按是否有 KV transfer group 返回空输出或转 connector；L2050–L2057 另对持久批次 token 列表作保护。
- **修法及结果：** 来源 57 扩为 L2027–L2057，正文同时指来源 16、57，页末索引同步。复核关闭。
