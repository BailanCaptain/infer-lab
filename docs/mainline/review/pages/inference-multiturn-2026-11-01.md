# 真实站内多轮排查：随证据转向，并在合适的位置停

本轮测试五条此前未用过的三轮案例：先给现象，再补定位日志，最后给复验结果。请求经过现有读者站点的问答接口；同链后续只发送当轮问题与服务返回的 sessionId，不附指定页面、评分依据或未来日志。设备数据均为合成记录，真实执行的是站内问答，不是硬件实验。

**结果：五条链选用的完整答案都能作出必要诊断、继承相关验收目标并给出合理停点，无未关闭 P1/P2。** 但不能说全部知识均已覆盖：启动案例首轮涉及容器限额的外部依据不足，自动审阅保留 undetermined；现场记录补齐后才有该案例的归因依据。修前的九轮核心判断本来就正确，不把后续修补描述成“九道错题变对”。

本轮没有新增或改写教学页、手册规则、图和目录。修订集中在问答会话及已有的联网提示：原来后续 Codex 调用只拿到此前用户问题，拿不到此前助手建议；现在同版本、同模型下保留有界的完整问答，作答与独立审阅共享这份上下文。

## 两处实现问题及修订

### 1. 应用会话连续，但上轮助手建议丢失

原实现保存最近用户问题，Codex 每次使用新的 ephemeral 进程，也没有原生 sessionId 可恢复。因此，用户说“你刚才第二步的记录齐了”，模型无法从输入找到只有上一轮助手说过的检查动作；独立审阅者同样缺少它。

先用实际 HTTP 编排的固定模拟答复复现：第一轮给出仅在助手回答出现的动作，第二轮断言作答输入和审阅输入都包含它，两项均失败，见[红测](../../../../tools/wiki-runtime/inference-multiturn-2026-11-01/history-red.log)。这证明传递缺陷，不冒充真实模型已经答错。修前案例由旧用户问题仍能推断主要现场事实，因此九轮通过并不能否定这个缺陷。

修订在 [chat-session.ts](../../../../server/chat-session.ts)、[chat.ts](../../../../server/chat.ts)、[chat-route.ts](../../../../server/chat-route.ts)和 [answer-quality.ts](../../../../server/answer-quality.ts)：

- 最近最多三个完整成功问答对，整个 JSON UTF-8 不超过 32 KiB。从新到旧保留连续后缀，不截半条日志，不跳过中间轮；超出窗口时明确提醒模型不能猜旧答细节。
- 同知识版本、同模型才提供旧答。知识或模型变化仍只保留旧问题，并沿用现有重检提示；失败/中断轮次不污染成功历史，旧会话文件兼容。
- Claude 原生续聊不重复注入；无原生会话时才补保存的问答。历史只是指代材料，旧建议不能冒充用户已执行的动作，旧判断须按新日志和当前正文重核。
- 独立审阅接收同一问答历史，实际字节计入既有输入预算，没有扩大窗口或放宽校验。

独立代码审查及兼容性验证见[history-review](../../../../tools/wiki-runtime/inference-multiturn-2026-11-01/private/history-review.md)。重载后的九轮均保存完整当前回答，六次追问的真实审阅输入包含相应前轮问答；审阅沿用既有清洗规则移除 HTML 注释等内容，原始 SSE、答案和会话历史另行保留。作答输入由编排回归测试核对，没有将本地重建称为截获的线上 prompt。

### 2. 未联网核对，不等于已证明工具不可用

H2 首答称“本轮联网核查工具也不可用”，但回执只能说明配置允许联网且没有记录到联网调用，不能证明运行时工具不可用。独立复核将它记为 P3 表述问题，不升级为错误根因。

复用原有 `claimsOffline` 和提示通道，补识别这一措辞；提示改为“未记录到联网调用，工具不可用的说法尚未核实，外部结论尚未完成联网核对”。[措辞红测](../../../../tools/wiki-runtime/inference-multiturn-2026-11-01/notice-red.log)、最终编排测试及[浏览器提示检查](../../../../tools/wiki-runtime/inference-multiturn-2026-11-01/browser-notice.log)均保留。原答不改，也没有用提示替它补外部来源。

H2 的容器限额、137 和具体事件机制尚不能称为库内完整覆盖。首轮的材料不足保留；第二轮的现场归属来自题设新日志，库负责阶段、内存边界和验收框架。现有缺口流程保留该信号，不为这次有边界的诊断另建泛化教程。
