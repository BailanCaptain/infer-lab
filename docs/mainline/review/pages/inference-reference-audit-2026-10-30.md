# 三份参考资料反向核对与公开案例验证（2026-10-30）

## 本轮结论

沿用户最初给出的 DeepSeek 生产实践、DeepInfer 和昇腾 950 白皮书反向检查，现有知识库已经有请求主线、测量、诊断、生产与容量、模型策略和硬件机制这些入口。本轮发现的主要缺口是几个跨层解释：离线性能数字怎样计数，请求数量如何转换成工作量，硬件资源怎样成为框架可用的缓存，以及传输报告成功后怎样继续核对内容。已补进六个现有页面，没有新增教学页。

当前可以给出的判断是：**学习者读完相应路径，有页面可解释三份资料的主要机制；从业者能够从这些页提取有条件的取证和对照方法。** 尚不能宣称读者已经学会、任意部署故障都能定位，或某设备获得了性能提升。公开资料中的完整生产系统、具体版本的实现和现场结果，仍需分别核验。

## 公开案例：先有现象，再看证据怎样改变判断

本轮使用项目 `vllm-error-trace` 的查询流程，先查知识库，再限定 GitHub 仓库与一年范围搜索，随后完整读取选中 issue/PR 的正文、评论和可用补丁。查询与检查回执在 `tools/wiki-runtime/github-trace/reference-audit-{search,64048,59586}.json`，累计 11 次 GitHub 请求。没有提交评论或修改外部仓库。

### A：传输成功，为什么第一步生成就错了

[vLLM issue #64048](https://github.com/vllm-project/vllm/issues/64048) 报告的是两台 GH200、Qwen3-8B、vLLM 0.31.0、NIXL 1.5.0 的 P/D 交接问题。单独生成正常，GPU KV 经 UCX rc 后出错，主机中转或 TCP 恢复；状态与字节总数检查均无异常。

这组现象只能把调查集中到该路径及伴随变化。记录中的进一步对照更有判别力：强化同步仍失败；分层核对找到后续层的内容差异；独立传输在特定登记范围和偏移条件下才复现。因此，一次较小的独立测试通过也不足以排除问题。

报告者最终把故障追到 RDMA 地址迭代中的宽度溢出，并指向 [Linux 修复提交](https://github.com/torvalds/linux/commit/15fe76e23615)。本轮查看了补丁，确认地址增量变量从较窄类型改为 `dma_addr_t`；没有在目标机器验证补丁是否存在于实际加载的 RDMA/OFED 模块。社区提出的绕过方式也没有写成本项目 A2 的通用参数。

知识库原有“找第一次分歧”的方法可以复用，但对跨实例交接的内容取证讲得不够具体。因此在正确性页原小节内补了两段：对齐请求、层、逻辑位置，分别在源块复用前与接收后消费前记录；同布局原样搬运可比较字节，有转换先还原同一逻辑表示；再用独立固定数据传输区分模型以上和以下的路径。未新增一个按 issue 编号命名的教学页。

### B：端到端测试跑完，是否就验证了修复

[vLLM PR #59586](https://github.com/vllm-project/vllm/pull/59586) 讨论 MLA kernel 行大小与 NIXL 传输块大小不一致时的描述符几何问题。该 PR 的单元测试构造了 128/256 对 64 的不一致；作者同时明确，附带的端到端场景实际都选择了 64，**并未触发目标缺陷**。

因此可以把单元测试当作该几何条件的修复证据，把端到端结果当作那套配置的冒烟记录；不能合并成“线上缺陷已经复现并修复”。本轮读取时 PR 仍 open、`merged=false`，没有 merge commit。head 为 `9e37d393a4f27b0efd545ec3bc11f704dbba1c06`，base 为 `cb6458c5ce61632524c0447d49790725c1e1d9a2`；审查中还要求补 SlidingWindowMLA 变式。没有据此宣布任何发布版本已经包含修复。

这个案例用于核对知识库既有的“最终配置、实际路径、实验触发条件、版本归属”方法，没有再往正文塞一段 PR 摘要，也没有开展第二次产品问答。
