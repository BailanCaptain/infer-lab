## 改前审查与实际修改

| 位置 | 级别与影响 | 修订 |
| --- | --- | --- |
| 性能分析“先估一笔账” | P2：从批量直接跳到 4096 大矩阵，读者虽能按公式算 FLOP/B，却未看到为什么新增一行输入不需要另一套权重 | 先完整展示输入 [1, 2] 乘一个 2×2 权重得到 [5, 2]；下一节沿用同一份权重解释第二行 [3, 4] 得到 [11, 4]，再扩大到原来的 4096 维账 |
| 性能分析首图 | P2：两个“完成”文字框隐藏了下一步究竟依赖什么 | 画出本卡矩阵结果与另一张卡的结果，汇合后相加为 [8, 3]；独立计算、通信和结果使用不同语义色 |
| 贯穿样例“现场怎样拿到这些记录” | P2：只有字段清单，读者不能看出怎样将慢算子认领到请求 D | 增加 D → 调度步 42 → rank 0 → 返回 D 的完整关联示例，明确是人工整理的教学格式、不是默认日志；缺的发送和代理时刻仍明确要求补采 |
| 测量“平均不慢” | P2：只口头区分请求平均和间隔平均，没有演示为何会不同 | 以一个 100 ms 间隔和九个 20 ms 间隔，算出 60 ms 与 28 ms，解释“一条请求一票”和“一个间隔一票” |
| 测量负载生成段 | P2：提醒记录迟发，但没有说明迟发会从哪项指标中消失 | 用计划 0 ms、实际 200 ms、发送后 100 ms 收到首 token 的示意，解释 TTFT 之外还存在的 200 ms 等待 |
| 性能排障首图 | P2：同一外观的阶段框不能帮助读者识别慢在哪里 | 换成三条请求的阶段分段图，分别突出等调度、设备执行、结果返回；保留原有六类诊断分支 |
| 本组其他图 | P2：大部分对象使用 plain，输入、计算、通信混成一种样式 | 贯穿样例与压测首图画出具体待计算位置和入选请求；两张时间线保留时间比例，用计算/通信/输出语义色；取证流程仍保留分支形式，计时图标清实际发送与首个输出之间的 TTFT |
