## 三、新结论的核实

**「为什么用两台」（two-node `:53-65`）：成立，有两处口径小瑕疵，见上面的 P3。**

- 每卡权重：单机 43 × 36 × 24 = 37,152 MiB，加 2,502 = 39,654 MiB = **38.72 GiB**；双机 43 × 18 × 24 = 18,576，加 2,502 = 21,078 MiB = 20.58 GiB。2,502 取自 `01-deploy-entry-schedule.md:352`，可以复算。
- 单机剩给 KV：54.40 − 38.7246 − 3.4 = **12.275 GiB**，除以 8,355,840 = **1,577 块**，1,577 × 640 = 1,009,280 ≈ 101 万 token。按页面显示的 12.28 复算是 1,578 块。
- 倍数：3,855 / 1,577 = **2.44**；两边都按精确值算是 30.42 / 12.28 = 2.48。「2.4 倍」都成立。
- 「单机放不下」确实不成立：就算按 64GB 十进制换算成 59.6 GiB，单机还剩约 8.5 GiB。这条单机账底稿里没有（在 01、02、03 里 grep「单机」「EP8」都是 0 处），页面已经在 `:65` 标了待核。
- 补充：教程 `0576b647:GLM5.3-Flash.md:20-21` 写的是 A3 单机 128GB × 8、A2 两台。建议在 `:53` 引一句「官方对 A2 的要求就是两台」，这比推导出来的理由更直接。这一条是建议，不算问题。

**「EP≥16 才准走 MC2，EP8 只能 All-Gather」：在 A2 上成立。**

- `vllm_ascend/ascend_forward_context.py@db701c1f#L240-L252`：`ep_world_size = world_size_across_dp // pipeline_parallel_size`；只有 `num_experts_per_device <= 24 and ep_world_size >= 16 and num_tokens <= mc2_tokens_capacity` 才返回 MC2，否则返回 ALLGATHER。`#L341-L344`：A2 进入这个分支。
- 单机 TP8、DP1：ep_world_size = 8 < 16，每卡专家数 288 // 8 = 36 > 24，**两个条件都不满足**，所以永远走 ALLGATHER。双机：16 ≥ 16、18 ≤ 24，满足（和底稿 `02-forward.md:631` 一致）。
- 限定条件：A3 的 `_select_a3_moe_comm_method`（`#L255-L282`）没有 EP≥16 这个条件，页面 `:63` 应当注明「A2 上」。

**门槛 128**：`#L202-L217`。`enable_prefill_mc2` 默认是 False（`ascend_config.py:165`），教程配了图尺寸，所以取 `max_cudagraph_capture_size` = 128，ceil(128/8) × 8 = 128。两页写的都和代码一致（two-node `:269`，one-request `:360-367`）。
