## 三、没落实 / 需要注意的条目

1. **18B 算式的两处取整不自洽（`glm-5-3-flash.md:281-283`，P3）。** 代码块写的是「主干 89.2 + 84.6 = 173.8」「MTP 74.3 − 72.5 + 2.0 ≈ 3.9」「合计 ≈ 177.6」。按块里自己给的数算：`74.3 − 72.5 + 2.0 = 3.8`（不是 3.9），`173.8 + 3.9 = 177.7`（不是 177.6）。精确值确实是 3.86 与 177.63（审查报告第三节 `glm-5-3-flash-review.md:69-71`：主干 173.77、MTP 74.33 − 72.48 + 2.013 = 3.86），所以结论没错，错在展示用的中间值取整后读者按页复算对不上。`:337` 的「主干 173.8 亿 + MTP 3.9 亿」同源。建议把 MTP 一行的减数写成 72.48，或在块尾注明「各项按精确值相加后取整」。
2. **NPU 的释义两页不一致（`glm-5-3-flash.md:325`，P3）。** 本页写「NPU（昇腾的 AI 加速卡）」，而 learning-guide 刚按 P3-10 改成「昇腾的计算设备」。`TERMS.md:81` 的备注是「软件设备、物理封装与板卡分别计数，不默认一一对应」，`:82` 更明确「数计算设备用 NPU；板卡与设备的映射按具体型号核对」。P3-10 在 learning-guide 上修掉的问题，在本页原样留着；这是同一条术语规则，不是本页独有的特例。
3. **「在机内按 TP8 切成 8 份」对 attention 略有扩大（`learning-guide.md:42`，观察项）。** `two-node:142` 把切法分三种，其中**每张卡各放一整份、根本不切**的包含 MLA 的 `fused_qkv_a_proj`、整个索引器、KDA 的 `f_a_proj` / `g_a_proj`、router gate、mHC 混合参数。所以 attention 并非全部按 TP8 切。任务要求的口径（三类部件每台一份 + 288 个路由专家按 EP16 分散）已完全对上 `two-node:89`，这一句只是入口页的粗粒度说法，第 2 页 `:142` 会补全，不算错，但如果要更严，可改成「机内再按 TP8 切开大部分矩阵」。
4. **索引器精度两页仍有出入（`glm-5-3-flash.md:319` vs `two-node:234`，P3，记录里已声明未改）。** 本页说索引器压池用的池内位置偏置加载后是 FP32（与 `02-forward.md:513` 的 `index_kpool_compress_ape`(FP32) 一致），`two-node:234` 仍写「整个索引器」留在 BF16。修订记录第八节已把这条列为「只列证据、未改」，取舍本身可接受（要改的是 two-node，不在本轮可改文件里），但这条跨页矛盾目前**仍然存在**，应在 two-node 的下一轮里收掉。
5. **索引器 FP32 副本未进 two-node 的每卡权重表（同上，观察项）。** `glm-5-3-flash.md:312` 说 `wk_weights_proj` 与 `index_kpool_compress_gate` 前向第一次运行时另存 FP32 副本；修订记录算出每卡约 54 MiB，归到激活峰值而非加载时权重。`two-node:149-157` 的权重表确实没有这一项，与记录的说明一致，不算漏，但 two-node 里也没有任何一句提到它。
6. **P2-1 建议里「two-node:234 改成链接回本页」没做（P3）。** 记录以「说法正确、不用改」带过。判断成立（不是错），但建议的另一半——让读者知道那是加载后口径——没有落地，`two-node:234` 单独读仍会和本页 `:308` 那张表的「HF 文件里」一列看着矛盾。
7. **learning-guide 里 HCCL、connector 仍无解释（P3，记录未覆盖）。** 审查报告第 19 行把「vLLM / vllm-ascend / HCCL / connector 没有解释」并列为扣分项，修订记录只处理了前两个（P2-5）。`:81`「外部 KV cache 与 connector」、`:89`「集合通信与 HCCL」是照搬 `toc.ts` 的小节名，严格说不属于本页自己引入的术语，影响很小，但这一条确实没落实。
