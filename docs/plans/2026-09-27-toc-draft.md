## 0. 结构怎么落到现有数据结构上

`toc.ts` 的数据模型只有两层：`TocPart`（左栏大标题）→ `TocSection`（灰色小标题）→ 页。而这次要的是三层：**组（导读 / 一条请求 / 多个请求 / 附录）→ 站（A0–A7、B1–B5）→ 小节（A4、A0 站内）**。三层压成两层，本草案选的是：

- **part = 组**，共 6 个：`guide` 导读、`request` 一条请求、`batch` 多个请求，加上附录的三个 part `rfork` / `params` / `references`（这三个保持今天的自动编排逻辑不动）。
- **section = 站**；A0、A4 这种大站拆成多个 section，站号写进 section 标题（`A4 · 稀疏注意力`），读者在左栏仍能看出站的边界。

这样选的理由：part 数从 11 降到 6，`WikiPage.tsx:131` 的 `"一二三四五六七八九十"[i]` 不会越界；`part.id === "params"` 的默认收起、`rfork` / `params` / `references` 三个 part 的自动归位代码一行都不用动。代价是「一条请求」这个 part 一口气挂 65 页。另一种切法（站 = part，共 17 个 part）见 §5 第 1 条。

页数：现有 133 页 → 删 3、合并 7 → 留 123 页，新建 6 页，新目录共 **129 页**。

## 5. 需要用户拍板的三件事

1. **三层压两层怎么压？** 本草案选「组 = part（6 个），站 = section」。另一种是「站 = part（17 个），小节 = section」：左栏每一站可独立折叠、站号直接当序号，导航更贴合「路线」这个说法，但要把 `WikiPage.tsx:131` 的中文序号换成站号（`A0`/`B3`），part 数也从 6 涨到 17。要不要走这条？
2. **附录三个 part 的顺序。** 任务里写的是「参数页 → 参考资料 → RFork」，但今天 `PARTS` 是 RFork 在 params 前面，`tests/rfork-wiki.spec.ts:8` 钉着 params 的序号。按任务顺序排就得改那条断言；按今天的顺序排（RFork → 参数 → 参考）断言自然对上。按哪个？
3. **A4 我多切了一节「注意力基础」（`attention-qkv` / `rope` / `gqa`）。** 建议的七节里，这三页无处可去，但 KDA 和稀疏注意力都以它们为前置。接受这一节，还是把它们塞进「稀疏注意力」那节的开头？

（另记两处小移动，若不同意可退回盘点表原站：`ai-core` 从 A4 挪到 A0「机器与设备」，`glm-5-3-flash` / `glm-5-3-flash-two-node` 从 A4 / A0 挪到导读。）
