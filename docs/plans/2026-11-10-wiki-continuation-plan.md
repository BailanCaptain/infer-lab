# 全站教学内容核验与整改接续计划

本计划接续“补齐 PP 与 Engram 部署文档”会话及 OpenCode 的续作。最初暴露的问题包括多节点部署参数漏讲、DeepSeek 的 Engram 与 P/D 资源口径缺失，以及学习页混入机器修订历史。用户随后明确将任务扩展为全站调查、分组整改和验收。

**目标是让学习者通过本站得到完整、准确、能串起来使用的解释。** 官方资料阅读和逐条引文核验是实现目标的方法；完成某个数量的阅读或引文判断，不能替代内容补全和学习路径验收。

本文件定义后续顺序和完成条件。本轮仅制定计划；执行结果继续放在 `docs/reviews/`，历史报告保留原时点含义，不在计划中维护另一份动态完成率。

## 目标与验收依据

- **Goal**：系统发现并修复同类遗漏、事实错误、条件丢失、跨页矛盾和教学障碍，保留已经有效的解释、推导与图示。
- **Acceptance Criteria**：沿用[第一轮方案](2026-11-03-wiki-remediation.md)、[全站分组方案](2026-11-03-wiki-group-remediation.md)、[官方资料与引文核验方案](2026-11-03-wiki-evidence-verification.md)及[写作标准](../wiki-writing-standard.md)。本计划将这些要求落实到接续任务和验收证据，不另设一套产品需求。
- **Architecture**：继续使用仓库里的正式页面、来源、图规格、历史阅读记录及逐项判断记录。用同一批记录分别呈现官方内容覆盖、主张核验和页面验收；不另造内容管理平台。
- **Tech Stack**：Markdown、现有 JSON 审查记录、固定版本的官方资料与源码、现有 pnpm 检查命令及浏览器验收。只有发现生成或发布根因时才修改产品代码。

终点是覆盖、准确性和教学可用性共同达标。每项工作须能说明它留下什么可复用成果、怎样验证，以及省略后会漏掉什么；下载量、脚本运行次数和报告篇数不作为交付指标。

## 第一步 对齐当前正文和历史记录

以执行开始时的正式页面清单、来源、图规格和文件哈希建立检查点。读取上述三段核验记录及实际差异，区分其他会话正在修改的文件，保留当前工作，不重置整个仓库。

逐项对齐使用页面 ID、来源编号与完整来源，并追踪修订后的来源映射。编号变化不能被当作新增工作；来源没变而主张发生变化，也不能沿用旧的支持结论。内容相同的原文复用已读记录，只重读发生变化或旧记录不足的部分。

对齐结果至少区分：

1. 尚未阅读，或者已读但没有主张判断。
2. 已判断且支持当前主张，或者仅作背景、重复来源、归档完整性依据。
3. 部分支持、不支持、原文无法取得，以及它们对应的未解决问题。
4. 已整改但未独审、未验证，以及已经完成本次改动验收。

“已读待判”不能由脚本批量转成支持。六项旧整改的关闭、OpenCode 的阅读摘要和 200 项的正式判断各按实际证据使用，不能互相替代。

**产物与通过条件**：保存可追溯到当前文件的对齐清单、冲突项和剩余任务；每个数字都能回到具体记录。随后才能冻结下一批候选。沿用现有记录格式及对齐工具；不先建设新的审计系统。

## 第二步 从官方资料反查本站缺口

这是发现“整件事没讲，因此也没有引文可查”的步骤。每一组开始前先做，不能等引文全部查完才补。

先盘点官方目录、侧栏、索引和已有教程中的技术链接，主动查找同主题的部署指南、特性说明、配置参考、兼容性表、排障说明与发布说明。用户给出的两篇模型教程保留为首批验收案例，资料范围继续向相关官方入口展开。

资料范围按以下规则登记：

- 已读的 Ascend 190 份 Markdown 与 28 份历史教程继续作为固定基线。固定提交及原文哈希沿用原清单；不重新宣称为本轮新增阅读。
- 核对与本站范围相关的 vLLM 官方机制、部署和配置文档；关联 Ascend 的安装、硬件、CANN/HCCL、模型及配套组件官方资料。先列目录，再判断覆盖，不能只检索本站已经出现的术语。
- 教程明确依赖的包含文件、命令模板、跳转目标、功能限制表和技术图示须实际读取。关联的模型仓库和论文，在承担解释或证据时一并纳入。
- 目录页、重复译文、退役提示和实质教程分开登记。与教学范围无关的链接说明排除理由；导航链接不无限递归为全互联网阅读任务，也不能凭“不是现有引文”排除相关技术材料。
- 发现基线之后的新官方能力时，另记版本增量，再核对本站四个教学版本及 RFork 的适用关系。教学钉点以 `wiki/seeds/` 为准，不直接用 latest 改写旧部署案例。

每个有实际内容的官方主题，记录它回答的学习者问题、阅读范围、版本条件、本站对应页与章节，以及缺口类型。缺口包括整项缺失、只有术语、只有开关没有机制或前提、缺少资源口径、跨页接不上，以及官方新能力被误写成旧版通用能力。

对覆盖充分的主题保留定位；对不适用的主题保留具体理由；对有缺口的主题形成整改项。判定“本站已有同名页面”不足以通过。

**已知外部尾项继续追踪**：用户提供的 DeepSeek 生产文章文字副本已经读过，不能退回“整篇不可取得”；三处缺失原图表仍待处理。论文已查看的 23 张位图不代表全部图表；按原文清单补核未读的 SVG、表格和相关图示。其他无法取得的原文沿用实际状态并尝试官方固定源，不把访问成功当成读完。

## 第三步 按原六组核验并整改

保留第一轮六组归属，接入新增正式页，避免换一轮分类后漏掉旧页。执行优先级先覆盖最初暴露的部署与资源问题，再沿请求链和基础解释完成全站。

| 执行顺序 | 原分组 | 本轮重点与完成证据 |
| --- | --- | --- |
| 1 | 03 硬件并行与部署 | PP、TP、DP、EP、上下文并行与多节点启动的关系；进程、节点、rank、API 入口以及物理卡、逻辑设备、副本的计数。用 GLM 和 DeepSeek 的具体配置检查解释是否齐全，按版本核事实。 |
| 2 | 04 缓存与状态 | Engram、KV 与其他模型状态的区别；设备和主机驻留、共享内存与 IPC 条件；P/D 实例、组大小和资源数量。核对缓存、offload、connector、失败处理与回收路径。 |
| 3 | 02 请求与服务调度 | 接上已做的 200 项，补齐入口、调度、执行、投机、结构化输出及返回链上的剩余判断；重点查同步、异步和组合配置的条件。 |
| 4 | 05 性能与可靠性 | 量化、图、LoRA、CPU 绑定、通信优化、观测及排障；区分支持范围、理论推导、实测收益与可复现步骤。 |
| 5 | 01 基础与模型前向 | 回核上面解释依赖的概念、张量、数学、显存和通信推导；检查条件在简化示意中是否丢失，跨页是否使用同一口径。 |
| 6 | 06 RFork 与参数来源 | RFork 独立版本、参数消费者、默认值与组合限制、自动定义和人工正文一致性；核对所有余项和跨组关系。 |

此顺序不延后已经确认的 P1/P2。任何组发现关联页面有同一错误，立即连同关联解释处理；内容仍只归属一个主位置，其余页面引用它。

每组都按同一流程闭合：

1. 对照官方资料完成覆盖检查，再通读对应正文、图和参数说明，保留有效信息清单。
2. 将当前主张逐项对到来源，阅读必要调用方和分支，核版本、模型、硬件、默认值与组合条件；对算式重算，对图文互相核对。
3. 修复漏讲与错误。源码行号有效、raw 哈希一致、HTTP 200 和全文读过均不能代替主张判断。证据不足时继续补证或准确缩小结论，不能靠删限制、改标签来关单。
4. 按写作标准由新的独立审查者阅读实际页面、图和本次差异；检查信息保留。P1 修订后复审，P2/P3 按标准修订并自查，关闭已确认问题后才能验收该组。
5. 运行相关检查，并在浏览器里按学习任务走通页面、导航、链接、表格和修改图。对跨页口径再核一次，再将结果并入全站记录。

正文只呈现现行解释、必要版本差异和有效来源。旧原文、修订哈希、“来源仍须人审”等维护历史留在维护记录，检查生成与发布路径是否会再次带入学习页。

## 下一批的 500 怎样安排

建议沿用 200 项试批的计量单位，从第一步对齐后的队列冻结 **500 个此前尚无逐项判断的来源出现项**，优先选择上述部署、资源与状态主题中能连成完整解释的页面。一个项是一次“页面 + 来源编号 + 完整引用”的出现；同一原文可以复用阅读，但不同页面的主张分别判断。

这意味着继续处理原任务的下一批，不承诺新读 500 篇官方整篇文档。官方整篇阅读、图表阅读、引文判断和页面验收分别计数，后续报告明确写单位，不再笼统说“500 页”或“完整 500 条”。

批次安排遵守以下边界：

- 排除已有有效判断及前批处理过的项，不靠重复来源或重新编号凑数。若对齐后未判项不足 500，就处理真实余量并说明。
- 覆盖检查发现的漏讲内容必须纳入本批整改，即使它原来没有引文。为修复而新增的来源另列，不能算作冻结 500 项的额外完成量。
- 500 项可能只覆盖部分页面的来源。未完成整页或整组要求时，只报本批范围完成，不能把整个页面、主题或全站标为通过。
- 本批发现并确认的问题完成必要修订、独审和验证后再收尾；不能为了刚好停在第 500 项，把已发现的严重问题留在正文。超出冻结范围的必要工作单独记账。
- 本批之后继续按六组余项推进，直至满足全站完成条件；具体批量根据本批实际成本调整，不改变原任务范围。

## 学习者路径验收

页面审查之外，每组设置跨页任务。验收者从学习入口或站内搜索开始，只依靠本站找到回答，再由维护者回核原始证据。最初两类问题至少验收下列路径：

| 学习任务 | 必须能从本站得到的结果 |
| --- | --- |
| 看懂 GLM 多节点启动命令 | 说明各节点运行什么、参数分别控制什么、API 从哪里进入，以及它们与并行设置的关系；找到对应版本的启动条件和验证线索。 |
| 比较 GLM 与 DeepSeek 的部署资源 | 分开列出物理卡、逻辑设备、并行组和模型副本；分别计算 P、D 的组大小与实例数量，不把名称相似当成计数相同。 |
| 理解 Engram 的配置选择 | 解释数据是什么、放在哪里、哪些进程共享、依赖什么 IPC 条件，以及模型和硬件限制；读者不必到别处补齐关键前提。 |
| 从开关走到判断是否生效 | 找到支持版本、默认行为、组合限制、可检查的日志或状态，以及失败时该沿哪条路径排查。 |
| 串起一个请求和资源变化 | 从入口、调度、前向、状态传递到输出和回收，跨页的时序、资源与术语不矛盾；保留原 GLM 算例的固定数值和成立条件。 |

其余组按各自主题补充任务。点击链接成功只证明导航可达；能复述概念、完成必要演算并找到条件才算内容路径通过。没有 NPU 的情况下，只验收到文档与源码支持的层级，不宣称命令、性能或精度经过设备实测。

## 验证与现存检查问题

每批内容修改后至少运行 `pnpm check:content`、`pnpm wiki:lint`、`pnpm wiki:audit`、`pnpm wiki:diagrams --check` 和 `pnpm build`，保存命令、退出码、关键输出及检查点。来源机械审计与逐项语义结论分开呈现。

若修改生成、索引或发布代码，先稳定复现或建立失败测试，再修复并运行相关测试、类型检查和 Lint；只做文档修改时不添加镜像实现的单元测试。浏览器实际打开受影响页、操作相关入口并查看修改图；规格同步与测试通过不能代替视觉验收。涉及教学 3D 时，先读并执行[教学 3D 标准](../3d-teaching-standard.md)。

前批记录仍有两类全站检查问题：`ascend-config-system.md` 的表达比例触发审计 1 项，以及另一会话的 `chunked-prefill-v2.md` 样例归类和重复触发 lint 3 项。执行时先复现并核对最新状态，再按真实内容和页面用途处理；不回滚其他会话改动、不降低规则。若仍存在，整站检查不得报全绿。

## 全站完成条件与汇报口径

全部完成必须同时满足以下条件：

1. **范围有清单**：当前正式页面全部归组；相关官方目录已盘点，技术材料、承接目标和新版本增量有明确归属。所有纳入范围的原文、命令、表格和图示达到记录所声明的阅读范围。
2. **覆盖无未处理缺口**：官方主题到本站解释逐项有去向，关键缺口已补齐；排除项有适用性依据，不能用“已有同名页面”代替。
3. **主张有有效证据**：当前引文和实际主张对应；无引文的关键推导、图中结论及跨页复用也检查过。部分支持、不支持和无法取得项得到实质处理，仍缺证据的项单列，不能被计成全面核验通过。
4. **修订完成验收**：每组修改按标准独审，已确认的 P1/P2 关闭，有效信息保留，图文和版本一致。
5. **学习与工程检查通过**：每组学习路径通过，受影响页面完成浏览器验证，全站相关检查通过；维护历史不再出现在学习正文。

若关键原文或图表始终无法取得，报告明确尚未完成的范围；不能用一次尝试或访问失败结案为“全部资料核验完成”。源码及文档证据与 NPU 实测分开，保留未实测边界。

每批汇报使用固定栏目：关闭了哪些教学缺口、核验了多少来源出现项、新全文读了哪些材料、修订和验收了哪些页面或学习路径、还剩哪些任务，以及实际额度观察。它们互不换算为一个笼统的完成百分比。

额度在每批开始与结束保存同一账户窗口的快照，注明是否刷新、整数显示及并发使用影响。此前 200 项期间观察到约 1 个百分点的增加，仅作样本；下一批用实际记录衡量，不线性承诺全部工作的消耗。

本轮交付为本计划和索引入口。下一执行动作是对齐当前文件与历史账本，然后进入部署与资源主题的官方覆盖检查及下一批核验。没有需要用户重新决定的产品问题。
