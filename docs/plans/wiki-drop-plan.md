# Drop 资料收录与知识整合实施计划

**Feature:** [F005](../features/F005-wiki-drop.md)。
**Goal:** 用户提交原始资料后，系统基于可追溯来源更新既有知识、创建必要页面、建立有依据的关系并标出矛盾，形成可审阅的整组变更；批准后，后续阅读与问答能够复用这些知识。
**Acceptance Criteria:** 规范和状态只在 F005 的 AC01–AC12 维护，本计划用编号映射步骤与验证。
**Architecture:** 保留原始来源、编译 Wiki、规则三层。网页和 CLI 调用同一 drop 服务；以持久批次串联输入、提取、相关页发现、整合、审阅和发布，复用现有快照、任务、模型、来源与审批组件。
**Tech Stack:** 现有 TypeScript、Node、Zod、React、Vitest、Playwright 与 Markdown 文件存储；首版无预设新增依赖。D01 已选文字＋网页链接，网页正文解析方案需通过样本选型。

## 2 终态数据契约草案

这是用于解释设计的概念契约；最终机器定义统一维护在 `src/content/wiki/drop.ts`，网页和 CLI 复用它，不要求用户手写 JSON 或 frontmatter。

| 对象 | 需要表达的信息 | 不得混同的语义 |
|---|---|---|
| 原始内容快照 | 按原始字节的 hash、存储位置、大小、格式、采集时间；解析版本与回指原文的定位 | 原文、解析文本、清洗后模型输入分别记录；转换后的行号不能冒充原始页码/源码行号 |
| 来源身份与修订 | 内部 sourceId、原始标识、标题、版本/分支/commit/日期等已知条件、内容快照、用户确认情况 | 未知允许为空；URL 相同不等于内容相同，hash 相同不等于出处相同；新到达不等于更新、更可信 |
| 收录批次 | batchId、提交幂等键、来源修订集合、可选用户收录目的、可选 seriesId/部分编号/是否收齐、创建时间 | HTTP 重试身份与来源内容身份分开；同材料不同收录目的可显式重新整合，不无限复用旧失败提案；模型推断的重点与用户填写的目的分开记录 |
| 运行记录 | 批次阶段、子任务 id、启动时知识 revision、固定 provider/model/相关执行配置、用量、错误/取消记录；测试运行另关联显式测试限制 | HTTP 连接生命周期不等于任务生命周期；取消不抹掉真实模型用量；测试限额不是正式批次的必填字段或默认值 |
| 知识与影响提案 | 每项知识的来源片段与条件、相关旧页、合并/补充/编辑/替代/并存决策、关系与理由、拟创建 id、未核范围、图规格/公式/目录变更及其依据 | 相似度只用于找候选；目录摘要不能作为修改正文事实的证据；资产变更与正文绑定同一提案，未解决事项不能静默降级成通过 |
| 审阅关联 | 复用 reviewId、base 内容指纹、完整 diff、来源/关系/冲突摘要、发布 revision | 批次显示状态由关联任务/审阅结果推导或统一更新，不另外维护相互矛盾的 published 标志 |

存储方案：尽量扩展 `wiki/_jobs/drops/` 的版本化记录，原文继续走 `wiki/raw/` 的内容快照，执行继续走 WorkflowStore，正式页继续走原有目录。不要引入独立数据库。旧单文件记录作为旧契约读取；新增 sourceId 的迁移只记录确有证据的映射，不猜旧文件所属系列和版本。

同内容不同出处允许共享原文字节，但来源归属必须各自保留。稳定概念 id 不从本次文件名/hash 随意派生；先解析已有页、别名与定义范围，再提出新 id。提案中的多份草稿建立批内 id 表，避免并行生成同名页或先写出悬空链接。

按 D04，用户可以分次向尚未启动的批次补资料，明确开始处理后固定本轮来源修订集合。同批材料互相对照并统一整合，不逐文件生成互不相关的审批。运行中、待审或已结束后继续提交的系列材料关联为新批次；既有提案不会因续传而自动改变，后续整合须说明相关前批次状态并重新核对知识快照。

### 生命周期与恢复

用户可见流程为：已接收 → 预检 → 提取 → 查找相关知识 → 整合 → 待审 → 已发布。分支结果包括隔离、需要补充、无需变更/仅归档、处理失败、取消和拒绝。

这些是展示阶段，不能直接塞成一套与现有 Job/Review 竞争的状态机。T3 将其映射到持久批次及子任务。记录每阶段输入指纹与产物；仅复用与输入、知识版本和模型配置仍相容的结果。旧版本材料已保存不等于已纳入正式知识。

领取 drop 批次时固定执行配置，所有后续模型子任务继承；用户切换全局设置只影响新批次。失败重试默认沿用原配置；显式改模型则生成可辨认的新尝试，受影响的生成与整合结果不能与旧模型结果无提示拼接。

多阶段读取应使用一致的知识快照。生成前检查来源与目标范围，发布前继续检查 base；全局扫描未完成时列明覆盖范围，不能说“全库没有”。并发发布相关页会使受影响提案过期，重新整合后产生新待审版本。

最小实现分四步，产物均保存到当前批次：

1. 从清洗材料提取知识、适用条件、来源片段和待澄清点，不先强制“一文件一来源页”。
2. 用标题、别名、章节、检索和关系发现候选；实际读正文，按当前知识缺口和新线索继续补读；解决缺口或不再获得新证据时结束，避免重复空转。可用的已有源码引用需要核对时，读取本机对应固定快照。按 D05，证据不足时可主动搜索官方文档、源码及相关讨论；补查记录所解决的问题、URL/版本/采集时间、取得的原文快照及用途，新增材料仍经输入清洗后交给受限整合步骤，不为写页模型扩大任意操作权限。相关讨论保留作者与未证实性质；搜索摘要不替代实际原文。无法读取、版本不匹配或证据仍不足就明确标为未核，不提出确定替代。
3. 提出稳定 id 与影响清单，核对别名/定义避免重复。需要多个新概念时，先建立允许路径与来源集合，再生成；不给模型全目录任意改写权限。
4. 对读过的页及同批新页进行合并、修订与关系判断。保留依据映射与不确定项，原有 `relations`/`contradicts`/revision 契约能表达的继续复用，反向边仍由 build 派生。

正文改动的原文、条件和引用必须可核对；不能在传播新事实时保留只支持旧说法的来源编号。推翻类修订沿用引擎生成历史规则。到达读取/生成边界时列出剩余目标，可分组继续，但不能以“只给了 6 页”伪装全量完成。

通过条件：上述反例全绿，完整提案说明新增知识、修改理由、关系依据、冲突与未覆盖范围；没有为赶通流程删除来源或参数生成区校验。

### T5 多页审阅与一致发布

**覆盖：** AC07、AC08、AC12；依赖 T4、D06。

**文件：** 修改 `scripts/wiki/review.ts`、`review-files.ts`、`integration-run.ts` 及现有测试，`server/review.ts` 及测试，现有 `src/app/wiki/` 审阅组件；新增 UI 文件前先找当前审阅入口，不再造独立审批系统。

失败用例：一项改正文、一项建边、另一项标矛盾；旧页在待审期间变化；重复批准；附修改意见退回后重跑；发布中断；取消任务迟到结果；准备读取的依赖页变化影响提案有效性。按 D06 验证整组批准或整组退回，不接受只发布部分文件的请求；退回意见传入修订，旧提案与意见保留，新完整提案未经重新批准不能发布。

运行：`pnpm exec vitest run scripts/wiki/review.test.ts scripts/wiki/integration-run.test.ts scripts/wiki/revisions.test.ts server/review.test.ts server/snapshot.test.ts`。

最小实现：待审包附本次来源与影响摘要、全部 diff、来源片段、关系说明和未决项，仍走现有批准/驳回与发布锁。已有事务恢复能力先复用，不能通过强制覆盖绕过 base 校验。发布后同一快照包含正式正文、索引、派生反向关系与可检索内容。

通过条件：批准前正式库字节不变；拒绝不改变正式知识；批准与恢复不产生重复日志/页面；读者不看到正文与索引分别属于两个版本的成功结果。

### T6 网页 Drop 流程

**覆盖：** AC01、AC02、AC03、AC08、AC10；依赖 T3、T5、D01–D04、D06。

**文件：** 新建 `src/app/wiki/DropPane.tsx`、`tests/wiki-drop.spec.ts`、`tests/fixtures/wiki-drop-server.ts`；修改 `src/app/wiki/ChatDrawer.tsx` 中抽屉入口/页签的实际挂载位置、现有审阅组件及 `src/design/wiki.css`。实施时先检查容器归属，只改真实挂载点。

先写浏览器失败场景：添加资料 → 校对清单 → 启动 → 看进度 → 看完整提案 → 拒绝/批准 → 跳到结果；刷新恢复、断连恢复、隔离原因、失败重试、重复提交、来源信息缺失、键盘操作与小屏布局。按 D03 增加两类对照：普通输入从启动直接进入完整待审提案，没有中间方向审批；影响正确整合的关键歧义显示具体问题，补充后恢复，避免重复启动已完成阶段。

运行：`pnpm exec playwright test tests/wiki-drop.spec.ts tests/wiki-review.spec.ts`。隔离 fixture 服务使用真实 drop/status/review 路由和临时库，仅模型输出固定，不把整个接口 mock 掉。

最小实现：用户提交原始资料，可选填写目的；界面明确标为选填，未填写也能启动。系统补充元信息但不伪造未知值；按钮明确区分预检、开始处理与批准。显示当前批次使用的模型、用量口径及处理范围。运行期间能离开页面后恢复查看；没有真实进度就显示阶段，不造精确百分比。错误保留用户尚未提交的输入。

通过条件：实际浏览器可走完整闭环，使用者不需要知道内部 jobId、来源 hash 或命令行协议；代码检查不代替 UI 验收。

### T7 教学、图表与目录影响闭环

**覆盖：** AC09，同时复查 AC05–AC08；依赖 T4–T6、D07。

**文件：** 先核对 `docs/wiki-writing-standard.md`；扩展 `scripts/wiki/integration-check.ts`、`review.ts`、`review-files.ts`、`integration-run.ts` 及测试，复用 `scripts/wiki/standard.ts` 和 `scripts/wiki-diagrams.ts` 的校验/渲染能力；调整 `src/content/wiki/toc.ts` 的目录数据应用入口及现有审阅组件；新建 `scripts/wiki/drop-assets.ts`、`drop-assets.test.ts` 承接受约束的图规格与目录提案。在 `scripts/wiki/drop-integration.test.ts`、`server/snapshot-diagram.test.ts` 与浏览器 drop 用例中追加资产案例。实际资产由所选资料决定，不预先改正式内容。

失败用例：新结论改变正文算式但图仍保留旧数；关系变化影响依赖页摘要；新教学页无阅读落位；来源页被错误套成教学模板；材料不足以满足对应写作标准。补图规格有效但渲染溢出、公式数值/单位不一致、目录重复或遗漏、共享图影响其他页、图文件在待审期间变化、渲染或发布中途失败的对照。

按已定 D07 实现完整自动链路：

1. 扫描受影响页的摘要、公式、图引用、共享资产使用方与目录落位；为每项修订保留来源依据和影响原因，未受影响内容不顺带重排。
2. 模型输出现有格式的图规格、正文公式和受约束的目录位置提案；宿主验证路径、稳定 id、目标节点和引用，复用现有渲染器生成 SVG。目录仍保留单一数据来源；必要的数据化调整在实施时明确迁移与兼容，不让模型任意改写 TypeScript。
3. 在暂存副本检查数值/单位、图规格与 SVG 一致性、图文引用、目录完整性及现行教学标准；对受影响页面实际渲染并检查溢出、遮挡与可读性。生成失败回到相应阶段修正，不能以“交给维护者手改”替代该自动能力。
4. 审阅包展示正文 diff、图的前后预览、公式变化和目录位置变化；新建资产展示新预览。正文、规格、派生图及目录变更共同参与 base 检查、整组批准、发布和恢复，模型不得绕过审批覆盖原文件。

保留旧内容的“待编排”兼容能力，但本次 Drop 需要的目录归属须完成，不能把暂存到“待编排”当作正确落位。校验失败或证据不足时如实停在未完成状态，保留可恢复的产物。

运行：`pnpm exec vitest run scripts/wiki/drop-assets.test.ts scripts/wiki/drop-integration.test.ts scripts/wiki/review.test.ts scripts/wiki/integration-run.test.ts server/snapshot-diagram.test.ts`、`pnpm wiki:diagrams --check`、`pnpm wiki:lint`、`pnpm exec playwright test tests/wiki-drop.spec.ts tests/wiki-review.spec.ts`。新增资产与目录浏览器断言必须覆盖桌面、小屏和审批前后预览；全量回归由 T8 承接。

通过条件：系统能自动完成一例正文/算式/图中数字联合更新，以及一例新概念配图与目录落位；全过程无需维护者手工补文件，人工职责是审阅批准。没有已知图文矛盾或未完成的资产影响被当作 drop 成功。资料并不要求每次新建图，但新增内容必须满足其页面类型的现行标准。

### T8 真实资料验收、完整回归与交接

**覆盖：** AC01–AC12，重点 AC11、AC12；依赖前述实现，按已定 D08 由开发助手准备具体样本。

**文件：** 新建 `docs/plans/wiki-drop-acceptance.md` 作为证据记录（实施验收时才创建）；更新 F005 验收表、F004 承接项对账与当前交接。原始真实样本与批次回执按正常资料流程保存，不在计划中编造结果。

- 一份版本清楚、涉及已有概念和新知识的技术资料：核对新增页、已有页修改和有依据的关系。
- 同源更新及分章资料：核对原文版本、合并、去重与系列完成情况。
- 一份纠错资料：区分补条件、版本并存和真正替代，核对引用及历史；至少一例带动已有算式与图的自动修订。新概念样本还须验证所需配图与目录落位，不能只验收纯文字收录。

每组先保存固定前测问题、知识 revision、模型与允许工具/来源范围；后测使用新会话并包含未用于编译的改写题、版本反例和无证据题。若前测已经答对，不强行宣称提高；记录新增来源、引用准确性或条件覆盖等实际变化。评判核对事实与出处，不只看措辞一致或模型自评分。隔离库批准仅是验收操作，真实正式发布仍走用户审批。

测试控制随样本显式设置并留存，用于定位失败和控制试验范围，不作为产品默认限额。用量按实际 provider 记录，供应商限制如实反馈，不把测试中断标作验收通过。当前只确定了样本选择责任与覆盖场景，具体材料、数值和真实结果在执行本步骤时记录。

最终运行：

```powershell
pnpm check
pnpm test:e2e
pnpm build
pnpm wiki:audit
git diff --check
```

参数扫描需要可用 Python 3.11+，沿用本机现有配置或 `WIKI_PYTHON`，不把某台机器解释器绝对路径写成共享要求。站外 URL 与内容语义的核对范围分别记录，不把来源行号审计通过说成所有事实已验证。

通过条件：逐条 AC 有证据与限制，真实模型缺项不得用 mock 补勾；P1/P2 在当前实现任务内解决；服务保持可用，运行数据不混入代码提交。按当时明确授权整理 Git 检查点，不由这份计划推定推送、合并或自动发布授权。
