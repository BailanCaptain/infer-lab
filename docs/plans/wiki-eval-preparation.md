本轮完成固定样本、证据预检和离线对照请求配置；**没有真实模型调用，没有语义评分，M1a / M1b 均未通过**。工作树 `infra-view-new-llm-wiki`，分支 `feat/llm-wiki`，基于 HEAD `8175224` 的既有未提交修改继续实施。本轮未改变正式知识页，未做批量导入。

## 为什么先做这一步

原始理念要求知识在使用中积累并改善后续回答。单凭新增页、命中链接或恢复上轮聊天，都不能证明这一点。验收规则仍只定义在 [F004](../features/F004-knowledge-loop.md)，步骤由 [T6](knowledge-loop-plan.md#t6m1-闭环验收与收益记录) 承接。

唯一机器样本在 [eval-suite.json](../../scripts/wiki/eval-suite.json)：六个场景、问题原文、预期事实、禁止泛化、依赖页和源码范围均在其中。本文不复制答案。选取 `profiling_chunk_config` 为待补主题：当前正式页面未命中该标识符或类名，本地钉定源码有明确配置检查及版本差异。未命中只能证明这些标识符未收录，不证明所有同义表述都缺失。

## 可重复的准备入口

在本工作树运行：

```powershell
pnpm wiki:eval
pnpm wiki:eval --phase after
```

命令只读本地 git 对象、读取知识库并保留可派生的版本副本，不调用模型、不联网、不生成草稿或发布。每份证据核对完整 commit、文件全文 SHA-256 和行号；缺文件、无效 commit、散列不同、缺回归页或问题原文泄漏时失败。before 阶段还拒绝已包含待补标识符的当前库，不能发现基线变了便悄悄挑换问题。问题改写与评分规则的修改都会改变 suiteRevision；正式对照必须保留同一版本。after 仅做结构预检，绝不自动判“改善”。

实际结果：

```text
status: prepared-only
suiteRevision: d8fde3370247e385fb1093df80f28c42235cc87bbcd1ef19af806d5e39ab5b80
knowledgeRevision: 17a712287d5b255b4d3c3ddbac610a5e79a1298cbbfdd39f4013043f4cb73ec8
pages: 19
verifiedEvidence: 6
modelCalls: 0
costUsd: 0
六个回答场景均为：尚未验证
```

基线副本保留在 `tools/wiki-runtime/knowledge/<knowledgeRevision>/`；复用既有快照校验，不另定义知识版本算法。正式材料、问答会话和评测标注仍各自独立：样本 JSON 不在 wiki 或运行副本内；原文泄漏检查不能代替人工判断语义泄漏。

## 离线对照配置

[buildChatRequest](../../server/chat.ts) 新增仅供服务端调用的 `control: { model, maxCostUsd }` 配置；HTTP 入参没有开放它。复用正常问答的规则、索引注入和受限文件工具，只保留 Read / Grep / Glob，禁 WebFetch / WebSearch；拒绝旧 session 和历史问题，关闭会话持久化。模型及正数单次额度必须显式提供，普通问答继续使用原工具权限。

这只是请求构造能力。原生 CLI 在真实调用中是否严格执行文件与工具限制、模型是否服从仅用快照回答的要求，仍未验证。单次 `maxCostUsd` 也不等于跨探针、编译、前后复问的总预算账本；本轮没有新增自动收费执行命令。

## 下一步与限制

1. 在用户给出的新增调用总预算内，用无敏感数据的小夹具验证原生 CLI 的目录边界和联网工具禁用；未真正触发被禁行为时只能记“尚未验证”。
2. 固定实际模型标识、调用配置及费用记录，针对上述基线执行六个独立新会话，逐例保存原文、检索结果和工具记录。将联网补料和离线对照分开。
3. 只把原问题和钉定原始来源交给编译过程，保持保留改写与评分标注不可见。当前聊天保存产生 source / I 记录；要验证缺失源码事实的改善，还必须确保原始证据被归档、进入审阅并支撑结论，不能把聊天记录升格为源码证据。
4. 批准明确 revision 后，再按同一六题开启独立新会话，人工按固定来源分别核对事实、引用、版本和回归。没有语义结果时保持未通过，失败时不替换样本。
