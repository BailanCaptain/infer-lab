# 知识库教学体系改版计划

**Feature:** 现有 F001 知识库的教学内容与阅读组织改版，关联 [F001](../features/F001-llm-wiki.md)，不另建功能平台。
**Goal:** 让具备基本 Python 和矩阵知识、没有 NPU 设备的读者，围绕 GLM-5.3-Flash 理解模型计算、单请求与并发推理、vLLM/vllm-ascend 架构，以及有官方依据的双机部署。
**Acceptance Criteria:** 本计划用下文“验收入口”组织此次教学改版检查，不复制或重定义 F001 的功能验收表；既有功能验收仍以 F001 为准。
**Architecture:** 目录按知识主题组织，导读按学习顺序串联。复用现有内容、来源和 figure 图形体系；参考 glm-flow 的模型结构，视觉样式适配知识库。模型与部署事实单处维护，专题通过链接和版本差异扩展。
**Tech Stack:** Markdown、现有 frontmatter/relations、YAML figure spec 与生成 SVG、现有 React 阅读页和 TypeScript 目录；不为改版引入新的文档平台或绘图服务。

本计划依据 [讨论记录](wiki-teaching-discussion-2026-09-25.md)。用户确认读者基础及无设备前提，先要求写计划、再经同模型 agent 审查，随后要求按步骤推进实施并由用户监督。实施进度和下一步只记在 [HANDOFF-LLM-WIKI.md](../../HANDOFF-LLM-WIKI.md)。计划中的预期不表示图、配置或部署已验证。

## 1. 已确定的教学定位

- **读者**：懂基本 Python，知道矩阵是什么；不要求学过 Transformer、部署过 vLLM 或拥有 NPU。张量维度和必要数学在使用处解释，不另开完整编程与线性代数课程。
- **贯穿模型**：GLM-5.3-Flash。通过缩小观察范围解释一个层、一次计算、一个时间步，不在章节间反复更换主模型。GQA 等对照机制要明确其与主模型的关系，不能把所有变体都说成主模型自带的结构。
- **专业深度**：正文使用准确术语，首次出现即解释。mHC 等机制保留真实位置、连接和必要状态，简述作用；训练与数学推导作为可选延伸。影响推理、缓存或容量的差异不能省略。
- **无设备学习**：主线以图解、可手算示例、源码阅读和官方配置解读完成。部署命令是可供有设备者复现的工程参考，不是读完课程的前置要求。
- **开源导向**：正文不能依赖本机绝对路径、私人材料、localhost 服务或私有模型接口；引用可追溯，示例数据及图源可说明。仓库公开发布本身不在本次执行范围。
- **双机案例**：采用有官方资料支持的同模型案例，后续固定版本和配置。不假定存在设备，不宣称跑过命令、不编造日志或性能数字。

## 2. 终点与范围

读者完成主线后，应能对着同一模型和系统图说明：输入如何变成张量、模型如何得到 logits 并选出下一个 token、后续步骤复用哪些状态、多请求如何共享计算且保持序列边界、框架各组件交接什么、双机执行在哪里需要通信。

本轮改版范围：教学页、目录与导读、相关图形能力、来源及术语整理、写作规则与交接。参数页的自动生成区、已有版本谱系和 RFork 工作版的独立事实边界继续保留。

不做：重写整个网站、重建 glm-flow 独立母版、增加完整训练课程、全套多模态教程、新建通用模型编辑器、购买/租用设备、运行真实双机实验、公开推送或部署网站。

### 终态内容约束

| 对象 | 终态约束 |
|---|---|
| 模型事实 | 模型介绍页承载解释，模型来源/配置记录承载固定依据；图与计算示例引用同一组事实，不各填一套数字 |
| 部署基线 | 模型 revision、量化产物、框架 commit/镜像、设备映射、并行配置、功能前提集中记录；不覆盖旧版本结论 |
| 教学页 | 保留稳定 id；有问题、前提、解释、图、必要的源码/版本依据及下一步链接；标题结构按主题需要组织 |
| 导航 | 一个主题有明确主位置；导读与专题可以链接同一页，避免复制正文；课程章号不充当新的知识分类 |
| 图 | `wiki/diagrams/<id>.yaml` 为本库图的表达源，SVG 由工具生成；共用语义颜色和组件 |
| 后续新增内容 | 先判断是新专题、现有概念变体、版本变化还是纠错，再决定新增或修订；保留影响检查与来源 |

不预先新增通用元数据层。若图需要共享数值，实施时先检查现有配置/生成入口能否复用，再决定最小的数据文件形式；图中文字不得变成新的事实来源。

## 3. 目录草案与导读

以下是建议目录，实施前结合迁移表确定标题。并列主题不代表必须按侧栏顺序从头读完。

| 分区 | 内容组织 |
|---|---|
| 开始学习 | 阅读指南、贯穿模型与整体图、单请求、多个请求、框架总览；这些是后面主题页的导读入口 |
| 模型结构与计算 | Token/Embedding/矩阵与权重 → Decoder 层/Norm/残差 → 注意力与位置编码 → MoE → 混合注意力与模型变体 |
| 推理机制与状态 | Prefill/Decode → KV 与混合状态 → 块表/缓存分配 → 调度与连续批处理 → 前缀复用 → 采样与投机解码 |
| vLLM 与 Ascend 架构 | 组件及进程 → 启动/加载 → 调度接口 → Worker/ModelRunner → 注意力后端与算子 → 图执行 → 源码阅读 |
| 昇腾硬件与软件栈 | 设备/卡/服务器 → 主机内存/HBM → AI Core → CANN/HCCL → 机间网络/机柜/超节点 |
| 分布式推理与部署 | TP/PP/DP/EP 等并行维度 → 通信与设备映射 → 官方双机案例 → PD/EPD 等专题 |
| 性能与扩展专题 | 容量和延迟分析、量化、图优化、异步调度、负载均衡、卸载、共享缓存、LoRA/结构化输出等具名主题；不混成无分组的“特性”清单 |
| RFork 工作版 | 保留独立总览、术语、机制、配置、维护与排错，版本独立 |
| 参考与更新记录 | 参数及版本、来源、PR/问答记录、术语；来源类型仍可识别，已形成教学页的内容回到相应主题 |

**建议导读顺序**：模型总览 → 必要的模型组件 → 单请求 Prefill/Decode → 多请求 → 框架职责与进程 → 硬件与并行 → 双机案例 → 按需求选择缓存/性能专题。读者随时可以从总览跳到组件详解，再回到原步骤。

标题以对象和学习问题为中心，如“调度器与连续批处理”“模型前向与下一个 token”。避免以脱离前提的结论、拟人化比喻或函数调用顺序充当整章标题。

## 6. 分阶段执行

2026-09-26 用户补充：所有衍生机制都须讲清基础、问题、继承、变化与取舍，避免从陌生缩写直接跳到最终实现。写作规则统一见 HANDBOOK「页面格式」；阶段 C 需回查已完成样章及基础页，后续每批独立审查包含这一项。概念比较与历史演进分别举证，不强行编排单线发展史。

同日追加两项明确范围，不得仅记作后续建议：

- **注意力基础先于 GLM 变体**：详细说明密集因果注意力的可见范围、Q/K 评分、softmax、V 汇合、Prefill/Decode 与代价，再讲稀疏模式、候选选择和被保留的计算。补独立 `sparse-attention` 教学页或等量明确章节，与 `attention-qkv`、`mla` 衔接；不能让 MLA 压缩、稀疏选择和 KDA 递推混成一种优化，也不能将因果掩码等同稀疏检索。
- **通信基础先于并行策略**：补独立 `collective-communication` 教学页，解释 rank、通信组、集合通信与点对点，逐项展开 Broadcast、All-Gather、Reduce-Scatter、All-Reduce、All-to-All、Send/Recv 的输入输出、张量形状与数据归属。随后逐页在 TP/DP/PP/EP/CP/SP 中对应计算切分、通信内容与同步位置；推理 DP 与训练梯度同步分清，官方双机仍用固定部署证据。
- **动态图按需要验收**：静态图承担设备、分片与前后状态；对分步归约、通信顺序、流水线微批次等需要时间维度的主题，评估并在确有教学收益时实现轻量逐步播放/手动推进，保留无需动画即可阅读的图文、暂停与减少动态效果支持。不得为动画引入无关基础设施；也不得只因既有组件没有动画就跳过评估。是否采用及理由记录在对应页迁移验收中。

每阶段产物进入终态内容，不做后续注定丢弃的演示页。以下描述执行任务与通过条件，实际完成情况只看交接入口。

**文件**：`wiki/HANDBOOK.md`、规划的 `wiki/sources/glm-5-3-flash-baseline.md`；只在确有需求时增补 `wiki/seeds/` 中对应钉点，不重钉或覆盖其他版本。

1. 以现有讨论中的官方资料为线索，重新核对准确型号、模型 revision/配置、源码和量化权重；核查双机命令与设备前提的文字不一致。
2. 固定实际可引用的镜像与 commit；若官方示例依赖开发版，如实标明，不拼接多个版本的命令来制造“完整基线”。没有设备时只做文档/源码核对及可行的静态检查。
3. 建立普通自回归教学视图与官方完整部署的差异表；官方配置若开启投机/其他功能，不能未经验证删参后称等价已验证配置。
4. 调整旧规则中“上半禁止代码名”“下半必须固定五类标题”“固定旧混合模型案例”等与新目标冲突的部分，保留来源、条件、版本与事实完整性要求。同步对应校验，不能让新正文靠屏蔽错误通过。

**限时调查**：模型/官方配置冲突初轮最多半个工作日；输出证据与未解条件。仍无法支持完整基线时明确记录，继续独立的目录和概念工作，不自行换模型、不捏造缺失参数。

**通过条件**：主例的每个数值/命令有固定依据；读者知道哪些是官方实例、哪些是教学假设；旧规则与新写法不互相冲突。去掉本阶段会导致全库重复返工和版本混用。

### 阶段 B：目录与四个代表性部分

**文件**：`src/content/wiki/toc.ts`、`src/content/wiki/toc.test.ts`；新增模型/导读/并发页，重写 `one-request.md`、架构总览相关页及所引用的必要基础段落；图在 `wiki/diagrams/`。

1. 先用目录测试复现 GQA/MLA 无明确主题归属的现象，以及新增/生成页落位问题；调整主题组织，保证无丢页、无无意重复、RFork 与参数入口保留。
2. 完成模型介绍与知识库风格的 2D 图，总览展开不改变真实结构。
3. 单请求围绕张量与状态闭环展开：服务就绪 → 输入准备 → 调度 → 执行 → 模型输出 → 采样/状态更新 → 返回与下一步。逐项对照固定版本，不能拿概念顺序充当已验证函数调用栈。
4. 多请求展示不同输入/输出长度、分批进入、结束释放，以及每步计算集合；说明序列边界和共享条件。
5. 由上述观察解释框架组件职责，再把请求步骤定位到进程、接口、适配后端和算子；模型计算图不能代替框架图。
6. 在实际阅读页审阅四部分及目录，核对深度、图形可读性、术语与学习衔接后再扩展；这是整体执行中的检查点，不是把其余工作视为取消。

**通过条件**：无设备读者能解释 Prefill 与 Decode 的输入差别，指出输出 token 如何进入下一步，区分请求/批次/进程/rank，并用正式组件名称说明职责。去掉这阶段的集中检验会把不合适的讲法推广到全库。

### 阶段 C：全库迁移与专题改写

**文件**：第 4 节列出的教学页及相关图；双机页；必要的 `wiki/TERMS.md` 与 relations。

按模型基础 → 状态与缓存 → 框架执行 → 硬件与分布式 → 专题的依赖顺序改写。每批完成来源核对和图文检查后再下一批；保持稳定 id 与历史来源，只有解释确实重复才合并。

**用户补充确认（2026-09-25）：分类和正文组织必须一起修正。** 每批页面同时核对主主题、标题、正文讲解及配置参考的位置，不能只搬目录就标记完成。“性能与扩展专题”的现状与逐页建议见 [内容定位排查](performance-section-audit-2026-09-25.md)，具体落位随正文核读确定，不把建议表当作已核验事实。调度、缓存、分布式机制分别回到自己的主题；服务能力与数值一致性明确区分。性能专题围绕瓶颈、指标、优化机制与代价组织，不能继续充当特性集合。正文先解释问题、状态与数据流、实现职责，再交代配置组合及适用范围；单项字段的默认值和版本记录优先链接参数参考，必要条件与证据仍保留在影响理解的位置。

优先解决已有讨论中的问题：前缀缓存的开启/匹配/驻留条件与 2048 的特定前提、计算量与访存量混淆、职责过度二分、C/S 引用编号错位、生硬指代。逐段判断，不全局替换“那条请求”后声称教学已改善。

双机页同时提供无设备可读的拓扑/配置推导，以及具备设备者的完整参考命令、前置条件、检查步骤和有来源的预期行为。未经运行的命令标“未实机验证”；示意输出不能伪装实际日志。性能影响可以定性解释或给明确假设下的推导，不能写成实测结论。

**通过条件**：迁移表逐页有去向，目录归属与正文主旨一致；读者能解释运行机制，而不只是找到启用参数。主线数字与前提一致，专题仍保留版本和独立适用范围。删去此阶段会留下样章与旧正文互相矛盾的半成品。

### 阶段 D：扩展规则与开源可用性

**文件**：`wiki/HANDBOOK.md`、`wiki/TERMS.md`、`README.md`、必要的目录/链接测试；不顺带重构自动编译和同步系统。

- 新模型/新架构通常增加结构与差异专题，链接共用概念；新证据推翻旧结论时同步修正文、图和依赖页。
- 新框架版本区分行为变化与概念变化；主模型或主部署升级另行做迁移，不随新材料入库自动替换。
- 新教学页有明确主题落位；PR/问答记录保留来源身份。核验现有写入路径对这些规则的支持程度，不能只改手册就声称自动流程已保障。
- 检查图源、模型资料及复用文件的许可证/署名；将运行必需资产和来源放在仓库允许分发的位置。继续沿用现有 RFork 公开前的权属确认事项，不能因为计划面向开源就视为已经获得发布授权。
- README 写清本地启动、内容构建、无设备阅读和可选部署参考。普通读者不需要 glm-flow 本机服务、模型下载或 NPU 驱动。

**通过条件**：从干净检出按说明可以构建/阅读；模型图无本机路径依赖；新增专题不会自动破坏主线，但旧错误仍被修正。不承诺“新知识永不影响旧内容”。

### 阶段 E：验收与交接

**文件**：相关测试/生成图、`wiki/TERMS.md`、`HANDOFF-LLM-WIKI.md`；已有功能验收表仅在确有相应验证证据时更新。

按下一节运行对应检查，逐项核对关键声明和来源，在浏览器完成真实阅读路径及交互检查。最后交接明确本轮改了什么、固定了哪些版本、还有哪些未实测条件。提交只包含本次任务变更，排除当前工作区已有参数同步及探针等无关修改；公开发布另行执行。

以下为未来执行命令，不是本轮结果。命令从 Wiki 工作树根目录运行；涉及代码的修复先有失败测试或稳定复现，修复后再验证。纯文案不编写镜像式测试。

| 改动 | 检查/命令 | 预期结果 |
|---|---|---|
| 目录归属 | `pnpm exec vitest run src/content/wiki/toc.test.ts` | GQA/MLA 归到模型主题；存量/新增页不丢失，RFork/参数边界保留 |
| 新图形零件 | `pnpm exec vitest run scripts/wiki/figure.test.ts` | 语义和绘制边界正确，原图无回归；测试通过仍需视觉核对 |

人工教学检查围绕七个问题：模型是什么；下个 token 如何产生；每步复用什么；多请求如何组织；框架各管什么；跨设备传什么；哪些是通用概念、主模型事实、版本行为或教学假设。正文与图应能相互支持，不要求读者靠猜测填补中间步骤。

## 8. 本轮基线与待调查项

本轮实际读取了现有目录实现、教学文件名/标题清单、HANDBOOK 的相关写作与图形规则、项目命令以及交接入口。此前已定位 glm-flow 2D 母版文档和源码入口。本计划中的迁移与实施步骤据此制定。

本轮没有重新逐条核验官方部署、浏览器验收现有图、运行模型或执行全库测试；本计划不会把历史调研自动升级为新版本验证结论。

目前无必须由用户补充的教学定位问题。执行者需继续调查：准确的模型/部署固定版本、文档中的设备映射冲突、既有图数据的共享方式及来源许可、规则调整影响的校验路径。这些先调查并给出具体方案，只有事实无法满足既定方向或需改变范围时才提请用户选择。
