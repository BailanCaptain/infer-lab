## 本轮独立核源

- **旧入口为何不能照抄运行。** 实读三份Ascend旧 `npu.py`（db701c1f、2c59ff10、2ed6cbba），确认旧模块导入、必填主机段数、单组断言及旧manager参数。对上游0fc695fc/568afb3a运行 `git ls-tree`，abstract/spec/mediums三个路径均不存在；`git show c42981d034 --name-status`确认删除。旧CPU manager构造函数不收block_size。这里只支持源码导入链不配套的判断，不声称跑出了NPU异常。
- **新worker确实按字节/组搬运。** 实读Ascend main native `cpu_npu.py` 65–264、275–344及main/rc2 `npu.py`。规范int8二维视图、按组数据引用和页尺寸、两方向传输与事件、CPU私有张量和共享映射均有实际实现。CPU-only不借共享区域去重；Tiering才走共享区域和相应rank槽布局。
- **预算与单份布局。** 实读rc2/main CPU spec 94–165、rc2 config 59–176/250–274、main config 94–135、rc2 parallel 874–885。预算按配置world_size计副本，replicated_layout须同时满足共享区域条件；纯MLA规格精确匹配、页面账吻合、TP>1、PP/PCP/DCP=1、world_size=TP、单节点mp等限制成立。常规world_size为PP×TP×PCP，external_launcher含DP的例外也成立。GLM混合组不能从“支持多组”推成已可用或可去重。
- **保存、完成和源页等待。** 实读旧scheduler 721–840/905–1027、CPU manager 120–218、调度器605–630/800–812、engine 206–215。计划筛无效/不可达内容后交管理器筛已存/阈值/容量；先分配和插入记录不等于ready；参与worker结果汇总后才完成；请求结束仍有保存时登记pending块，后续复用前触发等待。APC或connector任一存在即建请求哈希；另一个CPUOffloadingConnector受APC开关约束，名称区别成立。
- **部分尾状态。** 实读rc2 scheduler 270–307、951–1002、1314–1463、1464–1560及main gate 266–303。单物理块、相同逻辑块长、细哈希align递推组、非滑窗或专用状态组、无EAGLE、DCP=1的条件一致；保存还需调度输出中的boundary_state_offloads，全组按同一边界构造键，实际被管理器接纳的组才进入传输任务。正文未宣称普通70位置示例能无条件保存6位置尾巴。
- **官方文档与四版默认。** 完整读旧官方guide 108行和rc2 guide 139行；前者“显存满才拷”的简述不能覆盖实际提前保存实现。后者CPU-only锁页与Tiering mmap、文件系统配置/线程/块大小取舍、磁盘淘汰仍在开发均与正文相符。实读旧base及v26/rc2/main的offload_prompt_only字段，四版默认true成立。本独审没有宣称PR #13389讨论全文或当前网站全站已读。
- **GLM容量算例。** 复读本站 `concurrent-requests.md` 的32×67000、120–121块及9步推导、部署页7.969MiB块与13056B/位置口径。本文保留956–964MiB与8卡7.47–7.53GiB为池容量账，明确不能当恢复payload；实际已保存范围、状态布局、prompt限制及实测带宽仍未知。这种限定比按释放容量直接算offload耗时准确。
