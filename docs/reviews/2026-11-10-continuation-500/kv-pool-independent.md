## 重点核验结论

1. **全中少报一个属于调度记账。** 查询代码只在外部命中等于 `request.num_tokens` 时减一；这个长度包含已生成部分，不能把被抢占请求的全部 prompt 命中直接当全部请求命中。worker L758–763 又可能将实际加载长度补回整段。修订中的新请求 20/20/8 → 上报 11 的例子及位置/字节区别正确。
2. **身份键不等于权重认证。** 固定版 `KeyMetadata` 只用模型末级目录名，普通键没有权重版本和 TP 总大小。主张改为“可能同名而内容不兼容”恰当；不是必定报错，也不是必定静默成功。rc2 的 PP namespace 确实按 TP、层分区、模型/缓存/投机配置摘要构造，PP=1 返回空前缀；这仍不是权重文件校验。
3. **单组和多组失败已经分开。** 固定同步 worker L844–874 对非零返回和 None 返回都处理，但只有一组会登记无效块，多组记录错误。getter L1401–1405 只取出集合并清空；上游 scheduler L1358–1365 依赖非空无效块集合，L1581–1592 才让 fail 请求以错误结束。平台 L892–900 明确禁止混合模型的 recompute。正文已保留这些条件，旧待核没有再次将禁止项写成可选路线。
4. **rc2 写回等待变化核到了生产方和消费方。** scheduler L1043–1052 把本次抢占及已结束请求 ID 写入 `released_req_ids`；connector L288–298 交给 worker；worker L2912–2927 只让普通发送线程等待这些请求；`kv_transfer.py#L940-L959` 轮询这些 ID 是否还在 `stored_requests`。它确实区别于 main 等上一整批，不是仅凭注释推断。
5. **字节与容量修订合理。** 普通 K/V 随位置增长，递推状态按留档边界保留定长状态；不能统一乘 prompt 长度。容量应累加不同记录，再另计缓冲与后端成本。8,355,840 B 是该 GLM full 组每逻辑块的推导，未写成成功池传输的实测；实际登记/回填仍留待核。固定 worker 的主 MLA 分支要求完整物理页后再 view 成 kernel 块，不能用后续一般 strided MLA 迁移指南反推此数必错。
6. **版本表新增项有实际实现。** 已读 rc2 普通键、TP 子键启用条件、PP 分区检查与空组拒绝、Mamba 先加载后复制，支持目前表述。保存角色门槛与官方部署支持没有混为一谈；新表仍保留 CP 与两端 TP 不一致的限制。
7. **官方后续内容没有套回旧 GLM。** MLA 对象迁移的两次格式变化、严格租户不等于认证、SSD offload 不等于预取、独立服务 SSD 根目录和 IPC/TCP 端口区别都按 921ccc52 标示；相关参数需完整配套条件的表述与所读官方范围一致。
