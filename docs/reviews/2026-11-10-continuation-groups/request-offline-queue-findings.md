# 官方离线队列入口：补读结论与教学缺口

本记录只覆盖 99 项目录的第 93 项中的提交／等待队列及必要暂停边界。正文尚未改动，不将母页全文已读等同于所有关联功能已覆盖，也不计新增全文阅读数量。

## 本站缺口

当前请求链、进程页已经说明离线 LLM 与默认独立 EngineCore，尚未解释 enqueue / enqueue_chat / wait_for_completion 的使用边界。对初学者最有价值的问题是：脚本先交两组请求，随后一起取结果；是否第一组一定等到第二组交完才开始计算？

建议唯一主解释放在 request-call-chain 的通用变体中，API 页只回链。队列的收益是把提交和收结果分开；成本仍包括提交阶段的模板、分词／媒体处理，以及所有在途请求的状态和最终输出内存。它不是取消前处理成本的纯瞬时操作，也不是另一个 HTTP 异步任务服务。

## 必须保留的结论

1. 四个固定上游版本都提供这三个同步 Python 方法；enqueue 仅允许生成模型，enqueue_chat 先做对话模板处理，返回请求 ID 列表而非生成文本。官方母页说的是“不等待完成”。
2. 默认 V1 多进程 getter 为 1。提交会立即发送 ADD，后台 EngineCore 的循环自行处理输入并运行模型；因此第一组可以在第二组提交前就开始运行。LLM.enqueue 自身注释中“不开始处理”的一句话不能作为这一默认模式的统一结论。
3. 关闭 V1 多进程且没有其他显式强制条件时，InprocClient 的 get_output 才直接调用 step_fn。两种模式应在同图分支，而不把一种行为套到另一种。
4. wait_for_completion 等待当前引擎所有未完成请求，不接受一个 ID 子集来只等其中一组。默认接收两类输出；显式 output_type 是运行时类型断言，不是筛掉其他类型结果。
5. 共享 run loop 只收最终输出，按数字请求编号排序，即提交次序，不是完成次序。示意输入 3 条加 2 条得到 5 个请求 ID；完成顺序即使为 2、0、4、1、3，返回列表仍按 0、1、2、3、4。此处仅为单答案普通生成示意，不宣称设备实测或吞吐提升。
6. 提交循环对已经加入的请求逐一登记；后续某个输入预处理或加入失败时，会 abort 本轮已加入的 ID，再抛出异常。不能用“提交一整批”暗示数据库式全批同时可见。
7. 要保证所有请求先入队再开始，可在一个原本清醒、尚未提交工作给它的引擎上先 sleep(level=0)，加入各组，再 wake_up(tags=["scheduling"])，最后 wait。level 0 只暂停调度，不执行权重卸载。默认 mode=abort 会终止已有请求，所以应在本例提交前暂停，不能随意插进正在服务其他请求的引擎。
8. 四版调用表相同不代表所有实现字节相同：v0.26 起 wake 只有在执行器已无休眠内存时恢复调度；rc2/main 的完成暂停辅助函数还同步设备。新行为不能套回旧版本。多 DP 的暂停协同并未在本次进行硬件验证；不把这个局部例子扩成 GLM EP16 全套运行配方。
