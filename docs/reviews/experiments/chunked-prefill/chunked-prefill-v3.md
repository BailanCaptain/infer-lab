> **一句话讲透**：**Chunked Prefill（分块预填充）** 就是不让一条长提示词霸占整步计算——每一步先紧着正在吐字的老请求 `decode` 算，剩下的 token 预算有多少，就给新来的长提示词 `prefill` 切多少，分几步算完，最后一步才吐出第一个回答字。

---

## 1. 为什么要切？先看「不切」会卡在哪

在线大模型服务里，同一时刻往往混着两类截然不同的活：

- **Decode（老请求续写）**：前面的提示词早就读完了，现在每一步只需要喂进去 `1` 个刚生成的 token，算出下一个 token。它算得极快，但用户正盯着屏幕看字往外蹦，稍微顿一下就能察觉（看重 **ITL，字间延迟**）。
- **Prefill（新请求读题）**：用户刚发来一段长提示词，模型必须先把这几千上万个 token 全读完、存好历史（`KV Cache`），才能吐出第一个回答字（看重 **TTFT，首字延迟**）。

问题来了：**同一批（Batch）送进 GPU 的请求，必须等整批里最慢的那部分算完，大家才能一起拿到结果。**

假设我们把每一步最多允许计算的预算（`max_num_batched_tokens`）设为 **`8` 个 token**：
- 场上已有请求 **A、B** 正在 `decode`，每步各占 `1` 个 token；
- 这时新请求 **C** 带着 **`14` 个 token** 的长提示词插了进来。

切与不切，走出来的是两条完全不同的时间线：


把上下两条时间线摆在一起对比，差别一目了然：

| 排法 | 第 1 步要算多少 token | 正在看回答的 A、B 用户 | 刚发长文的 C 用户 |
| :--- | :--- | :--- | :--- |
| **不切（传统排法）** | `1 + 1 + 14 = 16`（单步被撑爆） | 明明只差 `1` 个字，却要陪等 `16` 个 token 的大步跑完，**屏幕明显卡顿** | 1 步算完，当场拿到第一个字 |
| **切开（Chunked Prefill）** | `1 + 1 + 6 = 8`（严守预算上限） | 每步最多只陪跑 `8` 个 token，**照常丝滑吐字** | 提示词切成 `6 + 6 + 2` 三步读完，第 3 步末拿到第一个字 |

这就是 Chunked Prefill 存在的全部理由：

1. **保住在线生成的丝滑感（稳住 ITL）**：用单步预算给计算量封顶，绝不让一条几万字的长文把同批所有正在说话的请求拖进一次漫长的停顿。
2. **消除等待队列的「队头阻塞」**：如果不切块，只要排在队头的长请求塞不进当前剩余预算，排在它后面的短请求也只能跟着干等；切块后，剩余预算有多少就先吃多少，短请求还能趁机插空算完。
3. **顺路拼批复用模型权重**：`decode` 每步只有寥寥几个 token，光搬运一遍庞大的模型权重非常亏；和切出来的 `prefill` 片段合进同一个 batch 后，大家一起乘同一份模型权重，GPU 算力利用率更高。

## 2. 调度器怎么切？其实只有一道减法

很多人第一次听「分块预填充」，以为调度器里有一套专门切提示词的复杂状态机。其实打开 vLLM 的 `scheduler.py`，第一行注释就写着：**调度器根本不区分 `prefill` 阶段和 `decode` 阶段。**

在调度器眼里，每条请求只有两个数字：
- **目标要算到第几个位置**（`num_tokens`）
- **目前已经算完几个位置**（`num_computed_tokens`）

两数相减，就是这条请求**「还差几个 token」**。每一步排班时，调度器只守两条极其简单的规矩：

1. **先老后新**：先排已经在跑的 `running` 队列，用剩下的预算再去接纳刚来的 `waiting` 队列。
2. **有多少吃多少**：每条请求这一步能分到多少个位置，永远只做同一道减法：
   $$\text{本步分配量} = \min(\text{还差几个},\ \text{本步剩余预算})$$

我们把刚才 `A、B（各需 1）+ C（14 个 token）` 代进这道公式，一步步看它是怎么切出 **`6、6、2`** 的：

| 调度步 | 先排 A、B | 剩余预算 | C 还差几个 | C 本步分到 `min(还差, 余量)` | C 本步算的区间 | 步末发生什么？ |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **第 1 步** | `1 + 1 = 2` | `8 - 2 = 6` | `14 - 0 = 14` | `min(14, 6) = 6` | 位置 `0..5` | 存下 `0..5` 历史；**段末采样结果直接丢弃** |
| **第 2 步** | `1 + 1 = 2` | `8 - 2 = 6` | `14 - 6 = 8` | `min(8, 6) = 6` | 位置 `6..11` | 追加 `6..11` 历史；**段末采样结果直接丢弃** |
| **第 3 步** | `1 + 1 = 2` | `8 - 2 = 6` | `14 - 12 = 2` | `min(2, 6) = 2` | 位置 `12..13` | 提示词全部读完，**正式吐出首个回答 `y₀`！** |
| **第 4 步** | `1 + 1 = 2` | `8 - 2 = 6` | `1`（已转 decode） | `1` | 送入 `y₀` | A、B、C 三条请求一起正常 `decode` |

## 3. 切成三截算，结果为什么和一口气算完一模一样？

初学者最常问的一个问题是：**「把一句话劈成 `0..5`、`6..11`、`12..13` 三截分步喂给模型，最后难道要把三段输出拼起来吗？」**

答案是：**根本没有「拼结果」这一步。** 分三步算出来的 `y₀`，和一口气算完 14 个 token 拿到的 `y₀` 数学上完全等价，靠的是执行链路上的三根接力棒不断线：

```wiki-diagram
file: chunked-prefill-flow
```

1. **位置编号（Position IDs）顺着往下排，绝不从 0 重来**
   第 1 段进模型时带着位置号 `0..5`；到了第 2 步，Worker 会从上次算完的进度（`6`）接着编号，把第 2 段标为 `6..11` 送进模型。因为因果掩码（Causal Mask）只看位置编号，所以位置 `11` 在做注意力时，看到的依然是 `0..11` 的完整上文。
2. **前文历史躺在显存里原地续写，不用重算前段**
   - **普通注意力层（Attention）**：第 1 步算出的 `0..5` 的 K、V 向量已经写进了显存块表（Block Table）；第 2 步只需要算出 `6..11` 的 K、V 追加到后面的格子里，做 Attention 时把显存里现成的 `0..5` 和刚算的 `6..11` 一起读出来打分即可。
   - **线性注意力 / 状态空间层（如 KDA、Mamba）**：这类层不按位置存 K、V，而是每条请求维护一份固定大小的递推状态。第 1 步算完把状态存回槽位，第 2 步把它当初始状态读出来接着往下推，同样无缝衔接。
3. **中间段末尾采出的 token 当场扔掉**
   GPU 跑完一步前向后，其实会顺手在每条请求的最后一个位置做一次采样。但在第 1 步（刚算到位置 `5`）和第 2 步（刚算到位置 `11`）结束时，C 的提示词根本还没读完，这时候猜出来的「下一个字」毫无意义——执行器会通过掩码（`discard_requests_mask`）把它**当场丢弃**，不写进输出队列。直到第 3 步算完位置 `13`，采出来的 `y₀` 才真正发给用户。

## 4. 代价在哪？天下没有白吃的午餐

既然切块能防卡顿，那能不能把每步预算切得极小（比如每步只算 32 个 token）？不行。把长提示词切碎，要付三笔实打实的代价：

### 代价一：长请求自己的首字更晚（TTFT 变长）
不切的时候，C 在第 1 步结束就能拿到 `y₀`；切成三段后，C 必须跨三步才能把题目读完，中间每一步还得陪着 A、B 一起跑，提交长文的用户等待第一个字的时间自然变长了。

### 代价二：前文 KV 历史要跨步反复读（省了单步时长，没省总算力，还多费显存带宽）
这是最容易被误解的一点：**Chunked Prefill 一丝一毫都没有减少总计算量（FLOPs），反而增加了显存读取量。**

在普通因果注意力里，位置 $i$ 必须和 $0 \dots i$ 的所有位置做一次打分：
- **总计算量不变**：不管是一口气算完，还是切成 `6 + 6 + 2` 三步算，总共要做的注意力配对次数都是 $1 + 2 + \dots + 14 = 105$ 次。
- **显存读取变多**：
  - **不切时**：`0..13` 共 **`14` 个位置**的 KV 在一次算子里一气呵成。
  - **切成三步时**：
    - 第 1 步读 `0..5`（**`6`** 个位置）
    - 第 2 步要把显存里的 `0..5` 重新拉出来，配上 `6..11`（读 **`12`** 个位置）
    - 第 3 步又要把显存里的 `0..11` 重新拉出来，配上 `12..13`（读 **`14`** 个位置）
    - 三步累计访问了 **`6 + 12 + 14 = 32` 个位置**——`0..5` 被多读了两遍，`6..11` 被多读了一遍！切得越碎，前文 KV 被从高带宽显存（HBM）里反复搬运的次数就越多。

### 代价三：步数变多带来的单步固定开销
把 1 步拆成 3 步，CPU 就要多跑两轮调度与输入准备；GPU 在第 1、2 步末尾还要在位置 `5` 和位置 `11` 上白做一次词表投影（LM Head）和采样，然后再把结果扔掉。

## 5. 实战怎么配？三个旋钮与线上真实账本

在 vLLM 中，控制分块预填充的核心参数只有三个：

| 参数 | 默认值 | 它是干什么的 | 调参直觉 |
| :--- | :--- | :--- | :--- |
| `--enable-chunked-prefill` | V1 默认开启 | 分块预填充总开关 | 在线混部服务保持开启；若手动关掉，单步预算必须大于等于模型最大上下文长度（`max_model_len`），否则启动直接报错 |
| `--max-num-batched-tokens` | 视模型与平台而定（如 `8192`） | **全批单步总预算**（一步最多算多少个位置） | **核心权衡旋钮**：调小（如 `2048`）优先保 `decode` 丝滑（ITL 更稳）；调大（如 `8192`~`16384`）减少重读 KV 的次数，长文 TTFT 更快、总吞吐更高 |
| `--long-prefill-token-threshold` | `0`（不限制） | **单条请求单步上限**（一条提示词一步最多吃多少预算） | 防止一条超长提示词把当步剩余预算吃干抹净。例如刚才的例子里若设为 `4`，哪怕剩余预算有 `6`，C 一步也只拿 `4`（切成 `4+4+4+2`），每步给后面排队的其他新请求留出 `2` 个空位 |

### 放到真实线上看一眼：20,000 token 是怎么分三步跑完的？

拿本站主线的 **GLM 双机部署**来算一笔真实账：
- 每台机器跑一个独立调度器，单步总预算 `max_num_batched_tokens = 8192`；
- 因为开了投机解码（MTP，每步顺带猜 3 个草稿 token），每条正在 `decode` 的请求每步固定占 `1 + 3 = 4` 个位置；
- 假设当前组里已经有 **12 条请求正在 decode**（每步先占走 `12 × 4 = 48` 个位置，剩 `8192 - 48 = 8144` 个位置预算）。

这时如果来了一条 **`6,000` token** 的中等提示词，因为 `6,000 < 8,144`，它根本不会被切开，1 步就能算完。
但如果插进来一条 **`20,000` token** 的长提示词，它就会像前面的 `6、6、2` 一样被切成三步：

1. **第 1 步**：12 条 decode 占 `48` + 长提示词切 **`8,144`** = **`8,192`（满载）** → 算完 `0..8143`，采样丢弃；
2. **第 2 步**：12 条 decode 占 `48` + 长提示词切 **`8,144`** = **`8,192`（满载）** → 算完 `8144..16287`，采样丢弃；
3. **第 3 步**：12 条 decode 占 `48` + 长提示词剩 **`3,712`** = **`3,760`** → 算完 `16288..19999`，吐出首个回答字！
4. **第 4 步**：长提示词也转入 `decode`（占 `4` 个位置），全批变成 `13 × 4 = 52` 个位置，恢复轻快推进。

> **工程实战里的一个冷知识：切多长，还决定了单步瞬时要借多少显存块。**
> 普通 KV Cache 块是按总长度慢慢攒的（上面这三步在 GLM 的 `640`-token 逻辑块下分别新借 `13 → 13 → 6` 块，切点 `8144 = 12 × 640 + 464` 直接停在第 13 块中间，完全不需要对齐块边界）。
> 但如果模型里带有「按单步新算长度借临时缓冲块」的组件（比如 GLM 稀疏注意力里按 4-token 窗口暂存零头的尾状态组），一段切 `8,144` 个 token 当步就要临时借走 **`2,037` 个块（约 15.9 GiB，占单卡 KV 池一半以上）**，算完下一步才归还！所以在这种模型上，控制单步分块预算不仅是在调延迟，也是在压单步显存峰值。

## 6. 一眼扫清常见误解

- **误解 1：「切开算能省显存、省总计算量」**
  **错。** 最终要存的 KV Cache 一格不少，注意力总计算量（FLOPs）一丝没省，反而因为跨步重读历史多花了显存带宽。它省下的是**单步最高耗时**。
- **误解 2：「每一段算完都会吐出一个字，最后拼起来」**
  **错。** 前面几段只是在往显存里攒 KV Cache，段末采出来的 token 全都当场扔掉；只有最后一段算完才吐出第一个回答字。
- **误解 3：「每步切出来的长度必须对齐 KV Cache 的块大小（block_size）」**
  **错。** 预算管「一步算几个 token」，块大小管「显存里几个 token 住一间房」，两边各算各的，切点随时可以停在某个块正中间（唯独部分混合架构模型开启前缀缓存对齐模式时例外）。
- **误解 4：「把预算设成 8192，每一步的耗时就固定了」**
  **错。** 预算封住的是**每步新算的 token 个数**，不是毫秒数。同样算 `8192` 个 token，前面挂着 10 万字历史的续算段，比从 0 开始的首段要多读海量历史，耗时依然会更长。如果希望 `prefill` 连这一丁点同批干扰都不要给 `decode`，那就得更进一步——直接把它们拆到不同机器上跑，也就是 **[PD 分离（Prefill-Decode Disaggregation）](../../../../wiki/concepts/pd-disaggregation.md)**。
