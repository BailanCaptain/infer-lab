## 设计约定

### 问题判断与目标

现有知识覆盖了大量推理机制，薄弱处主要是：指标与负载口径、从现象到证据的排查组织、依据瓶颈选择优化手段、端到端验证、生产系统取舍和新硬件映射。仅增加几个名词页不能使问答自然具备排障能力。

“性能问题”和“乱码”只是示例。最终范围包含启动、容量、正确性、执行、通信、缓存、接口、稳定性和版本回归等问题，也包含没有故障时的容量规划与优化选择。

前三份资料用于确定补全范围；GLM 样例继续引用自己的固定模型和代码依据，不将 DeepSeek 或 950 的实现移植成 A2 的事实。

### 两种进入方式

**学习者路线：** 阅读指南 → 模型与部署 → 单条请求 → 多条请求 → 贯穿分析样例 → 指标与实验 → 性能模型和诊断 → 按问题展开机制 → DeepSeek 生产案例与模型变体 → 昇腾 950。

**从业者路线：** 现象/目标 → 版本、模型与负载 → 最小证据 → 定位阶段 → 候选原因 → 区分候选的实验 → 同时验证效果、代价和正确性。可以直接进入样例后半段或诊断页，不必重读完整课程。

新增页数量是内容边界草案，不是必须凑齐的指标。下面共列出一个贯穿样例和十三个候选专题页；实写前若现有页面已足够，合并职责并更新计划。

### 每条诊断分支的共同结构

1. **入口条件：** 什么现象、什么部署下适用，哪些现象须转到其他分支。
2. **最小证据：** 请求、时间、批次、rank、版本、实际生效配置及错误上下文；写明从哪里取得，现有工具缺什么。
3. **候选原因：** 解释为什么符合现象；不把相关性写成根因。
4. **区分实验：** 一次检验一个假设，并说明伴随变化与风险。
5. **结果解释：** 哪种结果支持、削弱或推翻哪个候选；无证据时停在哪一步。
6. **下一步：** 回链机制、参数或源码；优化需复查延迟、吞吐、失败数、内存与正确性。
