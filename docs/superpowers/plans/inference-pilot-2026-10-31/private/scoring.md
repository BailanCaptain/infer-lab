# 试跑评分依据

本文件只发给评分者和复核者。参与者先提交原答，再解封。评分接受不同的合理方法，下面列的是证据边界，不是必须照抄的句子。

正式规则仍以[验收方案](../../2026-10-31-inference-user-field-acceptance.md)为准。本轮学习者只做两站，各 8 分，共 16 分；从业者一题 12 分。分数用于发现材料问题，不设置“一题通过即可完成验收”的门槛，不转换成正式五站 40 分或现场覆盖率。

## 通用记分规则

按首次无提示提交的答案评分。查阅题允许查阅，但合页复述、提示后补答各自留档。未答为 0，并同时注明超时、跳过、材料打不开等原因，不把原因藏进分数。0 表示错误或缺失，1 表示方向正确但关键条件不全，2 表示独立、正确且条件完整。

评分依据由资料与答案的实际对应决定，不因写出术语、关键词或链接就给满分。不能因参考答案列了三组实验，便拒绝同样有判别力的两组实验。两位评分者先各填分数和原答位置，最后保留分歧与复核理由。

## 学习者第一站

对应[任务单第一站](../learner-task.md#第一站-回答中途停住了)。复述与变式合起来按四维评分。

| 维度 | 2 分需要说明什么 | 1 分的典型情况 |
| --- | --- | --- |
| 机制 | 已在生成的请求若与新长输入同批，可能随这一步等更久；但停顿也可能来自未获调度或返回阶段 | 只说“人多就慢”，没有批次或具体等待关系 |
| 因果与代价 | 少处理每步长输入可能缩短同批生成的等待；新长请求需更多步才能出首字，还要核查实际分块、调度、吞吐与质量等取舍 | 只记住分块会快，或只说“有代价”而没说谁付出什么 |
| 条件迁移 | 算清 380 ms 间隔、100 ms 设备执行，优先补查其后 260 ms，能再分为 10 ms 到入队、250 ms 从入队到接收；不把片段间隔冒充逐 token ITL，不凭这份表确认代理或网络根因 | 找对返回方向，但混淆入队与发送，或把全部间隔算作计算；算术小错另记，若不改变方向可给 1 分 |
| 依据与条件 | 引用现有正文具体小节，解释对应的记录和边界；说明减少设备时间仍要核对结果的处理、发送、接收和实际用户间隔 | 只贴页名；或引用正确却把另一种记录的结论原样套用 |

### 数据应当怎样读

380 = 480 − 100；100 = 220 − 120。其余已知区间是 100–120 的 20 ms、220–230 的 10 ms、230–480 的 250 ms。这里只能按时间边界分段；不能直接把前 20 ms 命名为排队，也不能把后 250 ms 全叫网络传输。服务端入队不等于发送完成。

可以优先记录出队、实际写出、代理接收/转发和客户端读取的时刻，围绕同一请求和输出片段关联；也可从其中最靠近现有边界、成本最低的一项开始。全部时钟已对齐是题设，不能为补时钟信息否认已经成立的区间；现场当然仍需核对时钟与关联。

继续减小每步预算尚缺直接依据。若试验设备更快，仍要检查实际片段到达、首字、其他请求、失败和总交付，不可凭设备提前结束直接推算客户端一定提前。没有逐 token 到达记录，就只能说有效片段间隔。

依据复用[贯穿样例的等待分段](../../../../../wiki/concepts/inference-performance-walkthrough.md#这-240-ms服务在做什么)、[分块后的取舍](../../../../../wiki/concepts/inference-performance-walkthrough.md#d-不停了是否就算优化成功)、[记录不符时的分支](../../../../../wiki/concepts/inference-performance-walkthrough.md#如果记录不符合这个例子该从哪里查)，以及[测量页的片段与 token 区分](../../../../../wiki/concepts/inference-benchmarking.md#先把一个请求的几种等待分开)。这是新编数字练习，不引用外部实测。

## 学习者第二站

| 维度 | 2 分需要说明什么 | 1 分的典型情况 |
| --- | --- | --- |
| 机制 | 区分总交付、单个用户等待和达标交付；成功样本的 P95 不描述已超时和未完成项 | 只记得要看多个指标，说不清各自数什么 |
| 因果与代价 | B 的达标交付与成功样本 P95 改善，但成功总交付下降、失败增加；这不是整体验收通过 | 只说“不能只看 P95”，没有指出本表中的收益和损失 |
| 条件迁移 | 按下表算清吞吐；B 最多 88% 成功，必不满足 95%；A 可能为 94%–96%，尚待尾部结果 | 判定 B 不通过，但把 A 已通过或必不通过当成确定结论；算术错误单列 |
| 依据与条件 | 指到现有测量正文，补齐未完成结果、样本范围、输入输出分组和重复波动；保持题设已有的对照条件 | 只列“再压测”或“查日志”，没有说明补什么、会改变什么判断 |

| 可复核的计算 | A | B |
| --- | --- | --- |
| 成功输出 token/秒 | 94 × 40 ÷ 20 = 188 | 86 × 40 ÷ 20 = 172 |
| 达标请求/秒 | 80 ÷ 20 = 4.0 | 82 ÷ 20 = 4.1 |
| 最终成功率最低可能值 | 94/100 = 94% | 86/100 = 86% |
| 最终成功率最高可能值 | (94 + 2)/100 = 96% | (86 + 2)/100 = 88% |

B 的 P95 和达标吞吐确有局部改善，不能为了拒绝 B 而否认它们。A 至少要两条未完成中的一条最终成功，才满足本批成功率要求；若宣称全套 SLO 通过，还需要核对全部约定和最终交付，不能靠一个比例代替。

没有给出逐条延迟，不能从汇总数算全部请求的 P95；失败也不能随意填零。下一轮合理动作包括追完尾部、保留逐请求状态与有效文本片段时间、核对实际输出和质量、按长短输入分组、交错重复 A/B 并保留波动。题设已经说明输入与预热一致，重复索要相同口头说明不算新增判别动作；现场则需保留证明这些条件的记录。

依据复用[吞吐的统计范围](../../../../../wiki/concepts/inference-benchmarking.md#吞吐提高了多少要先说清数了什么)、[分位数的样本范围](../../../../../wiki/concepts/inference-benchmarking.md#平均不慢为什么总有人等很久)、[可比性和重复](../../../../../wiki/concepts/inference-benchmarking.md#怎样让两次压测真正可比)。

## 从业者启动案例

### 材料出处与边界

案例来自 [vLLM issue 56830](https://github.com/vllm-project/vllm/issues/56830) 的社区报告，使用本仓库 2026-10-30 抓取的[原始归档](../../../../../tools/wiki-runtime/github-trace/public-start56830-1030.json)。归档中的 `result.body.text` 含环境、报错、复现和对照；`evidence` 保存抓取时刻。第一阶段只给环境、启动进度与首个异常摘录，省略原报错附带的诊断建议，不改变报错类别和读数。第二阶段允许查库，显存量测页的“源码位置”已收录该报告的对照摘要，因此不能称为全程隐藏结论。评分看参与者能否正确使用已有结果、提出本现场仍需的证据；不把复述公开摘要计作独立发现或已验证根因。

归档报告称：H100 NVL、v0.29.0、同 GPU 另一容器持有显存，在量测期间释放时触发断言，稳定持有的对照启动成功。这是作者提供的复现记录，未在本项目设备验证。不得推广到所有版本、所有 GPU、Ascend 或同报告的 GB10；本题不考补丁状态，未核验当前已合并版本。

模型 `facebook/opt-125m`、比例 0.2、总量 93.09 GiB 与 82.94/90.17 GiB 来自同一 H100 复现部分。案例没有提供完整进程时间线，所以初答中“另一个进程释放了显存”只能是候选。原始报错也可能带建议，但建议文字本身不是现场证据。

### 六维评分

首答只有三问、5 分钟，记录事实、候选和第一个动作，不给 12 分总分。查阅后的完整方案才按下面六维评 12 分。两阶段的任务要求不同，不计算分差；只逐条记录新增、修正或确认了哪些判断，以及相应资料依据，不算正式有库/无库增益。每维 1 分为方向正确但下列条件不全，0 分为缺失或错误。

| 维度 | 2 分依据 |
| --- | --- |
| 阶段与对象 | 识别权重加载后、启动显存量测阶段的断言；区分分配失败的 OOM；整卡空闲量并不等于本进程使用量。先核现场安装/实际路径，不能照搬本站 Ascend 公式。 |
| 证据 | 获取同一物理卡、同一次启动与量测窗口的整卡读数、本进程分配/保留/峰值、其他进程分配释放记录；配合完整启动日志、traceback、有效配置与实际产物。可以先取其中最能分流的一组，不强求一口气采齐。 |
| 区分实验 | 固定版本、模型、预算和主要负载，控制另一进程占用在窗口内稳定或释放；或提出同样能区分全卡读数干扰与本进程分配失败的办法。说明在隔离测试环境复现、检查实际重叠时刻，重复或交错验证；不能只说多重启几次。 |
| 结果分流 | 只有释放组失败且时间对应，支持量测前提受干扰；稳定组也失败则继续核记账来源、其他占用和确切版本；量测通过但后续录图/真实请求 OOM 属新阶段，要重新看峰值。不能把一个假设当既定根因。 |
| 来源与适用条件 | 引用具体正文支持下一步，区分 H100 历史案例与 Ascend 示例、整卡与进程、容器与设备；不声称容器隔离必然隔开物理显存，不宣称某 PR 已修复本现场。 |
| 验收与代价 | 通过量测或 ready 还要验证完整请求、输出质量、代表性负载及资源约束；稳定占用/限制共用会影响部署和可用资源，改预算需重新量测，采集开销单列。明确未执行。 |

无需照抄“三组对照”。稳定持有与窗口释放两组可直接检验假设；无共用进程是有用的补充基线。只移走其他进程后启动成功，可提示干扰，但同时改变了占用量等条件，不能独自证明是释放时机。若材料或权限不允许对照，清楚写出可采证据、判别力和不能成立的结论，也可以得到相应分数。

不要把“82.94 − 90.17 = −7.23 GiB”解读为本进程实际用了负显存。它只是整卡两次读数的差，缺少其他进程和量测实现记录时不能归因给某个进程。删断言、盲目加大 KV 预算、只凭镜像标签升级指定版本，均不构成可信修复。

依据复用[通用入口的启动分支](../../../../../wiki/concepts/inference-troubleshooting.md#启动依赖与加载还没到接请求这一步)、[显存量测的整卡与进程区分](../../../../../wiki/concepts/kv-cache-memory-profiling.md#空闲显存变多为什么量测反而失败)、[量测之后的开销](../../../../../wiki/concepts/kv-cache-memory-profiling.md#为什么要先试跑代价落在哪里)。没有找到这些页也不自动判错：若其他现有正文确实支持同一判断，应按实际依据评分。

## 严重错误与归因

以下情况不能用总分掩盖：无证据断言唯一根因；把片段或入队当逐 token 或实际发送；丢掉失败请求宣布整体通过；把启动成功当完整服务验证；照搬其他平台公式或虚构修复版本；编造已执行实验。先确认错误来自题意、正文、资料范围还是回答，不把每个答错都归到知识库缺页。

记录：参与者____；原答位置____；四维或六维分数____；未完成/提示____；严重错误____；具体依据____；初评者____；复核者____；分歧与结论____。

本次若题目或评分本身有问题，修正后重新评原答要另列，不悄悄覆盖原成绩；新作答也单独存档。Agent 的好答案只说明本材料可以支持一次分析，不能计为真人读懂、已证明增益或现场修复。
