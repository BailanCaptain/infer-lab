# LLM-wiki 写作标准

本文件是 wiki 写作标准的唯一出处，适用于 `wiki/concepts/` 下的概念页、深入页和主线页。写作、改写、审查前必须先读；与计划、临时任务单、历史审查意见或其他文档冲突时，以本文件为准，用户另有指示除外。后续标准变更只更新此处，任务单链接本文件。

固定前提：GLM-5.3-Flash、官方双机 2×A2×8、TP8/DP2/EP16、W8A8；控制流钉住 `vllm@0fc695fc`，执行侧钉住 `vllm-ascend@db701c1f`，教程钉住 `0576b647`、模型配置钉住 `690b7052`；详情统一见 [glm-5-3-flash-two-node「部署前提」](../wiki/concepts/glm-5-3-flash-two-node.md#部署前提)。

## 写给谁，先讲什么

读者是初学者。每页须回答：这是什么；请求走到主线哪一站会遇到它、为什么需要；在固定部署下怎样运行、付出什么代价；如何对照源码。挂靠站点要链接到对应主线页的小节，页末通过 relations 说明下一步和相关站点。

先建立直觉，再沿请求逐步推演每卡形状、通信次数、字节数和显存。真实部署数字在原理讲清后出现；通用示意图可以简化卡数，数值例子必须明确标为「示意」，公式和机制仍须正确，不得把示意数当成实测。不要反复铺陈部署前提，也不要把维护者的编排理由写进教学正文。

数字取自已审查的主线底稿：[部署、入口与调度](mainline/01-deploy-entry-schedule.md)、[逐层前向](mainline/02-forward.md)、[采样与 decode](mainline/03-sample-decode.md)。读者页的 sources 直接指向钉住 commit 的源码、官方文档或论文，不以底稿代替原始证据；发现底稿矛盾先核实并推动统一，不另造一套数。

## 基础讲法：从理解到演算

读者只懂向量和矩阵乘法，未必学过 Transformer、vLLM 或昇腾。用户的反馈表达初学者的困惑，写手应判断怎样讲最顺，不能把一句反馈机械放大成整页规格。

每页按「是什么（直觉与具体例子）→ 为什么需要 → 怎么算或怎么做 → 细节与变体 → GLM 双机 → 常见误解 → 对照源码」推进；逐节检查，不能只修第一张图。前置概念首次出现须就地用一句话解释，链接不能代替解释。

讲到「怎么算」时，至少完整演一次小例子：取出哪些数、怎样相乘相加、结果放在哪里。同页尽量贯穿同一组示意数；第一屏只建立直觉，不强制开算。基础节使用示意数，GLM 数字集中到部署一节；通用机制与变体放在 GLM 之前，之后只留误解与源码。首节不堆链接，链接放在实际用到概念之处。

图按教学需要增加，不强求一节一图。张量用一个整体加格线；计算图要能看见数如何变化。静态通信图使用**静态分格**展示「发前各自有什么 → 谁把哪块发给谁 → 发后各自有什么」，样板是 [All-Reduce 分格图](../wiki/diagrams/collective-communication-all-reduce.yaml)。2026 年 10 月 21 日用户确认正文可以按需增加交互 3D，统一遵守 [教学 3D 标准](3d-teaching-standard.md)；不以跳动数字代替机制，不替换已有静态图中的必要信息。

讲不清时先看参考资料的实际图像，学习它如何组织概念与例子，再用本站图语言重画，不照抄。通信原语及 TP/DP/EP 的参考包括 [通信原语](http://www.xzclass.com/?p=3366)、[AMD MoE 指南](https://rocm.blogs.amd.com/software-tools-optimization/vllm-moe-guide/README.html) 与[并行参考](https://zhuanlan.zhihu.com/p/2003423046342554380)；只有文字抓取不算看过图，本地已存截图也可使用。图元不足时新增能力，先核对未提交改动，不改变既有图元行为；改后运行 `pnpm wiki:diagrams --check`。

逐节让初学者用自己的话复述：核心概念错误、前置概念先用后讲、需要演算却没有演示，都按 P1 处理。参考已达标的量化缩放、KDA 二维状态、RMSNorm/LayerNorm 对照、稀疏注意力重归一化与 DP 请求分配例子。深度和事实保留要求见下节「顺序不等于删减」。

## 深入页骨架：先直觉、后数字

> **顺序不等于删减。** 「先直觉、后数字」只规定讲的顺序。该讲清楚的机制、推导、数字和边界情况，一样都不能少：知识库也是问答的知识底子，页面讲得不全，问答就答不全。瘦身只删重复和水分，不降深度。（用户，09-28）

并行、特性、机制深入页按以下六步组织：

1. **第一屏：这是什么。** H2 用读者的问题命名；一句话定义只用已解释的词，必要的前置词先就地解释。配一张通用直觉图，只画原理、只标卡数，不标字节、不画 GLM 具体形状；箭头必须让人看出东西如何流动。
2. **第二屏：为什么需要、代价在哪。** 用属于该机制的具体例子支撑动机；需要数值时用已标明的示意数，GLM 部署数字留给下一节。讲明哪一步后通信、每层几次、在哪里等待；用一段话或不超过 4 行的小表区分相邻概念。
3. **然后落到 GLM 双机。** 按「一个 token 走一遍」展开，不按层类型排目录；R1 首次出现就说明是 prompt 为 4 token 的示例请求并回链。每节先一句结论，再配至多 1 个 calc；表与 calc 之间至少隔一段有解释作用的正文，否则合并。场景 M 等整批账单独放在后面的 H2，首次使用时交代设定并链接，不混进单 token 走读。
4. **特殊层集中一节。** KDA、稀疏 MLA、词表、共享专家等只讲切法与一般情况有什么不同，细节链接各自页面。
5. **常见误解 → 对照源码。** 参数名、报错字符串、commit 和版本表集中在对照源码；正文行内代码每千字不超过 13 个。参数名只在首次确有必要出现时和源码区使用代码样式，其余用普通文字解释。
6. **证据与待核放页末。** 对照源码之上零证据角标，所有角标归入页末来源；「待核：缺什么」也放页末。迁移内容以降低干扰，不删除已核实的信息。

**TP 直觉图示例：** 按数学上的「输入维 × 输出维」画成对矩阵：先 column parallel（沿输出维按列切），各卡从同一输入算出数值完整的几列，本地完成逐元素激活；再 row parallel（沿输入维按行切），接住本卡这几列，得到形状完整、数值尚未加齐的部分和；最后一次 All-Reduce（各卡按位置相加并取得结果）。图中竖条、横条、长边和维度标注必须一致。紧接图解释反例：非线性激活不能对部分和分别算完再相加，先行切就得在激活前先归约；两次都列切则需在中间 All-Gather 拼回输入。先列后行才省去中间通信，不能只画行切，也不能宣称反过来在数学上完全无法实现。存储转置的区别移到源码区。

**EP 直觉图示例：** 画出源卡与多张持有完整专家的卡，给专家编号，区分选中与未选中的专家；用箭头串起「一个 token → router 选 k 个专家 → dispatch 发到持有卡 → 各卡计算 → combine 回源卡按权重相加」。源卡自己也持有专家；均分示意中每卡格数一致。图只表达分工，k 的含义在图旁解释；实际卡数和选择数在 GLM 段交代。routed experts 指整个可供 router 选择的专家集合，不是某个 token 本次选中的子集；shared expert 是所有 token 都经过的共享专家，本部署中不按 EP 分，细节回链到 TP 页。

## 页面格式与信息层级

- 开篇一句话说清概念；不另设「一句话」H2。首次定义要解释作用，仅展开缩写或给中文译名不算解释。
- 数值推导用 calc 围栏，每块写 title；语法只以 [算式格式](wiki-calc-syntax.md) 为准，不另复制一套规则。符号公式、伪代码、形状与流程不要硬改成数值算式。
- 每个承载内容的小节最多 1 个 calc；表格与 calc 不相邻。不能靠拆出空洞小标题绕过密度要求；一个密集账单可以汇总、后置或链接唯一出处。
- 至少有一张表达主线站点位置的图；深入页至少有机制直觉图和代码流程图两张图，站点位置可融入后者。代码流程多的地方必须画先后与分支，文字解读图，不堆调用名。
- 静态图的画布宽度 ≤900px；放不下就纵排、拆图或精简节点，不靠缩小到看不清或横向滚动。静态图用 wiki-diagram，手写 spec 后生成 SVG，YAML 与 SVG 必须一致；交互 3D 使用 wiki-scene，遵守教学 3D 标准。不得用脚本批量生成或改写正文与图的内容。
- `## 对照源码` 放在最后，其后不再新增 H2；H3 只能从以下五项选用，顺序固定：**怎么开 → 会报什么错 → 开销和什么时候别开 → 版本差异 → 源码位置**。来源索引和待核留在页末源码区，不另起 H2。
- 学习正文只呈现当前解释及必要的版本边界，不附机器修订历史、旧原文、修订哈希或“来源仍须人审”等审计记录。修订分类、理由、旧结论、替代结论和依据保留在维护工作流的决策与审阅记录中；发布仍校验原文匹配和来源，但不把记录复制到正式页。旧待审提案含历史尾注时须重新整合，不得直接发布。
- 参数扫描只证明静态字段存在。新发现进入草稿，补齐用途、配置入口、运行时行为、代价和支持边界并审阅后才能成为正式参数页；只有“正文待补”的骨架不能进入目录、检索或问答。全站检查须逐页读正文并核对官方文档的关联入口，下载数量、来源数量和关键词命中数不代表阅读或覆盖完成。
- **版本差异必写**：逐项说明 v0.23 / v0.26 / v0.30.0rc2 / main 是否有此特性、默认值和行为差异；一致也明确写出。社区分支与配套 vLLM 的 commit 以 `wiki/seeds/*.yaml` 为唯一钉点；v0.30.0rc2 使用用户指定分支的固定快照，不混入 v0.30.0 正式版修复。GLM 贯穿案例仍沿用页首固定部署基线，不能把新版本的支持范围、默认值或显存数字套回旧算例。
- 所有证据角标只放页末来源，对照源码之上为 0；保留来源索引与结论的对应关系。全页角标不超过 30 处，C 级占比 <80%，不能为凑比例虚增来源。
- 正文行内代码每千字 ≤13；参数、类名、函数名才按需要用代码样式，不给普通术语套代码底色。交付密度统计时注明字数口径，区分教学正文与含源码区的全文。
- 免责句占比 <3%。直接说明成立条件和答案，不用否定式免责句代替回答；真实不确定性要说明缺什么证据，不能为降比例删掉限制条件。
- frontmatter、sources、relations、aliases 要完整；中文旧译名保留为检索别名。目录中每页只出现一次，relations 的理由要能帮助读者选下一站。字段和工具约束参见[盘点 §1](plans/2026-09-27-page-inventory.md#1-重写必须遵守的约束)，写作要求冲突仍以本文件为准。

## 术语规则

vLLM、Ascend 以及论文里有固定名字的机制、组件、特性使用英文原名，例如 KV cache、block table、prefix caching、chunked prefill、graph mode、EngineCore、MoE、All-Reduce、MC2、HCCL；源码标识符保持原样。请求、权重、张量、矩阵、向量、显存、带宽、吞吐、时延、维度、副本、节点等通用技术词用中文；「昇腾」「超节点」保留中文，包名、类名中的 Ascend 不改写。

首次出现就用一两句中文解释它是什么、做什么，图中的词也一样；不另造中文机制名。统一拼写查 [TERMS.md](../wiki/TERMS.md)。同形近形名称要区分，例如 AllGather 通信路径与 All-Gather 集合通信操作；R1、场景 M 等示例标签也须先说明再使用。

## 单一出处表

同一段推导只允许在一页里写，其他页只能写结论并链接过去，不能重算。以下六项沿用计划 §5.1 的分工；不在表中的新增推导也先确定唯一归属。

| 推导 | 唯一出处 |
|---|---|
| KV 预算、每块字节数、3,855 块（假设权重 21 GiB）/ 3,908 块（仅代入所列语言权重子账） | [glm-5-3-flash-two-node「剩下的显存变成多少 KV cache」](../wiki/concepts/glm-5-3-flash-two-node.md#剩下的显存变成多少-kv-cache) |
| 16 卡分组、每卡放什么、为什么用两台 | [glm-5-3-flash-two-node](../wiki/concepts/glm-5-3-flash-two-node.md) |
| MC2 容量门槛 128 | [one-request](../wiki/concepts/one-request.md)（MoE 那一站） |
| R1 的 15 块、七站的形状、字节数、通信次数 | [one-request](../wiki/concepts/one-request.md) |
| 图尺寸补齐、两组对齐、空闲组陪跑 | [concurrent-requests](../wiki/concepts/concurrent-requests.md) |
| 进程、类、函数调用链，按日志认站 | [request-call-chain](../wiki/concepts/request-call-chain.md) |

教学假设、所列模块的子账与实际加载占用必须区分；3,855 和 3,908 块均为预算算例，后者尚未扣除视觉塔、MTP 旋转矩阵和量化辅助张量等，不能称为精确设备容量。GB 与 GiB、主干与 MTP、每层与整次前向也须区分；引用结论时保留适用条件。共享专家等深入页交叉内容同样指定一处推导，其他页面回链。

## 写手常见错误

1. **把每台机器／每个 DP 组说成完整模型副本。** 固定部署中 EP16 把 288 个专家分在 16 卡，每台是 DP 执行组，两台合起来才构成完整模型。
2. **术语先用后解释。** 首次出现就地解释；不要让首屏别名、参数和未解释的图标签压过概念。
3. **两页重推同一个量，结果对不上。** 按单一出处表只保留一份推导，其余给结论和链接。
4. **先算账后讲概念。** 第一张图之前堆 calc、部署数字和形状表，读者仍不知道概念是什么；直觉图也不能画成部署图。动机必须用属于该机制的数字，不能用 EP 专家容量证明 TP 的必要性。
5. **TP 只画按行切，或图文切分方向相反。** 必须讲列切、激活、行切如何成对配合，并解释反过来为何不能省掉激活前的通信；不能靠「非等比例」图注掩盖方向错误。
6. **把 routed experts 定义成「被挑选的专家」。** 它指可供选择的整个集合；本次选中的是子集，另须区分共享专家。核心概念或定义讲错一律 P1，不能因后文用法正确而降为 P2。
7. **为简洁删事实，或把猜测写成事实。** 重排需保留已核实数字、条件、反例、链接和误解条目；纠错要给原始证据。静态推导、源码证据和硬件实测分清，未核项不能因换写手消失。
8. **只有数字没有解释，或反复更换算例。** 形状标明每一维代表什么；场景切换交代设定；表与 calc 之间用正文解释因果，不用一句空泛引语隔开。

- **重写丢信息**（09-28 P5 实测：GPT 写的前 7 页里有 4 页丢了旧版的关键结论，都记为 P1）。深改前必须先把旧版的结论、机制、数字、边界情况逐条列成清单；写完逐条勾选：新版里有，或者挪到了别的页（附链接），或者有证据说明该删。勾选结果写进写作记录。

## 审查与修订流程

流程是 **写 → 独立审查 → 修订**。每页首次写完由新的独立审查者阅读实际页面、图和 diff，不复用写手自查作为审查结论；历史报告仅供追踪。存在 P1 必须修订后复审，直到 P1 关闭；只有 P2、P3 时由写手全部改完并自查即可，不因此省略首次独立审查。

审查清单：

- **初学者测试：** 审查者只读前两屏，用自己的话复述概念与代价；说不出「是什么、代价在哪」记 P1，不能用全页数字正确代替这一关。
- **核心概念：** 对照原论文或钉住 commit 的源码核实定义、切分维度、计算顺序、通信与反例，图文一起核；任何核心概念错误均为 P1。
- **数字：** 与主线底稿及唯一出处一致，单位、统计范围、分支和版本条件完整；发现不一致先核原始证据，再统一来源。
- **不丢信息：** 对照改前版本逐条核数字、结论、前提、待核、误解和链接的去向；只比较数字字符串集合不足以证明语义保留。
- **格式与密度：** 六步顺序、首图、calc、图宽、流程分支、源码区 H3 顺序、四版差异、角标位置、行内代码和免责句逐项检查。
- **链接：** 本页及跨页链接能解析，锚点使用目标页现有标题；源码来源钉住有效 commit、路径和行号。外链未联网验证时如实标明。
- **实际阅读：** wiki 页面改动须在桌面浏览器打开、操作链接并检查前两屏、图、表与 calc；截图或工具通过不能替代对概念的核实。

审查记录写明级别、位置、影响、依据与修法；写手交付说明修订结果、仍待核事项和实际运行的验证结果。自查记录首图位置及图前数字/calc 数、calc 与行内代码密度、正文角标数，不为降低统计值损失信息。

## 自动检查

运行 `pnpm wiki:audit`；规则实现见 [standard.ts](../scripts/wiki/standard.ts)，强制名单、例外与阈值只在 [standard-pages.json](../scripts/wiki/standard-pages.json) 定义。名单内页面失败会阻塞审计，名单外只统计。2026-10-05 实测 104/104 页通过；这不替代人工教学审查。

| 检查类别 | 检查或报告的项目 |
|---|---|
| 本地证据（已有） | sources 的仓库、commit、文件和行号范围；图中 symbols 与钉住源码及页面 sources 的对应；页面与图的结构问题 |
| 结构与图（已实现） | 图宽、首图位置、对照源码及固定 H3 顺序；主线挂靠是否讲清、图是否足够由人工核对 |
| 密度与位置（已实现） | code-density、prose-marks、calc-density、stacked-blocks、hedge-ratio；统计值与例外按配置执行 |
| 人工复核提示 | 术语是否先解释再用、定义是否正确、直觉是否成立、信息是否丢失、跨页推导是否重复；统计提示不能替代人工判断 |

`wiki:audit` 的本地引用校验不证明外链可访问、raw 摘录内容或结论语义正确。另运行 `pnpm check:content` 与 `pnpm wiki:lint` 检查内容及链接等仓库约束；图变更运行 `pnpm wiki:diagrams --check`。实际通过范围以当次输出为准。
