AscendConfig 是 vllm-ascend 用来整理平台执行选项的配置对象：它把用户提供的设置转换为有类型的字段，并在相应实现中继续完成派生和校验。

本页解释三件事：同一个选项写在不同位置时怎样取值；为什么“键没有提供”与“显式设为 false”要分开理解；配置对象为什么有时复用、有时重新建立。这里依据的是归档材料中的源码摘录，尚未逐条核对完整工作树，也没有实机运行记录。

## 平台附加配置解决什么问题？

vLLM 需要表达不同硬件平台各自支持的选项。把所有平台选项都塞进一组通用字段，会让配置接口同时承担许多只对特定平台有意义的设置。

additional_config 是留给平台的附加配置入口。在材料所示的上游定义中，它默认是空字典，也可以是提供哈希计算接口的对象。AscendConfig 则负责把其中适用于昇腾的内容整理成执行侧使用的配置。

这两者承担不同职责：

| 对象 | 作用 |
| --- | --- |
| additional_config | 承载传入的平台附加设置 |
| AscendConfig | 解释昇腾设置，形成相应字段及派生结果 |

因此，“字典里有这个键”与“执行侧接受并使用了这个选项”是两件事。键还要经过配置解析；材料中的 main 开发主线实现还会进行类型处理、未知键校验，以及依赖其他配置的派生和互斥检查。

平台设置也参与总配置的哈希计算。哈希是由配置内容计算出的摘要，用来反映配置因素的变化。材料中的字典路径会先按键排序，再转换为 JSON 文本并计算哈希；不是把 Python 字典对象本身直接作为摘要。

这也带来输入约束：走这条字典路径时，内容必须能被 JSON 序列化。平台附加配置不是可以任意放入 Python 对象的容器。

## 同一个选项写在两层，最终用哪一个？

材料中的调度配置解析函数接收两个字典：外层的 additional_config，以及其中的 scheduler_config。后者是把调度相关选项集中组织起来的子配置。

对该函数处理的选项，查找顺序是：

1. 嵌套的 scheduler_config 中存在该键，就返回嵌套值。
2. 嵌套处没有、外层存在，就返回外层值，并提示迁移到嵌套位置。
3. 两处都没有，就返回调用方传入的默认值；如果指定的环境变量确实存在，还会记录环境回退提示。

决定前两步的是**键是否存在**。这与把值转换成布尔值、再判断是否开启不同。

下面用一个假设的布尔选项演示查找过程；option 只是示意名称，不是可直接启动的真实参数。

```python
additional_config = {
    "option": True,
    "scheduler_config": {
        "option": False
    }
}
```

解析时，从嵌套字典取出 option，得到 False。因为键已经存在，函数立即返回 False，不会继续拿外层的 True 替换它。外层同名键还会触发“已弃用且被忽略”的警告。这个例子的输入及结果仅用于说明材料中函数的分支语义。[A]

如果删除嵌套处的 option，外层的 True 才会成为结果，并产生迁移提示。如果两处都删除，结果取决于调用方传入的默认值。

最后一种情况需要继续追调用方。摘录中的函数虽然检查环境变量是否存在，却没有在这个分支直接读取和转换环境变量值；它最终返回的是传入的 default。仅凭这段函数，不能确定任意选项对应哪个环境变量、采用什么转换方式，或环境未设置时得到什么值。这些信息需要结合具体调用及环境读取器核对。

## 为什么类型校验会改变配置的含义？

配置常从 JSON、命令行或其他输入接口进入。布尔值 false 与字符串 `"false"` 的外观接近，类型却不同。

在普通 Python 中：

```python
bool(False)    # False
bool("false")  # True
```

第二个结果来自 Python 的规则：非空字符串转换为布尔值时为 True。如果配置实现直接使用这种转换，用户写下的字符串可能产生与预期不同的结果。

材料中的 main 开发主线摘录说明，AscendConfig 已改用 pydantic dataclass，也就是带字段类型与输入校验的数据类。其用户输入字段支持相应的宽松类型转换，例如把字符串 `"false"` 转为布尔值 False，把字符串 `"2"` 转为整数 2。

类型转换只是配置处理的一部分。某些结果必须结合总配置才能确定，例如跨配置的派生、降级与互斥检查。摘录将这些操作放在 derive_and_validate 方法中，由 init_ascend_config 显式调用。

这意味着，阅读配置时要区分三个阶段：

- 输入中提供了什么值；
- 字段类型处理后得到什么值；
- 结合其他配置后，最终执行设置是什么。

材料还列出若干纯派生字段，包括 enable_sp_by_pass、pd_tp_ratio、pd_head_ratio 和 num_head_replica。它们由程序计算，不属于用户可直接设置的开关。

## 配置缓存为什么不总能复用？

缓存的作用是保留已经建立的配置对象，在条件相同时复用。材料中的 main 开发主线实现并非“调用过一次就永久返回同一份”。

复用条件同时包括：已有缓存、不需要刷新、已有对象通过初始化检查，以及传入的总配置仍是此前绑定的同一个对象。

最后一个条件检查的是对象身份。用一个 Python 示意可以看出它与内容相等的区别：

```python
config_a = {"mode": "example"}
config_b = {"mode": "example"}

config_a == config_b  # True：内容相等
config_a is config_b  # False：不是同一个对象
```

即使两份总配置的内容相同，也不能仅据此认定会命中该缓存。实际复用分支比较的是原有总配置对象与当前对象是否相同。

这些条件解释的是配置对象的复用，不能据此推出运行中的全部组件都支持动态重配置。配置工厂返回新对象之后，哪些组件会重新读取它、已经建立的设备资源是否随之变化，仍需检查后续调用。

## 放到 GLM 双机部署中，该怎样使用这些结论？

在 [GLM-5.3-Flash 双机部署](../concepts/glm-5-3-flash-two-node.md) 中，配置核对属于开始执行模型之前的准备工作。理解配置入口有助于判断：设置是否被正确接收，是否写在当前实现接受的层级，以及警告是否意味着某个值被忽略。

本次材料包含上游配置定义、调度兼容逻辑及 main 开发主线配置重构的摘录，但没有提供足够的专用镜像调用代码来证明它们在固定 GLM 部署中具有完全相同的行为。因此，本页不据此给出双机启动参数组合，也不把 main 的类型校验和未知键处理直接套到该镜像。

这部分需要补齐的不是张量计算，而是配置到执行的连接：专用镜像调用哪个配置工厂、读取哪些字段，以及这些字段在设备准备阶段怎样被使用。确认后，才能把通用解析规则落实为该部署的操作说明。

## 哪些现象容易被混为一谈？

**显式关闭与没有提供配置。** 前者已经给出了值；后者才可能进入下一层回退。材料中的调度解析函数使用键存在性来区分两者。

**出现环境回退日志与函数直接读取环境。** 摘录中的调度函数检查环境变量是否存在，但返回调用方传入的 default。实际值如何从环境产生，要继续检查调用处。

**未知键被保留与未知键有效。** main 摘录中的 Omni 兼容分支会保留总配置上的扩展键，同时把未知键从 Ascend 校验输入中移除。这不能证明 Ascend 执行侧会使用这些键。

**输入校验与执行可行性。** 字段能够转换为布尔值或整数，只说明通过了相应输入处理。模型、设备和其他配置之间的关系，还需要后续派生与校验。

**同内容对象与同一个对象。** 缓存分支使用对象身份条件；仅比较字典内容不足以判断是否复用。

## 对照源码

### 怎么开

本页讨论的是配置入口和解析过程，不是一个可以单独开启的执行特性。

材料中的 vLLM 定义以 additional_config 承载平台附加配置，默认空字典；非空字典参与总配置哈希时，会先按键排序并进行 JSON 序列化。对应归档材料第 14–17、23–31 行。[I]

对材料所示的调度兼容解析函数，应优先使用嵌套的 scheduler_config。嵌套键优先于顶层同名键；顶层兼容路径仍会返回值，但伴随弃用提示。对应材料第 795–822 行。[I]

本次没有足够材料核对完整命令行入口、某个真实选项的全部取值及固定镜像的启动命令，因此不提供可复制的部署命令。

### 会报什么错

main 开发主线摘录声明未知键默认禁止；用户字段采用类型处理，依赖总配置的派生和互斥检查由工厂显式调用。材料没有完整给出各类失败的异常文本，不能据此列出准确报错字符串。对应材料第 920–926 行。[I]

未知顶层键存在一个条件分支：如果能够发现 vllm_omni，工厂会警告，并将这些键从传给 Ascend 校验的参数中排除，同时保留总配置上的扩展键。这个分支不证明未知子配置键也得到同样处理。对应材料第 1255–1264 行。[I]

调度键两层同时存在时，嵌套值生效，顶层值被忽略并产生警告；只有顶层存在时，使用顶层值并提示迁移。这里的警告表示兼容处理，并不等于配置建立失败。对应材料第 795–818 行。[I]

### 开销和什么时候别开

材料能够说明配置处理包含排序与序列化、字段处理及缓存条件检查，但没有提供耗时或内存测量，无法量化启动开销。

缓存复用条件见材料第 1080–1086 行：缓存存在、没有刷新要求、初始化检查通过，并且绑定同一个总配置对象。摘录没有覆盖新建对象检查失败后的完整返回与缓存更新分支，该行为仍需补读。[I]

纯派生字段不应作为用户开关填写。材料明确列出的字段为 enable_sp_by_pass、pd_tp_ratio、pd_head_ratio 和 num_head_replica。对应材料第 950–952 行。[I]
