Balance scheduling 为多个 DP 执行组增加一道共同的请求准入闸门：只要收集到的计数表中有一组正在运行的请求数达到上限，各组就暂停从等待队列接纳新请求，给已在运行的请求继续推进、完成退出的机会。

DP（data parallel）把不同请求或批次分配到不同执行组，各组维护相应的请求状态。这里的“均衡”采用限制新增工作的办法，不会把已经运行的请求从繁忙组搬到空闲组，也不保证各组最终具有相同的请求数。

本页依据提供的本地摘录解释机制。摘录包含不同提交的代码片段和设计说明；提交与在册发布分支的映射、完整配置条件尚未在本材料中核实，因此不登记已核对版本。

## 为什么本组还有空位，也可能暂停接纳请求？

每个执行组都有自己的等待队列和运行队列。等待队列保存尚待安排的请求；运行队列保存已经接纳、仍需继续处理的请求。scheduler 是决定本轮安排哪些请求、分别处理多少输入位置的调度器。

基础的本地准入判断只看本组：本组正在运行的请求数达到上限，就不能继续接纳。Balance scheduling 保留这个限制，再增加一个跨组判断：

> 查看各组运行请求数的快照；其中的最大值等于运行请求上限时，本组也暂停接纳等待请求。

因此，本组有空位只是接纳的必要条件之一。它还要考虑其他组是否已经满员，以及本轮是否有剩余的 token 处理预算、调度器是否暂停、本轮是否发生抢占。抢占是暂时让正在运行的请求退出执行，留待后续恢复。

这一机制针对的是“是否继续增加运行请求”，而不是本轮每条请求具体算多少个 token。一个 token 是分词器输出的离散符号；不同请求在同一轮中可能处理不同数量的 token，所以请求条数相同也不代表工作量相同。

## 它怎样知道别的组已经满员？

启用时，调度器维护一份计数表，每个位置对应一个 DP 成员。材料中的部署镜像片段为每个成员创建一个初值为零的 CPU 整数张量，用它保存该成员的运行请求数。

更新计数时，每个成员取出自己运行队列的长度，通过 All-Gather 交换。All-Gather 是一种集合通信：所有成员共同参与，把各自提供的分片收集起来，使每个成员获得完整集合；这里收集的是计数，不进行求和。

例如，两个成员分别提供计数 4 和 2，交换后各自都持有按成员顺序排列的计数表 `[4, 2]`。调度器随后读取其中的最大值，决定共同闸门是否落下。

这份表是一次交换得到的快照。它表达的是交换时各组的运行请求数，不能理解成随其他组变化而即时更新的共享变量。

## 用两个组、四个名额怎样手算一次？

以下取两个 DP 组、每组运行请求上限为 4，作为教学示意；这不是部署参数或实测结果。[A]

假设一次交换后，组 A 有 4 条运行请求，组 B 有 2 条。两个组都拿到同一份计数表：

| 判断步骤 | 组 A | 组 B |
| --- | --- | --- |
| 收到的计数表 | `[4, 2]` | `[4, 2]` |
| 本组是否已满 | 是 | 否 |
| 表中最大值是否等于上限 4 | 是 | 是 |
| 是否因共同闸门暂停接纳 | 是 | 是 |

组 A 已经没有本地名额；组 B 虽然还有两个名额，也会暂停接纳。已有运行请求仍可继续接受调度，这道判断不是把所有模型计算一起停下来。

随后，若组 A 有一条请求完成退出，下一次交换得到的表变为 `[3, 2]`，最大值便小于上限。共同闸门放行，但组 B 的下一条等待请求仍要通过本地检查：本轮有处理预算、调度器未暂停、未发生阻止接纳的抢占，并满足后续资源条件，才可能进入运行队列。

这个例子还说明，它没有把组 A 的请求迁给组 B。组 B 的计数不会因为闸门落下就自动增加，组 A 的计数也不会立即减少；计数变化仍来自请求的接纳、完成或其他队列状态变化。

## 为什么交换计数不能只放在调度函数里？

当一个组的本地请求已经处理完，其他组仍有工作时，这个空闲组可能执行 dummy batch，即为配合整体执行而参与的占位批次，而不进入普通的调度函数。

如果只有进入调度函数的成员才调用 All-Gather，就可能出现一部分成员等待交换、另一部分成员根本没有进入交换的情况。集合通信要求相关成员以匹配的顺序共同参与；缺少参与者会使等待无法完成。

材料中的后续实现因此把计数交换放在 DP 引擎的活跃迭代路径中：

1. 先执行父类的全局未完成请求判断。
2. 将 DP 通信组交给调度器。
3. 调用计数交换。
4. 返回父类判断的结果。

DP 通信组是明确规定参与成员及成员编号的逻辑集合。计数交换使用这个组，才能让各成员围绕同一批参与者形成一致快照。

材料要求：属于同一活跃波次的成员，即使本地已经排空，也要参与相应迭代中的计数交换。设计说明还提到父类中周期性的 All-Reduce；那是另一项通信，不能把它的周期当成计数交换的周期。

## 它带来什么代价，哪些差异仍然存在？

直接代价有两类。

一类是额外的跨组计数通信。交换的数据是运行请求数，数据本身很小，但成员仍需共同参与，调用位置和顺序也必须匹配。

另一类是主动放弃部分本地准入机会。某组已经满员时，尚有空位的组也暂停接纳；空位会暂时留着，直到后续快照不再触发闸门。这是共同限制新增工作所付出的代价。

它仍然保留几种不均衡：

- 请求长短不同，相同条数不代表相同计算量或缓存占用。
- 同一轮中各组处理的 token 数可能不同。
- 已运行请求的分布不会因为落闸而被重新安排。

因此，仅凭这个开关，不能推导出吞吐提高、时延下降或显存占用趋同。材料没有提供这些指标的实机结果。

## 放到 GLM-5.3-Flash 双机主线时，该看哪一步？

在[双机部署](../concepts/glm-5-3-flash-two-node.md)和[多请求并发](../concepts/concurrent-requests.md)的学习主线中，本机制应放在“各执行组决定是否从等待队列接纳新请求”这一站理解，而不是放在模型层内部计算中。

需要分清两个决定：请求分配给哪个 DP 组，与该组本轮是否接纳请求进入运行队列，是不同环节。本页解释的是后一个决定。

## 哪些相近说法需要区分？

**共同暂停接纳与请求迁移不同。** 前者改变等待请求何时进入运行队列；后者需要把请求及继续执行所需的状态转交给另一执行组。本材料中的闸门没有提供这种迁移。

**运行请求上限与 token 预算不同。** 前者按请求条数约束并发，后者约束本轮安排的输入位置数量。共同闸门读取的是条数，不能据此消除按 token 数产生的批次宽度差异。

**“任一组满员就暂停”与“空闲组追赶繁忙组”不同。** 材料中的判断针对计数最大值是否达到上限，并没有要求各组把请求数补齐到同一个值。

**开关能被解析与执行路径实际生效不同。** 显式指定其他调度器类的路径可能绕过被替换的默认调度器名称；完整生效判断还要结合模型、DP 引擎及配置校验。

## 对照源码

### 怎么开

本地材料中的 main 开发主线快照设计说明使用以下嵌套配置：

```json
{
  "scheduler_config": {
    "enable_balance_scheduling": true
  }
}
```

这份对象作为 additional config 提供。该设计说明还将适用运行形态限定为 PD-mixed：没有配置 KV 传输，或配置中的角色为 `kv_both`。这里的 PD-mixed 指同一执行形态承担 prefill 与 decode，而非把两阶段分给独立角色。

另一份代码快照显示，读取开关时先尝试 AscendConfig 中的调度器配置；读取异常后，再依次检查 additional config 的嵌套字段和顶层字段；都没有时返回关闭。这个回退顺序只对应材料展示的实现，不能直接推广为所有版本的配置优先级。

### 会报什么错

材料中的校验片段在启用开关后，若存在 KV 传输配置且角色不是 `kv_both`，会抛出：

```text
enable_balance_scheduling only supports PD-mixed mode
(kv_role='kv_both' or no kv_transfer_config), and is not supported in
PD-disaggregated mode (kv_role='kv_producer'/'kv_consumer').
```

另一个校验片段明确拒绝与 DyntraLB 同时启用：

```text
DyntraLB cannot be used with enable_balance_scheduling.
```

这些错误来自所摘录的特定快照。其他模型类型、调度器组合和配置的完整校验条件，当前摘录不足以逐项列出。

### 开销和什么时候别开

计数交换增加集合通信参与点；共同闸门则可能让尚有空位的执行组暂停接纳新请求。若目标是搬迁已有请求、按缓存占用重新分配负载，或消除 token 数导致的宽度对齐开销，这道按请求条数判断的闸门不能独立完成这些目标。

材料中的实现注释还指出，显式设置调度器类的重算、动态批和性能采集路径会绕过默认 Scheduler 名称替换。判断是否生效时，应追踪实际选择的调度器，不能只检查开关值。
