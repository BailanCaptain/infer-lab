Collective communication（集合通信）是通信组成员共同参与、按约定交换或合并张量的操作。通信组规定哪些成员一起工作，rank 是成员在相应范围内的编号；同一个数字只有结合所属通信组才有明确含义。

本页关注两个问题：一张卡算出的张量为什么还需要其他卡参与，以及读源码时怎样判断一次通信究竟处理哪个张量、返回什么结果。对于已有 Python 和矩阵基础的读者，可以先把张量理解成带形状的数值数组。

本次材料包含部分通信接口和 MoE 通信路径选择代码，能够支持局部条件分析。以下数学示例用于解释这些接口应当回答的问题；固定部署的完整通信时序、各集合操作的实现语义和物理流量，仍需补充原始依据后核对。

## 为什么一张卡算完了，还可能没有最终结果？

一次矩阵乘可以沿求和的维度拆开：各卡计算不同的一部分，最后把对应位置相加。此时每张卡上的输出虽然形状相同，数值却只是部分和。

这与沿输出维度切分不同。沿输出维度切分时，各卡可能已经算出了数值完整的不同列，后续需要的是拼接；沿求和维度切分时，各卡持有的是同一输出位置的不同贡献，后续需要的是加法。选择通信操作之前，必须先判断数据属于哪一种情况。

[Tensor parallel](../concepts/tensor-parallel.md) 讨论怎样分片计算；本页讨论这些分片之间怎样协作。通信并不能替代对张量含义的判断：把应当相加的数组拼起来，形状可能合法，计算含义仍然不同。

## 怎样用两张卡手算一次结果合并？

设有一个示意矩阵乘，输入只有一行，输出有两个数。将输入维度分给两张卡，每张卡保存相应的权重行。这里的数和分工都是教学设定。[A]

完整输入和权重为：

\[
x=\begin{bmatrix}2&3\end{bmatrix},\qquad
W=\begin{bmatrix}
1&4\\
5&2
\end{bmatrix}.
\]

rank 0 使用输入中的 \(2\) 和权重第一行，得到形状为 \(1\times2\) 的部分和：

\[
p_0=2\begin{bmatrix}1&4\end{bmatrix}
=\begin{bmatrix}2&8\end{bmatrix}.
\]

rank 1 使用输入中的 \(3\) 和权重第二行，得到同样形状的部分和：

\[
p_1=3\begin{bmatrix}5&2\end{bmatrix}
=\begin{bmatrix}15&6\end{bmatrix}.
\]

最终矩阵乘结果是逐位置相加：

\[
y=p_0+p_1
=\begin{bmatrix}17&14\end{bmatrix}.
\]

这一步相加称为归约。若希望两个成员最终都持有完整的 \(y\)，需要的逻辑结果就是 SUM All-Reduce：对成员的对应元素求和，并把结果交给每个成员。这里用它解释接口的作用；材料中的局部调用没有单独给出归约操作参数，不能由这组示意数判定所有调用采用何种归约规则。[I]

数据变化可以用表格检查：

| 阶段 | rank 0 持有 | rank 1 持有 | 数值含义 |
| --- | --- | --- | --- |
| 本地矩阵乘后 | \([2,8]\) | \([15,6]\) | 同一输出的不同部分和 |
| 按示意规则归约后 | \([17,14]\) | \([17,14]\) | 每个成员都得到完整结果 |

形状在归约前后都是 \(1\times2\)，变化的是数值是否完整，以及哪些成员持有完整结果。因此，仅看形状不能判断一次通信是否必要。

## 返回结果相同，输入张量也一定保持不变吗？

数学上的输出含义与程序中的内存行为是两个问题。Python 函数返回一个张量，既可能返回原输入，也可能返回新分配的张量。调用者需要知道：输入是否被修改、输出是否独立存在，以及哪些条件下可能没有返回张量。

材料中的基类 communicator 实现是：

```python
def all_reduce(self, input_: torch.Tensor) -> torch.Tensor:
    dist.all_reduce(input_, group=self.device_group)
    return input_
```

它把输入传给分布式通信接口，随后返回同一个输入对象。因而，上层接口即使有关于独立输出的说明，也不能无条件推广到所有底层实现。

另一段 PyHccl 实现的局部代码不同：被禁用时返回 `None`；启用时先核对输入设备，再通过 `torch.empty_like` 分配输出。这说明阅读一个操作时，至少要区分三个层次：

| 层次 | 要回答的问题 | 本次材料能确认的内容 |
| --- | --- | --- |
| 数学结果 | 哪些成员的哪些元素参与合并？结果归谁？ | 需要结合完整接口与调用条件继续核对 |
| 张量对象 | 输入是否修改？输出是否新分配？ | 两段实现具有不同的局部行为 |
| 执行条件 | 哪个设备、哪个通信组、是否启用？ | PyHccl 片段检查设备，且禁用时返回 `None` |

PyHccl 的输出分配并不证明它已经接入当前执行路径。材料没有给出足以闭合这一关系的完整调用链。

## MoE 为什么还要选择一整条通信路径？

MoE（Mixture of Experts，混合专家）用多个前馈计算模块组织模型计算。router 是决定每个输入位置交给哪些专家的小网络；专家分布在不同设备上时，输入及专家结果需要在设备之间移动。Expert parallel（EP）就是分配专家、按路由分发输入并组合结果的并行方式。

单个集合操作描述一次交换或归约的语义；MoE 通信路径还要组织路由、数据布局、专家计算及结果处理。材料中的 `ALLGATHER`、`ALLTOALL`、`MC2`、`FUSED_MC2` 是路径选择枚举，不能只凭名称把它们等同于一次同名集合操作。MC2 指通信与矩阵计算协同执行的一类实现；融合路径究竟包含哪些步骤，仍须阅读对应实现。

选择器的条件也说明，路径不是只由 token 数决定的。材料中的不同片段还检查专家数量、设备类型、EP 规模、LoRA 配置和模型量化状态。LoRA 是通过额外的低秩参数适配模型的方法；这里出现它，是因为相应适配逻辑会影响哪些 MoE 路径可用。

### 为什么判断顺序也会改变结论？

材料中的一个选择器先判断是否启用 EP，或者 EP 组是否只有一个成员；满足任一条件就选择 `ALLGATHER`。只有没有进入这一分支，才继续处理 LoRA 配置并选择 `ALLTOALL`。

因此，“配置了 LoRA 且启用 EP”还不足以单独推出路径选择。EP 组只有一个成员时，会先被前面的条件处理。读条件分支时，需要保留先后顺序。

另一个选择器先处理 MC2 容量条件，随后才比较执行规模与每个 token 选择的专家数。容量判断不满足，不意味着立即进入同一种回退路径。

## 在 GLM 双机主线里，怎样使用这些判断？

[GLM-5.3-Flash 双机部署页](../concepts/glm-5-3-flash-two-node.md) 提供部署入口，[单请求走读](../concepts/one-request.md) 提供沿模型执行定位通信的位置。本页的材料不足以重新认证这套部署的卡数分组、容量阈值和逐层通信账，因此这里保留判断方法，不重算部署数字。

对一个具体通信位置，应按以下顺序阅读：

1. 找到产生张量的计算，说明各维代表什么。
2. 判断本卡持有的是完整值、不同位置的分片，还是对应位置的部分和。
3. 找到实际参与的通信组，区分全局成员编号与组内编号。
4. 沿当前路径的条件分支，确认是否执行通信。
5. 检查返回张量和后续消费者，确认输入是否修改、结果放在哪里。

材料中的两个输出分支尤其值得分开检查。共享专家是输入共同经过、且不参与路由专家选择竞争的专家路径；它的输出和最终隐藏向量并不是同一个处理对象。

| 对象 | 材料中执行 TP All-Reduce 的条件 | 条件不满足时能确认什么 |
| --- | --- | --- |
| 共享专家输出 `shared_out` | 路径属于 `ALLTOALL`、`MC2`、`FUSED_MC2`，且未启用 shared expert DP | 所示分支不调用该次归约 |
| 最终隐藏向量 `final_hidden_states` | 路径不属于上述三种，且 `flash_comm_v1_enabled` 为假 | 所示函数直接返回输入 |

TP 是把一次张量计算分片到多个设备的 tensor parallel；这里的 TP All-Reduce 是在相应 TP 通信组内归约。表中条件只能说明这些局部代码是否调用归约，不能据此补出整层的通信次数，也不能判定其他位置是否已经合并过结果。

## 哪些结论需要额外区分？

**操作名称与实现路径是不同层次。** All-Gather 描述集合操作；材料中的 `ALLGATHER` 是 MoE 路径枚举。路径内部如何组合操作，需要继续读实现。

**逻辑张量大小与物理链路流量是不同统计对象。** 输入形状只能帮助计算张量载荷；物理收发量还需要实际算法、拓扑和执行记录。本次材料没有提供这些记录。

**局部返回不代表整层没有通信。** 最终隐藏向量的辅助函数直接返回时，只能说明这个函数没有执行该次 TP All-Reduce，不能排除此前或其他分支中的通信。

**不同设备策略的规模变量不能互换。** 材料中的某条策略使用跨 DP 的执行规模，另一些条件使用 EP 组规模；判断条件应沿用实际变量含义。

**代码快照不等于发布版本认证。** 引用某个实现片段，不能自动证明同名发布分支、固定镜像或其他提交具有相同行为。

## 对照源码

### 怎么开

集合通信不是一个统一的全局开关。所给片段包含直接调用的通信方法，也包含按配置和设备条件选择的 MoE 路径。

本材料没有完整启动命令、配置定义或经过执行验证的最小程序，因此本页不提供启动配置。复核时应从实际模型调用点向下追踪 communicator 与路径选择器，而不是仅搜索一个操作名。

### 会报什么错

PyHccl 的局部代码要求输入张量位于创建 communicator 时绑定的设备：

```python
assert in_tensor.device == self.device, (
    f"this hccl communicator is created to work on {self.device}, "
    f"but the input tensor is on {in_tensor.device}"
)
```

材料中的注释还警告，设备不一致可能导致 `"illegal memory access"`。这是源码注释和断言所描述的风险，并非本页实机复现的报错记录。

同一片段在 communicator 被禁用时返回 `None`。调用者如何处理这一返回值，材料尚未给出完整依据。

### 开销和什么时候别开

本页不能根据路径名给出通信耗时、网卡收发量或性能排序。选择器表明适用条件存在差异，但“被选中”不等于“在所有负载下最快”。

需要比较性能时，应在相同模型、张量形状、设备、并发负载和正确性要求下记录执行结果，同时确认实际走到哪条路径。本材料没有实测数据。
