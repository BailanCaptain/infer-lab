Data parallel（DP，数据并行）把不同请求分给不同执行组，各组推进分配给自己的工作。理解它需要分清两件事：**请求到达时选哪一组，以及选好以后各组怎样执行、何时需要共同协调。**

本页依据所给本地源码摘录解释这两个环节。材料覆盖固定控制流快照与若干执行侧片段，尚不足以完成三个社区分支的逐项验证，也没有硬件运行记录。

## 请求分给不同组以后，各组就完全独立了吗？

请求是一次服务调用及其输入、生成设置、执行进度和输出等状态。执行组则是承接这些工作的执行单位。把请求 A 分给组 0、请求 B 分给组 1，表示两组处理不同的请求；这件事本身并不能说明两组是否还要交换执行状态。

材料中的控制流对模型类型作了区分。MoE（Mixture of Experts，混合专家）用多个前馈计算模块和路由机制组织计算，稀疏 MoE 为每个输入位置选择部分专家。在所给引擎创建片段中，启用 DP 且模型为 MoE 时，使用专门的 DP EngineCore 进程；EngineCore 是推进调度、执行和结果更新的引擎循环。

同一片段把非 MoE 的 DP rank 当作独立的 DP=1 引擎处理，同时保留原来的组索引。rank 是参与分布式执行的成员编号，此处指 DP 组的编号。因此，**材料中的 MoE 协调路径不能直接推广到所有 DP 部署**。

DP 也没有单独回答“权重怎样分布”。张量计算是否分片、专家放在哪里，需要结合其他并行机制理解，分别见 [Tensor parallel](../concepts/tensor-parallel.md) 与 [Expert parallel](../concepts/expert-parallel.md)。仅凭请求被分到不同组，不能断定每组都持有完整模型。

## 新请求为什么需要选组，评分能告诉我们什么？

如果新请求持续进入同一组，该组的等待工作可能积累，而另一组仍有承接空间。前端选组的作用，就是在请求进入引擎之前决定把它交给谁。这与各组内部的 scheduler 不同：scheduler 是调度器，决定本组这一轮处理哪些请求、处理多少位置。

所给固定控制流采用以下判断顺序：

1. 请求已经指定 DP rank 时，采用指定的引擎。
2. 请求没有指定时，尝试 late interaction 专用选组逻辑。
3. 两者都没有选出引擎，才进入普通负载评分。

late interaction 是材料中单独处理的一类专用请求路径；本次摘录只展示其选择函数的位置，没有给出足以解释其内部算法的实现。本页因此只说明它在普通评分之前，不能把普通评分写成所有请求的必经步骤。

普通路径读取每组的等待请求数和运行请求数，按下式评分：

等待请求数 × 4 ＋ 运行请求数。

它选择分数更低的组。这是根据请求计数作出的选择，不是对请求完成时间的预测。两个同样计为“运行中”的请求，输入长度、剩余生成量等信息未必相同；所给评分表达式没有包含这些量。

## 用两组示意数字，怎样手算一次选组？

设有两个执行组，前端本地记录如下。这里的数字仅用于演示评分，不是实测负载。[A]

| 执行组 | 等待请求数 | 运行请求数 |
| --- | ---: | ---: |
| 组 0 | 1 | 3 |
| 组 1 | 0 | 6 |

组 0 的评分是 1 × 4 ＋ 3，得到 7；组 1 的评分是 0 × 4 ＋ 6，得到 6。请求 A 没有指定组号，专用选择也没有返回引擎时，普通评分会选择组 1。[D]

这说明运行请求更少的组不一定被选中：在这个评分里，一个等待请求贡献 4 分，一个运行请求贡献 1 分。材料给出了系数，但没有证明其设计动机，不能据此断言等待请求的实际耗时恰好是运行请求的四倍。

选择完成后，普通路径还会增加选中组的**本地等待计数**，增加量是 client_count。设该值为 1，组 1 的本地记录便从“等待 0、运行 6”变成“等待 1、运行 6”，新评分为 10。[A][D]

如果请求 B 紧接着到来，而统计尚未被其他更新替换，组 0 的本地记录仍为 7 分，普通评分就会转而选择组 0。[A][D]

这一步改变的是前端用于后续选择的本地估计，不等于立即获得所有引擎的全局实时状态。其作用是让刚刚作出的分配影响下一次选择，减少连续到达的请求反复依据同一份旧计数作决定。

## 请求已经选好组，执行循环还要同步什么？

请求选组处理“工作交给谁”，执行循环还要处理“各组是否继续运行、是否准备暂停”等状态。两者发生在不同阶段，不能合并成同一次协调。

All-Reduce 是集合通信操作：通信组成员共同提交输入，按指定操作归约对应元素，并使每个成员获得结果。具体到控制状态同步，输入是状态信息，不能把它与模型层中的张量通信混为一谈；通信基础见 [collective communication](../concepts/collective-communication.md)。

所给结束状态检查片段有一个步骤计数器：

- 每次调用先增加步骤计数。
- 计数不是 32 的倍数时，直接返回继续运行的结果。
- 到相应计数点时，才调用跨组状态同步，传入本地是否仍有未完成工作，以及待暂停状态。

因此，“每 32 次步骤计数同步一次”只描述这段**结束状态检查**。它没有说明模型执行中的其他 All-Reduce 也采用相同间隔，更没有说明组间每一步都只需这一项通信。

这里的“一步”对应引擎执行过程中的迭代或检查进度，不能直接换算为每个请求都生成了一个 token。token 是模型处理的离散符号，通常以整数编号表示；一个引擎迭代可能处理不同请求的不同数量位置。

## 执行前的 token 数量信息为什么还有单独的同步分支？

token 数量是执行输入的一部分。请求归属确定后，执行侧仍可能需要交换本轮输入规模等元数据；元数据是描述实际数据的信息，此处包括 token 数和计算图模式。

graph mode（图模式）通过捕获并回放满足条件的设备操作序列，减少逐次提交开销。它与请求选组不是同一个决策。

所给执行侧片段先判断 DP 大小。只有一个 DP 成员时，直接返回本地 token 数和图模式。多个成员时，继续检查是否可以跳过后续元数据 All-Reduce。

跳过分支会用本地 token 数构造一个长度等于 DP 大小的计数张量，并返回本地 token 数和原图模式。例如，本地 token 数为 3、DP 大小为 2 时，该构造得到的是两个本地数值 3，而不是通信取得的另一组真实计数。[A][D]

这一点决定了如何理解输出：**张量具有多个元素，不代表这些元素一定来自多个组的实际测量。** 需要沿分支确认它是本地构造，还是经过通信得到。

本次摘录没有完整展示后续普通同步路径，因而不足以确定同步后的补齐规则、最终宽度和图模式协调结果。这些内容不能从跳过分支反推。

## 哪些条件决定可以跳过元数据 All-Reduce？

所给跳过判断按顺序执行。前面的条件可以直接决定结果，后面的条件只对尚未返回的路径生效。

**分层通信开启时，不跳过。** 分层通信把数据交换按多个层级组织；本地片段明确先检查该设置并返回“不跳过”。因此，即使后面存在针对非 MoE 的跳过分支，也不能把它概括成“非 MoE 总是跳过”。

**分层通信未开启时，再判断当前执行的模型是否为 MoE。** 当前执行的可能是主模型，也可能是草拟模型。草拟模型先生成候选 token，再由主模型验证，相关背景见 [speculative decoding](../concepts/speculative-decoding.md)。所给判断会根据是否正在运行草拟模型，检查相应模型；当前模型不是 MoE 时，返回“跳过”。

**当前模型为 MoE 时，还要求当前端是 KV consumer。** KV transfer 用于传输后续执行需要的历史状态，KV consumer 是接收这些状态的一端。没有相关传输配置，或者当前端不是接收方，就不满足这一项条件。将 prefill 与持续生成分给不同执行组的背景，见 [PD disaggregation](../concepts/pd-disaggregation.md)。

通过上述条件后，还要检查 MC2 相关要求。MC2 是把矩阵计算与通信协同执行的一类昇腾实现。本地摘录给出的最后一个返回条件是：

- decode 的潜在最大 token 数需要 MC2 类路径；
- 并且 prefill 的批次 token 上限也需要该路径，或者已经启用重计算调度器。

decode 是在已有历史上继续生成；prefill 是处理提示词中尚未计算的位置并建立历史状态。这里检查的是相应路径的规模条件，不能用“当前只有很少 token”替代配置与潜在规模判断。

材料摘要说明 MC2 与 FUSED_MC2 均计入该类判断，但没有展示 needs_mc2 的完整定义及其阈值。因而本页可以保留上述组合条件，不能进一步给出可用规模范围或推荐配置。

## 在 GLM 双机主线中，应把 DP 放在哪一站理解？

[GLM-5.3-Flash 双机部署](../concepts/glm-5-3-flash-two-node.md)是本知识库的贯穿案例。沿请求学习时，可以先在 [单请求走读](../concepts/one-request.md)中确定输入、执行和输出的顺序，再在 [多请求并发](../concepts/concurrent-requests.md)中区分“不同请求进入不同组”和“同一组内部共同执行一批输入”。

本页材料直接涉及的是这些环节中的选组与执行协调：控制侧摘录标注固定的 vLLM 快照，执行侧摘录包含部署专用的 vllm-ascend 快照。它们提供了分析入口，却没有完整展示双机的专家分布、每卡张量形状、通信字节数或显存预算。

因此，本页不另算一份双机账单，也不把选组逻辑扩写成未经材料证明的模型分片布局。固定部署中的资源与通信结论，应回到上述主线页的唯一出处核对。

## 哪些相近说法需要分别理解？

**“分给不同组”与“各组完全独立”描述不同问题。** 前者是请求归属；后者涉及执行时是否还需要共同通信。所给控制流明确区分了 MoE 与非 MoE 路径。

**“运行请求少”与“评分低”不是同一条件。** 普通评分同时使用等待数与运行数，前面的手算例子中，运行请求更多的组反而先被选中。

**“每 32 次检查同步结束状态”不是所有通信的周期。** 模型计算、输入元数据与结束状态属于不同同步对象，需要分别检查各自调用点。

**“当前模型是非 MoE”也不是无条件跳过同步的充分表述。** 跳过判断先检查分层通信；随后才按当前执行的是主模型还是草拟模型检查模型类型。

**“使用 NPU 同步元数据”与“增加模型计算”含义不同。** 材料中的设备选择分支改变的是元数据同步所用的设备和通信组，不能据此推导模型权重布局或性能收益。

### 开销和什么时候别开

本地材料能确认两类额外工作：前端维护用于选组的请求计数，以及执行侧在相应分支进行跨组状态或元数据同步。材料没有给出这些操作的实测时延、带宽开销或吞吐变化。

普通评分只包含请求计数，不包含输入长度等工作量信息；它适合解释该实现怎样作选择，不能作为完成时间保证。显式组号和专用选组优先级更高，也需要在排查分配结果时一并检查。

元数据同步有明确跳过条件，应按分层通信、当前模型类型、KV consumer 身份和 MC2 路径条件依次核查。材料不足以支持“为了提速统一关闭同步”的配置建议。
