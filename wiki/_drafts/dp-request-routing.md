DP request routing 是前端为请求选择一个 DP 执行组的过程。DP（data parallel）把不同请求或批次分配到不同执行组；这里要解决的是“请求 A 交给哪一组”，随后才由该组继续安排计算。

本页依据提供的本地源码摘录解释选组机制。材料包含几份固定提交的片段，但没有给出它们与在册社区分支的完整对应关系，因此以下按源码快照区分行为，不把差异认定为某个发布版本的支持边界。

## 请求选组与组内调度分别决定什么？

假设服务有两个可接收请求的执行组，称为 DP0 和 DP1。请求 A 到达前端时，路由需要从候选组中选出一个接收者。请求交给该组后，组内 Scheduler 才根据请求进度、执行预算与可用资源，决定本轮处理哪些请求、各处理多少个 token。token 是模型处理的离散符号，通常用整数编号表示。

这两个决定的粒度不同：

| 决定 | 要回答的问题 | 结果 |
| --- | --- | --- |
| 请求路由 | 请求 A 应交给哪个执行组？ | 选中一个接收请求的引擎 |
| 组内调度 | 本组这一轮应计算哪些输入位置？ | 形成本轮执行工作 |

负载路由使用的 waiting 和 running 分别表示等待、运行中的请求数量。它们不是 token 数，也不是每条请求剩余计算量的精确描述。两组各有一条运行请求，不代表两组接下来的工作量相等。

执行组的含义见 [Data parallel](../concepts/data-parallel.md)；请求进入引擎后的循环见 [EngineCore](../concepts/vllm-engine-core.md)。

## 为什么选组前要先检查请求是否已有目的地？

按负载选组适合没有固定目的地的请求。材料中的路由入口还处理两类已有目的地约束的请求，因此选择顺序是：

1. 请求显式指定 DP rank 时，使用指定值。rank 是成员编号，这里表示请求要去的 DP 组。
2. 未显式指定时，尝试 late interaction 的固定选组规则。
3. 前两项都没有给出组号时，才比较各候选组的负载。

这意味着自动负载评分只是其中一个分支。负载较低的组不会覆盖显式指定的组号；特定查询的固定选组也先于负载比较。

late interaction 在材料中对应查询与文档评分路径：查询表示缓存在进程本地，后续文档评分需要复用同一查询的表示。为此，CACHE_QUERY 和 SCORE_DOC 两种模式在 query_key 为非空字符串时，对其 UTF-8 字节计算 CRC32，再对候选引擎数取余。CRC32 在这里把字符串变成一个整数，取余把它映射为候选范围内的索引。

只要候选引擎数保持相同，相同 query_key 就得到相同索引。它服务于查询表示的本地复用，不能据此推导普通文本生成请求会按共同前缀固定选组。

## 基础负载评分怎样选出一组？

材料中固定 GLM 控制流基线所用的源码快照，按“waiting 的四倍加 running”计算分数，选择分数最小的候选引擎。

这里给等待请求更高的权重：新增一条等待请求会让分数增加 4，新增一条运行请求会让分数增加 1。它是一种比较负载的规则，不能把权重解释成“等待请求的真实计算成本一定是运行请求的四倍”。

用一组示意数完整走一遍。假设当前前端记录：

| 候选组 | waiting | running | 本地分数 |
| --- | ---: | ---: | ---: |
| DP0 | 1 | 3 | 1 × 4 + 3 = 7 |
| DP1 | 0 | 6 | 0 × 4 + 6 = 6 |

这些数仅用于演示选组。[A]

请求 A 没有显式组号，也不符合查询键固定路由条件，于是进入负载分支。前端分别算出 7 和 6，选择 DP1。虽然 DP1 的运行请求更多，但在这条评分规则下，DP0 的一个等待请求使其分数更高。

选择完成后，前端会立即给选中组的本地 waiting 加上客户端数量。假设客户端数量为 2，DP1 的本地 waiting 从 0 变成 2，下一条请求看到的 DP1 分数就是 2 × 4 + 6 = 14。[A]

这里增加的是前端保存的估计值。它不表示真实队列瞬间多了两条请求，而是让刚收到的请求在下一次比较中立即产生影响。在这一评分规则下，每次本地补记带来的分数增量是客户端数量的四倍，这是代数结果，不是性能测量。[D]

## 本地补记为什么还需要协调器统计？

如果前端只使用上一次收到的队列统计，连续到达的请求可能反复选中同一组：第一条请求已经送出，但统计还没反映它，下一条请求仍把该组视为原来的负载。

本地补记填补了这段信息间隔。它使当前前端能够在后续选组时考虑自己刚刚送出的工作，同时也引入一个边界：本地估计依赖统计更新，不能当作引擎队列的实时镜像。

材料中路由函数的注释提到协调器每 100 ms 更新，但协调器片段展示了更具体的等待逻辑：

- 统计发生变化时，使用配置的统计更新间隔。
- 统计未变化时，等待间隔取 5,000 ms。
- 尚无上一步计数时，设置至少 50 ms 的超时，以接收当前步骤的统计。

因此，路由函数中的注释不足以证明所有情况下都严格每 100 ms 发布一次。现有摘录也没有完整展示前端如何接收统计、替换旧值以及处理所有并发情形；本页不据此推导本地补记在每次更新后的具体去向。

## 同分时为什么会出现不同结果？

选最小值还需要规定“分数相同怎么办”。

材料中的基础快照只在发现严格更小的分数时更换候选。因此，同分时保留扫描过程中先遇到的引擎。若扫描起点保持不变，同分就会持续偏向相同位置。

另一份快照在负载选组后，把扫描起点向后移动一组。下一次再出现同分时，优先遇到的组便可能不同。这改变的是同分选择；分数不同时，仍然选择最小分数。

例如，两组分数都为 6 时，从 DP0 开始扫描就选 DP0；下一次从 DP1 开始扫描就选 DP1。这个例子只说明起点轮转如何影响同分，不表示真实请求始终轮流分配。[A]

材料能够证明两份片段存在上述差异，尚不能确定这一变化首次进入哪个发布版本。[!]

## 引入在途数和 KV 使用率后，评分改变了什么？

另一份源码快照保留了显式组号、查询键固定选组优先的入口，但替换了负载分支的评分方式。

基础方案依赖 waiting 和 running 的计数快照，并给等待请求固定四倍权重。变化后的方案同时考虑两种估计：

- 当前前端发往该引擎、尚未完成的请求数，称为本前端在途数；将它乘以客户端数量。
- 协调器统计中的 waiting 与 running 之和。

基础分数取这两项中较大的值。两项是对负载的不同估计，取较大值不会把它们直接相加。

当存在等待请求时，该快照还依据 KV cache 使用率增加惩罚。KV cache 是保存后续注意力计算所需历史表示的缓存；这里的使用率用于反映缓存资源压力。

附加项为 waiting 乘以 6，再乘以“KV 使用率减 0.5 与 0 中的较大值”。因此，使用率不超过 50% 时，附加项为零；使用率为 100% 时，附加项等于 waiting 的三倍。后者只是附加分数，不是总分。

继续用示意数说明输入怎样影响结果：假设客户端数量为 2，本前端在途数为 3，waiting 为 2，running 为 3，KV 使用率为 75%。在途估计为 6，队列统计为 5，基础分数取 6；KV 附加项为 2 × 6 × 0.25 = 3，最终分数为 9。[A]

这项变化引入了本前端在途状态和缓存压力信号，但评分仍以请求计数为主要输入，不能保证不同组承担相同的 token 工作量。材料也未展示对超过 100% 的使用率输入进行截断，不能把这种截断写成既有行为。

该快照在选组后记录请求到引擎的映射，并增加对应引擎的在途数。材料开头的另一段片段展示了完成通知处理：成功移除请求映射后，才减少对应引擎的在途数。请求映射由此成为维护本地在途账的一部分，而不只是一次选组的返回值。

## 放到 GLM 双机主线中，应该采用哪套解释？

本页的 GLM 贯穿案例沿用固定控制流基线，对应材料中的基础评分方案：先检查显式组号，再尝试 late interaction 固定路由，最后按 waiting 四倍加 running 选组并补记本地 waiting。

在[双机部署](../concepts/glm-5-3-flash-two-node.md)和[多请求并发](../concepts/concurrent-requests.md)的阅读路线中，这一机制回答的是请求进入哪个 DP 执行组。它不负责决定每轮装入多少输入位置，也不替代组内调度。

材料中的在途数与 KV 压力评分属于另一份源码快照，不能套回固定 GLM 算例。当前材料没有提供实机运行结果，本页的选组演算均为规则演示。

## 哪些概念需要分别理解？

**请求均衡与工作量均衡。** waiting、running 和在途数都在数请求。请求长度、当前阶段和剩余计算量可以不同，分数接近不等于完成时间接近。

**显式选组与自动评分。** 显式指定的组号在入口处优先处理，不会再由负载分数重新决定目的地。

**查询键固定路由与 prefix caching。** 材料中的查询键规则为特定 late interaction 模式服务。prefix caching 是复用兼容的已计算前缀，不能由这里的 CRC32 规则推导它的普通生成路由行为。

**前端请求路由与 DyntraLB。** 材料把 DyntraLB 限定在 PD 分离部署的单节点 decode 侧：PD 分离把提示词处理和后续生成分配给不同执行组，decode 是在已有历史状态上继续生成。DyntraLB 处理该范围内多 DP rank 的 attention KV 负载，不是所有前端选组方式的统称。其配置校验还要求缓存消费端角色、DP 大于 1，并排斥 balance scheduling 和 profiling chunk。它的验证模型与边界应保留在[专页](../concepts/dyntra-lb.md)，不能直接扩展到 GLM 双机主线。

## 对照源码

### 怎么开

材料中的客户端工厂先判断 DP 大小。DP 大于 1 时，启用外部负载均衡模式会选择每个 DP rank 对应客户端的路径 `DPAsyncMPClient`；否则选择内部负载均衡路径 `DPLBAsyncMPClient`。DP 不大于 1 时返回 `AsyncMPClient`。

这是客户端类型的选择依据，尚不足以组成完整部署命令。现有摘录没有完整展示 hybrid LB 配置、所有启动默认值及其相互作用。

显式组号使用 `data_parallel_rank`。材料还展示了请求头 `X-data-parallel-rank` 的整数转换，但未完整给出从 HTTP 请求头到引擎请求字段的传递链路。

### 会报什么错

显式 rank 必须位于候选范围内。启用仅本地引擎模式时，上界取本地 DP 大小；否则取全局 DP 大小。越界会抛出 `ValueError`，消息形式为：

```text
data_parallel_rank <值> is out of range [0, <候选数量>).
```

材料在非整数请求头的异常处理处截断，因此无法确定该输入最终对应的 HTTP 响应。

另一项校验针对“DP 大于 1、启用外部 DP 模式、模型不是 MoE”的组合。MoE 是通过路由让输入经过部分专家模块的模型结构。该组合会被拒绝，报错建议使用不带 DP 参数的独立 vLLM 实例来接外部负载均衡：

```text
Non-MoE models do not support external data parallel mode.
For external load balancing, launch independent vLLM
instances without --data-parallel-* arguments.
```

这一限制针对材料中的外部 DP 模式，不能扩展为非 MoE 模型无法使用任何外部负载均衡。

### 开销和什么时候别开

自动负载分支遍历候选引擎、计算分数，并维护本地估计；带在途统计的快照还记录请求与引擎的映射。材料没有提供这些操作的时间、内存或吞吐测量。

当请求需要显式目的地或依赖进程本地查询表示时，应先遵守对应的选组约束。自动评分适用于没有这些约束的请求，其价值是利用已有统计分配新请求；实际效果取决于统计时效和请求工作量差异。

材料不足以给出 internal、external 和 hybrid 三种部署方式之间的完整选型建议，也不足以证明某种方式在 GLM 双机上性能更好。
