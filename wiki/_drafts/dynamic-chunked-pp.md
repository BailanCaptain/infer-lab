Dynamic chunked PP 在 pipeline parallel 中用耗时预测参与决定 prefill 块长，尝试让各块的执行时间更接近。Pipeline parallel（PP）把模型计算按顺序分成多个阶段；prefill 是处理提示词中尚未计算的位置、建立后续生成所需历史状态的过程。

本页依据本地材料中收录的文档和代码片段解释机制。材料包含不同提交的片段，但不足以完成四个社区分支的逐项验证；下面涉及配置组合的结论均保留各自片段的范围。

## 动态切块改变了什么？

[Chunked prefill](../concepts/chunked-prefill.md) 把提示词尚未完成的计算分配到多轮执行。固定块长方案主要按 token 数控制每轮工作量：token 是分词器输出的离散符号，通常用整数编号表示。

动态切块继承了这个分轮处理过程，增加了一项判断：在当前请求进度和本轮剩余预算下，预测处理多少个 token 比较合适。

因此，块长有两层约束：

- 原有调度逻辑先决定本轮最多可以给这个请求多少个 token。
- 动态预测再给出建议长度，所示 RUNNING 路径取两者中的较小值。

RUNNING 指已经进入运行队列的请求。材料展示的入口还要求：预测管理器存在且就绪，请求仍有提示词位置未计算；若开启在线计时，请求还须已经计算过至少一个 token。这个入口条件不能直接推广到材料未完整展示的等待队列路径。

预测器建议的长度可以变化，但所示调度路径不会因此突破原有 token 额度。

## 为什么相同 token 数未必代表相同工作量？

Attention 利用当前位置的查询与历史位置的键计算权重，再汇合相应的值向量。对于访问历史的注意力计算，当前处理多少位置、已有多少历史，都可能影响工作量。具体计算方式见 [Attention 与 Q/K/V](../concepts/attention-qkv.md)。

因此，按相同 token 数切出的块，不一定具有相同执行时间。PP 中，一个阶段算得更久，会使依赖其输出的后续阶段等待；块之间的耗时差是动态切块试图改善的问题。

材料中的文档说明，这项功能主要优化 prefill，并推荐用于 prefill 与 decode 分离的部署。这里的分离是把提示词处理与持续生成交给不同执行组。推荐场景不能证明其他场景一定受益，也不能证明预测后各块就会等时。

代价来自两处：启动时需要试跑以建立预测依据；选择在线校准时，还要测量真实执行耗时并反馈修正模型。

## 一次预测怎样变成实际块长？

下面只演示材料展示的平滑、下限、对齐和截断步骤，不假定未提供的耗时拟合公式。

设一组用于手算的示意输入：预测器求得原始长度为 150，基准块长为 100，平滑系数为 0.5，最小块长为 64，页大小为 64；原有调度逻辑给当前请求的额度为 120 个 token。这些数仅用于说明运算顺序。[A]

材料中的普通预测路径依次处理：

1. **向基准长度平滑。** 从基准 100 向预测值 150 移动一半，得到 `100 + 0.5 × (150 − 100) = 125`。
2. **取整数并应用下限。** 125 已是整数，也高于最小块长 64，结果仍为 125。
3. **向上对齐。** 对齐单位取页大小与 64 的较大值，本例为 64；125 向上对齐后成为 128。
4. **回到调度额度内。** 所示 RUNNING 路径再取建议值 128 与原额度 120 的较小值，实际分配为 120。[D]

这个例子区分了预测器返回值与调度器最终分配值：预测器内部的下限和对齐，不等于最终调度结果一定具有相同性质。

材料中的代码采用向上对齐，但设计文档写的是向下对齐。两者存在直接差异，不能合并成一个一致的实现说明。仅凭这些摘录，也不能确认后续路径是否还会调整最终分配值。

## 什么时候会预测，什么时候仍用原有切法？

材料展示的普通预测路径在模型未就绪、目标延迟缺失、二次项为零、判别式为负或求解结果非正时返回空结果。它表示这一条预测路径没有给出可用块长。

返回空结果之后，整轮调度如何继续，还取决于调度器的后续逻辑。材料没有完整展示相关分支，不能把它概括成“预测失败就无条件恢复固定块长”。

在线计时由 `need_timing` 控制。材料中的配置定义让它默认跟随功能是否启用：

- 开启时，模型执行器每步同步设备以测量执行时间，并反馈给预测模型做增量拟合；校准完成后会关闭计时。
- 从一开始设为关闭时，跳过在线校准，依赖启动阶段建立的预测模型。

这也解释了所示 RUNNING 入口为什么区分第一块：开启在线计时时，已经计算的 token 数须大于零，才能进入该动态预测分支；关闭在线计时后，这个进度条件不再阻止第一块进入。其他前提仍须满足。

选择跳过在线校准，可以避免这部分逐步同步开销；材料没有证明因此得到的预测精度在所有负载下都足够。

## 哪些相近说法需要分开理解？

**动态切块不等于扩大每轮 token 上限。** 所示 RUNNING 路径通过取较小值限制预测结果；更大的建议块长不能绕过原有额度。

**预测器就绪不等于在线校准已经完成。** 启动模型和后续在线反馈是两部分，关闭在线计时仍可依赖启动模型。

**支持异步调度需要说明版本和执行器条件。** 材料确实收录了 CPP 与异步调度组合的检查，不能笼统写成“一律不支持异步”；也不能把一个提交中的条件推广到所有分支。

**功能支持表不等于任意组合均已验证。** 文档列出 Eager、Graph、prefix cache 和 chunked prefill 支持，但摘录没有给出任意组合、任意模型与负载下的验证范围。

## 对照源码

### 怎么开

材料中标注为执行侧基线的功能文档要求：

- PP 阶段数大于 1，即 `--pipeline-parallel-size > 1`。
- 启用 `--enable-chunked-prefill`。
- 不启用 `VLLM_ASCEND_BALANCE_SCHEDULING`。

动态切块配置使用 `profiling_chunk_config`。本次新材料没有给出足以核定各版本配置嵌套位置的完整定义，因此不提供可直接复制的启动命令；配置入口需继续核对[配置页](../params/profiling-chunk-config.md)及实际运行版本。

### 开销和什么时候别开

功能文档估计启动 profiling 增加约 64 次前向计算，耗时为数十秒。这是材料记录的文档估计，本页没有实机测量。

在线校准的额外代价是每步设备同步与耗时反馈。`need_timing` 可从开始就关闭，以跳过这部分校准；是否适合这样做，仍需比较实际预测质量与运行开销。

材料中的调优建议是先搜索固定块长，示例候选值为 8192、16384、24576、32768，并称启用动态切块时的最优 `--max-num-batched-tokens` 通常为固定块方案的 2～4 倍。这些是该文档的经验建议，不是所有模型、设备和负载下的约束或收益保证。

没有 PP、未启用 chunked prefill，或与材料已明确禁止的调度策略组合时，不满足相应片段的启用条件。对于短时运行，还需要把启动试跑成本纳入比较。
