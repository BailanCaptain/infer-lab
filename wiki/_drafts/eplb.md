EPLB（Expert Parallelism Load Balancer）用于调整专家并行中的专家布局，目标是改善设备之间的负载分布。理解它，需要区分两件事：一次输入选择哪些专家，以及这些专家的权重放在哪些设备上。本页围绕后者解释适用条件、迁移代价和配置边界。

本页依据提供的本地摘录整理。摘录包含不同提交的配置、检查和文档片段；它们能说明各自快照的行为，但尚不足以确认四个社区分支的完整支持范围。

## 专家已经分到不同设备上，为什么还需要调整位置？

MoE 是用多个专家模块组织计算的模型结构；稀疏 MoE 让每个输入位置只使用其中一部分专家。expert parallel（EP）把专家分布到多个设备，执行时把输入送到持有相应专家的设备，再组合结果。基础机制见 [MoE](../concepts/moe.md) 和 [expert parallel](../concepts/expert-parallel.md)。

专家数量均分，并不直接说明执行负载均分：如果接下来需要执行的专家集中在少数设备上，这些设备就可能承担更多工作。EPLB 在已有 EP 分工上调整专家布局，尝试改变这种分布。这个动机解释属于机制推断；本次摘录没有提供完整的负载指标定义和规划算法，不能据此认定实现按执行时间、输入数量或其他某一种指标规划。

这里发生的变化涉及权重迁移。专家权重是执行专家计算所需的模型数据；调整布局需要把这些数据送到目标设备，并使后续执行能够使用调整后的布局。相比固定布局，这引入了传输、协调和额外资源占用。

## 怎样用一个小例子区分“专家数均分”和“工作量均分”？

下面是示意设定，用于演算布局变化的含义，不代表材料中的实际规划策略、测量数据或支持配置。

假设有两个设备、四个专家，每个专家处理一次输入的工作量相同；每份输入在本例中只交给一个专家。设备 0 持有 E0、E1，设备 1 持有 E2、E3。接下来一段输入分别需要四个专家执行 8、6、2、0 次。

| 专家 | 示意执行次数 | 调整前位置 | 调整后位置 |
| --- | ---: | --- | --- |
| E0 | 8 | 设备 0 | 设备 0 |
| E1 | 6 | 设备 0 | 设备 1 |
| E2 | 2 | 设备 1 | 设备 0 |
| E3 | 0 | 设备 1 | 设备 1 |

调整前，设备 0 承担 8 + 6 = 14 次，设备 1 承担 2 + 0 = 2 次。交换 E1 与 E2 的位置后，设备 0 承担 8 + 2 = 10 次，设备 1 承担 6 + 0 = 6 次。两边始终各持有两个专家，但工作量分布发生了变化。

这个演算只比较设定下的工作次数。要判断真实请求是否更快，还需要知道每个专家的实际耗时、传输开销，以及调整后的布局是否适合后续输入。材料没有给出这些测量结果，因此本例不能推出时延或吞吐收益。

## 调整布局为什么需要检查权重格式和硬件？

迁移一个专家，需要找到它计算所需的完整数据。量化用较低精度的数据及缩放信息表示权重，因此专家的数据可能既包括权重张量，也包括缩放张量，某些格式还包括其他辅助张量。只搬其中一部分，不能构成完整的专家计算状态。

材料中标注为 vllm-ascend@7d825229 的文档明确要求：模型支持 EP，MoE 的量化方法还要提供完整的专家权重迁移布局。支持范围同时取决于 model runner，即组织设备侧模型执行的组件，以及硬件代际。

同一材料给出的 MRv2（第二版 model runner）路径区分了以下格式：

| 权重格式 | 材料中的状态 | 成立条件或含义 |
| --- | --- | --- |
| BF16 / FP16 | 启用 | 迁移未量化的专家权重与偏置 |
| W8A8 / W8A8 Dynamic | 启用 | 使用持久保存的逐专家权重与缩放张量 |
| W4A8 | 启用 | 使用逐专家权重、缩放及 scale-bias 张量 |
| W4A4 MXFP / W8A8 MXFP | 启用 | 限定 950PR、950DT，保留原生 ND 专家张量 |
| W4A16 / W4A16 MXFP / W4A8 MXFP | 拒绝 | 专家权重布局尚未完成独立 EPLB 验证 |

“启用”描述的是该材料所列路径的状态，不能替代目标模型与硬件上的验证。文档列出的 MRv2 初始模型级验证对象是 Qwen3-30B-A3B W8A8，采用异步 EPLB；MRv1 的性能验证主要针对 DeepSeek-V3.1/R1。

材料还明确列出两个硬件边界：950PR、950DT 不支持 EPLB 与所列 W4A8MXFP4、W4A16MXFP4 量化类型的组合；A2 不支持冗余专家。冗余专家指额外保留的专家副本，“不支持冗余专家”只限定这种布局方式，不能据此判断 A2 上所有 EPLB 路径的可用性。

## GLM-5.3-Flash 双机部署能直接开启吗？

本库贯穿案例是 [GLM-5.3-Flash 双机部署](../concepts/glm-5-3-flash-two-node.md)。这里需要把固定执行快照与其他快照中的能力分开。

在固定执行侧 vllm-ascend@db701c1f 中，材料列出的动态 EPLB 默认关闭；其第二版 model runner 在检测到旧入口 dynamic_eplb 为真时，会直接抛出不支持错误。因此，不能把其他快照中的 MRv2 配置直接套到该执行快照上。

材料中另一份文档列出了较完整的 MRv2 EPLB 配置及验证对象，但验证对象是 Qwen3-30B-A3B W8A8，不能由此确认 GLM-5.3-Flash 已通过同样验证。对于本库的 A2 部署，还要保留“不支持冗余专家”这一硬件限制。

本次材料没有提供 GLM-5.3-Flash 在固定双机部署下开启 EPLB 的正确性、时延或吞吐实测。要形成可执行的部署建议，仍需补齐目标 runner、专家权重迁移布局和硬件组合的核对，并运行验证。

## 哪些结论需要分开理解？

**配置存在与执行路径可用是两层条件。** db701c1f 中有动态 EPLB 配置，但第二版 model runner 会拒绝该旧入口。看到字段定义，不能跳过执行器检查。

**代码路径启用与模型级验证完成是两种证据。** 材料列出了多种启用的权重格式，同时只给出了特定模型、格式和异步运行方式的初始验证对象。部署结论必须保留这个范围。

**异步执行仍然消耗资源。** 异步表示迁移工作可以与其他执行活动交错进行；它仍需要传输权重。是否减少请求等待，材料没有给出通用收益数字。

**同一名称下的不同入口需要分别核对。** 固定快照中的 dynamic_eplb 与另一份 MRv2 文档中的上游 EPLB 配置，不能共用一套默认值和兼容结论。

## 对照源码

### 怎么开

本次材料不足以给出 GLM 固定部署可直接运行的完整启动命令，可以确认的入口边界如下。

db701c1f 的配置摘录列出：

| 配置项 | 该快照的默认值 | 含义 |
| --- | --- | --- |
| `dynamic_eplb` | `False` | 默认不开启动态 EPLB |
| `expert_heat_collection_interval` | `600` | 热度采集间隔配置 |
| `algorithm_execution_interval` | `50` | 算法执行间隔配置 |
| `num_redundant_experts` | `0` | 默认不增加冗余专家 |
| `eplb_policy_type` | `2` | 策略类型的默认编号，摘录不足以解释编号对应算法 |
| `eplb_heat_collection_stage` | `"all"` | 默认采集阶段配置为 all |

摘录没有完整说明两个间隔的推进条件，不能把 600 与 50 直接换算成秒数或任意前向次数。

材料中的 MRv2 文档则要求：上游 EPLBConfig 字段通过 `--eplb-config` 传入，不能放进 `--additional-config`。其中 `use_async` 默认为 true；设为 false 会被改回 true 并给出警告。Ascend 的策略默认为 `stair`，也可选择 `default` 进行上游策略对照实验。这些规则属于该 MRv2 文档描述的路径，不是 db701c1f 旧入口的默认值。

### 会报什么错

db701c1f 的 `vllm_ascend/worker/v2/model_runner.py` 在 `dynamic_eplb` 为真时抛出：

```text
dynamic_eplb is not supported by Ascend NPU model runner v2.
```

MRv2 材料还列出两类会产生警告的行为：

- 将 `use_async=false` 规范化为 true。
- 自动选择传输方式时，整组回退到 Gloo，并按条件收紧未显式设置的迁移限制。

本次摘录没有给出这些警告的完整字符串，也没有给出所有不支持格式对应的异常文本。

### 开销和什么时候别开

专家迁移需要传输权重。MRv2 材料描述了 HIXL 与 `torch_gloo` 两种传输路径；后者使用 CPU 暂存。

自动选择 HIXL 时，所有 EPLB rank——参与 EPLB 的通信成员——必须使用同一类别的可用绑定：官方 `hixl` Python 包，或 vllm-ascend 的 ctypes 绑定。启动时会形成组内共识；任一成员没有可用绑定，或成员间绑定类别不同，整组就回退到 `torch_gloo`。显式指定 communicator 时跳过这一自动共识过程。

STAIR 的每 rank 与跨节点迁移限制默认均为 `-1`，表示不限制。只有**自动回退 Gloo** 时，未显式配置的限制才收紧到 `1`，以避免过多 CPU 暂存传输。显式值保留，例如 `cross_node_transfer_limit: 0` 仍禁止跨节点迁移；显式选择 `torch_gloo` 或 `hixl` 也保留配置值。

目标模型缺少完整的专家权重迁移布局、runner 明确拒绝该入口，或权重格式属于拒绝组合时，不能直接启用。对于检查可通过的组合，仍需比较迁移成本与实际收益；本次材料没有提供可通用于其他模型和流量的收益门槛。
