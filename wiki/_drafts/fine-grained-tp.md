Fine-grained TP 允许模型中的不同组件分别设置 tensor parallel（TP）大小：一次张量计算由多少个设备分片协作，不必对所有组件使用同一个设置。

它要解决的是模块之间需求不同的问题。embedding 按 token 编号查表取得输入向量；lm_head 把最后的隐藏向量变成词表中各 token 的分数；attention 输出投影把注意力分支的结果映射回后续计算使用的表示；稠密 MLP 则对每个位置执行前馈变换。这些组件访问权重、产生中间结果和组织通信的方式不同，同一组分片配置未必都合适。

本页依据提供的本地摘录解释机制及配置边界。材料含两个提交的片段，但不足以完成四个社区版本的逐项核对，版本缺口列在页末。

## 为什么普通 TP 之外还要分别设置模块的分片？

普通 [tensor parallel](../concepts/tensor-parallel.md) 把一次计算分给多个设备。例如，矩阵乘法可以沿输出维度切开权重，让各设备分别计算输出的一部分；也可以沿输入维度切开，让各设备产生需要相加的部分结果。切分轴决定输入要怎样提供，以及输出需要怎样通信才能接续下一步。

Fine-grained TP 保留这种“分片计算、协作形成结果”的基础，改变的是配置粒度：embedding、lm_head、attention 输出投影和稠密 MLP 可以分别指定协作组大小。材料中的文档使用 `finegrained_tp_config` 容纳这些设置。

独立设置的价值在于，可以针对模块分别权衡权重分布与通信成本。某个模块适合更多设备共同承担，不意味着其他模块也值得采用同样的组大小。跨设备协作增加后，还要满足通信参与顺序及执行形态的要求；这些要求可能抵消计算或容量上的收益。

这里的 MLP 分支有明确范围。材料中的文档提到稠密模型以及 MoE 模型里的稠密层；对应实现片段也用“不是 MoE 层”作为进入细粒度 MLP 分支的条件。MoE 是通过路由选择部分专家执行前馈计算的结构，因此不能把这里的稠密 MLP 设置直接理解成对所有专家重新分片。文档提到的稠密模型支持范围与另一提交的配置校验存在需要核对的差异，见页末。

## 这些设备沿哪个方向组成协作组？

[data parallel（DP）](../concepts/data-parallel.md) 用不同执行组处理不同请求或批次。DP 成员与 TP 成员是不同的编号维度：前者区分请求分工，后者区分一次张量计算的分工。

材料中的建组代码把全局成员编号排列为三个维度：

```text
[PP 阶段, DP 编号, 标准 TP 编号]
```

PP 是 pipeline parallel，即按模型计算顺序划分执行阶段。建细粒度 TP 组时，代码固定 PP 阶段和标准 TP 编号，再沿 DP 维度按指定大小连续分组。

因此，这段实现建立的是跨 DP 成员的模块协作组，并不是在一个标准 TP 组内部继续细分。它也不是让组内成员从此共同处理完全相同的请求：请求原来的归属与某个模块的跨设备协作，需要分别理解。

具体模块怎样准备输入、怎样取得输出，还要继续阅读该模块的前向实现。仅凭建组片段，不能确定它使用哪一种集合通信，也不能确定一次前向的通信次数。

## 用八个成员怎样手算出分组结果？

设一个示意系统只有一个 PP 阶段，DP 大小为 4，标准 TP 大小为 2，细粒度组大小为 2。这些数字只用于演示材料中的建组算法。[A]

全局编号按代码中的排列方式得到：

| DP 编号 | 标准 TP 编号 0 | 标准 TP 编号 1 |
| --- | --- | --- |
| 0 | rank 0 | rank 1 |
| 1 | rank 2 | rank 3 |
| 2 | rank 4 | rank 5 |
| 3 | rank 6 | rank 7 |

rank 是通信成员的编号，此处表内使用全局编号。

DP 方向有 4 个成员，每两个组成一段，所以先得到 DP 编号 `{0, 1}` 和 `{2, 3}` 两段。对每一段，再分别固定标准 TP 编号，最终形成：

```text
固定标准 TP 编号 0：
    第一段 → [rank 0, rank 2]
    第二段 → [rank 4, rank 6]

固定标准 TP 编号 1：
    第一段 → [rank 1, rank 3]
    第二段 → [rank 5, rank 7]
```

这四个组由示意编号及材料中的切片算法直接推出。[D]

以 rank 0 为例，它在标准 TP 方向上对应的另一成员是 rank 1；但在这个细粒度分组中，与它同组的是 rank 2。两种组沿不同维度取成员，所以“组大小都等于 2”并不意味着它们是同一组。

这一例子演示了组成员如何确定，尚未演示具体模块的矩阵计算。材料摘录缺少足够的模块前向输入、输出和通信代码，无法据此给出完整的数值执行过程。

## 为什么省下显存也可能增加生成时延？

材料记录了一组文档实验：DeepSeek-R1-W8A8，32 张 A2 64G，PD 分离的 Decode 侧，DP32、EP32，细粒度 TP 大小为 8。PD 分离是把提示词处理与后续持续生成分给不同执行组；EP 则是在设备间分配专家，并按路由交换输入和结果。

在该实验中，文档给出的各模块结果如下。TPOT 表示每个输出 token 的生成耗时；变化值为正代表耗时增加。

| 模块设置 | 材料记录的显存节省 | batch=24 时的 TPOT 变化 |
| --- | --- | --- |
| attention 输出投影 TP=8 | 5.8 GB | 增加 1.5 ms |
| lm_head TP=8 | 1.51 GB | 减少 1.2 ms |
| 稠密 FFN TP=8 | 0.9 GB | 减少 1.0 ms |
| embedding TP=8 | 1.51 GB | 减少 1.0 ms |
| 合计 | 9.72 GB | 未提供合计值 |

其中 FFN 是前馈网络，此处对应稠密 MLP。上述数字是本地摘录转录的文档结果，本页没有进行硬件复测。

attention 输出投影在这组实验中节省了显存，同时增加了 TPOT，说明容量收益与时延收益必须分别判断。材料没有提供合并开启后的总 TPOT，不能把各行耗时变化直接相加当成整体结果。

这组数字也只属于上述模型、设备和部署条件，不能套到 GLM 双机案例。embedding 又是按编号读取选中行的查表操作，分析它的访问成本时，需要看实际访问了哪些行，不能仅凭整张表的大小计算每一步读取量。

## 放到 GLM-5.3-Flash 双机主线，该怎样判断是否适用？

在请求路径上，本特性涉及的候选位置是输入 embedding、层内 attention 输出投影与稠密 MLP，以及生成分数的 lm_head。理解这些位置后，可以回到[单请求主线](../concepts/one-request.md)，分别核对相应模块原来的分片方式。

本次材料没有提供足够证据，证明这些设置在固定 GLM-5.3-Flash 双机部署中已经启用、可以直接启用，或能获得多少收益。因此这里不提供 GLM 启动命令，也不计算它的每卡权重或通信账单。

需要特别区分的是：材料中一个提交展示了沿 DP 方向建组的机制，另一个提交又对 attention 输出投影和 MLP 增加了全局 TP 等门槛。将后者用于判断固定案例之前，必须先核对提交与部署基线的关系，不能把不同提交的片段拼成同一个已验证方案。

## 哪些概念需要分别判断？

**模块组大小与标准 TP 大小。** 前者在材料中的建组方式沿 DP 维度取成员；后者是另一维度的分工。比较收益时，既要看大小，也要看成员及模块实际使用的布局。

**配置值为 1 与配置值为 0。** 材料中的多项校验由“大于 0”触发，而另一批限制由“大于 1”触发。填 1 仍可能触发模型类型、整除及调度器要求。

**稠密 MLP 与 MoE 专家。** 材料中的细粒度 MLP 分支要求当前不是 MoE 层。模型总体属于 MoE，并不代表模型里每个前馈模块都走专家路径。

**参数被接受与最终生效。** 部分配置会因图捕获范围不足被自动置零。启动时没有在最初的字段解析处报错，不足以证明后续执行采用了该设置。

## 对照源码

### 怎么开

材料中的文档把配置入口放在 additional-config 内的 `finegrained_tp_config`，列出 embedding、lm_head、attention 输出投影和 MLP 的独立设置。

本次摘录没有完整呈现可复用的启动命令、依赖版本与模型组合，因此这里只说明入口，不给出未经核对的部署配方。

材料还展示了另一个相关字段的启用判断：`olora_tensor_parallel_size` 只有大于 1 才使所示启用函数返回真。不能把它的阈值套给其余字段，也不能据此判断其完整支持范围。

### 会报什么错

材料标为提交 `7d825229` 的配置片段，对四个模块大小逐项执行以下检查：

| 触发条件 | 检查要求或行为 |
| --- | --- |
| 模块大小大于 0 | 模型必须属于 MoE |
| 模块大小大于 0 | DP 大小必须能被模块大小整除 |
| 输出投影或 MLP 大小大于 1 | 全局 TP 必须等于 1 |
| 输出投影或 MLP 大小大于 1 | graph mode 不能为 NONE |
| 输出投影或 MLP 大小大于 1 | 必须是 PD 场景的 KV consumer，即接收历史状态的 Decode 侧 |
| 输出投影或 MLP 大小大于 1 | 拒绝 prefill context parallel 大小大于 1 |
| 输出投影或 MLP 大小大于 0 | 必须启用 recompute scheduler |
| 输出投影或 MLP 大小大于 1 | 平台检查必须找到 PreemptOffloadConnector |

这里的 graph mode 是捕获设备操作序列并回放的执行方式。PreemptOffloadConnector 是材料中平台检查要求的状态传输组件；报错文本说明，这一要求用于避免被抢占的请求返回 Prefill 侧后重算 KV 所带来的精度问题。本次材料不足以进一步验证这条路径的完整行为。

阈值差异会影响排查。例如，输出投影大小填 1，仍会触发“大于 0”分支中的 recompute scheduler 要求，却不触发“大于 1”分支中的全局 TP 限制。

对全局 TP 限制，代码注释分别说明：attention 输出投影的 reshape 在 TP 大于 1 时会错位，MLP 在该组合下尚未测试。这两种依据应分别保留，不能都改写成已证实发生相同故障。

### 开销和什么时候别开

该提交还检查图捕获范围能否覆盖最大可能的一步输入。如果捕获上界缺失或小于最大步宽，就发出警告，并把输出投影与 MLP 两项都置为 0。

警告解释了原因：超出捕获范围的一步会转入 eager 执行，跨 DP 的 HCCL 集合通信可能挂起。HCCL 是昇腾通信库；集合通信要求组内成员按匹配的顺序共同参与。

材料说明，最大步宽取批次 token 上限与“最大序列数乘以每序列可能处理的位置数”两者的较小值，其中后者包含投机 token 数。捕获上界为空时，代码会尝试使用显式捕获尺寸列表的最大值。

因此，选择这两项配置时，需要同时核对执行形态、捕获范围、调度器和状态传输组件。仅增加协作设备数，不能替代这些条件。性能方面，应分别验证显存收益与生成时延；前文文档实验已经给出了两者方向相反的例子。
