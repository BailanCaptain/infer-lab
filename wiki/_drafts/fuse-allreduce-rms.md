## 一句话

`fuse_allreduce_rms` 是材料所示旧实现中的图融合开关：编译器识别相邻的矩阵乘、All-Reduce、残差相加和 RMSNorm，将匹配的计算片段替换为融合算子。

这里，All-Reduce 是通信组成员对对应元素求和、并让每个成员取得完整结果的集合通信操作；残差相加把子层结果与保留的输入相加；RMSNorm 根据向量的均方根缩放各分量，再应用可学习的增益。基础计算可参见 [MLP、residual 与 RMSNorm](../concepts/mlp-residual-norm.md)，通信语义可参见[通信基础](../concepts/collective-communication.md)。

本页依据提供的本地摘录整理。材料展示了旧开关的注册条件、默认值分歧，以及其他快照中的接口变化；尚不足以把这些变化完整对应到在册的四个社区版本。

## 为什么存在

矩阵乘、跨设备求和、残差相加和归一化在逻辑上各有职责：矩阵乘得到本设备的计算结果，通信把各设备的部分结果组合起来，后续相加和归一化再更新隐藏向量。图融合尝试把这种已经确定的相邻关系交给一个融合实现处理。它依赖计算片段的具体结构，因此“启用了开关”“注册了 pass”和“最终完成融合”是三个不同状态。

材料中的 `MiddleLayerMatmulAllReduceAddRMSNormPattern` 明确以 Matmul + AllReduce + AddRMSNorm 为识别目标。其注释说明，融合算子内部把 All-Reduce 组织成 Reduce-Scatter 与 All-Gather 两阶段。Reduce-Scatter 先对对应输入求和，并让各成员保留自己的结果分片；All-Gather 再收集各成员的分片，使成员取得完整集合。材料没有展开融合算子内部各计算与这两个通信阶段的完整交错顺序，因此这里不进一步补写执行细节。

### 怎样区分配置、注册和实际命中？

旧管理器通过原始配置字典读取开关：缺键时采用 `True`，显式传入布尔 `False` 时不追加 `MatmulAllReduceAddRMSNormPass`。但 pass 被追加后，还要经过编译范围检查和计算模式匹配。

材料展示的范围判断是 `compile_range.start > ALLREDUCE_NORM_FUSE_THRESHOLD`，其中阈值为 512。这个条件检查编译范围的起点，不能改写为“当前批次超过 512 个 token 就会融合”。即使范围条件成立，也仍需出现能够被模式识别的计算片段。

旧配置还存在两条需要分别看的路径：在启用 npugraph_ex 的分支中，结构化配置里的融合开关为真时才追加阈值分割点；管理器注册 pass 的代码则从原始字典读取开关。因而，单看配置字段的默认 `False`，无法解释所有读取路径的行为。这里的配置不一致属于材料明确呈现的差异。[!]

### 为什么后续不能照搬旧开关？

其他所示快照的配置字段列表和管理器摘录没有继续列出这个旧开关；材料中的发布说明也明确记载，移除了 matmul all-reduce 与 matmul all-reduce RMSNorm 融合，并关联 PR #12119。

这些内容支持“旧接口发生变化”的判断，但材料没有给出足够的分支与发布标签映射。不能据此确定首次删除版本，也不能推导所有 RMSNorm 融合都已删除：所示配置仍列有其他融合开关，它们各有自己的匹配目标。

## 开了的代价

使用这个旧开关的首要成本是核对配置路径和实际命中条件。字段存在、管理器注册 pass、编译范围允许、计算模式匹配，需要分别检查。仅凭启动成功或配置里写了 `true`，不能判断执行图已经变化。

旧文档把默认关闭的原因写为与 SP 冲突。SP 即 sequence parallel，是与张量并行配合、按序列位置分配部分计算及激活的方式，详见[序列并行](../concepts/sequence-parallel.md)。本次材料没有展示冲突的具体触发组合、改图顺序或自动互斥校验，因此同时使用前还需补充实现依据；本页不把冲突表现写成确定的报错或静默失效。

### 旧配置会怎样报错？

材料展示的两个配置装饰器默认采用 `extra="forbid"`，即拒绝未声明字段；相关配置列表没有列出旧开关。据此推断，把旧键传入这些配置类可能触发未知字段校验错误。[I]

这不是运行验证：材料未展示实际异常文本，装饰器也允许通过传入配置覆盖默认设置。所示管理器后来改为消费递归校验后的配置，并明确指出原始字典中的字符串 `"false"` 具有真值。配置时应使用布尔值，不能把字符串形式当成相同输入。
