GLM-5.3-Flash 的 A2 双机混部方案，把请求分组与单次计算的分工叠在一起：两台机器之间设置两个 DP 执行组，每台机器内部用八个设备共同完成张量计算。本页解释这些分组分别管什么，以及为什么双机混部、跨机专家协作和 PD 分离需要分别理解。

本页是依据本地摘录准备的文字草稿。材料包含部署文档片段与源码片段，能够支持下述配置和条件的解释；本次没有运行部署，也没有独立打开上游源码核验完整调用链。

## 两台机器怎样共同承担计算？

tensor parallel（TP）把一次张量计算分给多个设备，各设备计算自己的部分，再通过通信形成后续所需的结果。data parallel（DP）把不同请求或批次分配给不同执行组，各组维护相应的请求状态。两者的分工对象不同：TP 处理一次计算内部怎样协作，DP 处理请求交给哪个组。

材料中的部署文档明确列出：量化模型 GLM-5.3-Flash-w8a8 可以使用两台 Atlas 800 A2，每台配置八个 64 GB 设备；节点内 TP8，跨节点 DP2，每个节点对应一个 DP rank。rank 是成员编号，此处的 DP rank 编号属于请求执行组，不能直接当作全局设备编号。

按这个配置读一个小例子：请求 A 被分给其中一个 DP 执行组，该组内部的八个设备通过 TP 协作。另一个请求可以交给另一个 DP 组。这里的分配只说明请求由哪个组推进；专家是否位于该组内部，还要继续看 EP 分组。

两组各有八个设备，合计十六个设备。这是配置数量的推导，不是设备运行结果。[D]

关于请求如何进入执行组，后续可结合[多条请求](../concepts/concurrent-requests.md)阅读；本页不把请求分组进一步推断成负载均衡策略。

## 为什么 DP 分组还不能说明专家在哪里？

expert parallel（EP）把专家分配到多个设备上，再按照路由结果发送输入、计算专家输出并组合结果。专家是执行前馈变换的模块；MoE 使用路由机制为输入选择部分专家。请求由哪个 DP 组推进，与本次计算需要访问哪些专家，是两个不同的问题。

材料中的上游源码对 EP 分组使用 DP、prefill context parallel 和 TP 三个维度的乘积。prefill context parallel 是沿提示词上下文分配工作的并行维度；它在这里参与通信组成员的组织。

用同一组部署数量接着演示：如果 DP 为 2、TP 为 8，并假设 prefill context parallel 为 1，那么所示 EP 分组的大小为 2 × 1 × 8，也就是 16。[A][D] 这说明在该分组条件下，专家通信域可以覆盖两个 DP 组。它不能单独证明专家数量、每个专家的实际放置位置或每个 token 的路由结果。

因此，看到“一台机器对应一个 DP rank”，还不足以判断这台机器是否保存完整模型。需要同时核对专家分布和执行路径。一个请求在本机推进时，也可能需要另一台机器上的专家参与。

源码片段还给出了 EP 分组的创建条件：模型配置缺失，或者模型被标记为 MoE 时，进入所示分支；已知为 dense 的模型不进入这个分支。dense 模型是这里与 MoE 相对的模型类别，不能把这段专家分组规则直接推广给它。

## 跨机专家协作会自动使用 MC2 吗？

MC2 是把矩阵计算与通信协同执行的一类昇腾实现。它的通信组怎样构造，与某轮计算是否选择它，需要分开检查。

材料中的 Ascend 源码按全局 DP、prefill context parallel 和 TP 的乘积组织 MC2 通信组，形式与 EP 分组相似。但创建通信组只准备了参与成员，并没有证明每轮都走 MC2。

A2 的通信方法选择片段要求三个条件同时成立：

| 条件 | 选择函数检查的内容 | 对部署的含义 |
| --- | --- | --- |
| 每设备专家数 | 总专家数除以 EP 组大小所得值不超过 24 | 设备数量相同，专家规模不同，也可能走不同路径 |
| EP 组大小 | 至少为 16 | 双机的机器数量本身不是判定条件 |
| token 数 | 不超过传入的 MC2 容量 | 同一部署也可能随执行规模改变通信路径 |

三个条件均满足时，函数返回 MC2；否则返回 ALLGATHER。All-Gather 是收集各成员分片、让成员获得完整集合的通信操作；这里的 ALLGATHER 是实现中通信路径的名称，片段没有展开该路径的全部步骤。

这段选择代码没有直接检查“是否处于 prefill”。但传入的 token 数如何计算、容量如何设定，仍需沿调用处核对。仅凭这几行，不能把切换条件进一步写成“prefill 一定走某条路径”或“容量固定为 128”。

## 缓存布局为什么也会限制部署配置？

KV cache 保存后续计算需要的历史表示，避免重复计算已经处理的位置。混合模型可能同时具有不同类型的历史状态，缓存管理器需要按各自布局组织空间，而不是统一按普通 K、V 张量处理。

材料中的缓存分组补丁，会检查缓存规格里的模型标记。只要有一个规格的 `model_version` 为 `glm5_next`，就进入专用分组路径；否则回到原来的缓存分组函数。

这个专用路径明确要求 hybrid KV cache manager，即能管理混合缓存类型的缓存管理器。禁用它时，代码抛出异常，说明配对的 MLA/indexer 与滑动状态布局需要该管理器。MLA 是用压缩潜在表示组织注意力的一种机制；这里的 indexer 指索引相关组件，但片段没有展开它的输入、输出与缓存结构。

这条约束的准确范围是“进入所示专用路径时”。材料尚未完整建立模型配置、模型实现与该规格标记之间的对应关系，因此本页不据此给出 GLM-5.3-Flash 每层缓存形状、每块字节数或可分配块数。

设备容量也不能直接当作可用缓存容量。权重、运行时缓冲和临时结果都会影响剩余空间；具体预算应结合[KV cache 显存预算](../concepts/kv-cache-memory-profiling.md)核对实际配置。

## 双机混部与四机 PD 分离有什么区别？

prefill 处理提示词中尚未计算的位置并建立历史状态；decode 在已有历史上继续生成输出。PD disaggregation 将这两类工作交给不同执行组，并传输衔接所需的历史状态。

材料中的 A2 部署文档同时涉及两种方案：

| 方案 | 机器分工 | 文档给出的并行配置 |
| --- | --- | --- |
| A2 双机混部 | 两台机器构成两个请求执行组 | 跨节点 DP2，节点内 TP8 |
| A2 PD 分离 | 两台 Prefill 机器、两台 Decode 机器 | Prefill 为 DP2/TP8，Decode 为 DP8/TP2 |

四机 PD 方案中，Prefill 使用 eager mode，即逐步提交算子执行；Decode 使用 FULL_DECODE_ONLY 图模式，并关闭 FlashComm1。图模式通过回放捕获的设备操作序列减少提交开销。材料没有展开 FlashComm1 的机制，因此这里仅保留其示例设置。

两种方案的设备数量、角色和执行设置都不同。将四机方案的 Decode 配置用于本页双机方案，需要重新核对完整部署条件，不能只替换一个并行参数。

文档还列出 A3 的方案：单台 A3 部署，以及两台 A3 的 1P1D 分离部署，其中 1P1D 表示一个 Prefill 角色与一个 Decode 角色。它与 A2 双机混部同样具有“两节点”这个表面特征，但硬件和角色分工不同。

## 启动示例中的数字可以怎样理解？

材料中的 A2 双机混部 node 0 示例设置了全局 DP2、本地 DP1、起始 DP rank 为 0，与“每节点一个 DP rank”的说明一致。片段只包含 node 0 的部分命令，尚不足以组成完整双机启动步骤。

示例还将最大模型长度设为 133120。这个数表示该命令采用的长度设置，不能据此认定它是模型最大支持长度，也不能证明当前设备预算足够服务该长度。

同一示例显式关闭 V2 model runner。model runner 是组织模型执行的组件；材料中的文档将当时 Ascend 上该模型的支持范围限定为 V1。该结论属于所摘录的文档快照，不代表所有版本或未来版本。

示例中的环境变量还涉及内存分配与 HCCL（昇腾集合通信库）。示例设置能够说明文档采用了什么配置；若要判断某个变量是否必需、能否调整及调整代价，还需要它的消费者代码或对应接口文档。

## 哪些结论需要分别核对？

**两个 DP 组是否各自拥有完整模型，取决于专家分布。** 请求状态分组和专家通信域可以跨不同范围组织；只看 DP 数量，无法确定完整权重位于哪里。

**EP 组跨机，不等于全部数据都要跨机。** 实际传输需要结合专家放置、路由结果和通信实现判断。当前摘录没有足够信息计算跨机字节数。

**MC2 通信组存在，不等于每轮都选择 MC2。** 所示 A2 选择函数还检查每设备专家数、EP 规模和 token 容量。

**部署文档给出方案，与本次实机验证是两件事。** 本材料包含明确的 A2 双机支持说明，但没有运行日志、请求结果或性能测量，本页也没有据此报告吞吐、时延或实际显存占用。

## 对照源码

### 怎么开

材料中的 A2 双机混部示例包含以下设置：

- 全局 DP 大小为 2，本地 DP 大小为 1；node 0 的起始 DP rank 为 0。
- `VLLM_USE_V2_MODEL_RUNNER=0`，显式选择 V1 model runner。
- `PYTORCH_NPU_ALLOC_CONF=expandable_segments:True`。
- `HCCL_OP_EXPANSION_MODE=AIV`。
- `HCCL_BUFFSIZE=1024`。

这些是摘录中出现的示例配置，不构成完整启动命令；网络地址、另一节点命令、模型路径及其他启动项仍需核对完整教程。

材料还给出实验性 SFA 上下文并行入口：

```text
--additional-config '{"enable_dsa_cp": true}'
```

文档说明该路径在 TP 组内切分 SFA query tokens，主 KV、indexer pool 和 tail caches 仍保持复制，KDA 沿用既有 TP 路径；prefill 与 decode context parallel size 均须保持为 1。材料未展开 SFA 的定义和这些缓存的完整结构，因此这里仅记录配置边界，不将它解释成通用 PCP/DCP 能力。

### 会报什么错

在模型标记为 `glm5_next` 的专用缓存分组路径中，禁用 hybrid KV cache manager 会抛出：

```text
GLM-5's paired MLA/indexer and sliding state layout requires the hybrid KV cache manager.
```

这是所示布局的明确约束。材料没有提供双机启动、通信初始化或显存不足时的完整报错清单。

### 开销和什么时候别开

所示通信选择函数并未无条件采用 MC2；应先核对专家规模、EP 组大小和传入 token 数。材料也没有提供足够的运行结果，用于判断某个负载下 MC2 与 ALLGATHER 的性能差距。

实验性 SFA 上下文并行保留了文档列出的缓存副本，因而不能仅凭切分 query tokens 就断言这些缓存的显存占用随 TP 数量下降。

PD 分离需要不同角色的执行组与历史状态衔接。本材料中的 A2 配方使用四台机器，不能把它作为只有两台 A2 时可直接照用的配置。
