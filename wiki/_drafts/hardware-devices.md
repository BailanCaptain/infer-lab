NPU 是执行模型计算的处理器；Device 是程序用来选定计算设备的软件标识。本页解释 vllm-ascend 的执行角色怎样从本地编号得到 Device，以及为什么“选到了设备”“看到了几个设备”和“查到了总显存”是三个不同的问题。

材料提供的是平台定义与设备初始化代码的摘录。它足以讨论这些软件行为，但没有提供芯片、板卡、服务器与机柜的完整规格，也没有现场设备枚举或性能测量。物理硬件的数量、设备与板卡的映射关系，仍需对应产品资料和现场记录。

## 程序怎样确定把计算交给哪个设备？

平台定义把设备名称和设备类型都写为 npu，并指定由 ASCEND_RT_VISIBLE_DEVICES 控制设备可见范围。这里的“可见”指程序能够使用的设备范围；它与机器中实际安装了多少硬件是两个需要分别核对的问题。

执行角色 Worker 负责设备初始化等工作。材料中的 Worker 先构造 Device，再调用设备选择接口。摘录展示了两条寻址路径：

- 将本地编号交给平台的映射方法，得到可见设备编号，再构造 Device。
- 直接用本地编号构造 NPU Device。

本地编号 local_rank 是当前机器内执行成员的编号。第一条路径说明：执行成员的本地编号可以先经过映射，才成为设备标识的一部分。材料没有给出选择这条路径的完整条件，因此不能把其中一条路径当成所有启动方式的固定行为。

例如，设某个 Worker 的本地编号为 1。在直接寻址路径中，程序构造的标识是 npu:1，然后把它交给设备选择接口。这是一次编号代入的示意，不证明现场编号 1 对应哪块板卡、哪个物理位置，也不证明映射路径会返回相同编号。[A]

这一步在请求执行前完成：Worker 需要先确定使用哪个设备，后续初始化才有明确对象。关于执行角色与平台选择的职责，可以接着阅读 [NPUPlatform](../concepts/npu-platform.md)。

## 为什么设备选择的先后顺序也有影响？

设备选择不只是保存一个编号。材料中的注释要求：与 Triton 相关的导入应放在设备选择之后，以避免额外进程重复设置设备。Triton 在这里涉及另一条计算实现路径；只有可用性标志为真时，代码才导入相应模块。

这说明启动顺序承担了约束初始化行为的职责。理解这段代码时，应沿着“得到设备标识 → 设置当前设备 → 按条件导入相关模块”的顺序阅读，而不是把几个导入语句看成可以任意移动的准备工作。

材料还展示了一个按设备类型分支的步骤：设备类型为 A5 时，代码调用本地通信资源设置方法，并传入本地编号和 KV 传输配置。KV 传输配置用于描述历史计算状态的传输安排。这个分支只说明 A5 在此处执行了额外设置，不能据此判断其他设备的完整通信能力。

## 可见设备数量检查究竟检查了什么？

设备标识回答“当前执行成员选择谁”；设备计数回答“当前环境能看到多少个设备”。材料中的计数检查还受到启动方式限制，并非所有场景都会进入。

该检查要求以下条件同时成立：

- DP 大小大于 1，且本地 DP 大小大于 0。DP 是把不同请求或批次分给不同执行组的安排。
- 分布式执行后端既不是 Ray，也不是 external_launcher；Ray 是一种分布式执行框架，external_launcher 表示由外部启动器组织执行。
- DP 后端不是 Ray。
- 一个 DP 组内的节点数配置为 1。

条件成立后，程序在 NPU 可用时读取可见设备数量，否则将数量记为 0。随后检查本地执行规模是否超过可见设备数量。

因此，这段检查能帮助发现一种配置冲突：本地计划安排的执行成员多于当前可见设备。它并不核对设备的板卡位置、显存规格或网络连接；未进入这个分支，也不能据此认定配置已经通过其他检查。

## 为什么不同设备类型可能采用不同寻址策略？

材料中的硬件配置表按设备类型选择策略。在所提供的快照中，A2 使用 DIRECT 寻址，A3 使用 DUAL_CHIP_CARD 寻址；两者的 CPU 绑定策略也不同。CPU 绑定是安排执行线程使用哪些 CPU 资源的策略。

这些配置项说明，软件没有为所有设备类型采用同一套寻址与线程安排。它们仍不足以建立完整的物理映射：仅凭 DUAL_CHIP_CARD 这个策略名，不能算出现场板卡数量、每块板卡的软件设备数量或设备编号顺序。

本页因此把两个问题分开处理：代码选择哪种策略，可以从配置摘录核对；某台服务器里的实际设备怎样对应物理硬件，需要完整实现、产品型号与现场枚举共同确认。

## 放到 GLM 双机主线时，需要核对什么？

本库的 GLM 双机部署入口见[部署前提](../concepts/glm-5-3-flash-two-node.md#部署前提)。本次材料没有提供完整启动命令或现场输出，因此不能在本页重新确认两台机器各暴露多少设备、设备对应哪块板卡，以及每个 Worker 最终选择了哪个设备。

对照该部署时，设备选择这一站需要接上三类信息：

- 启动环境暴露了哪些设备。
- 本地执行成员采用哪条设备寻址路径。
- 完成设备选择后，初始化与资源查询返回了什么。

材料中设备初始化片段标注的执行侧提交是 db701c1f；其他快照中的寻址配置或显存接口，不能直接替代这一固定执行基线。这里没有实机运行结果。

## 哪些概念需要分别判断？

**设备编号与物理数量。** Device 是软件选择计算设备的标识；材料没有建立它与板卡、芯片封装或服务器槽位的一一对应关系。

**设备可见与资源足够。** 设备计数检查比较本地执行规模和可见设备数量；它没有计算模型所需显存。

**总显存与当前剩余显存。** 材料中的查询接口返回总量。即使查询成功，也不能把总量直接当成模型此刻可用的剩余量。

**接口暂不提供结果与硬件没有显存。** 某些快照主动抛出未实现异常，是为了避免过早初始化。这是接口行为及其初始化条件，不能解释为硬件资源不存在。

**配置表出现设备类型与完整支持承诺。** 摘录中的 A2、A3、A5 分支只展示局部软件策略，没有给出产品型号、驱动、固件与全部运行组合的支持矩阵。

## 对照源码

### 怎么开

这不是一个单独启用的模型特性。平台声明使用 npu 设备类型，并把可见设备控制变量指定为 `ASCEND_RT_VISIBLE_DEVICES`。Worker 构造 Device 后调用 `torch.npu.set_device(device)`。

摘录还展示了 `logical_device_id_to_visible_device_id` 与直接使用 local_rank 的两条寻址路径，但缺少前一条路径的完整触发条件。因此，本材料不能给出适用于所有启动方式的环境变量取值或启动命令。

### 会报什么错

材料展示了两类与本页直接相关的失败条件。

其一，在满足前述 DP 与执行后端条件时，本地执行规模不能超过可见设备数。材料说明存在相应断言，但没有提供完整报错字符串。

其二，总显存查询受初始化条件影响。部分快照中的 `get_device_total_memory()` 直接抛出 `NotImplementedError`；另一些快照在 torch_npu 尚未初始化时抛出同类异常，并给出：

```text
NPU total memory is unavailable before torch_npu initialization
```

后一种实现只有在 torch.npu 存在且已初始化时，才调用 `torch.npu.mem_get_info(device_id)`，取其总显存返回值。异常是否出现，要与调用时机一起判断。

### 开销和什么时候别开

材料没有给出设备选择、计数检查或显存查询的时延，不能量化这些步骤的启动开销。

这里更直接的约束是初始化时机。无条件抛出异常的接口注释说明，相关调用可能过早初始化 torch_npu，而重复初始化会造成错误；条件式实现则要求先完成初始化，再查询总显存。

跨节点内存池化、链路带宽、通信吞吐与缓存复用收益没有出现在本次可用证据中，本页不据此给出启用建议。

### 版本差异

本次材料给出了提交级摘录，但没有建立它们与在册分支的可靠映射。因此，v0.23 维护分支、v0.26 分支、v0.30.0rc2 分支和 main 开发主线均未在本稿完成逐项核对，frontmatter 的 verified 保持为空。
