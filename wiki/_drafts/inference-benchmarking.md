推理压测是在一组请求上记录时间、输出数量与成功情况，再按约定汇总服务表现。一个数字是否有用，取决于它究竟数了什么、从哪个事件计时，以及哪些请求进入了统计。

本页依据本地材料中的 vLLM 压测代码摘录，解释读取报告时容易影响结论的计量差异。材料没有原始压测记录，也没有完整的负载配置和测量窗口定义，因此这里讨论的是统计口径，不是某个模型或配置的实际性能。

## 一份压测报告究竟把什么汇总成了数字？

可以沿着三层关系理解报告：

| 层次 | 记录什么 | 汇总前要回答的问题 |
| --- | --- | --- |
| 接收事件 | 客户端什么时候收到流式消息 | 消息里有没有内容？是否合并了多个 token？ |
| 单请求指标 | 首次接收时间、后续间隔、请求延迟和输出长度 | 起点和终点是什么？输出长度从哪里取得？ |
| 整批统计 | 请求吞吐、输出吞吐、达标请求吞吐和峰值 | 哪些请求被纳入？时间分母覆盖哪段过程？ |

token 是模型处理的离散符号，通常以整数编号表示；客户端收到的流式消息则是接口传输的单位。二者并不保证一一对应。关于消息怎样承载生成结果，可以接着看 [streaming-output](../concepts/streaming-output.md)。

这一区别直接影响计量：收到三个消息，不足以证明模型只生成了三个 token；收到了第一条消息，也不一定意味着用户已经看到第一段答案。

## 为什么先核对事件，再比较 TTFT 和 TPOT？

TTFT 是从请求计时起点到工具认定的首次输出事件之间的时间。TPOT 是首个输出之后，平均每个后续输出 token 分摊的时间。材料中的聚合函数按下面的关系计算 TPOT：

\[
\mathrm{TPOT}
=
\frac{\mathrm{latency}-\mathrm{TTFT}}
{\mathrm{output\_len}-1}
\qquad
(\mathrm{output\_len}>1)
\]

这里的 latency 是请求函数记录的延迟，output_len 是工具最终采用的输出 token 数。要理解这个结果，必须继续查看这两个输入如何形成。

材料展示的一个固定实现中，Completions 与 Chat Completions 对成功和结束事件的处理不同：

| 接口 | 怎样认定成功 | 延迟终点怎样更新 |
| --- | --- | --- |
| Completions | HTTP 200 之后，还须收到至少一条带非空 choices 的消息；其中 text 可以为空 | 更新到最后一条带 choices 的消息；只有用量信息的消息不更新这一时间 |
| Chat Completions | HTTP 200 且解析过程无异常时，直接标记成功 | 非结束标记的数据消息都会更新时间，包括用量消息 |

因此，同名 TTFT 不足以证明测到了“首个非空答案文本”。同名请求延迟也可能覆盖不同的尾部等待：一个接口止于带 choices 的消息，另一个接口可能继续计入用量消息的到达。

这种终点差异还会进入 TPOT 的分子。比较两份报告时，应保留接口、工具快照和计时事件，才能判断差值来自生成过程，还是来自客户端的记录方式。

## 输出 token 数是直接数出来的吗？

材料中的指标函数优先采用请求结果里的 output_tokens。当这个值为假值时，函数进入回退路径：

- 有 tokenizer 时，对生成文本重新分词计数。tokenizer 是把文本转换成 token 编号的工具。
- 没有 tokenizer 时，把输出长度设为 1。

第二种情况表示工具采用了一个回退计数，不能据此断言模型实际生成了一个 token。

重新分词也有边界。材料中的代码注释明确说明，部分后端可能把多个输出 token 捆绑返回，所以不能直接用 ITL 条目数代替输出长度；注释同时提示，重新分词的计数可能略有膨胀。ITL 是工具记录的相邻输出事件间隔，它是否对应逐 token 间隔，要结合具体请求函数判断。

这意味着输出吞吐和基于间隔重建的峰值，可能使用不同的计数依据。阅读报告时，要分别说明两者的来源。

## 怎样手算一次 TPOT 和达标请求吞吐？

下面设定一个教学例子：测量窗口为 2 秒，有两个成功请求；请求 A 的输出长度为 4，TTFT 为 0.2 秒，请求延迟为 0.8 秒；请求 B 的输出长度为 1，TTFT 为 0.3 秒，请求延迟为 0.4 秒。这些数字仅用于演算，不是实测。[A]

请求 A 的首个输出之后还有三个输出 token，因此把剩余的 0.6 秒分摊到三个位置：

\[
\mathrm{TPOT}_A
=
\frac{0.8-0.2}{4-1}
=
0.2\ \text{秒/token}
\]

请求 B 没有可供平均的后续 token 间隔。材料中的实现不把它加入普通 TPOT 样本列表，但在 goodput 判定所用的列表中，把它的 TPOT 记为 0。这是工具的判定约定，不是一次零耗时的生成测量。

goodput 在这里指达标请求吞吐：单位时间内，成功且同时满足所配置目标的请求数。SLO 是约定的服务目标，例如 TTFT 不超过某个时限。材料中的实现支持选择 TTFT、TPOT 和 E2EL；E2EL 是该工具采用的端到端请求延迟。

沿用上面的示意请求，若设置 TTFT 不超过 0.25 秒、TPOT 不超过 0.25 秒，则 A 同时达标，B 因 TTFT 超限而不达标；恰好等于阈值也算通过。[A]

由此得到：

| 指标 | 示意计算 | 结果 |
| --- | --- | --- |
| 成功请求吞吐 | 2 个成功请求 ÷ 2 秒 | 1 请求/秒 |
| 达标请求吞吐 | 1 个达标请求 ÷ 2 秒 | 0.5 请求/秒 |
| 输出吞吐 | 工具计数的 5 个输出 token ÷ 2 秒 | 2.5 token/秒 |

这些结果是上述假设和材料中计算规则的推导，不表示任何真实系统的性能。[D]

三个指标回答不同问题：完成了多少请求、其中多少满足交付目标，以及工具累计了多少输出 token。只报告输出吞吐，无法替代达标请求吞吐。

## 失败请求和时间窗口怎样改变吞吐解释？

材料中的吞吐指标共用 dur_s 作为分母，但分子不同：

\[
\begin{aligned}
\text{请求吞吐} &= \frac{\text{成功请求数}}{\mathrm{dur\_s}}\\
\text{达标请求吞吐} &= \frac{\text{成功且达标的请求数}}{\mathrm{dur\_s}}\\
\text{输出吞吐} &= \frac{\text{成功请求的输出计数总和}}{\mathrm{dur\_s}}\\
\text{总 token 吞吐} &= \frac{\text{成功请求的输入计数总和}+\text{输出计数总和}}{\mathrm{dur\_s}}
\end{aligned}
\]

失败请求的输出长度在这些聚合计算中记为 0，输入量也只累计成功请求。因此，“总 token 吞吐”里的“总”描述这里选定的输入与输出计数之和，并不表示所有尝试过的请求都被完整计入。

材料没有给出 dur_s 的测量边界。单凭这些公式，无法判断分母是否包含预热、排队或其他阶段。要把结果用于容量判断，还需要补齐测量窗口和请求到达方式；这些缺口不能用指标名称推定。

## 为什么报告里的两个峰值不一定同时发生？

材料中的峰值输出速率没有直接使用每个请求的 output_tokens，而是先重建事件时间：

1. 用请求开始时间加 TTFT，得到第一个事件时间。
2. 依次累加 ITL，得到后续事件时间。
3. 相对于最早成功请求的开始时间，把事件放入一秒宽的时间桶。
4. 取各桶事件数的最大值。

因此，每个成功请求贡献的是一个首事件加上 ITL 条目数。当消息合并多个 token 时，这些事件的数量不能保证等于真实输出 token 数。

并发计数采用另一种分桶方式：一个成功请求的起止时间覆盖哪些整数秒桶，就给那些桶各加一。它描述的是桶内被计为活跃的请求数，不能直接等同于某一瞬间精确重叠的请求数。

在材料所列的 main 快照中，输出计数峰值和并发计数峰值分别取最大值。代码没有要求它们出现在同一秒。因此，把两列峰值并排抄入报告，不能解释成“服务在该并发下达到了该输出峰值”。

## 把这些指标用于 GLM 双机时，还缺什么？

这些计量问题位于客户端接收与报告汇总处。要用它们评价固定的 GLM 双机部署，应把同一组请求的接口、成功判据、输出计数方式、测量窗口和达标阈值一起保留下来。

本次材料没有 GLM 双机运行记录，也没有将这些客户端统计与服务端执行阶段对应起来的时间线。它能帮助解释报告字段，尚不能证明该部署的吞吐、时延或某个配置的收益。

## 哪些读法会把统计约定当成系统表现？

**goodput 为 0，需要先检查是否配置了目标。** 材料中的实现把达标计数初始化为 0，只有提供 goodput 配置才逐请求判断。未配置时的零值表示没有执行这项达标统计。

**短输出的 TPOT 为 0，需要区分使用位置。** 输出长度不超过 1 的成功请求不进入普通 TPOT 样本，却以零值参与 goodput 判定。报告应保留这个约定。

**HTTP 成功与压测成功，需要分别看接口实现。** 材料展示的 Completions 即使收到 HTTP 200，也可能因为没有有效 choices 消息而被标记为失败；Chat Completions 的判定路径不同。

**输出吞吐与事件峰值，需要分别核对计数依据。** 前者采用聚合后的输出长度，后者从 TTFT 和 ITL 重建事件。消息合并时，两者不能直接互相验证。

## 对照源码

### 怎么开

本地摘录展示了 goodput 配置的消费逻辑，没有提供足以复现一次压测的完整命令、请求负载和启动条件。

在已展示的聚合逻辑中，配置可选择 TTFT、TPOT 和 E2EL 阈值；阈值从毫秒转换为秒后，与请求指标比较。一个成功请求须同时满足所有已选阈值，等于阈值时通过。

### 会报什么错

材料所列 Completions 请求函数在没有收到有效 choices 消息时，将响应标记为失败，并设置错误文本：

> Never received a valid chunk to calculate TTFT.This response will be marked as failed!

这里的“有效”是该函数计算 TTFT 所用的消息判据。它不要求 text 非空，因此仍需另行区分接口首事件与首个可见答案。

### 开销和什么时候别开

材料展示了重新分词、逐请求阈值判断和按秒分桶的计算过程，没有给出这些统计操作的耗时测量，无法量化其压测开销。

选择指标时，应让统计对象与问题对应：平均生成节奏看 TPOT 时保留短输出规则；交付目标看 goodput 时明确阈值；分析峰值时保留桶宽和事件计数依据。
