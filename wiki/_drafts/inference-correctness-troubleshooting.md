推理正确性排查，是把最终输出的差异沿处理过程向前追踪，找出最早出现差异的位置，再判断它来自输入、选择规则、输出处理，还是模型执行。

这里的 token 是分词器输出的离散符号，通常用整数编号表示；采样是根据模型给出的分数选定下一个 token；流式输出则把逐步得到的 token 转成可见文字并分段发送。最终文字同时受到这些环节影响，因此，“回答不同”还不足以定位计算错误。

本页依据所给材料中的局部源码与文档整理排查方法。材料没有提供具体故障的输入、输出与运行日志，因此不能据此判定某次异常的根因。下面的排查顺序是综合这些材料得到的方法建议。[I]

## 为什么要从实际输入一路比到可见文字？

可以把比较对象分成四层：

| 比较对象 | 要回答的问题 | 接下来检查什么 |
| --- | --- | --- |
| 模板处理后的输入 | 两次执行实际收到的 token 编号是否相同？ | 模板调用、分词结果及接口返回类型 |
| 模型分数 | 在相同输入历史下，候选 token 的分数是否已出现差异？ | 执行路径、批次与复现条件 |
| 选出的 token | 分数如何被转换为一个确定的编号？ | temperature 等采样设置 |
| 返回的文字 | 相同 token 是否经过相同的停止与流式处理？ | 停止字符串、最少输出长度、缓冲与结束状态 |

这张表是组织证据的顺序，不是对故障概率的排序。[I] 如果已经在输入编号上发现差异，继续比较后面的分数时，就必须把输入差异作为前提；如果 token 编号相同而客户端收到的片段不同，输出处理是更直接的调查对象。

[Token 与分词](../concepts/token.md)解释文字怎样变成编号，[Sampling](../concepts/sampling.md)解释怎样从分数选择编号，[流式输出](../concepts/streaming-output.md)解释编号怎样变成发送给客户端的文字。

## 输入文字一样，为什么还要检查模板调用？

聊天模板负责把消息组织成供模型使用的输入。排查时，除了保存原始消息，还应保存模板调用参数和最终 token 列表。[I]

材料展示了一处针对 Transformers 返回类型变化的兼容处理：在所引 vLLM 快照中，调用聊天模板时，如果要求直接分词，且调用方没有显式提供 return_dict，就补入 False，使下游得到预期的扁平 token 列表。

这个分支有两个条件：必须正在分词，而且调用方尚未指定返回类型。显式传入 return_dict 时，该分支不会覆盖它。因而，核对模板调用不能只看“调用了同一个函数”，还要看实际参数与返回对象。

这条材料支持的是接口兼容行为，不能由此直接推断某次回答质量下降就是模板导致的。

## temperature 为零，究竟固定了哪一步？

模型为候选 token 计算分数后，还需要选择下一项。贪心选择直接采用最高分候选；随机选择则按相应分布抽取。temperature 影响的是这一步的选择规则。

所给采样片段先准备贪心结果和随机结果，再根据 temperature 是否小于阈值选择其中一个。材料给出的阈值是 \(10^{-5}\)。因此，在这段路径中，temperature 为零会选择贪心结果。

但选择规则固定，并不等于上游计算出的分数也被证明完全相同。这段代码没有提供跨批次、跨硬件或跨版本的数值一致性保证。

看一组便于手算的示意分数。假设只有候选 A、B、C，且贪心选择没有并列最高分：[A]

| 执行 | A 的分数 | B 的分数 | C 的分数 | 贪心结果 |
| --- | ---: | ---: | ---: | --- |
| 第一次 | 2.00 | 1.99 | 0.50 | A |
| 第二次 | 1.98 | 1.99 | 0.50 | B |
| 第三次 | 2.01 | 1.99 | 0.50 | A |

第一次取最大值 2.00，输出 A；第二次取最大值 1.99，输出 B。两次都遵守同一个贪心规则，结果仍不同。第一次与第三次都输出 A，但 A 的分数分别是 2.00 和 2.01，输出相同也不能证明中间数值相同。[D]

这组数只说明逻辑关系，不代表某种硬件上的误差幅度。实际排查需要保存同一生成位置的输入历史、候选分数和选出编号，才能继续缩小范围。[I]

## 为什么已经生成 token，却暂时没有文字发出来？

停止字符串是输出处理中用于识别结束位置的文本。若配置要求不把停止字符串返回给用户，流式输出就需要暂存一部分末尾字符，避免先把可能属于停止字符串的内容发送出去。

材料中的实现把保留长度设为“最长停止字符串的字符数减一”。请求结束时，所示输出获取路径不再保留这段流式缓冲。

例如，假设停止字符串只有 `END`，要求从返回文字中排除它，且请求仍在生成：[A]

- 当前累计文字为 `abcE`。
- 最长停止字符串有 3 个字符，因此末尾保留 2 个字符。
- 若本次尚未命中停止条件，当前可释放的前缀是 `ab`，末尾的 `cE` 暂时保留。[D]

这里计算的是字符缓冲，不是 token 数量。具体一次生成新增了几个字符，还取决于 token 转文字的结果。

因此，看到某个流式片段为空或比预期短时，应同时记录累计 token、累计文字、停止设置和请求是否结束，再判断差异出现在哪里。[I]

### 配置了停止字符串，为什么没有立即停止？

最少输出 token 数也是停止检查的条件。

材料中的停止字符串检查只在输出 token 数**严格大于** min_tokens 时执行；不超过该值时，还会更新后续检查使用的起点。因此，分析“为什么没有在某处停止”，需要知道当时已经输出多少个 token，而不能只确认停止字符串曾出现在文字中。

这个条件与前面的字符缓冲解决不同问题：前者决定何时检查停止字符串，后者决定流式过程中暂时保留多少末尾文字。

## 比较不同批次时，需要固定哪些复现条件？

批次是一次模型执行共同处理的输入集合。即使只关心请求 A，同批还有哪些请求、调度怎样组织执行，也属于需要记录的实验条件。

材料中的 vLLM 复现文档区分了两种运行形态：

| 运行形态 | 文档列出的复现方案 | 需要保留的条件 |
| --- | --- | --- |
| 离线调用 | 关闭 V1 多进程以使调度确定，或者启用 batch invariance | 关闭多进程会改变构造 LLM 的用户代码随机状态 |
| 在线服务 | 启用 batch invariance | 文档将复现范围限定为相同硬件、相同 vLLM 版本 |

batch invariance 的目标是让输出不受批次或调度变化影响。其机制与支持边界见[批不变性](../concepts/batch-invariance.md)。

关闭多进程是材料列出的离线方案，不能据此直接当作在线服务的等价方案。文档也没有给出跨硬件或跨 vLLM 版本的复现保证。

### 为什么设置了环境变量，还要查看初始化日志？

所给 Ascend 实现有两层条件：批不变性开关必须开启，而且 Triton 或 AscendC 批不变算子至少有一种可用。满足条件才执行初始化；依赖不可用时会输出警告并跳过。

材料中的安装说明还指出，预编译 wheel 不包含 csrc 目录及对应构建脚本。安装这种 wheel 时设置环境变量，不会重新编译算子；手动安装需要与 wheel 匹配的源码检出。

所以，一份有用的复现记录应包含安装产物、匹配源码、算子准备过程以及实际初始化日志。[I] “启动脚本写了开关”只能证明配置意图，尚不能证明相应执行路径已经启用。

## 在 GLM 双机案例中，应怎样使用这些检查？

本页材料中的输入、采样和停止处理片段标注来自 vLLM 固定快照 0fc695fc，可用于核对贯穿案例中这些环节的行为。

批不变性与 Ascend 配置解析材料另标注了 vllm-ascend 快照 7d825229。不能把这份执行侧材料直接当作 GLM 固定执行基线的行为证明。

应用到 GLM 双机故障时，可以沿用前面的比较对象：先记录实际输入，再比较选出 token 与返回文字；涉及批次影响时，补充每次运行的调度、依赖和初始化记录。[I] 当前材料不足以补写该固定部署上的具体分数差异、设备转储结果或实机复现结论。

## 哪些观察还不能单独确定根因？

**贪心输出不同。** 这说明最终选中的候选不同；还需要检查输入历史与候选分数，才能继续追踪差异来自哪里。

**最终文字相同。** 示意算例已经说明，不同分数也可能选中同一个候选。文本比较适合判断可见结果，不能代替数值比较。

**流式返回暂时为空。** 停止字符串缓冲可能推迟文字释放。需要把累计 token、可释放文字与结束状态分开观察。

**批不变性开关已设置。** 所给实现还检查算子可用性，缺依赖时会跳过初始化。

**配置键被过滤。** 材料中的部分键属于内部调度配置的遗留入口，会在内部解析后由类型化配置替代。仅凭它们没有进入某次构造参数，不能断言对应功能被关闭。

**出现未知键警告。** 材料展示了面向 vLLM-Omni 的兼容分支：保留共享配置中的扩展键，同时从 Ascend 校验参数中移除。警告是配置处理线索，本身不能证明模型计算错误。

## 对照源码

### 怎么开

以下是材料直接支持的配置入口与前提：

- 离线复现文档列出 `VLLM_ENABLE_V1_MULTIPROCESSING=0`，用于使调度确定；同时需要记录它对用户代码随机状态的影响。
- Ascend 批不变性使用 `VLLM_BATCH_INVARIANT` 开关，但还依赖 Triton 或 AscendC 批不变算子可用。
- 手动准备预编译 wheel 所需的批不变算子，需要匹配的 vllm-ascend 源码检出，不能把 wheel 的安装目录当作完整源码目录。

当前材料不足以给出适用于 GLM 固定执行基线的完整启用命令。

### 会报什么错

所给批不变性初始化片段在缺依赖时会警告并跳过，警告包含：

```text
Batch-invariant mode requested but Triton or AscendC batch-invariant ops is not available.skipping batch-invariant initialization.
```

配置解析片段先排除内部键，再用 `AscendConfig.__dataclass_fields__` 识别未知键。若存在未知键，且能够找到 `vllm_omni`，则进入兼容分支：警告这些键可能由其他项目使用，并从 Ascend 构造参数中移除。

本次摘录没有完整展示普通 Ascend 路径对未知键的最终异常处理，不能据此补写异常类型或完整报错。

### 开销和什么时候别开

材料没有给出这些复现设置的吞吐、时延或显存测量，不能量化性能代价。

可以确定的副作用是：关闭 V1 多进程会改变构造 `LLM` 的用户代码随机状态。做对照实验时，应把它作为实验条件变化记录下来。材料也没有把这种设置列为在线服务的复现方案。
