推理性能排查，是把读者感受到的等待对应到请求进度、调度安排和实际执行，再用对照实验验证改变是否有效。首个输出来得慢，与已经开始输出后反复停顿，是两个需要分别观察的问题。

本页依据本地材料中的调度器、优化文档与 Ascend 执行代码摘录，整理可以检查的条件和边界。材料涉及固定提交，但不足以完成四个社区分支的逐项核对，也没有目标 NPU 的负载数据或 trace（带时间信息的执行记录）。因此，本页给出的是排查依据与实验方向，尚不能判断某次现场问题的具体瓶颈。

## 首个输出慢与后续输出慢，分别在问什么？

TTFT（time to first token）是从提交请求到收到首个输出 token 的等待时间。ITL（inter-token latency）是后续输出 token 之间的时间间隔。token 是模型处理的离散符号，通常用整数编号表示，不一定对应一个汉字或单词。

这两个指标对应不同的体验：请求 A 提交后很久才开始输出，表现为 TTFT 较大；请求 A 已经开始输出，但相邻输出之间间隔较长，表现为 ITL 较大。只记录整个请求用了多久，无法区分这两种情况。

排查时，先保留请求 A 的提交时间、首个输出时间和后续输出时间，再关联服务端的调度与执行记录。怎样形成可比较的测量，见[推理测量](../concepts/inference-benchmarking.md)；怎样沿请求认识等待位置，见[贯穿样例](../concepts/inference-performance-walkthrough.md)。

## 为什么调整每轮 token 预算，会影响两种等待？

prefill 是处理提示词中尚未计算的位置，并建立后续计算需要的历史状态；decode 是在已有历史上继续生成输出。chunked prefill 把尚未完成的提示词计算分配到多轮调度，让一条长提示词不必在同一轮全部处理。

每轮 token 预算限制本轮可以安排多少 token 位置的计算。所摘录的 V1 文档描述：启用 chunked prefill 时，调度策略优先安排 decode，再用剩余预算安排 prefill；提示词工作放不下时，会分块处理。

因此，预算大小改变的是本轮装入的工作量及其组成。按该文档给出的调优方向：

| 调整方向 | 文档描述的倾向 | 需要分别验证什么 |
| --- | --- | --- |
| 减小每轮 token 预算 | 减少同轮 prefill 对 decode 的拖慢，偏向改善 ITL | 后续输出间隔是否缩短，提示词处理是否需要更多轮 |
| 增大每轮 token 预算 | 一轮处理更多提示词位置，偏向改善 TTFT | 首个输出是否更早，后续输出间隔是否受到影响 |

这些方向以启用 chunked prefill 为前提。材料没有提供当前负载下的测量结果，不能由方向直接得出最优预算或收益比例。

## 用一个小例子，怎样看懂预算与请求进度？

以下是示意条件：请求 A 已进入普通的逐位置 decode，本轮待计算 1 个位置；请求 B 还有 6 个提示词位置没有计算。假设缓存等其他条件允许调度，并按摘录文档描述的 decode 优先策略安排工作。[A]

每轮预算为 4 时，请求 A 先占用 1 个位置的预算，剩余预算为 3，因此请求 B 本轮处理 3 个提示词位置，还有 3 个留到后续轮次。把预算改为 7 时，在相同假设下，请求 A 仍占用 1 个位置，剩余 6 个位置可以容纳请求 B 的全部剩余提示词工作。[D]

这个例子能算出“本轮安排哪些位置”，却算不出这一轮持续多少毫秒。材料没有这些位置的执行耗时，也没有设备与负载数据。预算较大使请求 B 本轮推进得更多，并不单独证明请求 A 的下一次输出会更早。

调度器摘录还提供了另一种理解进度的方式：它维护请求已经计算的 token 数，以及提示词、输出 token 和投机 token 合成的目标数量，每一步尝试分配工作，使前者追上后者。投机 token 是先提出、等待目标模型验证的候选，机制见[speculative decoding](../concepts/speculative-decoding.md)。

这里的“提示词计算”和“继续生成”仍有教学意义，但所摘录的调度器并没有以两个独立阶段来组织内部进度。分析某次调度，需要看请求的实际计数和本轮安排，不能只给请求贴上阶段名称。

## 为什么一轮只算一个 token，也未必走 decode 图？

graph mode 是捕获符合条件的设备操作序列并回放，以减少逐次提交开销的机制。能否走某条图路径，要看该路径的判定条件。

Ascend 固定执行提交的摘录明确给出一个反例：一个 token 的提示词块仍可能属于 prefill，尤其是在 PD 交接处。PD 分离是把 prefill 与 decode 分配到不同执行实例，交接时需要衔接请求进度与历史状态。

在材料展示的投机配置分支中，执行侧检查每个请求已计算的位置数是否达到提示词长度，才据此判定全部请求已完成提示词计算。因此，即使当前批次的宽度看起来像 decode，也还需要核对请求进度。

同一摘录中，未启用投机配置时的检查条件较弱，只检查已计算 token 数是否大于零。这两个条件应保留各自的分支范围；它们也不足以单独证明最终回放了哪张图。现场还需要取得后续分派与实际执行路径的记录。

## 在 GLM 双机案例中，怎样组织一次对照？

GLM 双机案例的性能实验，可以围绕一个明确的问题展开，例如：“减少每轮提示词工作，是否缩短了当前负载的 ITL？”本页材料没有给出该部署的实测数据，也不足以重算其图模式、MTP 或通信账单。

一次可解释的对照至少保留以下内容：

1. **实验目标与输入。** 明确观察 TTFT、ITL 还是吞吐，并记录提示词长度、输出长度、并发与到达方式。
2. **最终生效配置。** 区分启动时填写的值与最终采用的值，记录 chunked prefill、投机配置和每轮 token 预算。
3. **请求进度与执行记录。** 将本轮安排的位置数、提示词完成情况和实际执行路径关联起来。
4. **修改前后的测量。** 先比较单项变化，并保留重复运行结果和波动情况。

这是一套建议的实验组织方式，尚未由本材料中的目标 NPU 实测验证。[I]

如果配置变化后 ITL 改善，匹配的对照实验可以支持“该配置在这类负载下改善了输出间隔”。若进一步声称收益来自某条图路径或某个算子，还需要对应的路径与时间记录；仅凭配置名无法完成归因。[I]

## 哪些判断容易越过现有证据？

**把预算建议当成 GLM 双机最优值。** 摘录文档给出的吞吐建议特别提到大 GPU 上的较小模型。硬件、模型与负载条件不同，需要重新测量。

**把本轮 token 数当成执行阶段。** 单 token 的 prefill 块已经构成反例。投机配置还会改变执行侧的进度判定条件。

**把显式 KV 大小当成跳过所有启动准备。** KV cache 保存后续计算需要的历史表示。材料中的显式大小路径仍执行 `profile_run()`，只是跳过相应的内存预算计算。

**把配置生效、性能改善与具体机制归因合成一个结论。** 三者需要不同的记录：最终配置证明采用了什么，测量说明体验怎样变化，执行记录才帮助解释变化发生在哪里。

## 对照源码

### 怎么开

本次材料能够核对的配置入口包括：

- `max_num_batched_tokens`：控制每轮 token 预算。优化文档的建议以启用 chunked prefill 为前提。
- `--profiler-config`：启用 profiler，即性能采集工具。摘录报错示例使用 torch profiler，并指定 trace 输出目录。
- 显式 KV cache 大小：摘录注释使用 `--kv-cache-memory` 这一名称；完整启动入口及其在各分支中的拼写仍需核对。

材料没有提供足以验证的 GLM 双机完整启动命令，因此本页不组装可运行部署命令。

### 会报什么错

在材料标记的 Ascend 提交中，未配置 profiler 就调用采集接口，会抛出：

```text
Profiling is not enabled. Please set --profiler-config to enable profiling.
```

报错随后给出的示例为：

```text
--profiler-config.profiler=torch
--profiler-config.torch_profiler_dir=YOUR_DIR_PATH_TO_DUMP_TRACE
```

这说明该接口需要先配置采集工具，不能由接口调用失败直接判断设备执行异常。

优化文档还写明：禁用 chunked prefill 时，每轮 token 预算必须严格大于最大模型长度。该条是摘录文档的约束；材料未提供对应校验代码与完整错误字符串。

### 开销和什么时候别开

较小预算可能让剩余提示词分散到更多轮，较大预算则会让一轮容纳更多提示词工作。取舍需要同时观察 TTFT 与 ITL。

文档举出 2048 作为较小预算的例子，并建议为吞吐考虑大于 8192 的预算，尤其面向大 GPU 上的较小模型。这些值是材料中的调优建议，不是 GLM 双机 NPU 的最优值或实测保证。

显式设置 KV cache 大小时，摘录路径仍运行 `profile_run()` 以编译模型，但跳过内存 profiling 计算；相邻说明指出该路径不遵循按显存利用率计算预算的方式。若启动发生 OOM，即内存不足，需要比较启动时的初始空闲内存并调整预算。材料不足以说明后续全部缓存限制，也不足以把设置的字节数直接换算成请求容量。

采集工具自身的时间与资源开销没有出现在本次摘录中，尚不能据此给出采集窗口或开销比例。
