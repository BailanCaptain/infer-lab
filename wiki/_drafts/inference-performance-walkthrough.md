并发后出现输出停顿，需要沿着“请求何时到达、何时获得计算份额、设备何时完成、客户端何时收到内容”逐段解释。本页用一个长提示词与一个正在生成的请求，演示怎样提出可验证的原因，再设计配置对照实验。

这里的分析方法依据材料中的调度、批队列、执行选择与流式计时片段组织，属于分析建议；材料没有本场景的实机时间线或基准结果。

## 输出之间的空白，可能发生在哪里？

token 是分词器输出的离散符号，通常用整数编号表示。prefill 处理提示词中尚未计算的位置，建立后续生成需要的历史状态；decode 在已有历史上继续生成，普通自回归路径通常每轮处理一个新位置。

设请求 D 已经开始生成，请求 N 此时带着较长提示词到达。两者进入同一执行组后，可能共同出现在一次模型执行中。这样的一次执行称为一个批次；它可以同时包含 D 的少量新位置和 N 的一段提示词。

读者在客户端看到的空白，尚不能直接归因于某个算子。至少需要区分：

| 观察位置 | 要回答的问题 |
| --- | --- |
| 客户端 | 两次内容消息之间隔了多久？每条消息包含几个 token？ |
| 调度侧 | 请求 D 是否获得本轮计算份额？请求 N 获得多少？ |
| 执行侧 | 批次何时提交、何时开始、何时完成？各个设备在计算还是等待？ |
| 输出侧 | 执行结果何时被处理，何时形成客户端收到的内容？ |

只有把这些事件关联到同一请求和批次，才能把“客户端停顿”缩小为某一段等待。把设备时间线与请求记录对齐，是本页提出的分析方法，尚不构成已完成的现场诊断。

## 为什么先安排生成中的请求，输出仍可能变慢？

scheduler 是决定本轮给哪些请求计算多少位置的调度器。材料中的 V1 调度文档说明：启用 chunked prefill 后，先安排待处理的 decode 请求，再把剩余 token 预算分给 prefill；放不下的提示词计算会分到后续轮次。

chunked prefill 因而改变的是长提示词每轮参与计算的份额。它能让正在生成的请求较早获得调度机会，但调度顺序并不等于完成时间：如果 D 与 N 被放进同一个批次，仍需检查这个批次的实际执行时间，以及 D 的输出何时能够送出。

材料中的调度器注释使用统一的进度描述：每条请求有已经计算的位置数，以及包含提示词、输出和投机草稿在内的目标位置数；每轮尝试让前者追上后者。这个内部表示可以统一安排工作，但 prefill 与 decode 的负载特征仍需分别观察。

材料中的文档也直接说明了预算取舍：较小的每步 token 预算可以减少 prefill 对 decode 的拖延；较大的预算可以让更多提示词位置在同一批次中完成，有利于首个输出更早出现。实际效果还取决于模型、设备、请求组成和执行路径。

## 怎样手算一次预算调整改变了什么？

下面只演算调度份额，不预测毫秒数。

设请求 D 本轮需要计算一个新位置，请求 N 还有十二个提示词位置未处理。假设两者均可调度，缓存和其他资源充足，没有其他请求，并且执行路径允许按所示份额分块。

方案 A 每轮最多计算九个位置。先给 D 一个位置，剩下八个位置给 N；本轮计划是 D 一个、N 八个。执行并更新进度后，N 还剩四个提示词位置。

方案 B 每轮最多计算五个位置。先给 D 一个位置，剩下四个位置给 N；本轮计划是 D 一个、N 四个。执行并更新进度后，N 还剩八个提示词位置。

两个方案中，D 都获得了本轮计算份额。变化在于 N 同轮参与计算的位置数：

| 方案 | 本轮总预算 | D 获得的位置数 | N 获得的位置数 | N 本轮后剩余的位置数 |
| --- | ---: | ---: | ---: | ---: |
| A | 9 | 1 | 8 | 4 |
| B | 5 | 1 | 4 | 8 |

这个算例能说明预算如何分配，却不能推出方案 B 一定缩短 D 的输出间隔。实际耗时需要执行记录；N 的提示词完成时间也需要纳入验收，不能只观察 D。

### 同样是一个位置，怎样判断它属于哪种工作？

一个批次只给某条请求安排一个位置，并不足以证明这条请求已经进入 decode。

材料中的执行侧注释给出了反例：prefill 的最后一块可以只有一个 token，在 P/D 交接处尤其需要注意。P/D 交接指提示词处理与后续生成由不同执行角色承担时的状态交接。即使请求已有部分位置算完，也可能仍有提示词没有处理完。

在所示投机解码分支中，执行侧检查各请求的已计算位置是否达到提示词长度，再决定能否使用 decode graph。graph mode 是捕获并回放满足条件的设备操作序列，以减少重复提交开销的执行方式。这段检查的适用范围是材料展示的分支，不能扩展为所有执行路径的共同判定规则。

## 调整预算时，为什么还要记录执行路径？

预算是主动修改的配置，批次组成则会随之改变。批次变化还可能触发不同的图选择或通信方案，因此“只改一个参数”并不保证底层始终走同一条路径。

材料中的 A2 通信选择函数就提供了一个具体例子。expert 是 MoE 中执行前馈变换的模块；expert parallel（EP）把专家分配到多个设备，并通过通信把输入送到相应专家、再组合输出。所示函数同时检查每设备专家数、EP 组规模与 token 数：满足全部条件时选择 MC2，否则选择 ALLGATHER。MC2 是协调矩阵计算与通信的一类实现。

因此，预算实验应分两层解释：

1. **配置效果：** 在相同负载与验收条件下，修改预算是否改善了目标指标？
2. **机制归因：** 批次规模、图选择或通信方案是否发生变化，哪段等待随之缩短？

第一层可以通过重复对照实验回答。第二层需要额外的执行记录。即使观察到改善，也不能仅凭预算变小就把收益全部归因于“少算了提示词”。

批队列同样影响时间线解释。材料中的 `step_with_batch_queue` 路径优先尝试填充批队列；没有新批次可以安排时，再等待队列中的结果并更新调度器。分析时需要分别记录计划形成、执行提交和结果处理，避免把这些事件视为同一时刻。

## 在 GLM 双机主线上，应该怎样组织一次验证？

本页挂靠在[多请求并发](../concepts/concurrent-requests.md)与[请求代码路径](../concepts/request-call-chain.md)之间：前者帮助理解多个请求如何组成批次，后者帮助定位这些事件由哪些组件处理。实际验证应围绕同一条请求，把两种视角接起来。

本次材料提供了固定控制流与执行侧快照的若干片段，但没有 GLM-5.3-Flash 双机的实测记录、请求分布和完整配置。因此，本节给出记录与实验方法，不报告该部署的实际耗时或容量。

建议为同一次实验准备三份能够关联的记录：

1. **请求记录。** 为 D、N 保留请求标识、到达时间、输入长度、生成设置、接收内容的时间及所在执行组。
2. **调度记录。** 为每个批次记录批次标识、成员请求、各请求本轮获分配的位置数，以及执行前后的计算进度。
3. **执行记录。** 为参与执行的 rank 记录提交与完成事件、设备活动、通信和执行模式。rank 是参与分布式执行的成员编号，其范围由具体通信组决定。

实验先保持请求内容、到达节奏、输出设置及服务配置一致，只改变每步预算。重复运行两个方案，并同时比较 D 的内容消息间隔与 N 的首个内容到达时间。单次改善只是线索，尚不足以说明更大负载下的容量或长尾表现。

还要核对请求路由。材料中的一个 DP 路由分支以“等待请求数乘四，再加运行请求数”的分数选择执行组；DP 是把不同请求分配给不同执行组的并行方式。这个分数使用请求计数，所示片段没有使用提示词长度或实测执行耗时。若两次实验进入的执行组或既有负载不同，测得的差异就不能全部归于预算调整。

## 哪些观察容易被解释得过头？

**“decode 先被安排，所以输出不会停。”** 调度优先级回答谁先获得份额；完成时间还取决于本轮执行、结果处理和发送过程。

**“本轮只有一个 token，所以一定是 decode。”** 提示词的最后一块也可能只有一个 token，需要结合提示词长度与计算进度判断。

**“客户端 ITL 降低，所以每个 token 都生成得更快。”** ITL 通常指输出 token 之间的时间间隔，但材料中的客户端实现按接收到的块计时。没有逐 token 事件时，应报告内容消息间隔，并说明一块是否包含多个 token。

**“换客户端后端到端延迟降低，所以服务加速了。”** 如果客户端改变了结束时间的定义，数值可以在服务行为不变时变化。尾随 usage 块是否计入结束时间，就会影响比较。

**“选择了 MC2，所以这轮一定更快。”** 选择条件说明执行走哪条分支；性能优劣仍需要同条件测量。

**“D 改善了，所以方案可以采用。”** 预算缩小也可能延后 N 完成提示词处理的时间。验收需要同时包含生成间隔、首个输出时间，以及目标负载下的整体表现。

### 怎么开

本页的预算实验围绕 `max_num_batched_tokens` 展开。材料中的 V1 文档称，在条件允许时默认启用 chunked prefill；启用后的策略是先安排 decode，再用剩余预算安排 prefill。原文位置为材料第 425 行。该说明来自材料所摘录的固定快照，不代表所有模型与启动方式均采用同样配置。

需要设备时间线时，材料展示的 Worker profiling 路径要求显式配置 profiler。报错中给出的示例是：

```text
--profiler-config.profiler=torch
--profiler-config.torch_profiler_dir=YOUR_DIR_PATH_TO_DUMP_TRACE
```

这段示例说明该片段要求的配置字段；材料没有提供完整启动命令或实机采集结果。

### 会报什么错

材料第 662—668 行显示：未配置 profiler，或配置中的 profiler 字段为空时，调用采集入口会报：

```text
Profiling is not enabled. Please set --profiler-config to enable profiling.
```

第 694—704 行展示的创建函数还检查以下条件：

- profiler 类型必须是 `torch`，否则报 `Unrecognized profiler`。
- 输出目录不能为空，否则报 `torch_profiler_dir cannot be empty.`。
- 读取到 `msmonitor_use_daemon` 为真时，拒绝与 torch profiler 同时启用。

预算配置也有条件约束：材料第 441—442 行的文档要求，在关闭 chunked prefill 时，每步 token 预算严格大于最大模型长度。这里保留的是摘录文档的要求；材料没有提供对应校验实现与具体错误文本。

### 开销和什么时候别开

预算越小，长提示词每轮可获得的份额可能越少。材料第 436—438 行将其描述为生成间隔与首个输出时间之间的权衡，并给出了面向大 GPU 上较小模型的吞吐建议。该建议没有附带本场景的基准数据，不能作为 GLM 双机的最优值。

profiling 本身也会影响测量。材料第 723—727 行的实现把 NPU profiler 的 `with_stack` 固定为假，并通过配置控制内存采集和 `with_modules`；注释指出 NPU 的 `with_stack` 有显著时间开销，但没有量化。因此，定位用的采集结果与最终性能验收结果需要分别保留，避免把采集开销混入常态表现。这是依据材料组织的实验建议 [I]。
