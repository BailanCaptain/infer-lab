KV cache 是为后续计算保留的历史状态。理解它时，需要分清三个问题：保存的内容是什么、这些内容怎样定位，以及另一条请求能否复用它们。本页依据提供的本地摘录整理；摘录能支持部分实现差异，尚不足以完整复核现有页面的容量推导与全部版本行为。

## 为什么保存历史与复用前缀是两个问题？

attention 利用查询与键计算匹配权重，再按权重汇合值向量；查询、键和值通常分别记为 Q、K、V。后续位置继续计算时，需要使用模型规定的历史表示，KV cache 为这些历史提供存储。具体表示随模型变化，普通 K/V、MLA 的压缩表示与递推状态需要分别理解，参见 [attention](../concepts/attention-qkv.md)、[MLA](../concepts/mla.md) 与 [KDA](../concepts/linear-attention.md)。

prefix caching 则处理跨请求复用：请求 B 能否接着使用已经为相同前缀建立的状态。它需要查找可复用的前缀，并判断命中了多少位置。

提供的缓存管理器片段显示，关闭 prefix caching，或请求被标记为跳过前缀缓存读取时，查找直接返回空缓存块和零命中。这个返回值描述的是前缀命中查询，不能据此认定整个生成过程不再保存或读取请求自己的历史。[I]

block table 是将请求逻辑块位置映射到缓存池物理块编号的表。缓存内容、地址映射与前缀复用分别回答不同的问题，相关机制见 [Block Table](../concepts/block-table.md) 与 [Prefix caching](../concepts/prefix-caching.md)。

## 提示词全部命中，为什么仍可能需要计算？

logits 是模型为候选输出 token 给出的分数，后续采样需要这些分数。提供的控制流片段明确保留最后一个输入 token 的重算，以取得 logits。

用一个只用于解释边界的例子：请求共有 5 个输入 token，即使这些位置都有可复用历史，片段中的最大命中长度仍设置为 4，最后一个位置留给本轮计算。[A]

这还不等于实际只重算一个位置。材料中的注释说明，缓存分配要求已计算 token 数按块大小对齐，因此重算范围可能扩大为整块。材料没有给出该例实际使用的块大小，无法进一步算出最终命中与重算位置数。

这说明，缓存里存在历史与本轮完全不执行模型计算之间，还有输出分数和分配边界两层约束。

## 缓存形状里的各维分别表示什么？

提供的一处普通注意力后端片段返回两种形状：

- LBHNC 或 HND 布局：`(2, num_blocks, num_kv_heads, block_size, head_size)`。
- 其他布局：`(2, num_blocks, block_size, num_kv_heads, head_size)`。

这里首维的 2 区分 K 与 V；其余各维分别表示物理块数量、KV 头数量、每块的位置数量和每个头的向量长度。两个分支交换了块内位置与 KV 头的维度顺序。

形状相同的元素总数不代表相同的访问布局。设备实现需要按约定解释各维，才能把数据写到正确位置。该片段只证明所示后端的形状分支，不能拿来描述所有模型的缓存，尤其不能直接替代 MLA 或递推状态的布局说明。

## GLM-5.3-Flash 的历史为什么需要分开讨论？

本页的 GLM 案例沿用知识库固定的专用实现基线：控制流为 vLLM 固定快照，执行侧为 Ascend 专用镜像快照。部署背景见 [GLM 双机部署](../concepts/glm-5-3-flash-two-node.md)。本材料未包含实机运行记录。

在专用实现的 `IndexerKPoolMLACacheLayer` 片段中，完整 MLA KV cache 被固定为 BF16，即每个数使用 16 位浮点格式。注释说明，A5 shared-KV 算子直接消费这一缓存，不做量化。这个结论限定于该实现，不能由权重采用 W8A8 就推断历史状态也采用 INT8。

v0.30.0rc2 分支的另一组摘录进一步区分了缓存对象、编号与物理页：

| 对象 | 调度块编号关系 | 物理页类别 |
| --- | --- | --- |
| 主 MLA cache | 与压缩 indexer cache 共享编号 | 主 MLA/KDA 大页 |
| 压缩 indexer cache | 与主 MLA cache 共享编号 | indexer/tail 小页 |
| compressor tail | 独立分配编号 | indexer/tail 小页 |
| 各 KDA/Mamba 缓存组 | 各组独立分配编号 | 主 MLA/KDA 大页 |

indexer 为稀疏访问提供索引相关历史，compressor tail 保存压缩过程中尚需保留的尾部状态；KDA/Mamba 组属于递推状态缓存。材料未给出它们的完整更新过程和张量形状，这里只说明摘录明确列出的组织关系。

共享调度块编号与共享同一份物理存储是两件事。表中的主 MLA 与压缩 indexer 就使用相同编号关系，却属于不同页大小类别。

该分支还出现了 SFA C8 打包 KV 路径：注释明确说明，它不依赖具体 indexer，使用 kpool-indexer 的模型也能使用。另一条 LI C8 路径则要求 LightningIndexer 的缓存布局。材料没有完整列出配置入口与运行条件，不能据此给出可直接执行的启用方案。

## 哪些区别会影响容量与配置判断？

缓存精度决定每个元素怎样存储，缓存形状决定有多少元素，页布局和分组方式又影响实际分配。只知道其中一项，无法完成显存预算。

本材料没有提供完整容量规格，也没有性能实测，因此不能据此比较专用镜像与 v0.30.0rc2 的每 token 字节数、缓存块数量或吞吐收益。已有部署算例应继续保留自己的模型、实现与精度条件，容量说明见 [GLM 双机部署](../concepts/glm-5-3-flash-two-node.md)。

同样，框架存在 KDA 算子、indexer 或通用缓存对齐代码，并不能单独证明某个完整模型已经接入。判断支持范围需要模型入口、状态规格和实际执行路径的证据。[I]
