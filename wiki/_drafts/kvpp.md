KVPP（KV Pipeline Parallelism）把一组设备上重复保存的历史缓存改为按层分工：每层指定一张卡长期保存，用到这一层时，再把缓存广播给同组其他卡。它改变的是历史状态的存放位置；参与计算的卡仍须及时取得本层需要的历史。

本页依据所给材料中的 vllm-ascend 开发主线固定快照展开。材料中的实现面向非混合 MLA/SFA 模型，要求 eager 执行，即逐步提交设备操作而不回放捕获图。材料不足以确认它属于哪个发布版本，也不能据此填写已核对版本。以下机制说明来自本地源码与文档摘录的整理，部署组合和性能均未在本页实机验证。

## 为什么相同的历史还要在多张卡上各存一份？

生成后续 token 时，attention 需要读取已经处理过的位置留下的历史表示。[KV cache](../concepts/kv-cache.md) 就是保存这些表示的缓存；[MLA](../concepts/mla.md) 使用压缩后的潜在表示组织多头注意力，其历史缓存不能直接套用普通 K、V 分开存储的布局。

缓存是否重复，取决于模型和并行路径。材料描述的前提是：在相应执行路径中，同组成员已经拥有内容相同的 MLA 缓存；其中，关闭 DCP 后，PCP 的 KV 汇集也会形成这样的副本域。TP 是把一次张量计算分给多个设备协作完成，PCP 是沿上下文位置分配 prefill 工作的执行路径。这里需要关注的是它们最终形成了怎样的缓存布局，而不是仅凭并行名称判断缓存一定重复。

有了相同副本，每张卡都能直接读取历史，但同一份历史也占用了多份显存。KVPP 保留组内访问历史的能力，同时减少长期保存的重复副本：某层由指定成员持有，其余成员在执行前取得临时副本。

这里的“组”是有明确成员范围的通信组。rank 是成员编号，必须区分组内编号与全局编号。材料中的 KVPP 组大小为 TP 大小乘以 PCP 大小，组不跨 DP 执行组，也不跨 PP 阶段。DP 负责分配不同请求或批次；PP 则按模型计算顺序划分阶段。KVPP 在这些边界内部重新安排缓存，不把整个分布式系统的缓存汇成一个共享池。

## 按层分工以后，省下了什么，又增加了什么？

每个 KVPP rank 都有两类缓存空间。

一类是**持久缓存**：本 rank 负责的目标模型层长期保存在这里。目标模型是正式执行推理或验证候选的模型，与用于生成候选的 MTP 模块区分。MTP 是多 token 预测结构，推理时可以用来生成投机候选；材料中的 MTP 缓存不参与 KVPP 的层划分，各 rank 仍独立分配。

另一类是**暂存区**：本 rank 执行其他成员负责的层时，先把这一层的历史接收进来，再供 attention 使用。材料中的预算保留两份暂存缓冲区，每份按最大目标层的缓存需求计算。暂存区会占显存，因此省去重复的持久缓存后，不能把容量收益直接算成组大小倍数。

代价主要发生在访问历史之前。Broadcast 是指定来源成员把同一份数据发给组内其他成员的集合通信操作。本层常驻卡作为来源广播缓存，其他成员等待所需数据可用，然后才能读取或更新相应状态。即使代码使用异步通信接口，计算也不能越过数据依赖。

材料中的广播以分配好的层缓冲区为对象。估算通信量时，应按这个缓冲区的分配容量计算，不能只数当前请求实际访问了多少历史位置。缓存池扩容后，单层需要传送的缓冲区也可能随之增大。

因此，KVPP 适合讨论的是“用更多数据搬运换取更多缓存容量”。它是否改善请求时延或整体吞吐，还取决于工作负载是否受缓存容量限制，以及广播能否被其他工作有效遮盖。

## 用两张卡、四层缓存怎样手算一次？

下面只演示缓存空间，假设有两张卡、四个等大的目标层；每层为一个逻辑块位置保存的全部缓存占 10 字节，没有 MTP 或其他独立缓存。这些数字是教学设定。[A]

未使用 KVPP 时，两张卡都保存四层历史。每张卡为一个逻辑块位置付出 40 字节：第一层到第四层各占 10 字节。

使用 KVPP 后，假设卡 0 负责第一、第三层，卡 1 负责第二、第四层。每张卡的持久缓存只剩两层，共 20 字节；但还要加上两份暂存区，每份 10 字节，共 20 字节。这样，每张卡仍需 40 字节，和原来一样。本例中，省下的持久副本恰好被暂存区抵消，缓存容量没有增加。[D]

执行第一层时，卡 0 提供该层历史，卡 1 接收到暂存区；执行第二层时，来源换成卡 1，卡 0 接收。改变来源的是层的所有权，参与计算的成员并没有因此变成只计算自己持有的层。

再把同一示意扩展到八个等大目标层，仍由两张卡各负责四层。不开 KVPP 时，每张卡每个逻辑块位置需要 80 字节；开启后，持久缓存为 40 字节，两份暂存区合计 20 字节，总计 60 字节。若每张卡可用预算都是 240 字节，则原来能分配 3 个逻辑块位置，开启后能分配 4 个。这是容量从 3 到 4 的变化，而不是两倍。[D]

这也解释了为什么层数、分配是否均衡、最大层大小都重要。各层不等大时，应逐层累加本 rank 的持久缓存字节，暂存区按最大目标层计算；MTP 等独立缓存再加进去。材料中的实现正是按实际布局计算成本，再用可用字节数做整除，而不是只按层数估算。

## PCP、PP 和 MTP 会怎样改变这套分工？

PCP 加入后，分工范围可以从 TP 成员扩展到 TP 与 PCP 的组合域。材料中的配置说明举例：TP4 加 PCP2 形成八成员 KVPP 组，TP1 加 PCP2 也能启用 KVPP。与 PCP 组合要求 Model Runner V2，即执行模型的新版 runner 路径；用户指南说明，不组合 PCP 时可使用 V1 或 V2。

PP 的影响是限定输入范围。层所有权规划接收的层名必须已经属于当前 PP 阶段，然后只在这个阶段内部继续分配。它不会跨阶段挪动所有权，也不能把别的 PP 阶段的层算进当前 rank 的持久缓存预算。

MTP 是另一种边界。材料只允许固定数量的 MTP 投机候选，不允许按批大小改变候选数量，也不允许其他投机方法。MTP 层不进入目标层的所有权映射，各 KVPP rank 保留各自的完整 MTP 缓存。估算收益时，需要保留这部分成本；阅读实现时，也不能假定 MTP 一定位于最后一个 PP 阶段。

物理缓存规划还有布局要求：摘录中的判断要求所有缓存规格都是 FullAttentionSpec，并且块大小相同。FullAttentionSpec 是框架描述缓存分配需求的一种规格类型；这里出现这个类型名，并不能单独推出模型一定访问全部历史位置。关于规格如何决定分配单位，可接着阅读 [KV cache 规格](../concepts/kv-cache-spec.md)。

## 在 GLM-5.3-Flash 双机主线中能直接开启吗？

KVPP 对应的是模型逐层执行时读取与更新历史状态的环节。它可以帮助理解：缓存的逻辑内容保持不变时，物理存放位置仍然可以改变，而这种改变需要新的通信与同步。

但本材料不能证明固定的 [GLM-5.3-Flash 双机部署](../concepts/glm-5-3-flash-two-node.md) 可以直接开启 KVPP。材料里的实现要求非混合 MLA/SFA 模型；本次摘录没有提供主线模型各层状态、混合结构标记与该实现逐项匹配的证据，也没有给出主线固定执行提交包含此特性的核对结果。

材料中确实报告了两个容量对照案例，但模型是 GLM-5.2，硬件为 950DT Products，不能替换成 GLM-5.3-Flash、A2 或主线的 W8A8 配置：

| 材料报告的配置 | 报告的 KV cache 容量倍数 |
| --- | --- |
| 单机八设备，GLM-5.2-W4A8C8，TP8 加 EP | 6.25 倍 |
| 双机各八设备，GLM-5.2-W8A8C8-mxfp8，TP8 加 PP2 加 EP，层划分为 38/40 | 5.35 倍 |

这些是材料转述的开关对照结果，并非本页实测。它们比较的是相同模型、硬件和内存预算下的 KV cache 容量，不是吞吐倍数，也不是整张卡显存的节省比例。

## 哪些容易混在一起的结论需要分开？

**缓存按层分配，与计算按层分段是两件事。** [PP](../concepts/pipeline-parallel.md) 把模型计算划成先后执行的阶段；KVPP 在当前阶段内部安排缓存所有权，同组成员仍会执行需要读取这些历史的计算。

**组内只留一份持久目标缓存，不代表每张卡只占自己的那几层空间。** 两份暂存区、未参与划分的 MTP 缓存，以及其他显存用途都必须保留。缓存容量增加的比例，也不能直接当作整卡显存下降的比例。

**缓存容量增加，与运行更快是两项指标。** 材料报告的非 pooling 工作负载中，容量增加同时引入了广播开销，吞吐没有改善。这个结果说明容量收益不能直接推成吞吐收益；它也没有证明所有工作负载都会得到相同结果。

**PD 分离与外部缓存池使用不同的连接器规则。** PD 分离把 prefill 和持续生成放在不同执行组；材料中的实验路径使用 MooncakeConnectorV2，KVPP 仅在 prefill 一侧开启。外部池使用 AscendStoreConnector，不能把前一个连接器分支中的限制无条件套到后者。

## 对照源码

### 怎么开

材料中的配置入口是 `--additional-config` 内的 `enable_kvpp`，默认值为布尔值 false。已有 additional config 时，需要合并到同一个 JSON，而不是丢弃原有设置。

```json
{"enable_kvpp": true}
```

这只是配置片段。完整启动还必须满足 eager、模型结构、runner 和连接器等条件，不能把它当作已验证的部署命令。

启用后，`KVPPConfig` 根据 TP 大小与 PCP 大小的乘积计算组大小，不跨 DP 或 PP。材料中的平台入口只在组大小大于 1 时调用 KVPP 校验；组大小等于 1 时，不能用“没有报出后面的错误”判断组合已受支持。

### 会报什么错

摘录中的检查与错误文本应按分支理解：

| 检查位置或条件 | 错误或限制 |
| --- | --- |
| DCP 大小不为 1 | `KVPP and DCP cannot be enabled at the same time.` |
| 非 AscendStoreConnector 的 KV transfer 分支，连接器又不是 MooncakeConnectorV2 | `KVPP PD disaggregation requires MooncakeConnectorV2.` |
| 上述非 AscendStoreConnector 分支中，角色为 kv_consumer | `KVPP must be disabled on the decode-only node.` |
| 未强制 eager | `KVPP currently supports eager execution only; set --enforce-eager.` |
| 不使用 MLA，或模型标记为 hybrid | `KVPP currently supports only non-hybrid MLA models.` |
| 投机方法不是 mtp | 仅支持 method='mtp' |
| 配置了按批大小变化的投机 token 数 | 仅支持固定数量的 MTP 投机 token |
| 缓存规格类型不符，或块大小不一致 | `KVPP requires one full-attention cache group with a common block size.` |

最后一条错误文本提到“一个缓存组”，但所给判断片段实际检查的是规格类型和块大小；本片段没有显式统计缓存组数量。错误文字与检查表达式应分别记录，不能据此补出未见的校验。

AscendStoreConnector 被连接器分支豁免，因此不能仅凭其中的 kv_consumer 检查，声称该连接器的 consumer 角色也一定在这里被拒绝。

### 开销和什么时候别开

物理预算包含本 rank 所有持久层，以及两份最大目标层暂存区。没有 owner 的层也计入持久预算，MTP 则不参与目标层分配。目标层较少、最大层较大或层分配不均衡时，暂存成本可能明显抵消收益。

广播路径从层 owner 向 KVPP device group 发送层缓冲区。代码使用异步 Broadcast，随后等待通信工作，并记录、同步设备事件。这个完成条件也保护 owner 对源缓冲区的读取，避免 attention 提前覆盖还在传输的数据。调度摘录在存在历史时启动预取，MLA/SFA 的接入点则在读取或更新缓存前等待。

如果现有缓存容量足够，额外广播可能没有对应的容量收益可兑现。材料中的非 pooling 工作负载就没有获得吞吐改善；是否值得开启，应比较相同模型、设备、预算与请求分布下的容量、时延和吞吐。

外部 memcache pooling 路径还有独立条件：使用 AscendStoreConnector，关闭逐层存取，开启异步加载，并丢弃部分块。材料说明 producer 与 both 角色都能保存和加载前缀，不支持逐层 pooling、KV events 和 consumer 回写。这些条件需要与 KVPP 本身的限制一起检查。
