LoRA（Low-Rank Adaptation，低秩适配）通过额外的适配器调整模型计算。本页关注三个相互关联的问题：适配器权重怎样处理，一批请求怎样受适配器名额限制，以及这些计算在昇腾上有哪些实现与支持边界。

本稿只依据提供的本地摘录整理。摘录包含配置、调度条件、权重处理和昇腾执行片段；完整的低秩矩阵计算、训练过程及设备性能仍需补充原始依据。以下将已展示的条件与尚未核实的部分分开说明。

## 一个适配器怎样影响计算？

模型使用权重把输入向量映射成输出向量；这一基础过程见[矩阵乘与权重](../concepts/matmul-and-weights.md)。LoRA 在此基础上引入适配器权重。本次摘录直接展示了其中一项处理：适配器带有秩、缩放系数，以及名为 lora_b 的权重。

秩在这里是适配器的配置量。摘录中的权重对象用实际秩和 lora_alpha 计算默认缩放：没有显式提供 scaling 时，缩放等于 lora_alpha 除以 rank；显式提供时，使用给定值。因此，默认公式有明确前提，不能覆盖所有适配器。

权重优化还会把缩放乘进 lora_b，再把独立保存的 scaling 设为 1。这个状态变化意味着：缩放效果已经进入权重，后续不能再把同一个系数重复乘一次。

摘录没有完整展示两个低秩矩阵的形状、与基础权重的组合公式或训练更新过程。这些是完整原理教学需要补齐的内容，不能仅凭缩放处理代码推导出整条计算路径。

## 缩放并入权重时，具体改变了什么？

下面只演示摘录已经展示的缩放处理，不将它当成完整的 LoRA 前向计算。

假设适配器实际秩为 2，lora_alpha 为 4，没有显式传入缩放；再从 lora_b 中取出两个示意元素 3 和 −1。优化前，默认缩放为 2。优化操作把这两个元素分别乘以 2，得到 6 和 −2，并将保存的缩放改成 1。

这些数是教学设定。这个例子说明了两个状态的区别：

| 状态 | lora_b 中的示意元素 | 独立保存的缩放 |
| --- | --- | --- |
| 优化前 | 3、−1 | 2 |
| 优化后 | 6、−2 | 1 |

这里改变的是缩放的保存位置。如果显式给定缩放为 0.5，代码就使用 0.5；如果缩放已经等于 1，优化方法直接返回。

## 一批请求为什么要限制适配器种类？

在线推理的一批输入可以来自多个请求，见[多条请求](../concepts/concurrent-requests.md)。这些请求可能共用一个适配器，也可能分别选择不同适配器，因此需要区分“请求数”和“不同适配器的数量”。

材料中的调度条件检查两件事：

1. 当前已经安排的不同适配器数量，是否达到配置上限。
2. 待安排请求的适配器 ID，是否尚未出现在当前集合中。

两项同时满足时，该请求触发这条跳过条件。已经安排过的适配器 ID 可以被其他请求复用，不会因为复用本身占用一种新适配器的名额。

以名额为 1 的示意批次为例：请求 A 使用适配器甲，已经被安排；请求 B 也使用甲，请求 C 使用乙。B 没有引入新 ID，因而不触发这条适配器限制；C 引入了乙，而名额已经用满，会触发它。B 是否最终进入当前批次，还取决于其他调度条件。

材料中的 num_active_loras 同样统计批内**不同的活跃适配器数量**。它不是请求数，也不是 token 数。

## CPU 缓存名额和批内名额有什么区别？

批内名额限制一次执行可以涉及多少种适配器；CPU 缓存名额限制主机内存中可以保存多少份适配器。主机内存是 CPU 一侧的内存，与设备显存分别计算。

材料中的配置要求 CPU 缓存上限不小于批内适配器上限。没有设置 CPU 上限时，校验过程把它设为批内上限。

加载过程还有一个影响资源理解的细节：进入新适配器加载分支时，先加载并验证新对象，再处理已有对象的移除或淘汰。代码注释明确说明，这可能让已加载适配器数量短暂超过 CPU 缓存上限。这个上限因而不是加载全过程中始终不越过的瞬时数量边界。

摘录没有给出每份适配器的实际字节数，不能据此算出峰值主机内存。加载方法另有非线程安全的说明，当前依赖单线程核心引擎循环调用；将它移到其他并发调用环境时，需要重新审视这一条件。

## 昇腾为什么会选择不同的执行路径？

算子定义张量上的计算，kernel 是具体设备实现，详见[算子与 kernel](../concepts/ops-and-kernels.md)。材料中的昇腾文档列出了 bgmv_shrink、bgmv_expand、sgmv_shrink 和 sgmv_expand 等 LoRA 相关 AscendC 算子，但算子存在不代表所有配置都走这些实现。

在材料所示的一份执行快照中，310P 或配置的最大 LoRA 秩达到 128 时，会导入 torch_ops 路径。另一份快照将硬件判断改为是否支持 LORA_CUSTOM_OPS。因此，判断实现路径时，需要同时看硬件能力、配置上限和具体快照。

单适配器槽路径也检查配置，而不是只数当前批次用了几种适配器。材料展示的条件要求同时满足：

- 设备属于 A2 或 A3；
- 存在 LoRA 配置；
- 配置的批内适配器上限为 1；
- 没有开启 fully_sharded_loras。

所以，即使当前批次恰好只使用一个适配器，也不能单凭这一点断定进入该路径。fully_sharded_loras 控制更完整的 LoRA 计算分片；配置注释认为某些长序列、大秩或大 TP 场景可能更快，但这不是设备性能保证。

## MoE、EP 与图模式怎样改变适用条件？

MoE 用路由机制把输入交给部分专家计算；expert parallel（EP）把专家分配到多个设备，并在设备间分发输入、组合输出，见[Expert parallel](../concepts/expert-parallel.md)。LoRA 与这些机制组合时，支持范围会随实现快照变化。

材料中的一份文档支持 dense 和 MoE 模型使用 LoRA，同时明确排除 MoE LoRA 的 EP 与量化组合。另一份文档则列出非量化、W8A8 动态量化分别配合 TP 或 EP 的四种受支持组合，仍排除其他 MoE 量化方法、Fused MC2 和动态 EPLB。W8A8 动态量化是文档明确列出的具体组合，不能扩展成所有量化方式。

通信选择也有分支优先级：未启用 EP，或者 EP 通信组只有一个成员时，先选择 ALLGATHER；只有排除这一分支后，存在 LoRA 配置且启用 EP，才选择 ALLTOALL。集合通信的含义见[通信基础](../concepts/collective-communication.md)。

材料中的注释把这一选择与融合实现联系起来：FusedMC2 路径中的计算、分发与组合封装在融合 C++ 算子中，Ascend MoE LoRA 无法按该路径进行 patch。这个条件覆盖正常前向和性能分析阶段的模拟执行，不能只按实际请求解释。

图模式通过捕获设备操作序列并重复回放来减少提交开销，见[ACL Graph](../concepts/acl-graph.md)。材料中有 LoRA 可使用 ACLGraph 的文档声明，但具体图参数选择还要求 FULL 模式、描述对象存在且其中 has_lora 为真。上游另有按活跃适配器数量分别捕获 CUDA 图的字段说明；它描述的是 CUDA 图，不能直接作为 Ascend 已采用相同行为的证据。

## GLM-5.3-Flash 双机案例能得出什么结论？

在[一条请求](../concepts/one-request.md)的主线中，LoRA 相关问题涉及批次调度与模型执行：调度侧要控制不同适配器数量，执行侧要根据模型、并行方式和硬件选择适配器计算路径。

本次材料没有提供 GLM-5.3-Flash 的 LoRA 支持声明，也没有该模型双机开启 LoRA 后的时延、吞吐或显存数据。文档对某些 MoE 组合的支持，仍需进一步核对能否覆盖这个具体模型及部署配置。

同样，不能从低秩参数数量较少直接推出整次请求的加速比例。材料已展示调度、加载、执行分支和通信选择这些额外条件，但没有提供将它们合成性能结论所需的测量。

## 哪些概念需要分别判断？

**适配器名额和请求名额不同。** 多条请求可以复用一个适配器 ID；满足适配器限制，只说明通过了这一项条件。

**实际秩和配置的最大秩不同。** 默认缩放使用适配器实际秩；材料中的部分执行路径判断使用配置的最大秩。把两者混在一起，会误判缩放或实现分支。

**支持声明和代码可达分支不同。** 文档可能明确限制某种组合，局部代码却已经出现相关分支。仅凭这一分支，不能认定整个组合已受支持。

**函数参数和实现能力不同。** 材料中的 MoE LoRA 函数虽然接收 fully_sharded 参数，却在函数内将其丢弃。参数出现在接口中，不足以证明这条路径实现了全分片。

## 对照源码

### 怎么开

本次摘录不足以组成完整启动命令。已展示、可以据此理解的配置包括：

| 配置项 | 材料中的含义与约束 |
| --- | --- |
| `max_loras` | 单批适配器数量上限，字段默认值为 1，至少为 1 |
| `max_cpu_loras` | CPU 缓存份数；未设置时取 max_loras，显式值不能小于它 |
| `fully_sharded_loras` | 默认关闭，控制是否使用全分片 LoRA 层 |
| `MaxLoRARanks` | 配置类型列出 1、8、16、32、64、128、256、320、512；枚举不证明各后端都支持每个值 |

这些是摘录中的配置事实，不能替代模型、后端和启动入口的兼容性核查。

### 会报什么错

CPU 缓存上限小于批内适配器上限时，配置校验抛出 `ValueError`，错误信息指出 max_cpu_loras 必须大于等于 max_loras。

材料中的 Ascend MoE LoRA v1 函数要求输入行已经预展开，并断言 `top_k_num == 1`。对应错误信息为：

> Ascend MoE LoRA v1 expects pre-expanded rows (top_k_num=1).

这里检查的是该函数接口接收的行组织方式，不能据此认定模型 router 每次只选择一个专家。

### 开销和什么时候别开

材料能确认加载数量可能短暂超限，以及某些 LoRA 与 EP 组合会改变通信选择；没有给出对应的字节数或时延。

采用全分片、增大适配器缓存或开启图模式前，应分别核对计算分片条件、主机内存容量和图路径兼容性。材料没有足以推荐 GLM 双机配置的性能依据。
