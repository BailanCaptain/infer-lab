低精度格式规定怎样用较少位数记录数值；在本材料涉及的块量化 FP8 权重中，完整表示还包括每块权重对应的缩放系数。理解加载过程，需要同时看文件里保存了什么、加载后设备上保存了什么，以及矩阵乘实际使用哪条计算路径。

本页依据本地材料解释原生块量化 FP8 的加载条件、硬件分支和逐层回退，并区分权重与 KV cache 的格式。材料不足以完整介绍别名中所有格式的编码规则，也不足以确认四个社区版本的支持范围。

## 为什么同一份 FP8 文件，加载后可能占用不同的内存？

checkpoint 是保存模型权重及相关配置的文件集合。材料描述的原生 FP8 checkpoint 在配置中声明量化方法为 FP8，并提供权重块大小。其量化权重采用 float8_e4m3fn，每个权重块另有一个 FP32 缩放系数。

这里有两类相互配合的数据：权重元素保存低精度数值，缩放系数说明对应权重块的数值尺度。[量化页](../concepts/quantization.md)提供低精度数值与缩放系数共同表示权重的基础解释。

文件中的表示并不直接决定执行时的表示。材料描述了两条加载路径：

| 硬件条件 | 加载时怎样处理 | 后续计算与内存含义 |
| --- | --- | --- |
| 950PR、950DT，且层满足相应条件 | 将块缩放系数重新组织为 MXFP8 所需形式 | 使用原生 FP8 矩阵乘；文档称权重元素保持一字节，缩放系数仍是表示的一部分 |
| 其他 Ascend 代际 | 加载时将块缩放解析到模型数据类型中的权重 | 文档描述为使用 BF16 矩阵乘，并要求按约两倍权重内存规划 |

因此，“直接加载 FP8 文件”说明可以接收这种 checkpoint，不代表每种设备都直接执行 FP8 矩阵乘。材料中的文档称后一条路径与 checkpoint 数值等价；本地材料没有提供实际运行结果或误差测量。

## 一个权重块从文件到计算，要经过哪些步骤？

以材料描述的一块量化权重为例，可以沿着输入、处理和输出理解加载过程：

1. **读取配置。** 加载器需要知道量化方法、权重块大小，以及激活量化方式。激活是模型计算中产生的中间张量；它的量化配置与权重文件的存储配置需要分别检查。
2. **读取权重块及其缩放系数。** 低精度权重和对应系数共同构成输入，不能只看权重元素的类型。
3. **选择执行表示。** 在材料所述的 950 路径上，加载器尝试重新组织成 MXFP8；其他代际按文档描述解析成模型数据类型中的权重。
4. **检查本层能否使用所选路径。** 即使设备走 MXFP8 路径，层的形状仍可能触发回退。最终交给矩阵乘的表示，应以该层处理结果为准。

材料没有提供可完整手算的权重数值、块形状及重组规则，因此这里不能进一步演示“读出哪些数、乘上哪个系数、得到哪个矩阵元素”。完整数值示例需要补充这些信息。

## 为什么有块大小，还不一定能走 MXFP8？

材料给出的限制分为三个层面。

**checkpoint 必须属于受支持的块量化形式。** 文档明确限定原生 FP8 入口只支持 block-wise 格式，即按块提供缩放信息。缺少权重块大小、采用逐张量或逐通道缩放的原生 FP8 checkpoint，不适用材料描述的入口。文档给出的处理方向是使用 ModelSlim 或 LLM-Compressor 重新量化。

**激活量化配置也必须满足检查。** 材料中的 `AscendFp8Config` 要求 `activation_scheme` 为 `dynamic`；其他声明会触发异常。因此，权重块大小只是条件之一。

**每层的矩阵形状还要满足 MXFP8 分组要求。** 矩阵乘沿共享维度相乘并求和，这个共享维度也称归约维度。材料中的实现检查归约维度是否满足 MXFP8 分组要求；不满足时，日志说明该层改用模型数据类型执行。

此外，checkpoint 中列为跳过量化的层仍按未量化方式执行。文档举出的例子是多模态模型中的部分 visual merger 层；不能据此推断其他模型有哪些跳过层。

这些条件共同决定实际驻留格式。仅凭“950 设备”或“原生 FP8 模型”两个标签，无法判断所有层的权重都始终保持一字节。

## 权重采用 FP8，KV cache 就也采用 FP8 吗？

权重是模型读取使用的参数；KV cache 保存注意力后续计算需要的历史表示。两者的用途、生命周期和配置入口不同，应分别检查。

材料中的 MXFP8 KV cache 方法面向 dense-attention 模型，即材料明确限定的一类注意力执行路径。其说明区分了缓存数值与缩放系数：

| 缓存部分 | 数值存储 | 缩放系数从哪里来 |
| --- | --- | --- |
| K | FP8 E4M3 | 写入缓存时产生动态的逐 token 分组 E8M0 系数 |
| V | FP8 E4M3 | 使用 ModelSlim checkpoint 提供的静态逐通道 E8M0 系数 |

缩放系数另存于额外的缓存张量中。因而，核算缓存占用时，需要同时检查数值载荷和系数。

这条说明不能直接推广到所有注意力结构，也不能仅凭权重 checkpoint 的量化格式判断它是否可用。更完整的缓存机制见 [KV cache 量化](../concepts/kv-cache-quantization.md)。

## 这些材料能怎样用于 GLM 双机案例？

本次材料没有给出 GLM-5.3-Flash 固定双机部署的逐层量化配置、实际加载格式或执行结果，无法据此为该部署增加原生 FP8 或 MXFP8 KV cache 的支持结论。

## 哪些说法需要进一步区分？

**“文件是 FP8，所以执行时也是 FP8。”** 文件表示与执行表示之间存在加载转换。材料明确描述了其他 Ascend 代际解析权重后使用 BF16 矩阵乘的路径。

**“950 使用 MXFP8，所以所有层都按同一种方式保存。”** 跳过量化的层和不满足分组要求的层具有不同处理结果，必须逐层检查。

**“W8A8 示例证明原生 FP8 也受支持。”** 材料分别提供了 W8A8 动态量化示例和原生 FP8 加载说明。两类入口的条件需要分别核对。

**“权重与缓存都叫 MXFP8，可以共用同一套条件。”** 材料对权重重组和 KV cache 给出了不同的输入、系数来源与适用条件，不能互相代替。

## 对照源码

### 怎么开

材料中的量化指南按模型生产工具区分启动方式：

- ModelSlim 生成的量化模型通过 `--quantization ascend` 启用量化功能。
- LLM-Compressor 生成的模型不必添加这个参数。
- 原生块量化 FP8 checkpoint 按发布形式加载，不需要离线重新量化；仍需满足块量化、动态激活量化等检查。
- 材料中的 MXFP8 KV cache 入口为 `--kv-cache-dtype mxfp8`，其方法说明限定于 dense-attention 模型。

材料还提供 Dense 与 MoE 模型的 W8A8 动态量化示例。这些示例没有给出所有模型、格式与硬件组合的完整支持清单。

### 会报什么错

当原生 FP8 配置的激活量化方式不是 dynamic 时，材料中的代码抛出 `NotImplementedError`，说明当前声明不符合要求。

归约维度不满足 MXFP8 分组要求时，材料给出的行为是记录警告并让该层回退到模型数据类型；它与直接拒绝配置属于不同处理结果。

对于缺少权重块大小的原生 FP8 checkpoint，材料中的文档明确说明该形式没有相应 Ascend 执行路径，但摘录不足以确认所有入口最终使用的异常类型和完整报错文本。

### 开销和什么时候别开

使用材料所述的非 950 加载路径时，文档要求按约两倍权重内存规划。这个说法针对该路径的权重表示，不是整个模型进程的内存倍数。

在 950 路径上，也需要检查逐层回退与未量化层，才能估计实际权重占用。MXFP8 KV cache 还要保存额外的系数张量；材料不足以计算其完整缓存预算。

材料没有端到端时延、吞吐、质量评测或实机部署结果，不能据此提出性能推荐。缺少受支持 checkpoint 配置或模型适用性证据时，应先补齐核对，再决定是否启用相应入口。
