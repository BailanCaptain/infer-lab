MLA（Multi-head Latent Attention，多头潜在注意力）的这组材料涉及两类历史表示：latent，也就是潜在表示；以及 positional，也就是位置相关表示。本页核对的是 GLM 专用实现怎样要求这些表示的缓存布局，以及不同源码快照对缓存精度和优化开关的处理。

要理解这些布局，先要区分 [attention 的 Q、K、V](../concepts/attention-qkv.md)：查询 Q 与键 K 形成匹配分数，所得权重用于汇合值 V。缓存布局决定历史表示怎样保存、写入和交给后续算子使用；仅知道模型使用 MLA，还不足以确定这些工程细节。

提供的材料是局部源码摘录，没有给出完整的 MLA 投影与吸收计算。因此，本页只整理能够接续核对的缓存约束，不据此补写完整数学推导、手算示例或性能结论。

## 为什么同样叫 MLA，缓存却不能直接互换？

材料中同时出现 packed MLA cache 和独立 latent、positional cache 两种接口要求。

packed 表示由该实现按约定组织的一份缓存张量。GLM 的一处稀疏 attention 执行入口，从缓存集合中取出名为 kv 的对象，并要求它是 Tensor，也就是张量对象。检查不通过便报错，没有继续计算的分支。

另一处名为 `_exec_kv_no_rope` 的方法，则要求缓存序列中至少有两个对象，断言消息将它们称为独立的 latent 与 positional KV cache。该方法的说明还强调保留 K3 的原始 q/k 切片。

这两处要求属于不同源码位置，不能把它们拼成“所有 MLA 都兼容这两种布局”的结论。是否能够写入一种缓存，与后面的 attention 算子是否接受这种缓存，是两个需要分别检查的接口问题。

同样，方法名中出现 no_rope，也不足以证明它完全不需要位置相关存储：材料中的这个方法仍检查独立的位置缓存。具体存了什么、怎样读取，仍要沿该方法的完整输入输出核对。

## 缓存维度与精度分别由什么决定？

GLM-5 Indexer KPool MLA 的构造代码，把缓存头维度设为潜在维度与 RoPE 维度之和。RoPE 是通过旋转向量分量引入位置信息的机制，详见 [RoPE](../concepts/rope.md)。

这个维度表达式说明实现为位置段预留了配置入口，却没有给出本次模型配置中两个维度的实际值。因此，不能仅凭这段构造代码判断某个具体模型一定保存额外位置段，也不能从这里计算每个历史位置占多少字节。

同一段代码把完整 MLA KV cache 的类型设为 BF16，即每个数使用 16 位浮点表示。旁边的注释说明，A5 shared-KV 算子直接使用这份缓存，不对它做量化。这里的精度结论只覆盖该实现明确指定的完整 MLA 缓存，不能扩展成模型全部权重、全部缓存和全部中间状态都使用 BF16。

缓存精度还存在另一条实现分支。后面的源码快照允许使用 KPool indexer 的模型进入 SFA packed KV cache 的支持判定；注释以 GLM-5.3-Flash 为例。这里的 indexer 是选择读取位置的索引组件，SFA 则是材料中稀疏 attention 实现路径的名称。

“进入支持判定”仍有条件：实际启用 SFA C8 路径还要求缓存类型满足 fp8 或 int8 等检查。另一项 LI C8 优化依赖 LightningIndexer 的缓存布局，继续受独立条件限制。不能把 SFA 路径的放宽，转述为所有索引器缓存都支持相同量化布局。

## 为什么缓存分组会限制优化？

材料中的 `indexer_kpool_mla_v1` 路径明确关闭了四项优化：稀疏索引器 C8、SFA C8、SFA prolog v3 和 MLAPO。

代码注释给出的关联条件是：压缩后的索引器状态共用一个 scheduler group，而 compressor state 使用另一个组。这里的 scheduler group 是调度器组织缓存状态的分组；compressor state 是压缩器需要保留的状态。

该注释要求 SFA 的融合缓存路径不能重新解释这套布局。也就是说，优化是否可用不仅取决于缓存里的数值类型，还取决于执行路径怎样识别和组织状态。换成另一种融合处理方式之前，需要确认它对缓存分组的理解与当前布局一致。

材料没有给出这些优化的完整实现，也没有给出它们各自的性能收益。因此，能够确定的是这条路径显式关闭了哪些开关，不能进一步声称所有 KPool 或 MLA 实现都不支持这些优化。

## 放回 GLM 双机主线，哪些结论能用？

在[一次请求](../concepts/one-request.md)走到 attention 计算时，需要把“保存历史”“选择读取位置”和“执行 attention”区分开。当前摘录主要覆盖缓存接口和配置判定，没有提供单个 token 的完整前向过程，也没有提供双机通信记录。

针对固定执行侧快照，材料能够支持以下局部核对：

- GLM-5 Indexer KPool MLA 构造时需要缓存配置，并显式指定完整 MLA 缓存的精度。
- 摘录中的稀疏 attention 入口要求 packed MLA cache 为张量。
- 特定 KPool 路径因为状态分组布局关闭了若干融合或量化优化。
- 插件为 vLLM 0.23.0 补充了 GLM5-Next 的 MLA 模型识别逻辑。

这些事实不能单独推出每卡显存、通信次数、吞吐或时延。双机部署条件仍以[部署页](../concepts/glm-5-3-flash-two-node.md)为入口；本材料也没有提供设备实测，因而没有可报告的 NPU 运行结果。

## 哪些看似相同的结论需要分开？

**缓存宽度相同，不代表布局兼容。** 一个入口可能要求 packed 张量，另一个入口可能要求独立缓存对象；还要检查各维的含义与读写方式。

**某份缓存使用 BF16，不代表所有状态使用 BF16。** 当前赋值只说明它所指向的完整 MLA 缓存。索引器状态、压缩器状态及其他缓存需要各自的依据。

**某条路径关闭 C8，不代表整个 MLA 机制不支持 C8。** 材料中的另一快照已把 KPool indexer 纳入 SFA packed KV cache 的支持判定，但仍保留类型与布局条件。

**插件识别模型，不代表完成运行验证。** 把模型按 MLA 语义解析，只解决配置识别的一环；后续缓存分配、算子执行和完整部署还需要分别验证。

## 对照源码

### 怎么开

当前材料不足以给出完整启动命令或推荐配置。

构造 GLM-5 Indexer KPool MLA 时必须传入缓存配置；该对象缺失会直接报错。SFA C8 的相关快照还会检查缓存类型，不能仅凭模型属于 KPool indexer 就认定已经启用。

模型识别方面，固定执行侧材料包含一个面向 vLLM 0.23.0 的插件补丁：它检查模型文本配置中的 `kv_lora_rank` 是否非空，以补齐 GLM5-Next 的 MLA 识别语义。该检查不等于完整的运行能力检查。

### 会报什么错

| 检查位置 | 消息 | 触发条件 |
| --- | --- | --- |
| Indexer KPool MLA 构造 | `GLM-5 Indexer KPool MLA requires cache_config.` | 缺少缓存配置 |
| 稀疏 attention 入口 | `Indexer KPool MLA sparse attention requires the packed MLA cache.` | 取出的 packed 缓存不是张量 |
| `_exec_kv_no_rope` | `MLA requires separate latent and positional KV caches` | 缓存对象数量未满足该方法要求 |

第三项是断言消息。该方法还断言 KV 归一化层存在。以上检查只描述材料中的具体入口，不代表所有 MLA 后端共用同一组报错。

### 开销和什么时候别开

材料没有性能测量，也没有完整的缓存分配形状，无法据此计算总容量或量化收益。

对于显式关闭优化的 KPool 路径，应保留它对状态分组布局的约束。材料没有证明绕过这些开关后仍然正确，也没有证明关闭它们会带来多少性能损失。

对于允许 SFA C8 判定的路径，需要同时核对缓存类型和下游布局要求。LI C8 依赖 LightningIndexer 布局，不能跟随 SFA C8 一并推断为可用。
