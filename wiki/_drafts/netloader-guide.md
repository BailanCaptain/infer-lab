Netloader 是一种模型权重加载方式：通过 NPU 之间的 P2P（peer-to-peer，点对点）传输取得权重。权重是模型训练得到、推理计算需要读取的数字；加载器负责把这些数字准备到模型可使用的位置。

本页材料覆盖功能说明、部分配置入口、握手条件和回退代码，尚不足以复原完整传输流程。下文区分材料中的固定提交，不据此认证整个发布分支，也不把配置示例视为已经完成的设备测试。

## Netloader 改变了模型启动的哪一步？

模型开始处理请求前，执行侧需要先准备模型对象及其权重。Netloader 介入的是这个准备阶段：材料将它描述为利用 NPU 间高带宽连接加载权重的插件。

P2P 描述传输双方之间的数据交换方式；它本身不说明权重是否匹配、接收后是否还要调整布局，也不保证整个启动过程更快。判断这些问题，需要继续核对具体版本的握手、传输和加载后处理实现。

材料说明 Netloader 使用模型加载器注册接口接入 vLLM，并将该接口的加入关联到 vLLM 0.10。这只能说明文档给出的接口背景，不能据此判断所有后续 vLLM 与 vllm-ascend 组合均可使用。

## 为什么网络加载仍需要端口和显存预算？

网络加载除了需要权重的来源，还需要建立连接、交换配置并准备通信资源。

材料要求每个 Worker 进程都有可用的监听端口。Worker 是负责设备初始化、模型执行及相关资源管理的执行角色；这里的要求按进程计数，不能把模型服务的一个对外端口直接当成所有 Worker 的监听端口。

材料还指出，建立 HCCL（昇腾集合通信库）连接需要额外设备内存。文档以 HCCL 缓冲区默认约 200 MB 提醒使用者预留空间，但这不是 Netloader 全部额外显存开销的精确上限。权重缓存、通信资源与其他启动分配需要分别核算。

因此，网络传输能否缩短启动时间，需要同时考虑连接建立、可用带宽、缓存占用和接收后的准备工作。当前摘录没有提供可复核的启动耗时测量。

## 一次握手怎样判断双方是否匹配？

握手是在传输前交换信息、判断双方是否满足连接条件的步骤。材料中标注为 `baa023ad` 的实现比较设备编号、模型路径以及 TP、PP 配置。

TP，即 tensor parallel，把一次张量计算分片到多个设备；PP，即 pipeline parallel，按模型计算顺序划分执行阶段。这些配置会影响每个参与者应持有哪部分模型，因此握手需要比较它们。

用一组**示意值**演示该条件。[A]

假设供方记录的设备编号为 2、模型路径为 `/models/example`、TP 为 4、PP 为 1，缓存模式为 `dram`。接收方提交相同的前四项：

- 提交缓存模式 `dram` 时，通过摘录展示的这组一致性比较。
- 提交缓存模式 `hbm` 时，缓存模式比较不通过，进入拒绝分支。
- 省略缓存模式字段、使其为 `None` 时，跳过这项缓存模式比较。

这三个结果只说明所展示条件的分支选择，不代表整个加载过程已经成功。缓存模式字段可以省略，也不构成跨版本协议兼容的保证。

这些比较检查的是配置字段。它们没有对权重内容计算哈希，因而不能单凭握手通过就认定两端持有完全相同的权重内容。

## INT8_CACHE 控制什么，为什么 draft 要单独检查？

INT8 是一种整数数值格式。[量化](../concepts/quantization.md)用低精度编码及相应缩放表示模型数值；加载量化模型时，原始整数参数与最终供算子使用的权重布局需要区分。

材料中的文档将 INT8_CACHE 描述为原始 INT8 参数的缓存策略：

| 取值 | 材料描述的处理 | 使用时意味着什么 |
| --- | --- | --- |
| `hbm` | 把原始 INT8 参数复制到 HBM | 会增加设备内存占用，文档提示占用可能较大 |
| `dram` | 把原始 INT8 参数复制到 DRAM | 缓存位置改为主机侧内存，需要另计主机内存预算 |
| `no` | 不做这项特殊处理，文档默认值为此项 | 文档提示可能出现发散或不可预测行为，未说明必然发生 |

这里的 HBM 是设备侧高带宽内存，DRAM 指该配置下的主机侧缓存位置。表中的风险描述属于材料中的文档说明，不能代替特定模型和配置下的实测结论。

draft 是投机解码中提出候选 token 的模型角色。标注为 `2c59ff10` 的代码在启动 draft 供方时，对非 `no` 的缓存配置强制选用 `hbm`。因此，在这段实现中，主模型配置 `dram` 并不意味着 draft 供方也使用 `dram`。

当前摘录没有给出各缓存模式的完整接收、后处理与发送流程，也没有证明这一 draft 特判在其他快照中保持不变。

## 这些材料能怎样用于 GLM 双机部署？

[GLM-5.3-Flash 双机部署页](../concepts/glm-5-3-flash-two-node.md)提供主线部署上下文。本次摘录没有提供该部署启用 Netloader 的完整命令、权重匹配记录或实机加载结果，因而不能据此给出该部署的推荐缓存模式、启动耗时或额外显存数字。

材料提到的 MTP/draft 端口规则可以作为核查项目。MTP 是多 token 预测结构或训练目标，推理时可用其配套模块产生投机草稿；是否启用以及如何配置，仍需回到具体部署核对。不能仅因文档讨论了 draft，就推定 GLM 主线已经选择了 Netloader。

## 哪些配置判断需要特别区分？

**配置文件优先读取，不等于逐字段合并。** 材料中的代码先尝试配置文件；仅在结果仍为 `None` 且额外配置非空时，才改用额外配置。不能据此写成“文件里缺少的键会自动从命令行补齐”。

**网络加载失败后的磁盘回退，需要整理加载器配置。** 材料展示的回退代码复制加载配置，过滤 Netloader 专用键，再切换为默认加载格式。直接把同一份额外配置交给默认加载器，可能遇到它不接受的键。

**端口基值合法，不代表偏移后的端口合法。** Worker 编号和 draft 偏移都需要计入最终端口。

**文档中的已测试模型名单不等于完整支持矩阵。** 当前摘录没有提供对应硬件、依赖版本、并行配置和结果，无法用名单证明所有组合可用，也无法用未列出证明不支持。

## 对照源码

### 怎么开

材料给出的启用入口是：

```text
--load-format=netloader
--model-loader-extra-config='<JSON 配置>'
```

该片段展示加载器选择和额外配置入口；来源地址、模型及分布式启动参数仍需按实际运行形态补齐。

额外配置涉及 `SOURCE`、`LISTEN_PORT`、`INT8_CACHE`，并可通过 `CONFIG_FILE` 指向配置文件。材料第 1894–1897 行展示的选择逻辑为：只有配置文件读取结果仍为 `None` 且额外配置非空时，才使用后者，最后以空对象兜底。这不是逐字段合并。

### 会报什么错

`baa023ad` 握手片段位于材料第 2529–2535 行。设备编号、模型路径、TP、PP 必须满足所示一致性条件；客户端提供缓存模式时，还会比较该模式，不匹配进入 `JOIN_NACK` 拒绝分支。

材料第 3044–3051 行标注为 `7d825229`，展示磁盘回退前的配置处理：

```python
load_config = deepcopy(self.load_config)
load_config.model_loader_extra_config = disk_fallback_loader_extra_config(
    load_config.model_loader_extra_config,
)
load_config.load_format = "auto"
default_model_loader = DefaultModelLoader(load_config)
```

该片段的注释说明，默认加载器不接受 `SOURCE`、`LISTEN_PORT` 等 Netloader 键；过滤时保留多线程加载设置，使来源端或回退后的磁盘加载继续使用这些设置。摘录没有提供过滤函数的完整实现，不能据此列出全部保留键。

### 开销和什么时候别开

材料第 91–92 行给出两项资源要求：每个 Worker 进程需要可用监听端口，HCCL 连接需要额外设备内存。文档用默认约 200 MB 的缓冲区作预算提醒，未给出整个加载过程的显存峰值。

材料第 39 行说明 `hbm` 可能显著占用 HBM；第 1399 行展示 `2c59ff10` 的 draft 非 `no` 配置转为 `hbm`。预算紧张时，应把 draft 实际缓存位置一起检查。

材料第 105 行提示，MTP/draft 监听端口按以下关系形成：

```text
LISTEN_PORT + RANK + 10000
```

文档要求基值低于 55535，并计入 `RANK`。仅检查基值，不能确认最终端口合法。

缺少可达来源、可用监听端口或通信内存预算时，应先解决这些启动条件。当前材料没有足够测试结果支持按模型给出统一的启用建议。
