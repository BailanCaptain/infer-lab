NPUPlatform 是昇腾接入 vLLM 的平台类：它声明设备接入信息，并在配置处理过程中检查或调整部分设置。读本页要解决的问题是：用户写下的配置经过平台处理后，哪些值会保留，哪些会改变，哪些组合会被拒绝？

本页依据本地材料中的代码摘录，主要讨论固定部署所用的执行侧快照，以及材料另列的 main 开发主线快照。它们的行为分别说明；本次没有设备运行结果，也没有完成三个在册分支的逐项核对。

## 平台类怎样影响一次推理启动？

模型执行前，软件需要知道目标设备叫什么、通过什么环境变量选择可见设备，以及配置能否进入相应执行路径。平台类提供这些接入信息，同时参与配置处理。

材料中的平台声明把设备名称和类型都设为 npu，把 Ray 使用的设备资源键设为 NPU，并把控制设备可见性的环境变量设为 ASCEND_RT_VISIBLE_DEVICES。Ray 是用于组织分布式执行的软件；这里的资源键用于标识设备资源，环境变量则用于控制进程可见的设备范围。

平台处理还会改变配置。例如，缓存块大小不只是一个静态默认值：模型类别、是否复用前缀、是否分块处理提示词，都可能影响它最终保留什么值。

因此，阅读启动配置时，需要分别看三个对象：

| 对象 | 要回答的问题 |
| --- | --- |
| 用户输入 | 用户显式写了什么，哪些项没有填写？ |
| 进入平台处理时的配置 | 前面的配置构造或处理步骤已经填入了什么？ |
| 平台处理后的配置 | 哪条分支修改了值，或者提前返回、保留了原值？ |

这一区分也适用于设备查询。同样是询问设备总内存，接口是否可调用还取决于源码快照和设备运行时的初始化状态。

## 为什么配置检查还需要看执行顺序？

配置规则不是互不相关的一组条件。前面的赋值会改变后面条件的输入，提前返回会使后面的规则不再执行。

以 KV cache 为例，它保存后续注意力计算需要的历史表示，避免重复计算已处理的位置；缓存块则是管理这类状态的分配单位。平台代码会调整块大小，但一个模型专用分支里出现的数，未必就是整条启动路径的默认值。

设备初始化也有顺序要求。材料中固定部署快照的总内存查询接口直接抛出未实现异常。代码注释解释，它意在避免相关查询过早触发 torch_npu 初始化；torch_npu 是 PyTorch 接入昇腾的设备扩展。这里需要保留“注释给出的设计理由”与“接口实际执行的动作”两层含义：前者解释动机，后者是直接抛出异常。

main 开发主线的另一份摘录采用不同处理：运行时已经初始化时读取总内存，否则仍抛出异常。查询能力的变化没有消除初始化前提。

## 怎样手工走一遍块大小调整？

下面用同一个缓存块大小设置，比较不同分支怎样改变结果。这是配置分支演算，不是性能测试。

固定部署快照中的块大小处理先把空值填为 128；进入后续模型专用判断还要求模型配置与调度配置存在。材料列出的相关路径可以这样阅读：

| 进入相关分支时的条件 | 处理结果 | 后续影响 |
| --- | --- | --- |
| 块大小为空 | 先填为 128 | 后面的分支看到的已不再是空值 |
| 模型类型为 deepseek_v4，块大小是 32、64 或 128 | 保留原值并返回 | 不再进入后面的通用修正规则 |
| 模型类型为 deepseek_v4，块大小不在上述集合内 | 改为 32 并返回 | 发出警告，后面的规则不再执行 |
| 未在此前返回，且模型被标记为混合模型 | 提前返回 | 保留此前得到的块大小 |
| 未在此前返回，块大小不是 128，且启用前缀复用或分块预填充 | 改为 128 并返回 | 采用这条通用规则要求的块大小 |

取块大小 64，比较两种输入。

对于 deepseek_v4，64 属于允许保留的集合，处理后仍为 64，并立即返回。即使还存在后面的通用修正规则，这次执行也到不了那里。

对于未被前面分支截住的普通路径，如果启用了 prefix caching，块大小 64 就会改成 128。prefix caching 是在兼容条件下复用已计算的相同前缀；chunked prefill 则把尚未处理完的提示词计算分配到多轮，两者任一启用都满足这里的触发条件。

再看空值输入：空值先变成 128，随后进入 deepseek_v4 分支时，128 已属于允许保留的集合。因此，不能只看到该模型分支里“空值设为 32”的代码，就断定这条完整路径默认得到 32。判断默认值必须把前面的赋值一起走完。

这里的“混合模型”对应源码中的模型标记和注释所述的 attention 与 mamba 混合结构。它是否覆盖某个具体模型，需要继续检查该模型如何设置这个标记。

## 简单编译后端为 eager，为什么还要检查图模式？

eager 表示逐次执行操作的路径；graph mode 则捕获满足条件的设备操作序列，之后回放，以减少重复提交操作的开销。简单编译后端的字段值与完整的图执行配置不是同一个判断。

材料中的平台声明把简单编译后端设为 eager，但配置处理仍包含图模式分支：

- 关闭 Inductor。Inductor 是 PyTorch 的一种编译后端。
- 图模式为 NONE 时，把编译模式也设为 NONE，并关闭 npugraph_ex。
- 所选图模式要求分段编译时，检查编译模式必须是 VLLM_COMPILE。

这说明，判断某次启动是否使用图执行，需要继续检查实际图模式及对应配置分支。仅凭简单编译后端这个字段，无法概括整个平台的执行方式。

材料没有提供这些路径的运行时开销测量，因而本页不比较 eager 与各图路径的实际速度。

## 在 GLM 双机主线中，这些规则怎样使用？

固定主线使用 GLM-5.3-Flash，执行侧钉住专用镜像中的源码快照。本页的配置规则应按该执行侧快照理解，不能仅凭镜像依赖的 vLLM 版本，把它归入同名社区 Ascend 维护分支。

阅读这套部署的启动过程时，可以带着三个具体问题检查平台处理：

1. 并行配置是否触发组合限制？
2. 进入缓存块调整时，模型标记和现有块大小分别是什么？
3. 所选图模式与注意力后端是否通过对应验证？

当前材料能说明部分检查分支，尚不足以重建 GLM 双机的完整启动调用链，也不足以确定它最终采用的缓存块大小、默认 token 预算和全部配置改写。尤其不能由“混合模型提前返回”这一条规则，直接推出 GLM 在此处的实际结果；还需要模型配置如何进入该分支的证据。

## 哪些相近结论需要分开理解？

**平台兜底值、模型专用修正值和启动最终值分别属于不同阶段。** 块大小演算展示了这一点：前面的赋值可能让后面的空值分支不再命中，提前返回也会改变后续规则是否执行。

**后端验证失败可能产生不同结果。** 材料中的 FA3 路径既有返回 False、改用插件后端的分支，也有直接报错的分支。FA3 在这里指请求 FlashAttention 后端时进入的特定验证路径，不能把其中一个组合限制推广到所有注意力后端。

**错误文案需要结合触发条件阅读。** PCP 是 prefill context parallel，把提示词处理阶段的相关工作沿上下文维度分配。main 摘录中的错误文案写着不支持 PCP，但实际条件同时检查了所用 model runner；model runner 是组织模型执行的组件。只复述文案，会丢掉影响结论的执行路径条件。

**接口声明与硬件可用性需要分别核实。** 当前材料包含代码与注释，没有设备运行记录，不能据此确认所有模型、依赖和硬件组合都已验证。

## 对照源码

### 怎么开

NPUPlatform 的材料展示的是平台声明与配置处理分支，没有给出一个独立的“启用 NPUPlatform”开关或完整启动命令。

核对现有启动配置时，重点跟踪三个输入：并行配置、缓存配置和编译配置。注意力后端还需检查是否请求 FLASH_ATTN，以及是否启用用于训练与推理一致性场景的批次不变选项。材料未提供该选项的完整算法定义。

### 会报什么错

固定部署执行侧快照包含以下条件性拒绝：

- `data_parallel_size > 1` 且 `prefill_context_parallel_size > 1` 时，抛出 ValueError。DP 把不同请求或批次分给不同执行组；这里禁止的是 DP 与 PCP 同时大于 1 的组合。
- 需要分段编译的图模式下，若编译模式不是 VLLM_COMPILE，触发断言。
- 请求 FLASH_ATTN 并进入 FA3 验证后，未启用批次不变选项时返回 False，改用已注册的插件后端；启用该选项后，MLA 或稀疏注意力组合会抛出 ValueError。MLA 用压缩潜在表示组织多头注意力，稀疏注意力则限制每个查询访问的位置集合，这两类机制在此处属于组合检查条件。
- 固定部署快照的 `get_device_total_memory` 直接抛出 NotImplementedError；main 摘录则在 torch_npu 尚未初始化时抛出该异常。

FA3 验证后续还要求安装的扩展提供 `flash_attn_with_kvcache`。这些都是所示验证路径的条件，不能据此判断所有 MLA 配置都无法选择注意力后端。

### 开销和什么时候别开

材料中的 FA3 验证提示可能出现性能下降，但没有提供下降幅度或测试条件。需要该路径时，应核对扩展接口、注意力组合和一致性选项，再在目标环境验证性能。

块大小修正会改变配置结果；当前材料没有提供足以计算显存利用率或吞吐变化的数据。图模式分支同样只有配置逻辑，没有运行测量。

总内存查询的注释说明了初始化顺序约束。固定部署快照直接拒绝该接口调用；main 摘录要求先完成初始化，再读取设备内存信息。

### 版本差异

本次没有完成 v0.23 维护分支、v0.26 分支和 main 开发主线的逐项验证，因此不填写 `verified`。v0.26 分支的对应源码日期也未由当前材料确定。

已提供的两份执行侧摘录存在以下差异；专用镜像快照单列，不归入 v0.23 维护分支：

| 项目 | 固定部署的专用镜像快照 | main 开发主线摘录 | 意味着什么 |
| --- | --- | --- | --- |
| 总内存查询 | 直接抛出 NotImplementedError | torch_npu 已初始化时返回总内存，否则抛出异常 | 查询接口的可用条件不同 |
| PCP 相关拒绝条件 | DP 与 PCP 同时大于 1 时拒绝 | 未使用 v2 model runner 且 PCP 大于 1 时拒绝 | 这些摘录展示的检查条件不同，不能只按错误文案概括 |

这张表只比较材料实际给出的片段，不能证明两份快照各自没有其他 PCP 检查。三个在册分支的默认值、完整检查集合和块大小规则仍需补充对应源码。
