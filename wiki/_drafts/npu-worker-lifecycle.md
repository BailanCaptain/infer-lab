Worker 是负责设备初始化、模型执行和相关资源管理的执行角色。启动时，它需要把设备、模型和后续计算所需的状态准备好，才能承担请求的计算。

理解这段过程，关键是区分几种准备工作：确定在哪个设备上执行、建立模型的权重存储、确定历史状态的缓存空间，以及为计算路径做试跑或图捕获。它们解决的问题不同，也有先后依赖。

本页依据提供的本地源码摘录整理。摘录覆盖部分启动方法及执行器调用，尚不足以还原从进程创建到首次请求的完整调用链；以下会分别说明已经能读出的顺序与缺少的证据。

## Worker 启动时，究竟在准备什么？

模型推理使用训练得到的数字，也就是权重，把输入逐步变换成输出。设备承担计算，权重提供计算所需的参数，而缓存保存后续计算仍要使用的历史状态。这三者需要分别准备。

[NPUModelRunner](../concepts/npu-model-runner.md) 是 Worker 内负责模型执行的组件。材料中的设备初始化方法先取得设备，再初始化 workspace manager，之后才构造 ModelRunner。workspace manager 管理执行所需的工作空间；摘录展示了它的初始化位置，没有展开工作空间的具体布局。

这段顺序体现了一项直接依赖：构造 ModelRunner 时需要传入设备，因此设备必须先确定。材料中的普通执行路径与开发中的 v2 路径都在这个位置选择 runner；v2 路径还会输出部分功能尚未可用的警告。

Worker 的角色与操作系统进程需要分开理解。进程是具有独立地址空间的执行实体；一个 Worker 角色具体由哪个进程承载，要结合执行器部署判断，见[引擎进程](../concepts/engine-processes.md)。

## 为什么设备、权重和缓存要分开准备？

设备初始化回答“计算在哪里运行”。模型加载回答“计算读取哪些权重”。缓存初始化回答“后续计算的历史状态存在哪里”。预热则让指定计算路径先运行一次，或为满足条件的设备操作建立可回放的图。

材料里有几个能看出这些依赖的位置：

- 构造 ModelRunner 之前，Worker 先保存设备并初始化工作空间。
- 模型加载启用 Sleep Mode 时，会进入标记为 weights 的内存池上下文。Sleep Mode 是暂停推理时释放或转移部分设备存储的机制，详见 [Sleep Mode](../concepts/sleep-mode.md)。
- 执行器先调用各 Worker 的缓存初始化，再调用编译或预热。
- 图捕获受 eager 设置控制；eager 表示沿该执行路径逐步提交算子，而不是复用捕获图。

分开准备也意味着启动有成本。试跑本身需要执行计算；图捕获可能建立额外的图相关存储；缓存需要分配空间。材料没有提供启动耗时或设备实测日志，因此这里不能给出这些成本的实际大小。

## 沿着一个启动例子，怎样判断哪些步骤会执行？

设一个示意启动场景：执行器已经取得要下发的缓存配置，现在准备让 Worker 完成缓存初始化及预热。这里不设显存容量或模型规模，只跟踪调用和状态变化。

材料中执行器的方法按以下顺序工作：

1. 向 Worker 广播 `initialize_from_config`，传入缓存配置。
2. 该次调用返回后，再广播 `compile_or_warm_up_model`。
3. 收集各 Worker 返回的编译时间信息。

因此，能从这段代码确认的是“缓存初始化调用在前，编译或预热调用在后”。至于配置如何生成、此前谁调用了显存预算方法，还需要上游调用方的源码。

接着看两个条件分支。

**显式 KV cache 预算。** KV cache 是保存后续注意力计算所需历史表示的缓存。材料中的预算方法使用 Python 真值判断检查显式预算：条件成立时，仍调用 `profile_run()`。注释说明，这次试跑用于编译模型，而该分支跳过内存测算。

这也给出了一个可直接按 Python 语义检查的边界：正整数预算满足这个条件；`None` 和整数 `0` 不满足。这里描述的是分支判断，不表示这些值都能通过其他配置校验。

**eager 与图捕获。** 另一个摘录先把图内存计数设为零，再检查是否强制 eager；只有没有强制 eager 时，才调用 `capture_model()`。

这段代码足以说明 eager 会跳过这里的图捕获。它没有展示完整预热列表的构造和循环，因此不能仅凭这个分支判断此前是否实际执行过尺寸预热。试跑、尺寸预热和图捕获应分别沿各自入口确认。

## 内存池为什么还要区分权重、缓存和元数据？

内存池是按特定管理方式组织的一组分配。材料中的模型加载路径，在启用 Sleep Mode 时取得分配器，并检查其当前使用量是否为零，然后进入 weights 内存池上下文。

这个检查失败时，断言信息指出：Sleep Mode 在每个进程中只能用于一个实例。该限制属于这里展示的 Sleep Mode 分配路径，不能推广成所有运行形态下的 Worker 数量限制。

另一份摘录展示了缓存初始化的细分：

先确保 KV transfer 已初始化，再调用 ModelRunner 初始化 KV cache，同时传入标记为 kv_cache 的内存池上下文。KV transfer 是缓存传输相关机制；这段调用本身没有说明当前部署是否实际发生缓存传输。

摘录中的注释明确要求：可丢弃的 kv_cache 池只承载缓存的底层存储，初始化过程中创建的持久元数据应留在池外。原因是 Sleep/Wake 会影响可丢弃池，而持久元数据仍需保留，才能继续描述和管理这些存储。

这里区分的是存储的生命周期：缓存主体可以按池的规则处理，描述缓存的持久元数据则需要更长的存续时间。具体有哪些元数据、怎样恢复缓存内容，仍需继续核读 ModelRunner 和分配器实现。

## 放到 GLM 双机主线中，应该怎样使用这些结论？

本页在请求主线中的位置是服务启动阶段：Worker 先准备执行环境，服务随后才能接收并执行请求。部署背景见 [GLM-5.3-Flash 双机部署](../concepts/glm-5-3-flash-two-node.md)，请求进入执行阶段后的路径见[请求调用链](../concepts/request-call-chain.md)。

材料标识了一组固定源码：执行侧为 vllm-ascend 的 db701c1f，执行器为 vLLM 的 0fc695fc。当前摘录分别展示了 Worker 的部分准备动作，以及执行器下发缓存初始化、编译或预热的先后关系。

这些片段没有完整展示双机环境中的预算收集、缓存块数计算和模型长度同步。因此，本页不能据此确定：

- 每个 EngineCore 收集哪些 Worker 的预算；
- 两台机器是否需要对齐缓存块数；
- 缓存配置生成后，是否改变并同步最大模型长度；
- 教程配置实际执行了哪些预热尺寸，以及占用多少显存。

这些问题影响资源计算和启动行为，需要保留为待核项。当前材料也没有提供实机运行结果。

## 哪些相近的启动动作需要分开理解？

**指定缓存预算与执行试跑是两件事。** 显式预算分支仍有试跑调用；跳过预算测算，不等于跳过模型编译所需的准备。

**eager 与预热不是互斥概念。** 已展示的 eager 条件控制图捕获。其他试跑或预热是否执行，要检查对应的调用位置和条件。

**总显存、空闲显存与请求内存是不同的量。** 材料中的请求内存由总显存乘显存利用比例得到，然后再与启动时空闲显存比较。其他进程已占用的空间会影响空闲量；比例计算本身不会消除这些占用。

**方法在文件中的位置不代表运行顺序。** 运行顺序要看调用方。本材料直接展示了执行器先下发缓存初始化、再下发编译或预热；其余阶段仍需沿调用链补齐。

## 对照源码

### 怎么开

本页讲的是启动生命周期，材料没有展示一个独立的“开启 Worker 生命周期”开关。

实际阅读时，可以先看执行器的 `initialize_from_config`：它负责下发缓存初始化及编译或预热。再回到 Worker，分别核读设备准备、模型加载、预算分支和图捕获条件。

材料保留了显式缓存预算与强制 eager 的内部配置判断，但没有展示完整命令行解析。别名中的加载格式、safetensors 加载策略和远程代码信任选项也没有相应定义片段，本稿不补写其默认值或启动命令。

### 会报什么错

材料展示了两类检查：

- 设备初始化阶段，若启动空闲显存小于请求内存，代码进入异常分支。摘录没有展示完整异常文本。
- 开启 Sleep Mode 的模型加载路径要求分配器当前使用量为零。断言文本为：`Sleep mode can only be used for one instance per process.`

v2 ModelRunner 的提示属于开发状态警告：它说明部分功能尚未可用，不等于该次启动已经失败。

### 开销和什么时候别开

显式缓存预算分支仍执行试跑，因而不能用它消除所有启动计算。它跳过内存测算，预算是否适合现场设备仍需要单独验证。

强制 eager 会跳过已展示的图捕获调用。采用哪条路径，应结合模型兼容性、启动成本与运行负载判断；当前材料没有性能对比，不能给出统一推荐。

另一份预算分析摘录在图捕获之前记录 torch 内存峰值。注释解释，这样做是为了避免图内存池分配抬高激活峰值。激活是模型执行中的中间结果；把它与图存储混在一起，会改变预算统计的含义。该片段没有完整展示后续预算汇总公式。
