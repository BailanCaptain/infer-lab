## 配置值怎样触发平台校验？

材料第 23–49、57–59 行展示了两个快照中的相关代码：

| 摘录快照 | 配置读取 | 平台校验 |
| --- | --- | --- |
| `2c59ff10` | 从 additional_config 读取 layer_sharding，缺失时取 None | 配置值为真时，要求存在 KV 传输配置，且角色为 kv_producer |
| `db701c1f` | 同样从 additional_config 读取，缺失时取 None | 所示校验代码与上一行一致 |

这里的触发条件是 **Python 真值**，并非只看键是否存在。校验先取出配置值；若它是假值，就直接返回。缺少该键、值为 None 或空列表，都不会触发后面的角色检查。

例如，假设配置中写入空列表，校验会在读取 KV 传输配置之前返回；若写入非空列表，则继续检查 KV 传输配置。这个示例只演示分支选择，不证明列表元素符合后续计算的要求。[A]

配置值为真时，以下任一条件会抛出 ValueError：

- 没有 KV 传输配置；
- KV 传输角色不是 kv_producer。

摘录中的原始报错为：

```text
additional_config.layer_sharding can only be enabled in PD-disaggregated's P node.
```

PD disaggregation 是把 prefill（处理输入序列）与 decode（逐步生成后续 token）分给不同执行组的部署方式；此处报错将允许使用的位置称为 P 节点，而代码实际检查的是 kv_producer 角色。

这段函数没有检查配置元素的类型或名称。通过这一项角色校验，只能说明没有被这条条件拒绝，不能据此确认整个配置有效。

## 这项检查在配置流程的什么位置？

材料第 61–80 行展示了 `db701c1f` 快照中平台配置检查入口 `check_and_update_config` 的一段流程：

1. 若存在设备配置，且设备类型不同于当前平台设备类型，直接返回。
2. 若模型配置缺失，记录 warning 后返回。
3. 调用量化自动检测。
4. 调用 layer_sharding 校验。

因此，前述 ValueError 的触发还以流程实际走到第 4 步为条件。片段明确展示了调用位置，但没有包含完整启动调用链或运行日志，不能据此补写实机启动结果。

配置入口的进一步背景可参照 [Ascend 配置体系](../concepts/ascend-config-system.md)。

## RFork 怎样决定绕过权重传输？

RFork 是一种从已有 Worker 获取模型权重的加载方式。材料第 1–21 行展示了 `2b115d02` 快照中的判断与回退准备。

辅助函数 `_is_layer_sharding_enabled` 取出 additional_config 中的 layer_sharding，再返回其布尔值。因此，空列表不会触发这里的 layer_sharding 绕行分支；非空值会触发。

随后代码按以下顺序选择原因：

| 条件 | 记录的绕行原因 |
| --- | --- |
| layer_sharding 配置值为真 | additional_config.layer_sharding |
| 上一条件不成立，且动态 EPLB 判断为真 | dynamic EPLB |
| 两项判断均不成立 | 保持 None，不进入所示回退分支 |

EPLB 是调整专家放置以平衡负载的机制；本次材料只展示其判断函数的调用，没有给出“动态 EPLB 已启用”的内部判定条件。

两项检查通过 if / elif 连接。若二者同时为真，这段代码只记录 layer_sharding 作为绕行原因。

只要原因不是 None，代码就记录以下 warning，并调用 `_make_fallback_load_config` 构造回退加载配置：

```text
RFork transfer is disabled when %s is enabled; using the default model loader.
```

这表明片段中的分支意图是禁用 RFork 传输并使用默认模型加载器；摘录到构造回退配置为止，没有展示后续加载调用及其执行结果。
