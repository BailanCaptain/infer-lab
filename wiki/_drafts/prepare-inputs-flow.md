输入准备把“每条请求本轮要计算几个位置”变成模型可以直接读取的 token 编号、位置和配套信息。同一批里，请求的历史进度和本轮计算量可以不同，因此不能只把几段 token 接起来，还要保留每一项属于谁、位于该请求的哪个位置。

本页依据提供的代码摘录，说明标为 vllm-ascend 固定提交 db701c1f 的输入准备片段及材料中的异步输入片段。材料不是完整调用链，也没有四个社区版本的逐项核对记录；下文按已展示的赋值和分支解释，不将其扩展成所有版本的行为。

## 调度计划为什么还不能直接交给模型？

[Scheduler](../concepts/vllm-scheduler.md) 是决定本轮让哪些请求继续计算、各算几个位置的组件。计划里的“请求 A 算两个位置、请求 C 算一个位置”描述的是工作量；模型实际执行还需要三个不同的问题的答案：

| 信息 | 回答的问题 |
| --- | --- |
| token 编号 | 这个输入位置放的是什么离散符号？ |
| 序列位置 | 它在所属请求中排第几个？ |
| 请求归属与边界 | 展平后哪些项属于同一条请求？ |

token 是分词器输出的离散符号，通常用整数编号表示。编号本身不表示它在序列中的位置：同一个 token 可以出现在一条请求的多个位置，也可以出现在不同请求中。

材料中的输入准备从 CPU 上按请求保存的 token 表取数，写入本轮使用的连续输入缓冲区。它还会准备序列长度、缓存位置和采样选择信息。这些信息服务于不同环节，不是同一组编号的不同叫法。

## 为什么先提交块表，再展开输入？

[block table](../concepts/block-table.md) 把请求的逻辑缓存块位置映射到缓存池内的物理块编号。模型处理新位置时，需要知道后续状态应写到哪里，以及历史状态如何定位。

所示函数先要求总调度 token 数大于零、请求数大于零，然后提交当前请求的块表。接着才在 CPU 上展开本轮各 token 的请求归属。代码注释给出的目的，是让块表复制与后续 CPU 操作有机会重叠。

这解释了顺序的意义：先发起可提前进行的数据准备，再计算其余索引。摘录没有提供复制耗时、实际重叠比例或端到端收益，因而不能据此给出性能数字。

请求归属的展开使用重复操作。某条请求本轮算几个位置，它的请求行号就在展开数组里出现几次。这样，每个展平位置都能找到所属请求的历史进度。

## 两条请求怎样变成一段连续输入？

下面用同一组示意数走完取数过程。位置从零开始计数，token 编号只用于演算。

设 CPU token 表每行有八格，本轮有两条请求：

| 请求 | token 表行号 | 已计算位置数 | 本轮调度位置数 | 本轮要读取的位置 |
| --- | --- | --- | --- | --- |
| 请求 A | 0 | 2 | 2 | 2、3 |
| 请求 C | 1 | 1 | 1 | 1 |

token 表设为：

```text
请求 A：[10, 11, 12, 13, 14, 15, 16, 17]
请求 C：[20, 21, 22, 23, 24, 25, 26, 27]
```

按本轮调度量重复请求行号，得到请求归属：

```text
req_indices = [0, 0, 1]
```

前两项属于请求 A，最后一项属于请求 C。这个数组中的 0 和 1 是请求行号，不是 token 编号，也不是序列位置。

为演示材料中的位置相加规则，设本轮请求内偏移为：

```text
请求内偏移 = [0, 1, 0]
```

每个位置先通过请求归属取出“所属请求已计算了多少个位置”，再加上本轮请求内偏移：

```text
已计算位置数按归属展开 = [2, 2, 1]
本轮请求内偏移         = [0, 1, 0]
序列位置               = [2, 3, 1]
```

因此，请求 A 本轮从位置 2 接着算，请求 C 从自己的位置 1 接着算。展平并没有把两条请求变成同一条序列。

取 token 时，代码把二维 token 表视为一维数组。每行八格，因此请求行号乘八就是该行在一维数组中的起点：

```text
请求行偏移 = [0, 0, 8]
序列位置   = [2, 3, 1]
取数索引   = [2, 3, 9]
```

一维索引 2、3 对应请求 A 的 12、13；一维索引 9 对应请求 C 的 21。本轮输入于是成为：

```text
input_ids = [12, 13, 21]
positions = [ 2,  3,  1]
```

这两个数组长度相同、逐项对应，但含义不同：前者告诉模型读哪个 token，后者告诉模型该 token 在所属请求中的位置。

本例的 token 表、调度量和请求内偏移均为教学假设；按摘录中的索引规则得到的数组是手算结果，依据与适用边界列在页末。

## 序列长度为什么还要区分乐观值和修正值？

按上述示意数，若把本轮调度位置都计入，请求 A 的长度为四，请求 C 的长度为二。

材料中的 CPU 乐观序列长度采用同样的加法：已计算 token 数加本轮调度 token 数。请求范围之外的缓冲区则清零。

“乐观”指出这里存在接受结果的假设。[speculative decoding](../concepts/speculative-decoding.md) 会先提出候选 token，再由目标模型验证；调度时准备的候选不保证全部被接受。因此，用于提前准备的长度与最终有效长度可能不同。

摘录展示了一条有条件的修正路径：只有需要同步 CPU 序列长度，并且异步投机路径处于活动状态时，才调用 CPU 乐观长度修正。该活动状态还要求有效采样计数存在、上一轮请求索引映射非空。

这段材料展示了调用条件，没有展示修正函数的完整实现。因而可以说明“哪些条件下进入修正”，但不能据此补写每个请求最终如何扣除无效候选、何时更新所有相关状态。

## token 的序列位置怎样连接到缓存位置？

序列位置回答“这是请求中的第几个位置”；缓存槽位回答“本次状态写到缓存布局的哪里”。两者之间还隔着块表和具体布局。

例如，两个请求都处理自己的位置 3，并不意味着它们写入同一处缓存。请求归属不同，块表可能不同；采用不同状态布局时，写入规则也可能不同。因此，不能直接把本页手算出的序列位置当作设备内存地址。

所给摘录明确展示了 slot mapping 的分支。slot mapping 是为待写入状态准备的位置映射：

- 当 prefill context parallel（PCP）与 decode context parallel（DCP）的并行规模乘积大于一时，代码按请求边界的相邻差值展开请求归属，再进入专用位置映射路径。
- 其他情况下，进入摘录所示的通用 kernel 路径。kernel 是设备上执行具体计算的实现。

这里的请求边界用于表示每条请求在展平输入中的起止范围。相邻边界相减，就得到相应请求占据多少项。

材料没有展开两条位置映射路径的完整实现，也没有提供 GLM 各类状态的完整布局。因此，本页只能确认这里存在配置分支，不能将某一种普通分页公式推广到所有状态。

## 本轮哪些输出行需要送去采样？

模型执行后会为相应位置产生词表分数，采样再据此确定输出 token。输入准备还要告诉后续环节：本轮应该选哪些输出行。

摘录区分了是否存在已调度的投机 token。

没有已调度投机 token 时，代码不生成投机解码元数据，每请求的采样数设为一。未启用 context parallel（CP，即沿上下文分配计算或状态的并行方式）时，输出行索引取每条请求结束边界减一，也就是该请求本轮最后一行；启用 CP 时，则由相应管理器计算索引。

存在已调度投机 token 时，代码根据草稿数、累计调度量及适用的 PCP 补齐信息构造投机解码元数据，再使用其中的输出行索引。该分支把每请求采样数设为草稿数加一。

“选择了采样行”与“请求向用户新增了一个输出 token”仍是两个事件。材料中的注释明确提到，部分 chunked prefill 请求也会采样，但结果会被忽略。chunked prefill 是把尚未完成的提示词计算分配到多轮执行；中间一轮的采样结果未必成为最终输出。

## 异步执行为什么仍可能复制 CPU 输入？

异步输入路径尝试利用上一轮留在设备侧的采样结果，但能复用多少，取决于本轮输入与上一轮结果的对应关系。

材料中的一个分支比较两个数量：

- 能匹配上一轮采样结果的 token 数；
- 本轮总调度 token 数减去已统计的投机 token 数。

前者小于后者时，代码先把本轮整段 CPU 输入复制到设备侧。该分支说明，本轮有些所需输入不能全部由上一轮采样缓存提供。

因此，是否异步与是否发生主机到设备复制，需要分别判断。所给材料足以说明这个复制条件，不能量化复制成本，也不能证明其他未展示路径的搬运情况。

## 放到 GLM 双机时，哪些内容还需要补证？

阅读 GLM 双机中的输入准备，可以沿本页已经说明的对象继续追踪：调度量怎样展开为请求归属，历史进度怎样形成位置，不同状态怎样取得写入映射，哪些模型输出行进入采样。

但本次新材料不足以把这些通用对象完整落到 GLM-5.3-Flash 双机的每类状态上。需要追加核对的内容包括：

- GLM 使用的各类注意力状态分别需要哪些映射，以及写入频率有何不同。
- 各注意力后端接收的请求边界是否包含补齐行。
- 请求重排阈值如何随投机配置确定。
- 无请求的执行组怎样构造空批次，是否绕过正常输入准备。
- 专用镜像的控制流与四个社区分支分别在哪些位置一致、在哪些位置分叉。

## 哪些相近的量需要分别理解？

**token 编号与位置。** token 编号决定读入的符号，位置决定该符号在所属请求中的顺序。本页示例中，编号 21 位于请求 C 的位置 1。

**序列位置与缓存槽位。** 序列位置属于请求的逻辑顺序；缓存槽位依赖请求映射和状态布局。相同序列位置可以对应不同存储位置。

**调度量与有效输出量。** 本轮调度了多少位置，描述模型要处理多少输入；接受了多少候选、向用户输出多少 token，还取决于后续验证与结果处理。

**乐观长度与最终有效长度。** 乐观长度服务于提前准备，投机候选的接受情况可能要求修正它。

**异步执行与数据搬运。** 异步改变工作之间的等待与重叠关系；材料展示的异步分支仍可能复制整段 CPU 输入。

## 对照源码

### 怎么开

输入准备是模型执行前的一段内部流程。所给材料没有提供独立启用它的用户参数，也没有完整展示 runner 的选择入口，不能据此给出启动命令。

阅读摘录时，可按以下数据关系定位，而不必先记住所有辅助函数：

1. 调度量和当前请求数决定本轮输入规模。
2. 块表先提交，请求行号随后按调度量重复。
3. 请求历史进度与请求内偏移相加，形成序列位置。
4. 序列位置与 token 表行偏移相加，形成取数索引。
5. 长度、缓存映射和采样索引按各自条件准备。

代码片段不连续，这个顺序只覆盖所展示的数据依赖，不代表完整函数的全部执行阶段。

### 会报什么错

材料第 38—47 行展示了两个断言：总调度 token 数必须大于零，请求数也必须大于零。任一条件不成立，都会触发相应断言。

这不足以判断完整系统如何处理空批次；空批次是否走另一个入口，需要检查调用者。材料也没有提供其他错误字符串、触发栈或完整配置校验，不能补写特定报错。

### 开销和什么时候别开

这里涉及 CPU 索引计算、从 token 表取数，以及相应数据复制。代码注释说明提前提交块表意在与后续 CPU 操作重叠；使用 `torch.index_select` 而非 `np.take` 的理由也是代码注释中的性能判断，本材料没有对应基准测试。

异步输入的复制分支见材料第 1077—1082 行。性能评估需要实际记录本轮请求组成、可复用采样数量、复制字节数和执行时间。现有材料没有 profiling 结果。

由于没有独立开关和完整替代路径依据，本页不能给出“关闭输入准备”的建议。工程上可比较的是具体复制、同步或并行路径的成本，而不是省略模型执行所需的输入信息。
