读 vllm-ascend 源码，是沿着一个具体问题，查清输入从哪里来、经过哪些条件判断、状态怎样改变，以及结果交给谁使用。找到同名函数是起点；回答“这次运行为什么走到这里”，还需要把它与调用条件和后续使用位置连起来。

本页以提供的本地源码摘录演示这种阅读方法。材料涉及多个固定提交，能支持局部分支分析，尚不足以完成四个社区版本的整页核对，也没有设备运行结果。

## 怎样把一个大问题改成能沿代码追踪的小问题？

“这个功能开了吗”通常包含几个不同的问题：

- 安装包有没有声明入口？
- 配置读取后得到什么值？
- 校验是否接受这个值，或者又把它改掉？
- 执行时是否满足分支条件？
- 进入分支后，张量或状态发生了什么变化？

这些问题需要分别找证据。可以先写一条观察记录：

> 我在什么源码快照中，给了什么输入，想确认哪个分支是否执行，以及执行后什么发生变化。

例如，想确认一个配置值为什么没有生效，就从配置输入开始，记录读取结果，再找赋值和消费者。消费者指实际读取这个值并据此选择行为的代码。只读配置定义，无法回答最终行为。

想确认一次等待是否来自图回放，则从等待调用开始，向前检查条件，向后检查回放；同时记录这段代码属于哪个执行路径。图回放是复用已经记录好的设备执行图，再次提交其中的操作。

阅读路径涉及 vLLM 与 vllm-ascend 的分工时，可结合[接入概览](../concepts/vllm-ascend-overview.md)和[目录地图](../concepts/vllm-ascend-repo-map.md)定位；追踪一条请求经过哪些执行环节时，参见[请求代码路径](../concepts/request-call-chain.md)。

## 为什么入口、登记表和开关都需要继续往下读？

入口声明回答的是“安装包向框架提供了哪些可发现的入口”。材料中的 setup.py 声明了平台插件入口，以及 KV connector、模型加载、服务 profiling 和模型注册等通用插件入口。KV connector 是衔接历史状态传输的组件；profiling 用于收集执行过程的信息。

声明中的名字与函数路径告诉读者从哪里继续查，却没有展示这些入口在某次运行中是否成功加载和调用。

算子登记也有类似边界。算子是规定张量输入、输出和运算含义的计算操作；登记表将一个名字关联到某个实现。材料中，FusedMoE 与 KimiGatedDeltaNetAttention 的映射追加在一个版本判断分支内。读到这里，可以记录“满足这个判断时追加这两项”；实际模型是否选中这些实现，还要继续找选择与调用位置。

配置开关则可能经历更多变化：

> 用户输入 → 读取或回退 → 有效性检查 → 状态回写 → 执行条件判断。

例如，输入值已经是 true，后续仍可能因为运行角色不合适而报错，也可能发出警告后改成 false。因此，阅读配置时应同时追踪“值来自哪里”和“谁还能修改它”。

## 能用一个小例子看清配置优先级吗？

材料中的配置读取片段先检查键是否存在：

```python
if config_key in additional_config:
    value = additional_config[config_key]
    return value
```

这里判断的是键的存在性。字典中存放的值即使是 false，也会被取出并立即返回。

设有以下教学输入：配置键存在，值为 false；环境变量回退若被执行，会得到 true。这个设定只用于解释控制流。[A]

逐步执行：

1. 查询字典是否包含配置键，结果为真。
2. 取出该键对应的 false。
3. 返回 false，结束这次函数调用。

因此，这段读取逻辑返回 false。环境回退路径没有在这次调用中执行。这个结论来自“键存在就返回”的顺序，而不是来自 false 与 true 的大小或优先级。

接下来还要检查调用者。读取函数返回 false，不足以单独说明整项功能最终关闭，因为调用者可能继续合并其他条件。

材料中另一些快照的 FlashComm 有效值采用逻辑“或”：显式开启与 DSA-CP 开启，只要其中一项为真，有效值就为真。DSA-CP 是此处受多项条件约束的上下文并行路径；本页只分析其配置逻辑。

同样取“显式开启为 false，DSA-CP 为 true”的教学输入，逻辑“或”的结果就是 true。[A] 这个例子说明，读取阶段返回的一个值与后续计算出的有效值可以不同。两个片段属于不同快照，不能据此拼出一套跨版本通用的配置规则。

## 配置合并后，还会发生哪些变化？

材料展示了三种值得分别记录的行为。

**拒绝不适用的组合。** Balance Scheduling 的相关检查限制了可用的传输角色。这里的传输角色表示执行组在 prefill 与 decode 分离部署中承担的职责：producer 提供历史状态，consumer 接收并继续计算，both 表示兼具两种角色。所摘录检查允许没有传输配置，或者角色为 kv_both 的情况；存在传输配置且角色不符合要求时会拒绝。

读这类代码，需要同时抄下条件和错误结果。错误消息列举的典型角色，有时比实际条件覆盖的范围窄，判断范围应以条件表达式为准。

**接受输入，但改写状态。** 重计算调度相关片段在 producer 角色上发出警告并关闭选项。重计算指通过重新执行先前计算恢复所需状态。这里“程序继续运行”和“这个选项继续有效”是两个不同结果，阅读记录应写明最终赋值。

**根据多个条件保留开关。** 材料中的 DSA-CP 最终值要求原开关、模型属性检查与序列并行 MoE 条件同时成立。序列并行在这里涉及按输入位置分配计算；MoE 是通过路由选择部分专家执行前馈变换的模型结构。

其中，模型检查使用属性存在性判断，检查对象是否具有 index_topk 属性，并未检查该属性的具体值。存在性、数值合法性和模型兼容性分别需要相应证据。

配置还可能回写另一个字段。材料中的一处分支在 prefill 上下文并行规模大于 1、且序列并行判断成立时，将批次 token 上限调整到 TP 与 PCP 规模乘积的倍数。TP 是把张量计算分片到多个设备；PCP 在这里指 prefill 的上下文并行路径。分析这种代码时，应记录原字段、进入条件、回写字段和后续使用位置，避免把用户输入直接当成运行中的最终值。

## 读执行代码时，怎样跟住张量和等待条件？

先给每一步写出“输入 → 操作 → 输出”，再补齐分支前提。

材料中的语法约束路径提供了一个清楚的例子。logits 是模型为候选 token 产生的一组分数；语法掩码根据输出格式约束，限制哪些候选可以继续参与选择。

在提供的片段中，只有 grammar_output 非空时才执行这条路径：

1. 保存 logits 原有的数据类型。
2. 将 logits 搬到 CPU，并转成 float。
3. 应用语法掩码。
4. 将结果搬回原设备，并恢复原有数据类型。

这份记录交代了数据在哪里、表示怎样变化、处理后回到哪里。代码注释提到的编译优化限制，也应保留在这条具体路径内；材料没有提供把它扩展成整个 Ascend 编译能力结论的依据。

等待调用则适合整理成条件表。材料中的某处图回放前同步，需要以下条件同时成立：

| 条件 | 此处要求 |
| --- | --- |
| 图运行模式 | FULL |
| 是否属于 EAGLE 草稿模型路径 | 否 |
| 是否启用 enpu | 否 |

EAGLE 在该判断中属于草稿模型相关路径；草稿模型用于提出候选 token。enpu 在本页仅作为源码中的分支开关记录，材料没有提供其完整机制。

三个条件全部满足时，片段先等待当前 NPU 流完成，再调用图回放。流是安排设备操作顺序的执行队列。条件不满足时，只能确认这里没有执行这次同步；判断整条请求是否还有其他等待，需要继续检查别处。

同理，一处同步调用可以帮助定位观察点，却不能单独证明性能停顿或异常的根因。还需要运行时路径、时间记录等证据。

## 怎样把阅读方法用于 GLM 双机主线？

沿请求阅读时，可以把问题分成“控制侧怎样安排工作”和“执行侧怎样完成工作”，再分别追踪对应代码。每一个交接点都记录传入对象、返回对象和被修改的状态。

材料包含 vLLM 控制侧与 vllm-ascend 执行侧的片段，但没有给出完整的 GLM 双机请求轨迹、每卡张量形状、通信次数或显存账单。本页因此只提供阅读动作，不重建这些部署结论。

例如，在执行侧，材料展示了 NPUModelRunner 继承 GPUModelRunner。继承表示子类可以复用并扩展父类行为。接下来应检查目标方法由谁提供、是否被子类覆盖，以及运行时是否还有替换；仅凭类声明，无法判定某个具体方法最后执行哪份实现。运行时替换的阅读基础见 [Patch 机制](../concepts/ascend-patch-system.md)。

材料还展示了执行器配置值 mp 与 uni 分别对应 MultiprocExecutor 和 UniProcExecutor 的选择片段。执行器负责组织模型执行；这段映射可以作为继续查找执行入口的线索，但该片段没有明确标注所属提交，尚不能据它确认固定 GLM 部署实际采用的执行器。

## 哪些相近表述需要分别核实？

**“字段存在”与“功能有效”有不同证明要求。** 属性存在性检查只回答对象有没有这个字段；有效性还可能取决于字段值、模型能力与其他配置。

**“后端字段写成某个名字”与“执行了同名算子”有不同证明要求。** 材料中有将 all2all_backend 写为 flashinfer_all2allv 的分支，注释将其描述为禁用某条 SP MoE 路径的变通方式。确认实际执行的通信实现，需要继续追踪这个字段的消费者。

**“允许选择 runner”与“模型兼容”有不同证明要求。** runner 是组织模型输入与执行的组件。材料中的一处补丁直接采用 VLLM_USE_V2_MODEL_RUNNER 的值，未设置时返回 false；注释将模型兼容性判断交给 NPU runner。由此只能确认这处选择逻辑，模型支持情况仍需后续实现与验证。

**“版本判断函数的名字”与“精确版本范围”有不同证明要求。** 材料出现 vllm_version_is 调用，却没有提供该函数定义。可以记录它返回真或假时分别执行什么，精确匹配语义仍需补读定义。

## 对照源码

### 怎么开

本页的方法可以从一个配置、错误、等待调用或张量转换开始。阅读前记录仓库与固定提交，再沿同一快照追踪定义、赋值、校验和消费者。

材料中的 setup.py 入口声明可作为插件阅读起点；配置问题可从 additional_config 的读取逻辑开始。配置输入与最终行为之间的完整关系，参见 [Ascend 配置](../concepts/ascend-config-system.md)。

本页没有提供可以验证固定双机部署的启动命令。

### 会报什么错

本地材料包含以下错误或警告线索：

- Balance Scheduling 的角色限制：存在传输配置且角色不符合 kv_both 要求时拒绝。
- 重计算调度在 producer 角色上的警告：发出警告后关闭选项；未来弃用的文字属于当时声明，不能据此认定某个后续版本已经删除。
- 重计算调度在其他不适用条件下的错误：完整适用范围仍需结合连续上下文核对。

排查时保留错误条件、错误结果与后续赋值，避免只搜索消息文本。

### 开销和什么时候别开

源码阅读本身可以在没有 NPU 的条件下完成。材料展示的 CPU 搬运、数据类型转换和流同步，是后续测量开销的观察点；材料没有实际耗时，不能据此给出性能数字或推荐开关组合。

当问题涉及实际加载、设备执行或性能时，应补充运行日志、最终配置和测量结果。静态分支分析负责说明可能路径，现场证据负责确认本次走过的路径。
