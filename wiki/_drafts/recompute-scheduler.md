RecomputeScheduler 是面向 PD 分离中 D 端的调度器实现：请求被抢占后，它尝试通过保存历史状态或交回 P 端重新计算，让请求获得继续执行的机会。

PD 分离是把提示词处理与后续生成交给不同执行组：P 端执行 prefill，计算提示词并建立历史状态；D 端执行 decode，在历史状态上继续生成。历史状态通常由 KV cache 保存，即保留后续 attention 计算需要的历史表示，避免从头计算已经处理过的位置。

本页依据本地材料中的代码与文档摘录整理。材料包含若干固定提交的片段，但不足以完成四个在册社区版本的逐条核对，因此不登记已验证版本。

## 请求被抢占后，为什么需要恢复路径？

调度器决定当前一步让哪些请求执行。抢占表示正在执行的请求暂时让出资源；如果继续生成所需的历史状态不能留在设备上，恢复时就需要找回这些状态，或者重新计算它们。

在 PD 分离中，重新计算提示词可以交给 P 端。D 端需要把“需要重新计算”这一事件通知出去，代理再组织后续请求。代理是位于调用方与执行实例之间的服务，负责接收请求、转发请求并处理返回结果。

材料中的一个调度器类说明采用“尽力保存”的策略：能够卸载被抢占的 KV 就卸载，无法卸载时再回 P 端重做 prefill。这里的卸载是把历史状态移出当前设备存储，以便后续恢复。因此，调度器名称里的 recompute 不表示每次抢占都会立即从头计算。

这两条路径付出的代价不同。保存路径需要传输并保留历史状态；重新计算路径需要再次执行已经做过的计算。选择了保存路径，也不等于保存操作已经完成。材料没有提供这两条路径在具体设备上的耗时、成功率或吞吐实测。

## D 端怎样把“需要重算”交给代理？

材料中固定 GLM 执行快照展示了一种特殊输出：D 端为需要重算的请求返回 STOP，新增 token 列表为空，同时将停止原因设为 `recomputed`。

这几个字段承担不同职责。STOP 表示这一段引擎输出结束；空 token 列表表示该帧没有新增生成内容；`stop_reason="recomputed"` 则把恢复事件与普通结束区分开。处理这条路径的代理需要识别停止原因，再决定怎样重新提交请求。

这是一项跨组件约定：调度器产生恢复信号，代理解释该信号并组织续接输入。仅看到 STOP，尚不足以判断用户要求的生成已经全部完成。

## 已经生成的内容怎样接回输入？

材料中的另一份代理实现按 token 编号组织重试输入。token 是分词器输出的离散符号，通常用整数编号表示；编号列表保存了模型实际接收和生成的符号顺序。

该实现把原提示词的 token 编号与已经输出的 token 编号相接，并从原生成额度中扣除已输出数量。对于聊天请求，拼接结果通过 KV 传输参数中的专用字段传递；对于其他请求，拼接结果直接替换 prompt。实现还要求返回 token 编号，供这条续接路径使用。

可以用一组示意编号完整走一遍：

- 请求 A 的原提示词为 `[11, 12, 13]`，最多生成 5 个 token。
- 被抢占前，请求 A 已输出 `[21, 22]`。
- 代理组织的重试历史为 `[11, 12, 13, 21, 22]`。
- 剩余生成额度为 5 减去 2，即 3 个 token。

这些编号只是说明列表拼接和额度扣减的示意数，不代表真实词表中的文字。[A]

重新提交时，已经输出的两个 token 成为继续生成所依据的历史，剩余三个名额用于后续输出。这份摘录说明了输入与额度如何变化，没有展示客户端如何跨重试合并流式结果，也没有证明重试前后会得到与未抢占执行完全相同的输出。

## 为什么还会重算最后一个提示词 token？

“被抢占后回 P 重算”和“接收 KV 后重算最后一个提示词 token”是两个不同环节。

材料中固定 GLM 执行快照的一段说明指出：在 PD 分离的 D 端启用本调度器时，接收 KV 后，调度器把已计算 token 数设为 N−1，使 D 端在 MTP decode 前重算最后一个提示词 token。这里 N 是提示词 token 数；MTP 是多 token 预测结构，推理时可用配套模块生成投机候选。

例如，提示词有 4 个 token 时，已计算数量被设为 3，留下最后一个提示词位置供 D 端执行。这是对材料中 N−1 规则的示意展开。[A]

同一段说明要求 Worker 元数据不要把这一步当作 prefill。Worker 是负责设备执行与相关资源管理的角色；元数据则告诉执行侧本轮输入应按什么路径处理。因此，调度进度与执行阶段标签需要配合：进度上留下一个位置重新计算，并不意味着执行侧应按普通 prefill 处理。

## GLM 双机主线能据此开启吗？

本页与主线的连接点是[多请求并发](../concepts/concurrent-requests.md)：多个请求共同竞争执行预算与缓存资源时，需要进一步理解被抢占请求怎样恢复。本机制讨论的是其中采用 PD 分离后的 D 端恢复路径。

固定 GLM 执行快照提供了两项局部依据：向外返回重算信号，以及接收 KV 后在 MTP decode 前重算最后一个提示词位置。局部代码存在，尚不足以证明某个 GLM 双机部署已经接好对应代理、传输连接器与全部状态恢复路径。

材料没有提供 GLM-5.3-Flash 双机上这条恢复链的实机运行记录，也没有逐项展示模型全部历史状态如何保存和恢复。因此，本页将其作为源码阅读与有条件的工程参考，不给出已跑通的部署命令或性能结论。

## 名称与开关容易掩盖哪些区别？

**启用开关与最终选中调度器是两件事。** 材料中的平台代码先处理重算调度配置，后续还可能把调度器类改为动态批处理调度器。检查配置时需要追到最终选择结果，不能只检查开关值。

**无法卸载与必然回 P 也不是同一个结论。** 另一份代码片段在卸载未成功后检查细粒度 TP。TP 是把一次张量计算分片到多个设备执行；细粒度 TP 允许特定模块使用单独的分片配置。当 attention 输出投影或 MLP 的并行尺寸实际大于 1 时，该片段阻止返回 P；后续处理会终止请求。尺寸为 1 时则保留回 P 重算的路径。

**重算信号与正常生成结束需要分别处理。** 材料中的恢复帧同时具有 STOP 和专用停止原因；代理需要按完整约定解释它。

**接收 KV 后重算一个位置，与抢占后重建历史范围不同。** 前者是 MTP decode 前的局部处理，后者涉及请求恢复。两者都出现“重算”，触发条件与工作量却不同。

## 对照源码

### 怎么开

材料中的参数表将 `recompute_scheduler_enable` 列为布尔开关，默认关闭，适用位置是 PD 分离的 D 端，角色为 `kv_consumer`。

另一段文档说明，调度器配置正在迁移到 `scheduler_config`：迁移期间仍支持旧顶层键，但旧格式已弃用；同一字段同时出现在两处时，以嵌套配置中的值为准。材料没有给出旧格式最终停止支持的版本。

实际核对需要连起三处：开关从哪里读取、角色校验怎样处理，以及平台最终选中了哪个调度器类。当前摘录不足以提供覆盖各社区分支的完整启动命令。

### 会报什么错

材料中的校验代码对 P 端作了单独处理：当角色为 `kv_producer` 时，记录 warning，并将重算开关关闭。

在这个分支之外，如果没有 KV 传输配置，或角色不是 `kv_consumer`，所示代码会抛出 ValueError，说明本开关只支持 PD 分离的 D 端，不支持 PD 混合模式。

同一材料中的参数文档却声称 P 端开启也会启动失败，与上述代码分支不一致。[!] 当前能确认的是摘录所示分支会警告并关闭；其他启动检查是否还会影响最终启动，需要完整调用路径才能判断。

### 开销和什么时候别开

恢复链的主要代价来自历史状态传输、重新计算，以及代理重新提交请求的处理。材料没有给出可以量化这些代价的实测数据。

工程核对中有三项直接影响行为：

- 代理是否识别专用重算停止原因，并按实现约定组织续接输入。
- 平台后续配置是否覆盖了重算调度器的选择。
- 卸载失败时，当前模块分片配置是否允许回 P。

只有开关而缺少对应恢复链时，不能据此认定请求能够继续完成。细粒度 TP 下的终止分支也说明，卸载失败后的结果必须按具体实现与配置判断。
