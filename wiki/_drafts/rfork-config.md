RFork 是让新起的 Worker 从已经加载好模型的 Worker 读取权重的工作版加载方式。Worker 是负责设备初始化、模型执行与资源管理的执行角色；已经加载好、可以提供权重的来源 Worker 称为 seed。本页解释配置由谁读取、无效值怎样处理，以及哪些看起来相近的设置实际上属于不同组件。

本页依据提供的本地代码摘录整理，范围限于材料标示的 RFork 工作版快照。配置解析结果来自静态阅读，未进行设备运行验证；材料不足以确认它与社区发布分支的对应关系。

## 一项设置究竟交给谁？

RFork 加载器负责读取客户端设置。它注册的加载器名称是 rfork，初始化时从模型加载器的附加配置中构造配置对象；对应字段名为 `model_loader_extra_config`。后续建立加载会话时，再检查连接 Planner 所需的信息。

Planner 是管理可用 seed 的外部服务。它与 vLLM 逐 token 选择执行工作的 scheduler 是不同组件；客户端字段虽然叫 `rfork_scheduler_url`，这里填写的是 Planner 地址。

seed 还会启动自己的服务。该服务有绑定地址、端口和健康检查超时等函数参数。函数接受某个参数，只能说明调用它时可以传入这个值，不能据此认定模型加载器的 JSON 配置也开放了同名设置。

因此，配置需要按接收者区分：

| 接收者 | 本材料展示的入口 | 影响什么 |
| --- | --- | --- |
| RFork 加载器 | 模型加载器附加配置 | 构造客户端配置 |
| RFork 加载会话 | 已解析的配置对象 | 检查 Planner 地址及模型身份信息，启动 seed 服务 |
| seed 服务函数 | 函数调用参数 | 监听地址、端口与健康检查超时 |
| 独立示例 Planner | 自己的命令行参数 | 服务监听位置与 seed 分配策略 |

例如，修改客户端请求超时，改变的是客户端采用的超时设置。示例 Planner 的监听端口则由它自己的启动参数决定，两者没有共享一个配置入口。

## 为什么无效值有时回退，有时直接报错？

材料展示了两类处理方式。

一类把无效输入当作“这一层没有可用值”，继续尝试环境变量或默认值。字符串设置和两个 timeout 使用这种方式。

另一类要求输入本身满足约束，不满足就抛出异常。心跳间隔、租约释放重试间隔和释放尝试次数使用严格校验。

这一区别会影响排错方向：看到程序采用默认值，应检查前面的值是否被解析器拒绝；看到配置异常，则应修正类型或取值，而不是继续调整连接重试。

### 字符串设置怎样选择配置项？

字符串读取函数先按给定顺序找到第一个**存在于配置中的键**，再检查它的值。如果值不是字符串，或者是空字符串，就尝试环境变量；环境变量也没有可用字符串时，才使用默认值。

这里的顺序是“先选键，再检查值”，不是“遍历所有别名，找一个有效值”。第一个键即使无效，也会挡住后续别名。

另外，摘录中的检查没有去除首尾空白。只含空格的字符串也会通过非空检查；通过这一层不代表地址格式正确或服务可达。

### 两个 timeout 接受哪些值？

seed timeout 与 request timeout 使用有限正数解析器。它接受整数、浮点数，以及可以转换成浮点数的字符串；转换结果必须大于零，并且不能是无穷大或非数值。

| 输入 | 解析结果 |
| --- | --- |
| `5`、`5.0`、`"5"` | 得到正数 5 |
| `true` | 拒绝，布尔值不作为数值接受 |
| `0`、负数 | 拒绝 |
| `"abc"`、`"inf"`、`"nan"` | 拒绝 |

这些只是解析规则，尚不能说明两个 timeout 分别包围了哪些网络或传输操作；精确作用范围还需要对应调用点。

同样，第一个存在的配置键一旦无效，函数就转向环境变量，不再检查后续别名。

## 能不能顺着一组输入算出最终值？

可以。下面用 request timeout 说明配置优先级。材料给出的默认常量是 10 秒。

假设配置里同时存在两个键：

```json
{
  "rfork_request_timeout_sec": 0,
  "request_timeout_sec": 20
}
```

再假设对应环境变量的值是字符串 `"7"`。

解析过程是：

1. 找到优先键 rfork_request_timeout_sec，其值为 0。
2. 0 不是正数，解析失败。
3. 停止检查配置中的后续别名，因此不会采用 20。
4. 环境变量 `"7"` 可以转换成有限正数，最终得到 7 秒。

如果环境变量也无效，最终才会采用默认的 10 秒。这个例子说明，增加一个别名值并不一定能覆盖错误的优先键；应修正或移除那个优先键。示例输入及解析结果的依据集中列在页末。

### 哪些字段必须使用真正的 JSON 数字？

心跳间隔与租约释放重试间隔要求有限的正整数或正浮点数。数字字符串不被接受，布尔值也不被接受。

租约释放最多尝试次数要求正整数。浮点数即使写成 3.0，也不满足整数类型检查。

材料给出的默认常量如下。它们说明默认配置值，不证明所有调用路径的完成时限或实际重试过程。

| 设置 | 默认常量 | 输入要求 |
| --- | --- | --- |
| seed timeout | 5 秒 | 可转换为有限正数的整数、浮点数或字符串 |
| request timeout | 10 秒 | 可转换为有限正数的整数、浮点数或字符串 |
| 心跳间隔 | 30 秒 | 有限正 JSON 数字 |
| 租约释放最多尝试次数 | 3 | 正 JSON 整数 |
| 租约释放重试间隔 | 30 秒 | 有限正 JSON 数字 |

后面三个设置由对应的 rfork_ 配置键直接取值或采用默认值，所展示的读取逻辑没有环境变量回退。不能把 timeout 的宽松解析规则推广到它们。

## seed 端口为什么可能没有按预期固定下来？

端口配置分为“读取基值”和“为当前 rank 计算端口”两步。rank 是分布式执行成员的编号；这里使用的是 global rank。

读取 `rfork_seed_port_base` 时，配置工厂只保留整数类型，其他类型直接变成 0。因此，数字字符串或浮点数不会按其数值设置端口基值。布尔值虽然会通过 Python 的整数类型初筛，后续校验仍会拒绝它；负整数及大于 65535 的整数也会被拒绝。

启动 seed 服务时，基值为 0 表示交给操作系统分配端口。基值为正时，服务尝试使用“基值加 global rank”的结果；如果结果超过 65535，后续代码会告警并改用 0。

例如，假设基值为 65534，当前 global rank 为 2，两者相加得到 65536，超过端口范围，最终改为动态分配。这个示意只演示计算和回退，不代表端口绑定已经经过实机验证。

这也说明，基值本身通过校验，并不保证每个 rank 都会使用固定端口。端口能否成功绑定，还需要检查实际运行环境。

## 独立 Planner 和清理函数还有哪些不同规则？

材料中的 Planner 是一个独立示例程序。其命令行帮助说明：

| 参数 | 展示的默认来源或范围 | 含义 |
| --- | --- | --- |
| `--host` | RFORK_MOCK_HOST，未设置时为 0.0.0.0 | Planner 的绑定地址 |
| `--port` | RFORK_MOCK_PORT，未设置时为 1223 | Planner 的监听端口 |
| `--alloc-policy` | 只接受 fifo 或 lru；帮助说明默认取 RFORK_MOCK_ALLOC_POLICY 或 fifo | seed 分配策略 |

这些属于示例 Planner 的启动设置。材料没有展示它们可以通过 RFork 客户端配置修改，也没有提供足够逻辑解释两种分配策略的完整选择过程。

清理传输引擎的函数又有自己的参数规则。TransferEngine 是提供内存登记和数据传输能力的对象；这里的 finalize 操作负责其清理。该函数要求最多尝试次数为正整数，但允许重试间隔为零，只要间隔是有限的非负整数或浮点数。

这与租约释放重试间隔必须**大于零**的规则不同。两者作用于不同资源，不能因为都叫“重试间隔”就共用约束。

清理失败也不一定进入下一次尝试。所展示的分支只有在已配置 not-ready 错误码、返回结果提供可调用的 get_code 方法，并且错误码相匹配时，才可能继续重试；总次数仍受上限约束。

## 哪些相近设置需要分开理解？

**timeout 接受数字字符串，不代表所有时间参数都接受。** 两个 timeout 会先转换再判断；心跳与租约释放间隔直接要求 JSON 数字。

**端口基值合法，不代表每个 rank 的最终端口都固定。** 加上 global rank 后仍可能越界，并触发动态端口回退。

**seed 服务函数有默认参数，不代表客户端开放了同名字段。** 函数接口与用户配置接口需要分别核对。

**最多尝试次数的默认值，不足以解释完整重试行为。** 当前材料没有展示租约释放调用逻辑，无法确认次数是否包含首次尝试、什么错误会重试，以及等待发生在哪一步。传输引擎清理函数的重试条件则有单独摘录，不能拿来补齐租约释放逻辑。

### 会报什么错

摘录展示了以下校验消息：

- 缺少 Planner 地址：`rfork_scheduler_url is required; configure it with model_loader_extra_config or RFORK_SCHEDULER_URL`
- 缺少模型标识或部署策略名：`RFork requires non-empty model_url and model_deploy_strategy_name`
- 心跳或租约释放重试间隔类型、数值不合格：消息要求对应字段为 finite positive JSON number。
- 租约释放最多尝试次数不合格：`rfork_lease_release_max_attempts must be a positive JSON integer`

这些异常发生后是否会进入其他加载路径，还取决于调用方的异常保护范围；提供的摘录不足以完整确认。
