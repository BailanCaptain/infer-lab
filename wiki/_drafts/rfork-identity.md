RFork 身份匹配用一组描述信息区分权重来源，帮助接收方找到与自己所需分片相符的候选者。它解决的是“可以向谁借权重”，权重数值是否完全相同还需要另外的内容校验。

本页讨论 RFork 工作版相关材料中的身份描述机制。RFork 是让新起的 Worker 从已加载好模型的 Worker 读取权重的加载方式；Worker 是负责模型执行与设备资源管理的执行角色。提供权重的来源称为 seed，正在接收权重的一方称为 receiver。完整加载流程见 [RFork 总览](../concepts/rfork.md)。

## 为什么模型名字相同，还不能直接借权重？

权重是模型训练得到、推理时读取的数字。一个模型分布在多个设备上时，每个 Worker 可能只持有其中一部分，这部分称为分片。

例如，tensor parallel（TP）把一次张量计算分给多个设备，各设备持有相应的权重分片。两个 Worker 即使使用同一个模型地址，也可能分别持有矩阵的左半部分与右半部分。它们属于同一模型，却不能互相替代。TP 的切分方式见 [Tensor Parallel](../concepts/tensor-parallel.md)。

expert parallel（EP）则把不同专家放在不同设备上。专家是 MoE 中执行前馈变换的模块；MoE 通过路由机制让输入经过部分专家。因此，两个 Worker 的张量形状相同，也可能只是它们分别持有数量相同、编号不同的专家。专家分布见 [Expert parallel](../concepts/expert-parallel.md)。

身份匹配需要同时回答三类问题：

| 要区分什么 | 描述信息提供什么帮助 |
| --- | --- |
| 模型与部署配置是否相符 | 比较模型标识、revision、量化、架构及其他影响权重布局的配置 |
| 准备传输的张量结构是否相符 | 比较张量名称、形状、数据类型与 NPU 格式 |
| 是否属于同一个分片位置 | 区分 TP、PP、EP 编号，以及需要隔离的 DP 分片编号 |

这里的 rank 是成员在某个分布式通信范围内的编号。TP rank 与 EP rank 分别标识对应通信组中的位置，不能把它们当作全局唯一的设备编号。

## 配置指纹、结构摘要和 seed key 各负责什么？

材料展示了三个不同层次的描述。

**兼容性指纹描述配置。** fingerprint 是根据所选描述信息生成的摘要。材料中的配置描述符包含协议版本、模型地址、部署策略名、模型 revision、量化配置摘要、架构和 RoPE 信息。revision 用来标识模型版本；量化配置描述低精度数值表示相关设置；RoPE 是一种用于表示 token 位置的旋转位置编码。这里能确认这些信息被纳入描述符，辅助函数怎样提取、规范化它们仍需核对。

配置描述还包含有效 KV 角色和 mix placement。前者区分与 prefill、decode 分工有关的角色，后者涉及专家放置。材料注释指出：不同角色可能生成不同的推理张量，而专家放置可能在张量形状不变时改变其内容。因此，仅比较形状不足以覆盖这些差异。

**结构摘要描述实际准备传输的张量集合。** 它从已构建模型中取得可传输张量的名称、shape、dtype 和 NPU format。shape 是各维的长度；dtype 是元素的数据类型；NPU format 是设备侧的存储格式，与元素精度是两回事。结构摘要补充的是模型实际形成的张量结构，而不只是配置里声称的结构。

材料要求使用可传输张量收集函数的输出，以排除只在运行时使用的临时缓冲区。离设备检查时，读取 NPU 格式会得到空值；这种检查得到的格式信息与设备上取得的实际格式信息需要分别理解。

**seed key 描述候选分组。** 材料中的 key 描述符把兼容性指纹、结构摘要、模型标识、TP／PP／EP rank、分片 DP rank 和草稿模型标记组合起来。PP 是按模型计算顺序划分执行阶段的 pipeline parallel；草稿模型是投机解码中提出候选 token 的模型，与正式验证和输出的目标模型角色不同。

这些信息用于身份筛选。传输阶段怎样核对张量清单、读取字节，见 [RFork 传输](../concepts/rfork-transfer.md)。

## 用两个小矩阵，怎样看出结构相同与内容相同的区别？

设两个候选 seed 都提供名为 W 的二维张量，形状均为两行两列，数据类型与设备格式也相同。下面是为讲解设定的数值。[A]

候选 A 的两行分别是：

- 第一行：1、2；
- 第二行：3、4。

候选 B 的两行分别是：

- 第一行：5、6；
- 第二行：7、8。

如果结构摘要只取名称、形状、数据类型和设备格式，二者提供的这些输入完全相同。摘要没有读取其中的 1、2、3、4 或 5、6、7、8，因而无法借此区分这两组数值。[I]

数值差异会改变计算结果。取行向量 x 为 `[1, 1]`，右乘候选 A 的矩阵时，第一个输出是 1×1＋1×3＝4，第二个输出是 1×2＋1×4＝6；换成候选 B，输出分别变为 12 和 14。[D]

这个例子说明：名称、形状、类型与格式一致，只说明这些结构属性一致。要判断权重数值是否相同，需要覆盖内容的校验依据。

## 为什么 DP rank 有时也要参与匹配？

data parallel（DP）把不同请求或批次分配给不同执行组。在普通复制权重的布局里，各 DP 组可以持有相同权重；与专家分布或细粒度 TP 结合后，不同 DP 位置也可能持有不同内容。

材料中的分片选择逻辑按条件返回 DP rank：

| 条件 | 返回结果 |
| --- | --- |
| 细粒度 TP 被判为启用 | 读取并返回 DP rank |
| 未启用细粒度 TP，但模型的 MoE 标记不是明确的 False，且 DP 大小是大于 1 的非布尔整数 | 读取并返回 DP rank |
| 不满足上述条件 | 返回空值 |

细粒度 TP 允许特定模块采用各自的 TP 切分配置。这里的判定检查输出投影、词表输出层、嵌入层和前馈模块四项配置；任一项是大于零的非布尔整数，就判为启用。布尔值 True 不属于这段代码接受的整数配置。

MoE 标记未知时，条件中的“不是 False”仍然成立。不过，即使进入需要分片编号的分支，若配置对象没有 DP rank 属性，读取结果也仍为空值。条件表达了隔离意图，字段是否实际齐备还要检查调用现场。

举一个示意：两个 Worker 都是 TP rank 0，但分别持有专家集合 A 与专家集合 B。如果其他 key 输入相同，加入不同的 DP rank 可以把它们分开；若对应字段缺失，便不能依靠这个字段完成区分。[I]

## GLM 双机案例能直接采用哪套身份规则？

本页材料没有提供 GLM-5.3-Flash 固定双机基线中身份模块的完整调用链，也没有证明这里展示的描述符就是该基线实际使用的方案。

因此，对 GLM 双机中的某个 Worker 判断“它能向谁借权重”时，需要核对该部署真正加载的 RFork 实现、各组的分片位置，以及生成 key 时实际传入的字段。不能把另一份身份模块中的结构摘要或 DP 隔离规则直接套入固定部署。

这一缺口影响候选匹配范围的判断；本页没有据此给出双机候选池数量或匹配结果。

## key 相同，究竟能说明什么？

key 相同表示参与 key 构造的描述信息得到相同结果。其解释范围取决于实现选了哪些字段、字段如何提取，以及调用方是否提供了完整值。

结构摘要增加了对实际张量结构的描述，但仍不读取权重数值。它不能作为逐字节校验和。即使两份权重来自相同架构，只要数值不同，后续模型计算就可能不同。

DP rank 是否参与也取决于布局。普通复制 DP 与内容分片 DP 的需求不同，“DP 总是复制权重”或“DP rank 总要进入 key”都不足以描述材料中的条件逻辑。
