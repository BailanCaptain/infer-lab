RFork 是让新起的 Worker 从已加载模型的 Worker 读取权重的工作版加载方式。Worker 是负责模型执行的工作进程；提供权重的一方称为 seed，接收权重的一方称为 receiver。本页解释接收端为什么需要选择权重处理顺序，以及为什么张量元素数相同仍不足以证明可以直接传输。

本页依据提供的本地摘录，分别讨论 RFork 工作版与一个社区源码快照。它们的行为边界分别保留，尚未完成源码独立核验，也没有设备实测记录。

## 为什么接收权重还要关心布局？

模型权重是推理时读取的数字。张量除了包含数字，还具有形状、数据类型，以及设备实际采用的存储格式。加载后的处理又可能改变这些表示，或改变模型对象持有哪一块存储。

processed layout 指经过加载后处理的权重布局；checkpoint layout 指本页另一条接收路径所对应的加载表示。checkpoint 是保存模型参数的检查点。这里需要区分的核心是：接收端在传输前准备后处理布局，还是在传输后继续执行相应处理。

这项选择发生在模型启动、接收权重的阶段。理解这一位置可以接续阅读 [RFork 启动](../concepts/rfork-startup.md)；它与每次请求的逐 token 计算是不同阶段。

接收端需要同时回答三个问题：

- 当前准备的张量，是否已经处于应当接收的后处理阶段？
- 本地张量的形状与存储格式，是否满足传输检查？
- 收集到的对象是模型权重，还是应由接收端自己维护的运行时临时状态？

这三个问题不能只用“要搬多少个元素”回答。

## 为什么有的路径先处理，有的路径后处理？

加载后处理可以改变权重布局。RFork 工作版摘录中，processed-layout 路径先调用加载后处理，再执行 NPU 同步。NPU 是执行模型计算的设备；同步在这里用于等待异步布局转换完成，随后才能暴露相应缓冲区供传输使用。

另一条 checkpoint-layout 路径在传输后调用加载后处理，但临时跳过特定的未量化 MoE 方法。MoE 是用多个专家模块与路由机制组织计算的模型结构；这里跳过的是其中一个具体实现的后处理，不能据此解释为所有模型模块都跳过后处理。

两条路径可以按接收端的处理阶段对照：

| 路径 | 摘录展示的处理顺序 | 需要保留的区别 |
| --- | --- | --- |
| processed layout | 加载后处理 → NPU 同步 → 暴露缓冲区供传输 | 传输前要等待异步布局转换完成 |
| checkpoint layout | 传输 → 带特定 MoE 跳过逻辑的加载后处理 | 传输后仍有处理调用，不能概括为完全不处理 |

processed-layout 分支还在加载后处理外包了一层临时上下文。材料没有完整展示该上下文的实现，因此这里只确定其调用位置，不扩展说明内部替换规则。

## 什么条件会选择 processed layout？

在 RFork 工作版摘录中，以下任一条件成立，就要求 processed-layout transfer：

| 判断对象 | 摘录中的条件 | 对接收流程的影响 |
| --- | --- | --- |
| 模型量化配置 | quantization 不是 None | 选择先准备后处理布局的路径 |
| 权重 NZ 配置 | 值不是布尔类型，且转换成整数后等于 2 | 选择同一路径 |
| 硬件布局策略 | 策略名称为 FORCE_NZ | 选择同一路径 |

量化是用低精度格式及相应缩放表示数值的方法，详见[量化](../concepts/quantization.md)。ND、NZ 则是设备存储格式，涉及数字如何排列，详见 [ND 与 NZ](../concepts/tensor-layout.md)；数值精度与存储排列需要分别理解。

布尔类型的排除条件有实际含义：虽然 Python 中布尔值也能转换成整数，这段判断明确不让布尔值通过“整数等于 2”这一条件。

硬件策略检查捕获 AttributeError 或 RuntimeError 时返回 False。这只是该检查的异常分支，不能解释为检测已经证明硬件不需要 NZ。材料也没有给出 NZ 模式的完整定义，因此本页不据此解释其他模式的全局作用范围。

## 形状不同，为什么有时还能接收？

形状描述张量有几维、每维多大；元素总数则是各维长度的乘积。二者相关，但含义不同。

下面是解释形状检查的示意：本地张量形状为 2×3，seed 给出的形状为 3×2。二者都包含 6 个元素，因此通过“元素数相同”这一步检查。但是否能够继续，还取决于本地存储能否成功建立 seed 所需的视图。[A]

材料中的形状调整逻辑分两步：

1. 比较本地元素总数与 seed 形状要求的元素总数。不同则记录形状不匹配并返回 False。
2. 元素数相同时，尝试用 `view(seed_shape)` 调整张量视图。成功后把结果赋给张量的数据；发生异常则记录失败并返回 False。

`view` 是按指定形状建立张量视图的操作。这里的代码没有展示一套通用的设备格式转换过程，因此“形状调整成功”不能代替“存储格式兼容”的检查。

社区快照的摘录还展示了另一项检查：读取本地 NPU 存储格式，并与 seed 清单中的格式比较。清单是描述待传张量属性的元数据表；本地格式无法读取时，该代码分支直接返回失败结果。

本地材料没有给出形状调整、结构摘要和完整清单校验之间的全部调用顺序。这些检查应分别理解，不能拼成一条已经核实的完整调用链。

## 为什么临时缓冲区要留在接收端？

模型权重决定模型如何计算，运行时临时缓冲区则为当前实例执行计算提供空间。两者即使都表现为张量，也不应自动采用相同的传输规则。

RFork 工作版摘录明确把 topk_indices_buffer 列入运行时专用张量名称集合。材料注释给出的原因是：这类临时张量属于本地执行状态，应保留接收实例选择的容量，因为 seed 与 receiver 可能使用不同的调度限制。

例如，假设 seed 与 receiver 为临时缓冲区选择了不同容量。直接沿用 seed 的容量，就不能保证仍符合 receiver 自己的执行配置。[A] 因此，收集权重时需要区分检查点派生的模型状态与本地执行所需的临时状态。

摘录只直接展示了名称集合及设计注释，尚不足以确定完整名称匹配方式、全部过滤条件与测试覆盖范围。

## 共享权重为什么可能连后处理都跳过？

draft 是投机解码中提出候选 token 的草稿模型，target 是负责正式验证与输出的目标模型。token 是分词器输出、通常用整数编号表示的离散符号。

RFork 工作版摘录包含一个单独的共享权重复用分支：当排除块集合非空，并且会话确认可以复用共享权重时，代码直接把模型切换到评估模式后返回，跳过后续所有加载后处理钩子。钩子是在指定阶段被调用的处理函数。

材料注释解释了原因：共享张量已经由 target 处理。再次处理可能修改共享存储，或重新绑定 Parameter 的数据。Parameter 是 PyTorch 表示模型参数的对象；重新绑定数据意味着该对象引用的底层张量可能改变。

这一提前返回有明确条件。它不能推广为所有 draft 都无需后处理，也不能仅凭“共享了部分权重”就认定可以走这条分支。

## 这些规则怎样用于 GLM 双机？

本页材料没有给出 GLM-5.3-Flash 双机实例实际采用的 RFork 版本、布局选择结果或传输清单，因此无法确定该部署会走哪条接收路径。

将这些规则用于具体部署，需要补齐接收端的量化配置、权重 NZ 配置、硬件布局策略，以及运行代码的固定快照。共享权重复用还需要会话检查结果。这些证据决定实际分支；模型名称本身不能替代它们。

## 哪几项检查需要分别理解？

**元素总数与形状。** 相同元素数允许代码继续尝试调整视图，但视图操作仍可能失败。

**形状与设备存储格式。** 形状描述各维长度，存储格式描述设备上的排列方式。调整形状不等于已经核对格式。

**模型状态与运行时状态。** 权重传输面向需要接收的模型状态；临时执行缓冲区可能需要保留接收端自己的容量。

**传输完成与后处理完成。** checkpoint-layout 路径仍展示了传输后的处理调用；共享权重复用分支则可能提前返回。处理顺序需要按实际分支判断。

**工作版与社区快照。** 本页分别引用两份快照的摘录，不能把其中一份展示的检查自动补到另一份实现中。

## 对照源码

### 怎么开

材料未提供完整启动命令或配置入口，不能据此给出可复制的启用步骤。

RFork 工作版的路径选择会读取模型的 `quantization`、Ascend 配置中的 `weight_nz_mode`，以及硬件的 `weight_layout_policy`。processed-layout 分支随后调用 `process_weights_after_loading`，并执行 `torch.npu.synchronize()`。

### 会报什么错

形状调整摘录展示了两类日志：

- `Weight shape mismatch for %s: local=%s, seed=%s`：本地元素总数与 seed 形状要求的元素总数不同，函数返回 False。
- `Failed to reshape RFork tensor %s from %s to %s: %s`：建立目标形状视图时发生异常，函数返回 False。

社区快照摘录还展示了 `RFork could not read the local NPU storage format for %s.`，对应无法读取本地 NPU 格式并返回 None。

材料没有展示这些返回值如何一路传播到启动入口，因此不能进一步确定最终异常、清理或回退行为。

### 开销和什么时候别开

processed-layout 路径把加载后处理放在传输前，并增加等待 NPU 异步转换完成的同步点。材料未提供耗时或额外显存的测量值。

路径选择与布局正确性有关，材料不足以支持为了缩短启动时间而绕过它。共享权重复用分支同样依赖会话确认结果：其跳过后处理的理由是避免再次修改已处理的共享状态，而非一个适用于所有接收端的优化开关。
