RFork 的生命周期管理负责协调三件进度不同的事：权重是否已经传完、向来源借来的名额是否已经归还，以及本机是否可以作为新的权重来源。权重传输成功，只完成了其中一件事。

RFork 是让新起的 Worker 直接从已加载好权重的 Worker 读取权重的工作版机制。Worker 是负责设备初始化、模型执行与资源管理的执行角色；提供权重的一方叫 seed，接收权重的一方叫 receiver。生命周期管理位于[启动与加载](../concepts/rfork-startup.md)过程中，也延伸到失败后的回退和进程退出。

本页依据本地材料整理，材料标注的工作版为 rfork@3284850b。材料包含部分实现和设计说明，尚不足以独立核实完整状态转换及其他版本的行为；本页因此是待源码复核的文字草稿。

## 为什么传完权重以后，还需要管理会话？

接收权重前，receiver 要向 Planner 借用一个来源名额。Planner 是管理来源与可借名额的外部服务，不是 vLLM 逐步安排推理请求的调度器。借用名额的记录叫租约，租约有自己的有效期。

传输还涉及另一类资源：接收端为权重准备的设备内存，以及向传输后端登记的可访问内存范围。登记之后，这些内存就成为传输操作所依赖的资源。注册、查询远端元数据或读取权重的过程中都可能失败，因此需要有人记住哪些资源仍待清理。

会话把这些进度放在一起管理，但不同进度不能互相代替：

| 进度 | 它回答什么问题 | 它不能单独回答什么问题 |
| --- | --- | --- |
| 权重传输完成 | 本次传输是否完整成功 | 来源名额是否已归还 |
| 租约归还得到确认 | 本机是否还记着这份借用 | 传输期间租约是否始终有效 |
| 可以发布为 seed | 是否满足本机启动来源服务的条件 | 远端未来的读取何时结束 |
| 清理满足回退条件 | 是否可以继续默认加载路径 | 是否已经完成全部外部账务收尾 |

其中，发布为 seed 是让本机成为其他 Worker 可以发现并借用的权重来源。它与本机使用已传入的模型进行推理，是两个不同的动作。

## 会话状态怎样反映传输中的变化？

材料中的生命周期枚举包含七个名称：

| 状态名 | 本次材料能确认的含义或使用位置 |
| --- | --- |
| INITIALIZED | 枚举中定义了初始化状态；摘录不足以展开其全部进入和退出条件 |
| LEASED | 传输要求处于这个状态，并持有租约 |
| CLEANUP_REQUIRED | 注册内存前先进入此状态，以覆盖后续失败或异常 |
| TRANSFERRED | 整个传输成功后设置，并安排后台归还租约 |
| READY | 实际启动来源服务所要求的状态之一，同时要求没有源租约 |
| SERVING | 枚举中定义了服务状态；摘录不足以展开其全部转换条件 |
| FINALIZED | 传输引擎终结成功后才设置 |

这些名称不是一条可以任意顺次经过的流水线。枚举只声明有哪些状态，具体函数中的条件才决定允许怎样转换。

最值得理解的是 CLEANUP_REQUIRED 的设置时机。实现先把会话标为需要清理，再调用内存注册。原因在于，失败不一定发生在“什么都没做”的时候：注册、元数据查询和读取都可能在内存已经被登记后失败，调用也可能抛出异常。

这样安排以后，失败路径会留下一个明确的收尾要求。只有整个传输成功，状态才改为 TRANSFERRED，并安排后台释放租约。内存登记与读取的具体职责见 [RFork 传输](../concepts/rfork-transfer.md)。

## 权重已经可用，为什么成为新 seed 还要等？

考虑一个示意过程：来源 Worker S 已经加载好权重，接收 Worker R 向 S 读取权重。R 完成传输后，后台开始向 Planner 归还这次借用名额。[A]

此时可能出现两个进度：

- R 的权重传输已经完成，可以继续使用传入的模型推理。
- Planner 尚未确认这份租约已经归还，R 仍持有源租约。

在材料展示的分支中，如果满足启动状态与注册要求，但仍持有源租约，而且归还流程没有被停止或耗尽重试，会话会保存稍后启动 seed 所需的参数，确保后台归还重试正在运行，并返回 DEFERRED。

DEFERRED 表示发布被延期。它没有表示来源服务已经启动，也没有要求丢弃传入的模型。材料中的日志明确说明，传入的模型仍可用于推理。

实际启动来源服务要求会话处于 READY，且没有源租约。因此，判断 R 是否已经成为 seed，要检查发布结果，不能只检查权重是否到位。

## 怎样判断租约是否已经归还？

材料中的归还接口把响应分为三类：

| 结果 | 材料展示的判定 | 对会话意味着什么 |
| --- | --- | --- |
| RELEASED | HTTP 200 或 404 | 按客户端协议接受归还结果 |
| RETRYABLE | HTTP 408、429、5xx，或 requests.RequestException | 进入可重试的处理分支 |
| REJECTED | 其余响应状态 | 没有被当作成功或可重试结果 |

HTTP 404 的含义尤其需要保留边界。客户端日志直接注明：它表示租约不存在，不代表已经验证了及时归还。因此，RELEASED 是客户端按协议接受的结果，不能据此补出一段传输期间的历史。

沿用 R 从 S 读取权重的示意：如果 R 归还时收到 404，客户端可以把这次归还视为已完成；仅凭这一响应，无法判断租约是在读取完成后才消失，还是更早已经过期。[A]

这一区别影响对并发容量的判断。归还成功回答的是当前协议如何收尾，而不是过去整个传输区间是否都在租约有效期内。

## 租约有效期怎样影响一次传输？

TTL 是有效期。材料中的说明把示例 Planner 的默认租约 TTL 设为 60 秒，并保留环境变量 RFORK_MOCK_LEASE_TTL_SEC 和命令行选项 `--lease-ttl-sec`。命令行值覆盖有效的环境变量值，时长必须是正整数秒。这些规则属于材料描述的示例 Planner，不能当成所有外部 Planner 的默认行为。

晚一些获取租约，可以缩短占用名额的时间。材料把缩短后的范围描述为内存注册、元数据获取、传输和归还，避免把更早的准备阶段也算入借用时长。

缩短占用范围并没有给出传输耗时上限。材料记录过一次约 23 秒的注册与传输区间，同时明确指出这只是一次观测；在负载增加或网络停顿时，60 秒 TTL 仍可能不够。本页没有独立运行这次测量，也不据此给出部署容量结论。

来源心跳过期与租约过期仍是独立机制。心跳用于报告来源仍然存活；租约用于记录借用名额的有效期。材料同时说明续租仍是提案，不能把来源心跳正常解释为本次租约持续有效。

## 为什么租约过期后，不能直接释放传输内存？

Planner 管的是名额账本，传输引擎执行的是按地址读取。两者的进度可能分开：账本中的租约过期时，一次读取仍可能正在进行。

材料中的续租提案明确区分了两种动作：

- 对已经过期的租约，禁止在它之下启动新的读取。
- 对已经在途的读取，等待完成，或使用传输后端支持的取消握手。

第二项尤其关系到内存安全。在途读取可能无法取消，不能仅因调度租约过期，就释放或注销它仍可能访问的缓冲区，也不能据此销毁来源。

这段内容是设计要求，不能读成当前工作版已经实现了相应保护。材料提出，若要严格保证并发限制与内存安全，还需要来源侧读取准入、能够阻止失效持有者继续操作的 fencing token，或显式排空正在进行的读取。仅有 Planner 容量计数不足以提供这些保证。

## 传输失败后，怎样决定能否回退？

回退是放弃本次 RFork 尝试，继续默认模型加载路径。默认路径可能再次分配模型内存，因此回退前的清理直接影响显存能否安全复用。

材料展示了一个明确的拒绝条件：清理结果属于 RForkFallbackCleanupResult，且其中的 can_schedule_seed 为假时，加载器抛出 RuntimeError。报错说明来源服务或已注册内存的清理失败，持有张量的引用仍被保留；继续分配第二个模型会让旧权重仍被固定时再申请一份权重内存。

这里的“保留引用”有具体作用：让底层张量存储继续存活，避免仍被登记的地址变成已释放内存。它同时意味着旧资源尚未彻底退出，不能把“传输失败”直接等同于“已经腾出显存，可以重新加载”。

本次摘录没有提供完整的回退清理结果定义及重试循环。因此，不能仅由这个拒绝分支补出全部允许回退的条件，也不能确定清理最多尝试几轮。

## 退出时，怎样才会进入 FINALIZED？

材料展示的 shutdown 分支有两个前置条件：

- 来源服务停止成功。
- 本机会话的源租约已经清除。

只有两项都满足，才调用传输引擎的终结操作；只有该操作成功，状态才进入 FINALIZED。这个状态因此比“发起退出”更具体，它记录的是满足条件后终结成功的结果。

本次摘录未覆盖完整 shutdown，也未给出传输后端终结操作对远端在途读取的全部承诺。结合前面的读取安全要求，退出时仍需区分本机清理状态与远端读取状态；不能单凭一个本机状态名称推导全部远端读者已经结束。[I]

## 这与 GLM 双机推理有什么关系？

本页讨论的是工作版的权重加载与资源收尾，不涉及模型每层的矩阵计算，也没有提供 GLM-5.3-Flash 双机部署中启用 RFork 的运行记录。

因此，本页不能把租约时长、来源发布条件或回退行为自动套入官方双机部署。若要把这套加载方式用于该部署，需要另行核实每个 Worker 的权重分片身份、实际 Planner 协议、传输后端版本，以及失败和退出时的读取排空约定。这里保留的是工作版机制边界，不给出未经运行验证的部署命令。

## 哪些进度最容易被当成同一件事？

**传输完成与租约归还是两个进度。** 完整传输成功后才安排后台归还，归还尚未完成时可能出现延期发布。

**模型可用于推理与已经成为 seed 是两个结果。** DEFERRED 分支明确允许传入模型继续用于推理，但来源服务还要等待启动条件满足。

**归还接口接受 404 与租约始终有效是两种判断。** 前者是当前响应的处理约定，后者需要传输期间的时间证据。

**来源存活与借用仍有效使用不同计时。** 材料把心跳过期与租约 TTL 分开，并把续租保留为提案。

**名额到期与读取结束属于不同系统。** 在途读取可能仍依赖已登记的内存，其结束或取消必须由传输协议确认。

### 会报什么错

回退清理不满足条件时，材料展示的 RuntimeError 为：

```text
RFork fallback aborted because seed service or registered memory cleanup failed; tensor owners remain retained. Refusing to allocate a second model while old weights are pinned.
```

它对应来源服务或已注册内存未清理完成的情况，处理目标是查清旧资源为什么仍被保留。

延期发布的日志为：

```text
RFork seed promotion is deferred until the source seed lease is released; the transferred model remains available for inference.
```

它对应 DEFERRED 结果，表示推理可继续，来源发布仍在等待。

租约归还日志中的说明为：

```text
404 means absent, not verified timely release
```

这条日志保留了接口确认与及时归还之间的区别。

### 开销和什么时候别开

本次材料没有给出生命周期管理线程、HTTP 重试或保活引用的完整资源开销，不能据此计算额外 CPU、网络或显存用量。

已展示的工程约束是：清理失败时可能继续保留张量所有者；租约未解决时可能延期发布；租约 TTL 不保证覆盖所有传输耗时。没有完成清理时，应先解决旧资源的收尾条件，不能强行继续分配第二个模型。

材料未提供可独立关闭生命周期保护的开关，也未证明绕过这些条件是安全的。
