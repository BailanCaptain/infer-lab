RFork 是让新起的 Worker 从已加载权重的 Worker 接收权重的加载方式。Worker 是负责设备初始化、模型执行和资源管理的执行角色。排查 RFork 时，需要分别回答：权重有没有接收成功、旧资源有没有清理完成、借用来源的租约有没有归还，以及当前 Worker 能不能再成为权重来源。

这些状态会互相影响，却不能只凭一条报错合并判断。例如，归还租约失败可能阻止当前 Worker 发布为新的来源，但材料中的实现明确允许模型加载或推理继续。

本页依据提供的本地代码摘录，讨论其中标注的 RFork 工作版和另一个 vllm-ascend 代码快照。它们的发布分支映射、现场依赖版本和实际运行结果尚未由本材料确认。

## 一次加载中，哪些状态需要分别检查？

提供权重的 Worker 称为 seed，接收权重的 Worker 称为 receiver。Planner 是管理可用 seed 和借用名额的外部服务；这里的调度与 vLLM 逐步调度推理请求是两件事。

排错可以沿四条线展开：

| 检查对象 | 要回答的问题 | 材料支持的判断 |
| --- | --- | --- |
| 传输依赖 | 所需接口能否导入、能否调用？ | 缺少必要 API 会在初始化或注册阶段失败 |
| 权重元数据 | 张量清单是否足以描述待接收的数据？ | 缺少形状或数据类型、形状与元素数不符，会使校验失败 |
| 内存清理 | 已登记的内存是否确认注销？ | 注册失败或回滚返回失败，都不能直接证明登记已经解除 |
| 来源租约 | Planner 是否确认本次借用已经结束？ | 租约未解决可能阻止发布 seed，但不必然阻止推理 |

租约是 Planner 分配的一次借用名额。内存登记则是向传输引擎登记可访问的内存范围。归还租约和注销内存分别处理这两类资源，确认其中一项完成，不能替代另一项的确认。

启动顺序见 [RFork 启动](../concepts/rfork-startup.md)，加载完成后各状态的关系见 [RFork 生命周期](../concepts/rfork-lifecycle.md)。

## 为什么失败后不能立即重新加载一份模型？

传输引擎可能已经接受了部分内存登记，随后批量注册才报错。错误本身不能指出究竟哪些登记仍然存在，因此实现需要尝试逐项注销，并保留尚未确认清理的状态。

材料中的注册回滚逻辑会保留尝试过的地址及其存储保活引用。保活引用的作用是让对应存储继续存在，避免登记仍有效时底层内存已经释放。由此，注册函数返回失败，只能说明本次注册流程没有成功完成，不能说明它没有留下资源。

默认模型加载器的回退路径也受到这个约束。当清理结果表明 seed 服务或已登记内存没有安全清理时，实现会抛出异常，中止回退。报错说明它拒绝在旧权重仍被固定时再分配第二份模型。

排查这类问题时，应把“传输为什么失败”和“失败后为什么不能回退”分别记录。后一个错误可能是前一个错误触发清理后暴露的资源状态；仅重复启动默认加载，不能证明旧资源已经安全退出。

## 怎样从元数据错误缩小范围？

manifest 是张量清单，用来描述要接收的权重。材料中的校验至少要求每个相关条目包含形状和数据类型，并检查形状推算的元素数是否等于条目声明的元素数。

例如，下面是一组用于理解校验的示意数据：

- 条目声明形状为 2 行、3 列。
- 这个形状包含 6 个元素。
- 如果条目声明的元素数也是 6，这一项检查通过。
- 如果声明为 5，形状与元素数不一致，校验失败。

这个例子只演示清单内部的一致性检查。即使元素数一致，也还不能据此确认远端与本地的形状、布局和分片完全匹配；本次摘录没有展示足够代码来完整说明这些后续比较。

另一个容易混淆的情况是额外形状元数据请求失败。材料中的工作版允许一种有条件的继续：权重清单已经具有完整的形状和数据类型时，可以使用这份完整清单。缺少这些字段时，额外请求失败就不能由这条分支消化。

因此，看到形状请求失败，应同时保存权重清单内容。只有请求错误，没有清单字段，无法判断是否满足继续执行的条件。

## 没有走 RFork，是否说明传输出了故障？

材料展示了一个主动绕过 RFork 的条件：启用动态 EPLB 时，代码记录警告并改用默认模型加载器。EPLB 是专家负载均衡机制，这里的动态路径被实现列为禁用 RFork 传输的条件。

这条日志说明加载路径发生了选择。排查时应先确认配置是否触发该分支，再调查连接或传输错误。

获取 seed 也需要看具体结果。在材料标注的 vllm-ascend 快照中，获取 seed 的接口返回 404，表示当前没有可用 seed；其他非 200 状态会进入异常处理。但函数最终返回空结果也可能来自被捕获的请求异常、运行时异常或值错误。只看到上层得到空结果，还不足以判断 Planner 正常返回了“无可用 seed”。

配置对应关系见 [RFork 配置](../concepts/rfork-config.md)。

## 租约归还失败，会影响哪些后续动作？

接收权重之后，receiver 需要结束对来源名额的借用。当前 Worker 是否能够发布为新的 seed，是另一个后续动作。

材料中的实现会在租约释放被拒绝时保留未解决租约，并取消延迟发布 seed 的请求。对应日志明确写出：Worker 不会通告 seed，模型加载或推理可能继续。

因此，应分别记录三个结果：

1. 模型加载是否已经完成。
2. 推理是否实际可用。
3. 当前 Worker 是否已经发布为 seed。

这三项需要各自的观察依据。租约错误日志能够解释第三项为何受阻，不能单独证明前两项成功或失败。

关闭流程也存在相应边界。工作版在来源租约未解决时，会保留 TransferEngine 状态，不再启动新的释放重试；已经在途的请求仍可能得到确认，否则后续恢复依赖 Planner 的到期或回收策略。TransferEngine 是 YuanRong 提供的传输对象，不是 Planner 本身。

## 为什么同样是 404，含义却不同？

HTTP 状态码需要连同接口操作一起解释。

| 操作 | 材料中的 404 含义 | 能得出的结论 |
| --- | --- | --- |
| 获取 seed | 当前没有可用 seed | 本次获取没有得到可用来源 |
| 归还租约 | 目标租约不存在，客户端按已释放处理 | 客户端可以结束这次释放流程，但不能证明租约曾被及时归还 |

归还租约时，材料中的客户端将 200 和 404 都归入已释放结果，同时明确提醒：404 表示不存在，不证明及时释放。它没有给出该租约为何不存在的现场证据。

本次可用材料也没有展示足以解释现场 400 的 Planner 服务端处理逻辑。需要保存具体请求所对应的响应体和 Planner 记录，才能继续判断；已有页面中的历史描述不作为本次新增事实的依据。

## 这对 GLM 双机部署意味着什么？

本页材料讨论的是权重加载和资源收尾，没有提供 GLM-5.3-Flash 官方双机部署的实际日志，也没有建立这些 RFork 快照与该部署基线的兼容关系。因此，本页不能据此给出 GLM 双机的启动命令、传输耗时、额外显存占用或成功率。

若在该部署中调查 RFork，首先需要确认实际使用的代码和加载路径，再逐个 Worker 记录依赖初始化、元数据校验、内存清理、租约归还和 seed 发布结果。材料中的“推理可能继续”仍需由实际推理结果确认。

## 哪些判断容易把排查带偏？

**“注册失败，说明没有任何内存登记成功。”** 批量注册错误不能确定哪些登记仍然存在，实现因此保留地址和存储引用，等待注销确认。

**“已经开始回退，就一定会用默认加载器启动。”** 清理不满足安全条件时，回退会中止，避免旧权重仍被固定时分配第二份模型。

**“租约归还失败，说明推理也失败了。”** 材料中的日志把发布 seed 与模型加载、推理分开处理，后两项可能继续。

**“归还接口返回 404，证明租约按时还掉了。”** 该结果只说明查询时租约不存在。

**“达到配置重试次数后，各快照都会停止。”** 本次材料展示了两种不同策略，必须对应实际运行代码判断。

本次摘录没有提供完整启用命令，不能从依赖导入或局部条件反推出一套可运行配置。

已能确认的依赖检查包括：YuanRong 的 TransferEngine、MemoryRegistration 和 ErrorCode API；材料还说明内存登记需要可调用的批量注册接口。另一个 vllm-ascend 快照要求 TransferEngine 提供可调用的 `get_rpc_port`，用于初始化后取得实际端口。材料没有给出满足这些能力的 YuanRong 版本号。

### 会报什么错

| 报错或日志片段 | 直接表达的状态 | 下一步需要保存的证据 |
| --- | --- | --- |
| `RFork requires the YuanRong TransferEngine, MemoryRegistration, and ErrorCode APIs.` | 必要依赖 API 导入失败 | 完整异常链、依赖版本和实际导入环境 |
| `RFork requires YuanRong TransferEngine with get_rpc_port support.` | 该快照要求的端口查询接口不可调用 | 实际传输对象的接口及初始化异常 |
| `RFork registration rollback is incomplete` | 注册回滚没有确认全部完成 | 后续注销结果及保留资源的日志 |
| `must include shape and dtype` | 清单条目缺少必要元数据 | 对应条目的完整内容 |
| `shape metadata does not match numel` | 形状推算元素数与声明不符 | 形状、声明元素数及条目名称 |
| `RFork fallback aborted` | 清理未满足回退条件 | seed 服务清理和内存注销的具体结果 |
| `RFork lease release stopped` | 释放流程已停止，租约仍未解决 | 释放响应、重试过程及 Planner 记录 |

这些日志标出代码观察到的状态；本次材料没有现场复现，不能将它们直接解释为某次部署的最终根因。

### 开销和什么时候别开

材料明确展示动态 EPLB 会绕过 RFork，改用默认加载器。除此之外，本次摘录不足以给出完整的互斥组合或性能适用范围。

能够确认的资源代价是：未确认注销的内存需要继续保活；未解决租约可能延迟或阻止发布 seed；安全清理未完成时，默认加载回退会被阻止。材料未提供这些状态持续多久、占用多少显存的实测结果。

### 版本差异

本次材料标注了两个代码快照，其租约释放重试策略存在差异。

| 条件 | RFork 工作版快照 `3284850b` | vllm-ascend 快照 `7d825229` | 排查影响 |
| --- | --- | --- | --- |
| 释放被拒绝 | 停止释放重试，取消延迟发布 seed | 停止释放重试，取消延迟发布 seed | 需要查明拒绝原因，不能等待普通重试自行恢复 |
| 可重试结果达到配置次数 | 停止重试，保留未解决租约 | 继续后台重试，提高重试间隔 | 配置次数在两份实现中不具有相同的停止含义 |

这两个快照没有在本次材料中完成发布分支映射。v0.23 维护分支、v0.26 分支、v0.30.0rc2 分支及 main 开发主线的支持范围、默认值和对应行为均未完成逐项核对，因此本页不登记这些版本的 `verified`，也不推断它们与任一快照一致。
