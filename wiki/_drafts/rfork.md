RFork 是一种权重加载方式：让新启动的 Worker 从已经加载好权重的 Worker 接收权重。Worker 是负责设备初始化、模型执行和相关资源管理的执行角色；提供权重的来源称为 seed，正在接收权重的一方称为 receiver。

本页讨论 RFork 工作版的局部加载逻辑，主要材料涉及工作版 `3284850b`。它关注的是模型开始执行请求之前，权重如何准备好，以及加载失败后哪些资源必须先处理。Worker 的整体启动过程见 [NPUWorker 启动](../concepts/npu-worker-lifecycle.md)。

材料展示了共享权重复用、按名称读取、失败清理、租约释放及部分绕过判断，尚不足以还原完整启动过程。下面将这些局部行为连起来解释；具体模型支持范围、配置入口及真实设备表现仍需完整源码和运行记录核实。

## 接收权重时，为什么还要关心权重的状态？

模型中的权重是计算要读取的数字。加载不仅涉及这些数字是否已经到达，还涉及它们是否处于后续计算所需的状态。例如，材料中的加载后钩子，是加载流程在准备权重后调用的后续处理；相关注释明确指出，重复处理可能修改共享存储，也可能重新绑定 Parameter 的 data。

这里的共享存储，指不同模型对象引用同一段底层内存。两个对象即使名称不同，也可能访问相同的权重字节。如果其中一个对象已经完成处理，再经由另一个对象重复处理这段内存，就可能影响前者。

材料给出了一条针对 draft 的分支。draft 是投机解码中提出候选 token 的草稿模型；target 是负责验证和正式输出的目标模型。在存在排除块、且会话确认可以复用共享权重时，这条分支跳过全部加载后钩子，直接返回处于 eval 模式的模型。eval 模式表示模型进入评估模式，并不单独证明服务已经可以接收请求。

这一分支的关键在于“会话确认可以复用”。材料没有展示完整检查，因此不能把它推广为所有 draft 都可以跳过加载后处理，也不能据此列出支持的模型组合。共享存储与加载后处理的完整关系需要结合 [RFork 张量布局](../concepts/rfork-layout.md) 阅读。

## 为什么有些重叠字节会读两遍？

接收方需要知道每个逻辑权重名称对应哪些字节。材料中的 manifest 是这样的张量清单；相关代码注释说明，清单校验之后，读取仍按逻辑名称组织。因此，两个名称如果对应重叠区域，可能重复读取其中一部分。

这种重复读取有传输代价。材料同时给出了保留它的理由：仅凭接收方地址重叠，不能证明两次读取可以合并。还必须确认，在整个重叠范围内，来源地址到接收地址的偏移映射相同。

用一组示意地址可以看清区别。下面的区间均包含左端、不包含右端，地址只用于说明映射关系。[A]

| 逻辑名称 | 来源字节区间 | 接收字节区间 |
| --- | --- | --- |
| A | 100–108 | 1000–1008 |
| B | 104–112 | 1004–1012 |

A 的 8 个字节依次放入接收区间 1000–1008；B 的 8 个字节依次放入接收区间 1004–1012。两次读取在接收区间 1004–1008 重叠，而这个重叠区间都对应来源区间 104–108。因此，这一组映射在重叠部分一致。分别读取会传输 16 字节，接收区间的并集为 12 字节，其中 4 字节重复传输。[D]

再把 B 的来源改成 204–212，接收区间保持不变。接收地址 1004 现在分别对应 A 的来源地址 104 和 B 的来源地址 204。接收位置仍然重叠，来源映射却不同；只按接收地址合并，会丢掉这种区别。[D]

这个例子只解释为什么“本地地址重叠”不足以作为合并条件。它不表示第二种清单会通过实际校验，也不表示当前代码已经实现第一种情况的读取合并。材料中的做法是接受可能的重复读取，保留按逻辑名称组织的传输。清单校验与读取过程可继续阅读 [RFork 传输](../concepts/rfork-transfer.md)。

## 加载失败后，为什么不能立即再分配一个模型？

接收权重的过程可能已经登记了可供传输使用的内存。登记使传输系统能够访问相应地址，也要求这些地址背后的存储在访问期间保持有效。因此，一次加载失败后，程序还要处理已登记内存及相关服务的清理状态。

材料中的失败分支检查一个清理结果对象：当它确实是 RForkFallbackCleanupResult，且 can_schedule_seed 为假时，程序抛出 RuntimeError，中止回退。报错说明，此时 seed 服务或已登记内存的清理失败，保存张量存活状态的引用仍被保留。

这项限制保护的是内存生命周期。假设旧模型占用的权重仍被登记、不能释放，默认加载器又开始分配新模型，就可能让两份权重同时占用设备内存。材料中的代码因此拒绝继续分配。

“本次接收失败”与“已经安全回到重新加载之前的状态”是两个不同结果。判断是否可以回退，需要看清理结果，不能只看传输是否结束。更完整的启动与回退过程见 [RFork 启动](../concepts/rfork-startup.md)。

## 租约释放失败，会怎样影响后续状态？

租约是 Planner 分给接收方的一次借用名额；Planner 是管理 seed 和借用名额的外部服务。租约状态与模型权重状态分别管理，所以模型已经加载，并不自动意味着租约已妥善释放。

材料中，释放请求收到 HTTP 200 或 404，都会返回 RELEASED。日志同时明确解释了 404 的含义：租约已经不存在，但这不能证明它此前得到了及时释放。因而，看到 RELEASED 只能按该实现的返回语义理解，不能据此补出释放发生的准确时间。

另一段代码处理持续未解决的释放过程：当释放被拒绝，或者达到配置的最大尝试次数时，程序停止重试、记录释放耗尽状态，并取消延迟的 seed 启动。对应日志写明，模型加载和推理仍可能继续，但该 Worker 不会把自己发布为 seed。

这说明至少需要分别观察以下状态：

| 状态 | 它回答的问题 |
| --- | --- |
| 模型加载状态 | 本 Worker 是否已经具备继续使用模型的权重 |
| 租约释放状态 | 向 Planner 借用的名额是否已得到明确处理 |
| seed 发布状态 | 其他 Worker 是否可以把本 Worker 当作权重来源 |

这些状态可以分离。材料明确保留了“加载或推理继续，但不发布 seed”的路径；至于请求何时真正可用，还需要其他启动阶段的证据。生命周期的完整讲解见 [RFork 生命周期](../concepts/rfork-lifecycle.md)。

## 放到 GLM 双机主线时，哪些问题仍需核实？

本页材料没有提供 GLM-5.3-Flash 在固定双机部署中使用 RFork 的完整执行链，也没有提供设备运行结果。因此，这里只能列出将上述机制用于该部署前必须回答的问题，不能给出已跑通结论或启动命令。

需要核实的内容包括：接收方与来源方的权重分片是否对应；加载后处理是否会改变共享存储；实际生成的清单是否通过校验；失败后能否安全解除内存登记；租约异常时能否按预期阻止 seed 发布。每个问题分别涉及身份、布局、传输或生命周期，不能由“字节已经传完”一项代替。

材料还缺少共享权重复用的完整检查、布局传输条件的判定实现，以及完整配置解析。补齐这些内容后，才能判断具体模型、硬件和配置组合的适用范围。

## 怎样区分传完、可用与可借？

传完权重描述的是传输阶段；模型是否可用还涉及加载后处理与后续初始化；可借则要求 Worker 成功发布为 seed。材料中的租约失败分支已经说明，这几个结果不会必然同时成立。

共享权重也不意味着可以重复处理。恰恰因为不同对象可能引用相同存储，满足特定复用条件时，代码会跳过所有加载后钩子。

接收地址重叠同样不意味着可以直接去重。合并读取还要考虑来源到接收位置的完整映射；当前材料所示实现选择按逻辑名称读取，并接受别名造成的重复传输。

回退则以安全的资源状态为前提。清理失败时中止加载，是材料明确给出的行为边界。

## 对照源码

### 怎么开

本次摘录没有提供完整配置入口、环境要求和启动命令，无法据此编写可执行的开启步骤。配置参考可从 [RFork 配置](../concepts/rfork-config.md) 继续查阅；执行前仍需核对其对应工作版与运行环境。

材料提供了动态 EPLB 的判断函数。EPLB 是根据专家负载调整专家放置的机制。所示判断顺序是：

1. 若 parallel_config.enable_eplb 为真值，直接返回真。
2. 否则读取 additional_config 中的 eplb_config。
3. 若 eplb_config 不是字典，返回假。
4. 若它是字典，检查 dynamic_eplb 或 expert_map_record_path 是否有真值。

因此，仅出现字段名不足以满足该判断。材料第 1109–1118 行支持上述条件，但不包含全部配置校验。

### 会报什么错

材料第 321–325 行展示的回退中止错误为：

> RFork fallback aborted because seed service or registered memory cleanup failed; tensor owners remain retained. Refusing to allocate a second model while old weights are pinned.

这条错误对应资源清理失败：旧权重仍被保活，程序拒绝分配第二个模型。排查时需要继续寻找此前的服务停止或内存清理异常，而不是只处理最后这条报错。

租约释放被拒绝或重试耗尽则是另一种状态。材料第 849–854 行展示的是停止释放重试、取消 seed 发布的错误日志；日志明确允许模型加载或推理继续，不能把它等同于上述加载中止。

### 开销和什么时候别开

材料第 183–186 行说明，别名可能造成重叠字节重复读取。它支持“存在额外传输”的结论，尚不能量化实际带宽开销。

共享权重复用分支避免了特定条件下的重复加载后处理；完整复用条件没有给出，不能将它作为通用优化开关。

所示代码也说明，资源清理失败可能阻止回退，租约释放失败可能阻止 seed 发布。这些是采用该路径时需要处理的运行状态。本次材料没有启动耗时、显存峰值或真实网络测量，无法据此判断哪种负载下启用 RFork 更划算。
