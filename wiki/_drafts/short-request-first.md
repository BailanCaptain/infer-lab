ShortRequestFirst 是一种等待队列策略：先选择需要恢复已有进度的请求，再让提示词较短的新请求优先于较长的新请求进入计算。它还可以根据长请求的等待时间调整顺序，让等待过久的长请求排到短请求之前。

这里的“短”按提示词的 token 数判断。token 是分词器输出的离散符号，通常用整数编号表示；一个 token 不一定对应一个汉字或单词。提示词短，不代表回答也短，更不代表整次请求一定更快结束。

## 为什么要改变等待请求的顺序？

scheduler 是决定本轮给哪些请求安排多少计算工作的组件。请求进入服务后，可能需要先在等待队列中排队，再取得计算机会；基础过程见 [Scheduler](../concepts/vllm-scheduler.md)。

FCFS 是 first come, first served，即先到先服务的顺序。如果一个长提示词请求先到，随后到达的短提示词请求可能需要等待前面的工作获得处理机会。对于长短提示词差异很大的流量，这种顺序未必符合业务目标：有些服务更重视短请求尽早看到第一个输出 token。

从请求到达到收到第一个输出 token 的时间称为 TTFT，即 time to first token。ShortRequestFirst 试图通过改变等待顺序，减少短提示词请求在这一阶段的排队。不过，TTFT 还包含请求进入计算后的处理时间；仅调整队列不能直接给出时延保证。

它保留了 scheduler 分配计算工作的基础机制，改变的是等待队列中的选择顺序。代价也来自这里：新的短请求可以越过先到的长请求，因而不再保持所有请求的全局到达顺序；如果短请求持续到来，长请求可能等待更久。

## 三条队列分别放什么请求？

材料中的实现把等待请求分成三条队列，分类有先后顺序。

| 队列 | 放入条件 | 为什么需要单独处理 |
| --- | --- | --- |
| immediate | 请求被抢占，或已有计算过的 token，或已有输出 token | 这些请求已有进度，需要先恢复已有工作 |
| short | 不属于恢复类，且提示词 token 数不超过长度门槛 | 让新的短提示词请求优先获得候选位置 |
| long | 不属于恢复类，且提示词 token 数超过长度门槛 | 保存新的长提示词请求，并允许按等待时间提升 |

抢占指请求的执行被暂停、让出资源，随后需要重新取得计算机会。这里的恢复类判定不只检查抢占状态：已有计算进度或已有输出，也满足材料中的恢复条件。

分类时先检查恢复条件，之后才检查提示词长度。因此，一个提示词很长、但已经计算过部分 token 的请求会进入 immediate，而不是 long。

short 和 long 的边界包含等号：提示词长度等于门槛时进入 short。分类使用提示词长度，不使用预计回答长度，也不使用预计运行时间。

## 怎样手工走一遍分类和选择？

设定一个仅用于演示的小例子：长度门槛为 4 token，长请求等待提升门槛为 10 毫秒。假设这些请求都已进入等待队列，当前没有此前固定的队列选择。[A]

| 请求 | 提示词长度 | 已有进度 | 分类 |
| --- | --- | --- | --- |
| 请求 A | 8 token | 已计算 2 token | immediate |
| 请求 B | 4 token | 无 | short |
| 请求 C | 7 token | 无 | long |

请求 A 的提示词虽然最长，但已有计算进度，所以先进入恢复队列。请求 B 的长度恰好等于门槛，进入 short。请求 C 超过门槛，进入 long。

选择时先看 immediate。只要请求 A 仍是该队列的候选，就先选择恢复队列；长请求是否等待过久，不会使它越过恢复队列。

当恢复队列为空时，再比较 long 的队头与 short：

- 如果请求 C 的等待时间为 9 毫秒，还没达到 10 毫秒门槛，选择 short 中的请求 B。
- 如果请求 C 的等待时间为 10 毫秒，已经达到门槛，并且 short 非空，就选择 long 中的请求 C，让它越过请求 B。
- 如果 short 已空而 long 非空，仍然选择 long；这时无需依靠等待提升。

这些步骤演示的是候选队列的选择。请求取得候选位置之后，是否能在本轮执行，仍取决于 scheduler 的其他约束。

恢复队列为空时，正的等待门槛才可能改变长短队列之间的先后。材料中代码使用“大于或等于”的比较，因此恰好达到门槛也符合提升条件。

## 等待提升怎样改变公平性？

不启用等待提升时，三条队列的基本顺序是：

恢复请求 → 新的短提示词请求 → 新的长提示词请求。

启用等待提升后，在没有此前固定队列选择的选择路径中，顺序变为：

恢复请求 → 达到等待门槛的长队头 → 短请求 → 其余长请求。

“达到等待门槛的长队头”仍属于 long 队列，并不是第四条独立队列。实现检查的是长队列队头的等待时间。

等待门槛设为 0 时，不会让长请求立即提升。材料中的等待时间函数在门槛小于或等于 0 时返回空值，关闭这条提升路径。因此，默认配置中的 0 表示不按等待时间提升长请求。

这带来两种取舍：

- 不启用等待提升时，短请求优先更严格；持续到来的短请求可能使长请求一直等待。
- 启用正的等待门槛后，达到门槛的长队头可以越过短请求，但仍排在恢复请求之后。

这个门槛控制的是候选顺序，不是服务承诺的最长等待时间。达到门槛之后，请求仍须取得本轮所需资源；材料没有给出无饥饿或端到端等待上限的证明。

## 长度门槛和等待门槛应该怎样选择？

材料建议在请求长度明显不均、短请求 TTFT 比严格到达顺序更重要时考虑启用。如果请求长度大多相近，分流作用有限；如果业务要求严格的先到先服务顺序，保持关闭更符合目标。

长度门槛应根据提示词长度分布选择。材料给出的工程起点是 P70—P85，即大约有 70%—85% 的请求长度不超过所选位置；随后仍须结合真实的长度直方图调整。对于短请求和长请求形成两个明显簇的流量，材料建议把门槛放在短请求簇的上沿附近。

这不是通用最优值。门槛过低，会把许多本来希望优先处理的请求分入 long；门槛过高，大多数请求都进入 short，长短分流又会减弱。

等待门槛需要另看长请求的排队情况。材料提出的调参过程是：

1. 先将等待门槛设为 0，测量严格短请求优先时长请求的等待分布。
2. 用长请求等待时间的 P90 或 P95 表示通常情况下较高的等待水平，记为 W_normal。
3. 确定业务能接受的长请求额外排队延迟，记为 W_slo。
4. 在 W_normal 到 W_slo 之间选择等待门槛，再观察实际效果。

如果更重视短请求 TTFT，材料建议偏向较大的 W_slo；如果更重视长请求公平性，则偏向较小的 W_normal。这些是调参建议，材料没有提供相应基准数据。

等待门槛应主要参考长请求等待时间的尾部，而不是短请求的平均 TTFT：前者描述需要保护的长请求已经等了多久，后者还混合了短请求进入计算后的耗时。

如果 W_normal 已经接近 W_slo，材料认为更可能需要检查长度门槛或系统容量。这个判断不能单独用来诊断某个服务，仍需实际流量与资源数据。

## 放到 GLM 双机请求流程中，应当在哪一站理解它？

在[多请求并发](../concepts/concurrent-requests.md)的学习路线中，应把 ShortRequestFirst 放在“等待请求准备进入本轮计算”的位置理解：它决定候选顺序，随后才是相应请求的计算工作。

跨 DP 准入与这个顺序属于不同决策。DP 是把不同请求分配给不同执行组的并行方式；材料中的 balance scheduling 控制跨 DP 执行组的准入，而 ShortRequestFirst 控制等待队列。材料对固定 main 快照的说明是，关闭 balance scheduling 后，仍可以保留 ShortRequestFirst 等待队列。

本次摘录包含其他提交快照中的队列实现和兼容检查，但没有给出固定 GLM 专用镜像执行侧的对应实现。因此，本页不提供该双机部署的启用命令，也不把这里的配置兼容性直接套用于该镜像。相关缺口列在页末，等待集成时核对。

## 哪些区别会影响使用判断？

**短提示词与短请求总耗时不同。** 分类只看提示词 token 数。一个短提示词请求仍可能生成很长的回答，因此这不是按总运行时间实现的最短作业优先策略。

**恢复请求与新的短请求不同。** 恢复条件先于长度判断；已有进度的长提示词请求可以排在新的短请求之前。

**等待提升与最长等待承诺不同。** 正的等待门槛允许长队头改变候选顺序，恢复优先和资源限制仍然存在。

**要求 FCFS 与保持全局 FCFS 顺序不同。** 配置要求使用 FCFS 调度策略，但装入 ShortRequestFirst 队列后，长短分流会改变等待请求之间的顺序。

**队列变化与已运行请求的重排不同。** 材料明确把作用范围限定为等待队列。它没有据此给出打断正在运行的长请求、让新短请求立即执行的机制。

## 对照源码

### 怎么开

摘录中的配置路径为：

```text
additional_config.scheduler_config.short_request_first_config
```

三个配置项的含义如下。这里的默认值来自材料展示的配置定义，不是已经运行验证过的启动结果。

| 配置项 | 材料中的默认值 | 意味着什么 |
| --- | --- | --- |
| `enabled` | `False` | 需要显式启用这项等待队列策略 |
| `threshold` | `256` | 非恢复类请求的提示词不超过 256 token 时进入 short |
| `long_max_wait_ms` | `0.0` | 默认关闭按等待时间提升长请求的路径 |

这些内容见材料第 109—113 行。当前草稿只有本地归档材料，没有实机启动记录。

安装函数还要求在请求接纳前完成队列安装：材料说明，原 waiting 队列必须为空；如果已经安装 ShortRequestFirst 队列，则直接返回。集成时应继续核对安装入口与调用时机。

### 会报什么错

材料中的启用检查要求：

- 调度策略必须为 FCFS。
- 不能与 batch-job-aware scheduling 同开。
- 不能用于 PD 分离中接收历史状态的 D 端，即 `kv_role='kv_consumer'` 的路径。

PD 分离是将提示词处理与后续持续生成分给不同执行组，并通过历史状态传输衔接。上述限制针对材料列出的接收端角色，不应仅按服务器所在位置判断。

与 profiling-chunk 的兼容条件随快照变化。它是按 profiling 信息控制提示词分块的调度路径：

- 在 `2ed6cbba` 摘录中，与 ShortRequestFirst 同开会被拒绝。
- 在 `baa023ad` 摘录中，允许同步调度下组合；若同时使用异步调度，则抛出 `ValueError`。[!]

后一快照展示的报错是：

```text
ShortRequestFirst with profiling_chunk_config requires synchronous scheduling. Please disable async scheduling.
```

配置校验方面，材料说明 `2ed6cbba` 拒绝负的长度门槛、负的等待时间和未知键；`baa023ad` 保留三个默认值，改用 Pydantic 配置校验。

### 开销和什么时候别开

这里能直接说明的主要代价是请求之间等待机会的重新分配。材料没有给出队列管理的 CPU 开销、吞吐变化、TTFT 改善幅度或显存变化的实测结果。

请求长度较均匀、严格到达顺序更重要，或者部署路径触及上述互斥条件时，不适合直接启用。

材料还说明，连续三次选择中，长请求因等待过久越过短请求时，会出现退化警告。这表示策略正在频繁让长请求优先，材料将长度门槛过小列为常见原因，而非确定诊断。

相应建议是先检查并增大长度门槛；若仍需调整，再考虑增大等待门槛，或者关闭功能。修改之后应同时观察短请求 TTFT 与长请求等待分布，避免只优化其中一侧。
