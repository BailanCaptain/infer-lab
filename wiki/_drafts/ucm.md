Unified Cache Manager（UCM）为 vLLM 与 vllm-ascend 提供外部 KV cache 存储层，面向相同输入开头的复用。KV cache 是模型处理输入后留下的历史表示，后续计算可以继续使用；prefix caching 则让兼容请求复用已经计算过的相同开头。

本页讨论外部存储怎样扩大缓存的可访问范围，以及它与 prefill、decode 分工的关系。Prefill 是处理提示词并建立历史状态的阶段；decode 是利用历史状态继续生成输出的阶段。材料主要摘自 vllm-ascend 固定提交的部署文档，下面的配置与性能条件属于文档说明，尚未在本页对应的环境中实机验证。

## UCM 在前缀复用中增加了什么？

[Prefix caching](../concepts/prefix-caching.md)解决的是“这段开头已经算过，能否接着使用其历史状态”。UCM 在这个基础上增加外部存储层：可复用状态不只留在某个执行进程的设备内存中，也可以存放到外部后端。

这种变化针对一个具体问题：缓存存在于一个进程可访问的设备内存里，另一个处理请求的进程未必能直接使用它。材料中的测试就遇到了这种情况：预热请求与正式请求可能被分给不同的 DP 进程。DP 即 data parallel，是把不同请求或批次分配到不同执行组的方式。请求分配发生变化后，预热留下的本地缓存未必在接手请求的进程那里。

共享外部存储让这些进程有机会访问同一份缓存。这里继承的仍是前缀复用：模型需要能够使用取回的历史状态；改变的是状态的存放位置与访问范围。仅有共享存储，并不能证明任意模型、状态格式和配置组合都能命中并接续计算。

## 为什么扩大访问范围也会增加开销？

外部缓存用存储与数据搬运换取少算一部分前缀的机会。是否值得，取决于省下的计算时间与查询、读取、搬运缓存所花的时间。[I]

设备内存中的缓存、当前机器的本地存储、多个节点共同访问的存储，承担的访问范围不同。材料中的 PD-Mixed 配置允许使用本地 SSD 或 NFS 挂载路径；因此，共享后端并不是所有 UCM 用法的统一前提。

跨节点集中式 PD 则有明确要求：全部 prefill 与 decode 节点都必须访问共享存储，例如 NFS 挂载目录或 3FS。NFS 是通过网络访问文件系统的方式；这里需要的是各节点实际看到同一份数据。两台机器各自使用同名本地目录，仍然是两份独立存储，不能完成这种交接。[I]

材料还把持久化前缀存储列为 UCM 能力之一。持久化说明状态可以由存储后端保存；本次摘录没有给出跨进程重启的完整写入、识别与恢复协议，因而尚不能据此确认重启后的复用行为。

## 用一段相同开头，怎样理解“能复用多少”？

设请求 A 的输入有 10 个 token，请求 B 的前 8 个 token 与 A 相同，后 2 个不同。Token 是分词器输出的离散符号，通常用整数编号表示，一个 token 不必对应一个汉字或单词。这个长度只用于示意。[A]

请求 A 先完成开头 8 个位置的计算，并把可复用状态存入外部后端。请求 B 到来时，系统需要判断这段开头是否有兼容缓存；若能够命中、取回并接续这 8 个位置的状态，B 就可以继续处理剩下的 2 个输入位置。[A]

这个例子中，8 个相同位置占全部 10 个输入位置的 80%。它描述的是设定的前缀比例，不是保证命中的比例，也不是运行时间减少的比例。[D]

实际还要看缓存保存边界、状态兼容条件和取回过程。本次摘录没有提供这些规则的完整实现，因此不能由“文本前 8 个 token 相同”直接推出“必定复用 8 个位置”。材料中的性能测试也区分了预热比例与实际命中情况。

## UCM 与 PD 分离怎样配合？

[PD 分离](../concepts/pd-disaggregation.md)把 prefill 与持续 decode 分给不同执行组。Prefill 建立的历史状态需要交给 decode 使用；前缀复用与这次状态交接可以由不同组件承担。

材料列出了两种不同的安排：

| 安排 | 材料描述的职责 | 需要关注的条件 |
| --- | --- | --- |
| 集中式跨节点 PD | prefill 与 decode 节点共同访问存储后端 | 所有相关节点必须实际访问共享存储 |
| P2P 分布式 PD | Mooncake 经高速网络把 KV cache 从 prefill 直接传给 decode；UCM 在 prefill 侧提供前缀复用 | 文档将其面向同构 P/D 节点与较低时延需求 |

P2P 是点对点传输。这里的 [Mooncake 连接器](../concepts/mooncake-connector.md)承担 prefill 到 decode 的直接传输，UCM 则承担 prefill 侧的缓存复用。选择 UCM 作为前缀存储，不意味着每种部署都必须让 decode 从同一存储路径读取全部状态。

材料还列举了其他 PD 模式、稀疏注意力方法及 ReRoPE 支持，但没有提供完整的模型、平台与功能组合验证矩阵。这些能力列表不足以证明它们可以任意组合使用。

## 文档里的性能结果适用于什么条件？

材料中的测试有明确的预热与容量前提：

- 总请求数为 128，并发数为 128。
- 请求对应的 KV cache 总量保持在 prefill 实例可用的 HBM 容量范围内。HBM 在这里指设备侧存储缓存所用的高带宽内存。
- 每次测试前，先发送 128 个预热请求，输入长度为目标输入长度的 80%，输出长度为 1。
- 正式测试发送完整目标输入，输出长度设为 1000。

这些结果代表特定预热条件下的比较，不能直接当成冷缓存、其他复用比例或缓存容量不足时的结果。

文档解释，正式请求可能没有落到预热时的同一个 DP 进程，因此只使用设备内存的前缀缓存，其实际命中情况会低于预设的 80%。共享外部存储用于缓解这种访问范围限制。这个解释针对该测试的请求分配方式；它不构成任意部署都能达到相同命中率的保证。

本次摘录包含一段性能表数据，但未同时提供足以独立核对各数值归属的完整表头，因此这里不重新编排具体性能数值。

## GLM-5.3-Flash 双机能直接采用这些结论吗？

本次材料没有给出 GLM-5.3-Flash 双机与 UCM 的完整验证记录，也没有展示该模型全部历史状态如何保存、如何按前缀取回并接续计算。

因此，目前能接续理解的是外部存储与前缀复用的关系，尚不能确认该模型在固定双机部署中的缓存粒度、可命中位置、资源开销或性能收益。要形成可执行的部署说明，还需要固定外部 UCM 版本、存储后端及框架组合，并核对模型状态的保存与恢复路径。

## 哪些结论需要分开判断？

**相同路径与共享数据是两件事。** 跨节点集中式 PD 要求访问同一份后端数据，路径字符串相同只是配置表面一致。

**前缀复用与 P/D 传输是两项职责。** 材料中的 P2P 模式由 UCM 提供 prefill 侧缓存，由 Mooncake 直接传输到 decode。

**预热比例与实际命中情况不同。** 80% 是材料中预先建立缓存的输入比例；请求路由与缓存可访问范围会影响后续是否用得上。

**功能列表与组合验证不同。** 文档列举某项能力，不能替代特定模型、后端和版本组合的验证记录。

## 对照源码

### 怎么开

材料中的部署示例通过 `kv-transfer-config` 选择连接器，并给外部配置文件提供路径：

```json
{
  "kv_connector": "UCMConnector",
  "kv_role": "kv_both",
  "kv_connector_extra_config": {
    "UCM_CONFIG_FILE": "/path/to/ucm_config_example.yaml"
  }
}
```

`UCMConnector` 是示例选择的连接器名称；`UCM_CONFIG_FILE` 指向 UCM 配置文件。该片段是文档示例，尚不足以构成完整可运行命令，也不能据此认定其他角色或配置方式不受支持。

本次摘录没有提供可核对的异常字符串或错误处理分支，不能建立报错与原因的对应表。

### 开销和什么时候别开

外部缓存会引入访问存储与搬运状态的工作。低复用率、取回成本较高，或本地缓存已经能满足需求时，收益需要通过同条件对照测试判断。[I]

评估时至少固定请求分配、预热比例、输入输出长度、并发与容量条件，再比较首 token 时延、持续生成速度和总完成时间。本页没有实机数据。
