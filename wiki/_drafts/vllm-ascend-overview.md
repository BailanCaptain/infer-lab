vllm-ascend 是社区维护的硬件插件，用来让 vLLM 在昇腾 NPU 上运行。NPU 是执行模型计算的设备；硬件插件则是连接推理框架与设备实现的软件。它通过插件入口被发现，再参与平台选择、模型注册和执行侧准备。

本页要回答的是：安装这个包以后，vLLM 怎样找到它，它又在哪些位置改变执行路径？阅读时可以把一次接入分成三个问题：入口是否被加载，平台选择了哪套实现，以及被选中的实现怎样准备和执行本轮工作。

本稿只依据所给本地摘录整理。摘录包含不同提交的代码片段，足以说明下面列出的入口与条件分支；完整调用关系、三版行为和实际运行结果仍需对应源码与运行记录补齐。

## 一个 Python 包怎样成为 vLLM 的硬件插件？

Python 能够导入一个包，说明解释器找得到它。推理框架使用插件还需要额外一步：找到包声明的接入入口，并调用这些入口。

这里的 entry point 是安装元数据中的入口声明：它把一个插件名称与一个 Python 函数对应起来。vLLM 可以按组查找这些声明，而不必预先把每种硬件的代码写进同一个入口文件。

材料中的 GLM 执行侧基线声明了两组入口：

| 入口组 | 声明的职责 |
| --- | --- |
| 平台插件组 | 通过 Ascend 平台入口接入硬件平台 |
| 通用插件组 | 提供 KV connector、模型加载器、服务 profiling 和模型注册入口 |

KV connector 是缓存传输相关的接入点；模型加载器负责接入模型加载方式；profiling 用于记录执行过程，帮助分析耗时；模型注册让框架能够找到相应模型实现。入口名称说明接入职责，具体执行条件还要继续追踪入口函数。

vLLM 的插件加载片段同时读取允许加载的名单，并按指定组发现 entry points。因此，接入有两道检查：安装元数据里是否有入口，加载筛选是否允许这个入口。详细机制见[插件发现与模型注册](../concepts/platform-plugin-registration.md)。

## 为什么需要平台接口，还需要 patch？

硬件适配既涉及“选择哪个设备实现”，也涉及“现有框架路径中哪些行为需要改变”。

Platform 是框架与硬件适配之间的接口契约。材料中的 NPUPlatform 声明设备类型为 npu，并设置设备可见性环境变量、分派键等信息。分派键用于把操作交给相应的设备实现；设备可见性变量用于限制进程可见的设备。接口的完整职责见 [Platform](../concepts/vllm-platform-interface.md)。

平台还会参与选择执行组件。Worker 是负责设备初始化、模型执行与资源管理的执行角色；model runner 是 Worker 内组织模型执行的对象；注意力后端则承接特定注意力机制及其状态布局对应的设备计算。

这些选择有条件。例如，材料中的自动 Worker 选择仅在并行配置存在、且 Worker 类设为自动选择时发生；其中先判断 310P，再判断 Xlite 图配置。注意力后端也按设备和模型机制分支选择，310P 使用独立映射。由此阅读一次执行路径时，需要把设备、配置和模型机制一起带上。

patch 则是在运行时替换或调整现有函数、类等行为。材料中的全局 patch 入口说明：EngineCore 子进程会加载通用插件，而端到端测试的 conftest 钩子不会在这些子进程中运行，因此影响 scheduler 和引擎代码的 patch 也需要经过插件入口应用。EngineCore 是组织请求推进与执行协作的引擎核心；scheduler 是按请求进度与资源预算选择本轮工作的调度器。

这个入口用进程内标志避免重复应用。一个进程记录“已经应用”，不会替另一个进程完成应用。进一步追踪见 [Patch 机制](../concepts/ascend-patch-system.md)。

## 怎样用一个小例子检查接入过程？

下面是示意检查，不是实际运行记录。

假设请求 A 已提交到服务，维护者想确认 Ascend 插件是否参与了执行。可以沿三个阶段逐步查：

1. 在安装元数据中找到平台入口，确认它把 Ascend 名称连接到注册函数。此时得到的是“入口已声明”。
2. 检查 vLLM 的插件发现与允许名单，确认该名称能够进入加载集合。此时才接近“入口被加载”。
3. 继续检查平台选出的 Worker、Worker 创建的 model runner，以及模型采用的注意力后端。这里确定的是请求执行将使用的具体实现。

例如，材料中的 NPUWorker 根据一个布尔条件选择两种 model runner。条件为假时创建原有 runner；条件为真时导入并创建 v2 runner，同时输出“仍在开发、部分功能不可用”的警告。包名相同，条件不同，最终创建的执行对象就可能不同。

这个例子展示了源码阅读的基本顺序：先看输入条件，再看分支产生的对象，最后检查对象参与的执行与状态变化。只看到类已定义或模型已注册，还没有走完这条链。

## 请求执行时，哪些状态值得继续追踪？

对照 [vLLM V1 的请求循环](../concepts/vllm-v1-shape.md)，可以继续区分请求进度、缓存分配信息和设备上的实际状态。所给摘录直接展示了执行侧的几类操作。

Worker 的缓存初始化路径按缓存配置分配 NPU KV cache，并先确保缓存传输相关初始化完成。KV cache 保存后续注意力计算需要的历史表示，避免重复处理已经计算的位置；不同注意力机制保存的内容可以不同。启用 sleep mode 时，片段还会选择带有 kv_cache 标签的内存池。

模型执行也需要区分本轮工作类型。材料中的 runner 根据注意力状态判断本批是否包含 prefill，即对输入位置进行计算的阶段。注释还说明，chunked prefill 把较长输入分轮处理后，当前批次可能只包含某个请求的部分输入；该分支即使产生了采样结果，也会忽略尚未完成输入处理的请求对应的结果。一次执行中出现采样计算，因此不必然意味着请求 A 已获得可输出的新 token。

这些片段能帮助定位状态变化，但不足以独立建立完整的“上游负责什么、插件负责什么”清单。完整边界需要把调度计划、缓存规格、执行输入与结果返回逐项接起来，见[请求代码路径](../concepts/request-call-chain.md)。

## GLM 双机案例中，为什么还要看模型专用路径？

本页沿用 GLM-5.3-Flash 主线；双机设备与并行条件见[部署前提](../concepts/glm-5-3-flash-two-node.md#部署前提)。所给摘录没有部署运行记录，下面讲的是固定执行侧基线中的代码条件。

硬件插件除了选择通用执行组件，还可能为某个模型处理专用状态布局。材料中的 GLM 路径提供了三个例子。

缓存分组函数会检查缓存规格中是否存在 model_version 为 glm5_next 的条目。没有时调用原始函数；命中时才进入专门逻辑。这个专门路径要求混合 KV cache 管理器，因为报错说明中提到了配对的 MLA/indexer 与滑动状态布局。MLA 用压缩表示保存注意力历史；indexer 是筛选相关历史位置的索引组件。这里的限制属于命中该模型条件后的路径。

递推状态初始化也按状态是否存在来区分。递推状态是计算下一位置时继续使用的历史汇总；材料中的代码在包含 prefill 时，清零没有初始状态的那些条目，而非清零整个状态池。请求已有状态能否继续使用，需要由对应索引和初始状态标记决定。

索引器还区分真实计算行与填充行。填充行是为了满足缓冲区或执行形状而保留的位置。材料中的路径在 FULL graph 模式保留捕获时的固定形状，在其他模式按实际 token 数与位置缓冲区长度的较小值取行数，避免 eager MTP 的填充行参与缓存寻址。MTP 是多 token 预测结构，推理时可用于生成投机草稿；这里需要关注的是草稿步骤的缓冲区长度与本步真实查询行数可能不同。

这些例子说明，阅读插件不能停在安装与平台注册：模型状态布局还会继续影响缓存管理和执行输入。

## 哪些结论需要分别判断？

**能导入、能发现与已运行成功是三个状态。** 导入检查 Python 包是否可访问；发现检查安装入口与加载筛选；运行成功还需要初始化、模型加载和执行都完成。

**编译选项与图执行需要分别看。** 材料中的一个平台片段把简单编译后端设为 eager，并以注释说明禁用 torch.compile；另一处模型代码仍明确区分 FULL graph。前一个字段不足以判断整个系统是否使用图捕获与回放。

**注册名称与支持范围需要分别看。** 某个入口、后端或模型名称出现在代码中，说明存在接入位置。支持哪些设备、量化格式和功能组合，还需要相应条件检查与验证记录。

**平台通用逻辑与模型特判需要分别看。** GLM 专门缓存分组在命中模型条件后才执行；它的约束不能直接套到其他模型。

## 对照源码

### 怎么开

本材料支持按入口与条件检查接入过程，尚不足以给出完整安装和启动命令。

先检查安装元数据中的 `vllm.platform_plugins` 与 `vllm.general_plugins`，再核对 `VLLM_PLUGINS` 的加载筛选。进入平台后，检查自动 Worker 选择是否满足条件，以及最终创建了哪个 runner。需要配置细节时，继续阅读 [NPUPlatform](../concepts/npu-platform.md) 和 [Ascend 配置](../concepts/ascend-config-system.md)。

### 会报什么错

材料保留了以下具体边界：

- GLM 专门缓存分组路径中，显式禁用混合 KV cache 管理器会抛出 `ValueError`，说明配对 MLA/indexer 与滑动状态布局需要该管理器。
- Ascend GLM-5 Indexer 路径启用 FP4 cache 时，会报 `Ascend GLM-5 Indexer uses BF16 Q, not FP4.`。
- GLM-5 kpool 路径缺少 k、gate_score、compress_ape 或 positions 时，会报这些输入为必需项。
- 启用 v2 model runner 会输出仍在开发、部分功能不可用的警告；材料未列出完整缺失功能。

这些信息定位的是各自条件分支，不构成完整报错目录。

### 开销和什么时候别开

材料没有实测时延、显存或吞吐数据，无法量化插件、patch 或不同 runner 的净开销。

能够明确的是：v2 runner 带有功能未完整的警告，选择前需要核对所需功能；GLM 专门路径中的混合缓存管理器是布局要求，显式关闭会直接报错。索引器中的填充行处理则与执行模式相连，不能脱离图形状和缓存寻址要求单独修改。
