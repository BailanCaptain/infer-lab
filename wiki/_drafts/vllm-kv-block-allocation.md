KV block allocation 是在模型执行前，为请求取得缓存块使用权，并在不再需要时归还使用权的过程。这里的“块”是框架管理缓存的单位：普通注意力可以用它保存历史位置的表示，递推模型则可能用它保存不断更新的状态，二者的容量计算不能直接混用。

本页依据归档材料中的代码摘录解释管理过程，重点是“空闲”“命中”“归还”怎样改变容量。材料没有提供完整源码调用链和全部版本映射；以下内容是局部机制的中间草稿，尚未完成发布分支验证。

## 为什么块里的内容还在，却已经可以借给其他请求？

理解块分配，需要区分两件事：**块里保存了什么**，以及**现在有谁持有它**。

引用计数记录块当前被持有的数量。对于材料展示的普通块，引用计数为零，表示当前没有持有者；这并不要求块里的旧内容已经被擦掉。启用 prefix caching 时，这些内容还可能被登记为可复用的前缀。prefix caching 是在兼容条件下复用已经计算过的相同开头，从而减少重复计算的机制。

因此，一块缓存可以同时满足：

- 当前无人持有，可以被重新分配；
- 旧内容仍有缓存记录，后续请求可能命中它。

空闲块队列保存可供重新使用的块。若请求恰好需要其中已经缓存的内容，管理器可以让请求重新持有这块；若请求需要新的空间，块池也可以取走它，并撤销旧缓存记录。前一种情况是在复用内容，后一种情况是在复用存储位置。

[Block Table](../concepts/block-table.md) 解决的是另一件事：请求的某个逻辑块对应哪个物理块编号。块分配负责取得使用权，块表负责记住映射。

占位块 null block 是特殊情况。材料展示的初始化会从空闲队列取出编号为 0 的块作为占位，并注明其引用计数不按普通方式维护。因此，不能把池的总块数直接理解为全部可借出的普通块数，也不能把普通块的释放规则直接套给它。

## 一次分配要经过哪些容量判断？

材料展示了管理器与底层块池两层判断，它们处理失败的方式不同。

管理器先估算本轮需求，再检查可用容量。一处检查使用“空闲块数减去预留块数”作为可用数量；需求超过它时，返回 `None`，表示本次分配条件不满足。另一处摘录直接与空闲块数比较，并启用了面向特定缓存规格的准入上限。它们是不同代码位置，不能合并成一个适用于全部调用的公式。

底层 BlockPool 则提供实际取块操作。材料中的 `get_new_blocks` 从空闲队列头部取出指定数量的块；若数量超过空闲块数，会抛出异常。启用缓存时，取出的块还会先经过旧缓存记录的驱逐处理，再增加引用计数。

这解释了为什么“管理器返回失败”和“块池抛异常”不能互换理解。管理器的返回值可供调度逻辑选择下一步；底层异常则表示调用提出了超过当前空闲数量的取块要求。

分配之前还可能先释放不再参与计算的块。材料以 sliding window 为例：这种注意力只访问当前位置附近的一段历史，窗口之外的块可能已经没有继续保留的必要。即使当前请求最终因容量不足无法调度，也可以先完成这部分释放，以减少后续驱逐。

这类提前回收取决于缓存规格。它不能推广成“所有模型都会在请求执行过程中不断归还旧位置的块”。各类状态如何编成块，见 [KV cache 规格](../concepts/kv-cache-spec.md)。

## 命中了前缀，为什么还可能占用空闲容量？

命中解决的是“已有内容能不能复用”，容量检查解决的是“取得这些内容的使用权后，还剩多少空间”。两者有关联，但不是同一个问题。

材料中的 `touch` 负责让请求持有命中块。对引用计数为零的普通块，它先把块移出空闲队列，再增加引用计数；对已经有持有者的块，则增加引用计数。于是，同样是命中，空闲容量的变化可以不同。

下面用一组示意数走一遍。假设空闲队列里有 5 个普通块，其中块 7 保存着请求 A 可以复用的前缀，引用计数为零。请求 A 除了命中块 7，还需要 2 个新块。[A]

| 时刻 | 块 7 的引用计数 | 空闲队列中的块数 | 发生了什么 |
| --- | ---: | ---: | --- |
| 分配前 | 0 | 5 | 块 7 无人持有，但旧前缀内容仍可命中 |
| 请求 A 取得块 7 | 1 | 4 | 块 7 离开空闲队列 |
| 请求 A 再取得 2 个新块 | 1 | 2 | 两个新块也离开空闲队列 |

这次操作只需取得 2 个新块，却一共减少了 3 个空闲块：其中 1 个是重新持有的命中块。上述结果由示意设定逐项计数得到。[D]

如果块 7 在请求 A 到来前已经被请求 B 持有，它本来就不在空闲队列中。请求 A 再持有它时，只增加引用计数，不会因为这次持有再移走一个空闲块。

材料中的容量估算明确把即将被持有的、可驱逐的命中块计入需求。它还排除了本次会跳过的一部分命中块，所以不能简单按“所有命中块数量加新块数量”计算任意路径。

前缀命中也不意味着模型完全不用执行。材料说明，即使提示词全部命中，仍需重算最后一个 token，以取得 logits。logits 是模型对候选输出 token 给出的分数，后续采样据此选择输出。在所示路径中，已计算长度还有块对齐要求，因此实际重算范围可能扩展到一整块。

## 请求归还块以后，哪些块会先被重新使用？

归还使用权不等于立即删除缓存内容；有其他持有者的块，也不会仅因一个请求归还就变成空闲块。

材料展示了两个固定提交中的不同职责位置。

在固定控制流快照的请求释放路径中，管理器逆序遍历请求持有的块，把没有缓存 hash 的块与已有 hash 的块分开。hash 在这里用于标识已登记的缓存内容。已有 hash 的块走普通释放，无 hash 的块通过前置方式归还。这个顺序有助于优先复用没有前缀缓存价值的存储位置。

另一个固定快照把相关次序写进块池的释放逻辑：只有引用计数归零且不是 null block 的块进入复用队列。没有 hash，或者缓存功能关闭时，块进入优先复用的一侧；启用缓存且有 hash 的块进入较晚复用的一侧。

其中包含两种队列策略：

- LIFO，即后进入者先复用，用于材料所示的非缓存块复用路径。
- FIFO，即先进入者先复用，用于材料所示的缓存块路径，形成近似“较久未使用者先淘汰”的行为。

“有 hash 就一定后复用”缺少条件：材料明确包含“关闭缓存”的例外。两个快照的代码位置和策略细节也不能仅凭提交号推定为某个发布分支的完整行为。

## 滑窗与递推状态为什么需要不同的容量算法？

普通历史块可以按位置增加，但并非所有状态都遵循“位置越多，永久保留的块越多”。

sliding window 只保留计算仍需访问的历史范围。材料中的 chunked prefill 容量估算，会考虑窗口中需要承接的旧位置、本轮最多处理的位置数，以及模型允许的最大长度；再额外覆盖窗口起点没有对齐块边界的情况。

例如，示意设定每块容纳 4 个位置，当前需要的位置是 C、D、E、F，它们可能分布成 `[XXCD][EF]`：虽然只需要 4 个位置，却跨越了 2 个块。[A] 这个例子说明的是块边界开销。材料原注释把 `[CDEF]` 称为“6-token window”，文字与列出的 4 个位置不一致，不能沿用这个长度表述。

材料还展示了面向 SWA、chunked-local 等可回收规格的准入上限。该上限只在相应调用启用限制、且存在配置上限等条件下生效，不能推广为所有注意力类型的统一限制。

Mamba 则是另一类情况：它通过递推状态承接历史，不能把每个块都理解成一段普通 K/V 历史。所示 align 模式按主模型的位置数计算，不为 lookahead token 分配块。lookahead token 是投机执行提前预留或考虑的位置；该代码注释的依据是当时的草稿模型没有 Mamba 层，这个前提不能推广到未来所有草稿模型。

同一 Mamba 分支还区分首次分配和后续分配。在算出的新增需求大于零时，已有分配记录的请求按新增一块处理；首次 prefill 则为运行状态及投机状态预留块。最终容量返回值还会加入相应的可驱逐命中块数量。

另一个限制与执行时序有关：若请求将命中的末块属于本轮刚登记的块，材料中的 Mamba 分支会返回“池总块数加一”，使管理器本轮不调度该请求。这是借容量检查表达执行依赖，不能直接解释成物理显存已经耗尽。

## 这些机制怎样接到 GLM 双机的请求流程？

在[单请求主线](../concepts/one-request.md)中，块分配属于模型执行前的准备：调度决定本轮要推进哪些位置，缓存管理据此检查并取得状态空间，之后才具备执行这些位置的资源条件。[多请求主线](../concepts/concurrent-requests.md)则需要同时考虑不同请求对同一空闲池的需求。

本页材料包含固定控制流与 Ascend 执行侧的局部摘录，但没有提供完整双机分组、每卡缓存规格、块预算及实际运行记录。因此，本草稿不据这些片段重算 GLM 的块数或显存，也不把上游 Mamba 分支直接认定为 Ascend 替换管理器的全部行为。

Ascend 摘录提供了一个具体差异：在父类估算基础上，如果外部已计算的位置超过本地前缀命中块覆盖的范围，同时本轮还要调度新的主模型位置，就增加一块容量记账。这里“外部”指不由本地命中块完整覆盖的已计算部分。材料注释将该调整用于同步加载外部 KV 的情况。

这项补充说明，分配需求既可能来自本地新计算，也可能来自外部状态交接；它不是所有请求无条件多分配一块的规则。

## 哪些看起来相同的结果，其实原因不同？

**空闲与已清零是不同状态。** 空闲表示可以重新取得使用权；是否清零、何时清零，还涉及执行侧的初始化与写入路径。

**缓存命中与不占容量是不同结论。** 命中能复用计算结果，但无人持有的普通命中块被重新持有时，会离开空闲队列。

**归还与驱逐是不同操作。** 归还改变持有关系；驱逐撤销旧内容的缓存登记。材料中的已缓存空闲块可以在被重新分配时再遭驱逐。

**分配失败与物理显存耗尽也不同。** 除普通容量不足外，材料中的 Mamba 分支还会主动制造一个超过池容量的需求值，以阻止存在执行依赖的本轮调度。

**分配失败后的处理取决于请求路径。** 材料展示的 running 请求路径会尝试抢占其他请求；所述 waiting 路径则在失败时退出当前接入过程。不能把前一种行为写成全部请求的统一规则。

## 对照源码

### 怎么开

块分配是所示缓存管理路径的组成部分，材料没有给出一个独立的“开启块分配”开关。

prefix caching 会改变命中检查、旧缓存记录维护以及部分块的复用方式；材料还说明，禁用缓存或请求要求跳过缓存读取时，不查前缀命中。具体启动参数、默认值和完整配置组合没有出现在本次摘录中，需另行核对。

### 会报什么错

底层取块数量超过空闲数量时，材料展示的错误为：

```text
Cannot get {num_blocks} free blocks from the pool
```

这是 `get_new_blocks` 的 `ValueError`。管理器的容量不足路径则返回 `None`，两者应分别定位。

所示 running 请求路径在分配返回 `None` 后尝试抢占。PRIORITY 策略按优先级与到达时间选择对象，其他所示策略取 running 队列尾项；本次摘录不足以复原全部调度策略。

### 开销和什么时候别开

块分配本身承担执行前的资源管理职责。需要权衡的是相关复用与状态策略：

- prefix caching 需要维护缓存记录，命中重新取得使用权时仍可能减少空闲容量。
- 可回收状态需要在分配前识别并释放已跳过的块。
- 外部 KV 加载与递推状态可能引入额外预留或调度约束。
- 清零是否发生不能从“块已借出”单独推出。

材料末尾只展示了清零元数据初始化的条件，没有展示完整清零执行路径。因此，“没有调用此处初始化”不足以证明借出的块在所有路径上都不清零；“调用了初始化”也不等于已经观察到设备清零完成。
