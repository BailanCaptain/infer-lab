**在 Atlas A2 / A3 上跑多卡大模型解码时，常被三件事扯后腿：细碎算子靠主机或慢速控制路逐个唤醒露出气泡、HCCL 集合通信借用 AI Vector 向量算力核做搬运和求和挤占了计算资源，以及机内 HCCS 与跨机 RoCE 协议割裂；昇腾 950 用芯片内硬件调度器 STARS 2.0、独立通信处理单元 CCU 与统一总线 Unified Bus 2.0（`UB 2.0`）正面改造了这条跨卡接力链。** 要分清这三件新硬件究竟省掉了哪一段开销、又有哪些等待连硬件卸载也省不掉，最好顺着两张卡合并一次部分结果的全过程走一遍。

## 两张卡各算了一半，为什么还不能继续

沿用[集合通信页](collective-communication.md)的两卡小算例：张量并行切分后，卡 0 算出了部分结果 $[1, 2]$，卡 1 算出了 $[10, 20]$。这里的“部分”指同一输出向量的每个分量都只算了一半权重贡献；两张卡必须按位置相加凑出完整的 $[11, 22]$ 且各自拿到手，下一层归一化或投影才能开算。这个“跨卡求和并让每张卡拿到完整结果”的原语就是 **All-Reduce**。

这段接力位于[请求主线的逐层前向](one-request.md#第-4-站-逐层前向每张卡上的形状通信和字节)层内。注意一个无论换多快硬件都改不了的因果前提：卡 0 在第 2 ms 算完，只代表自己的 $[1, 2]$ 就绪；只要卡 1 的 $[10, 20]$ 还没算出来，最终的 $[11, 22]$ 就绝无可能提前诞生。

## 为什么还需要专门安排这些任务

把一次“本地矩阵乘 → 跨卡交换求和 → 下一段本地计算”跑通，在 A2 / A3 时代如果每个微秒级小算子和通信步都靠主机 CPU 介入唤醒、或者抽调设备侧通用 AI CPU 与 AI Vector 核去组织搬运和加法，既容易在任务切换处留下下发气泡，又会在重通信场景（如大规模 MoE `All-to-All`）里抢走宝贵的算力核。昇腾 950 把“排班派活”和“通信搬运求和”分别交给了两类专用硬件：

- **STARS 2.0（芯片内硬件任务流调度器）**：主机只需把带先后依赖关系的整串**任务流（Task Stream）**成批下沉到设备侧，STARS 2.0 就在芯片内部按同步条件（前序任务做完才放行后序任务）直接派发计算与通信资源，完成后再统一回报状态。
- **CCU（专用集合通信处理单元）**：独立于 Cube 核与 Vector 核之外的硬件通信引擎。软件预先装入集合通信算法脚本，STARS 2.0 直接把通信任务派给 CCU，由 CCU 独立完成跨卡数据拉取、同步握手与归约求和——把这套活从通用算力核与主机总线上移走，就叫**通信卸载（Communication Offload）**。

阅读排障指标时千万分清两层完全不同的“调度”：引擎层的**[请求调度](vllm-scheduler.md)**决定这一步让哪几条用户对话上卡、分配多少 token 预算；芯片内的**设备调度（STARS 2.0）**只负责把已经排好队的算子与通信微任务顺畅喂给硬件单元。客户端请求在引擎队列里干等，查 STARS 任务流数量毫无帮助。

## STARS 和 CCU 怎样把这一轮接起来

继续追踪卡 0 上的 $[1, 2]$。主机下沉任务流与依赖关系后，AI Core 先算完本地矩阵乘并置位完成标志；STARS 2.0 检测到依赖满足，立即唤醒 CCU 执行预置通信脚本：分步拉取对端分片、按位求和、等待全部参与卡凑齐，最后写出 $[11, 22]$ 并解锁下一段本地计算。

白皮书把 CCU 内部拆成各司其职的前后端：
- **CCUM（通信管理前端）**：接收名为 `Mission` 的通信任务包，负责解析算法指令与同步步点；
- **CCUA（通信执行后端）**：内置暂存跨卡分片的片上缓冲 **MemorySlice**，以及专门做跨卡加法的 **Reduce Unit（硬件归约单元）**——因此求和不必再借用 AI Vector 核；需要跨节点搬运数据时，CCU 直接调用底层的 **URMA（Unified Remote Memory Access，统一远程内存访问）**接口异步收发。

图中灰色虚线传递控制指令与完成信号，紫色实线传递跨卡张量数据，青色代表本卡计算结果（卡 1 一侧同样对称运行同一份通信脚本；All-Reduce 的环状/树状切分原理见[集合通信原语页](collective-communication.md#all-reduce)）。

为了让任务唤醒不被繁忙的数据读写堵住，STARS 2.0 走一条独立的片内专用快车道 **HSCB（硬件高速控制总线）**向 Cube、Vector 等单元直接派发指令。白皮书提到的“纳秒（ns）级硬件调度开销”专指 HSCB 上这一下派发交互——能显著压缩算子间的空隙气泡，但绝不能拿几十纳秒直接替代算子计算、跨卡传输与木桶慢卡等待的毫秒级耗时。

## 远端那份数据究竟怎样到手

在 A2 上，单机 8 卡走专用的 `HCCS` 高速链路，跨机走 `RoCE` 以太网 RDMA，两侧接口与拓扑视角并不统一。昇腾 950 引入 **Unified Bus 2.0（统一总线，简称 `UB 2.0`）**作为统一的跨芯片/跨节点互联架构与协议栈（再次提醒：这里的 `UB` 指跨卡互联总线 `Unified Bus`，不是[算子页](op-to-ai-core.md#host-tiling把张量任务划给设备)里向量核的片上缓冲 `Unified Buffer`）。围绕“卡 0 怎样拿到卡 1 的 $[10, 20]$”，UB 2.0 提供了两套互补的远端访存方式：

- **URMA（异步队列单边传输，适合成块吞吐与通信计算重叠）**：发起方把搬运描述符塞进名为 **Jetty** 的硬件发送队列，再写一下 **Doorbell（门铃寄存器，专门用来敲醒硬件来取活的触发器）**；硬件随即在后台经互联端口把请求发往远端，由对端的 **UMMU（统一内存管理单元，负责检查跨卡虚拟地址权限并翻译成物理显存地址的硬件门卫）**校验放行。敲完门铃后，发起方算力核可以立刻转身去算不依赖这份数据的其他任务；但在真正读取收到的结果前，必须先确认硬件返回的完成通知。
- **UB Memory（远端内存直接读写语义，适合细粒度低延迟访问）**：计算核直接对着映射好的远端地址发出读写指令（`load / store` 或原子操作），硬件自动解码目标节点与地址并经远端 UMMU 校验后取回数据。白皮书称之为“同步访存语义”，意思是需要该返回值的那条指令链必须等远端数据往返到手才能往下走——并非整颗芯片所有核跟着停摆，更不代表远端显存的物理延迟能缩到和本卡 HBM 一样短。

下图对比卡 0 读取卡 1 $[10, 20]$ 时 URMA 与 UB Memory 的交互差别：上半部通过 `Jetty + Doorbell` 异步排队并凭完成通知衔接，下半部按地址直接发起远端读：

```wiki-diagram

```

图中的完成通知只表达“使用数据以前需要取得相应完成依据”。具体操作的通知条件、内存可见性和顺序，必须遵守所用接口的约定。拿到远端地址本身，也不代表程序自动拥有访问权限或可以省略同步。

如果这次通信要经过以太网交换机，**UBoE（Unified Bus over Ethernet，以太网承载 UB）**让 UB 的相关通信功能承载在以太网上。它描述互联的承载方式，URMA 描述怎样提交访问，二者可以出现在同一条数据路径中。950 的以太端口和部分 UB Link 复用底层物理资源；把某个端口用于以太网，会减少相应的 UB Link 能力。因此评估带宽时，应按实际端口配置列账，不能把两种用途的峰值直接相加。

## 接入内存池以后，模型就能直接多留历史了吗

前面追踪的是两张卡交换结果。白皮书还画了另一类连接：计算卡经 UB 访问 CPU 内存池或存储资源池。**内存池**把其他机器的内存作为可访问资源；**存储资源池**则组织存储设备。它们扩大可使用的数据存放范围，但“硬件能访问”到“这条请求能复用历史”之间，还有软件工作。

例如某条请求的历史块还在远端池里，本机设备内存已满。引擎先要知道池中哪份数据对应这个前缀、采用什么格式、算到了哪个位置，再决定把哪些块取回，或是否有算子能够按支持的路径访问远端。若当前实现仍要求计算前把 KV 搬进本地设备内存，池再大也不能直接增加本轮可驻留的 KV；它减少的是丢弃后的重算。管理前缀、寻找块和取回的机制，复用 [KV Pool](kv-pool.md)，不由 UB 链路本身完成。

因此，观察“加了内存池仍然慢”时，先按[生产案例的三个完成点](deepseek-serving-case.md#再追问一句哪些历史能找回哪些还得准备)区分查到前缀、取到主机、进入设备；实现若走另一条路径，就记录其实际取数与可用边界。容量增加、命中增加与数据及时到达是不同结果，不能只用池容量解释首字延迟。

白皮书里的**超节点**是多张计算卡通过高速互联组织起来的系统。连接关系叫**拓扑**：Full Mesh 让节点彼此直接相连，Clos 通过多级交换组织通路；实际部署也可以混合。排查时要知道源和目的经过哪些端口、交换设备，与其他流量共享哪一段。支持较大规模的超节点，并不意味着一次模型计算应使用全部卡；并行组的大小和代价仍回到[大规模 EP](large-scale-ep.md)判断。

还有一种容易漏看的流量：某芯片只替别处转发数据。950 的 UB On Chip Switch 可在同一个通信晶粒（IO Die）的端口间转发，不经过计算晶粒和设备主存（DRAM）。因此，判断通信出口是否繁忙，还须计入替别处转发的流量；本卡计算和内存空闲不足以排除出口争用。接入以太网络时，还要区分经 UB Switch 转换与芯片直接采用 UBoE 两条连接方式，不能从同一个“以太网”标签推断路径相同。

## 通信卸载以后，为什么下一段仍然晚

回到最初两张卡，用一组**教学时间记录**做判断。两次试验执行相同的计算与通信，卡 0 都在 2 ms 产出 [1, 2]，卡 1 都在 5 ms 产出 [10, 20]。为单独观察协调开销，假设本例等两份完整输入就绪后，才进入剩余的协调、交换与求和，且这几段依次执行。

下表是按同一轮任务手工对齐的示意记录，不是某个分析工具的原生日志，也不是 950 实测。对照的变化是“剩余协调”从 0.8 ms 降到 0.2 ms；交换与求和仍花 0.6 ms。

| 同一轮的事件或区间 | 原路径 | 协调工作卸载后 |
| --- | ---: | ---: |
| 卡 0 的部分结果就绪 | 2 ms | 2 ms |
| 卡 1 的部分结果就绪 | 5 ms | 5 ms |
| 两份就绪以后剩余的协调 | 0.8 ms | 0.2 ms |
| 随后的交换与求和 | 0.6 ms | 0.6 ms |

从卡 0 看，2–5 ms 的等待来自另一张卡尚未算完。协调更快以后，这 3 ms 仍然存在。下一段开始时刻由较晚的输入，加上尚未完成的后续工作决定：

$$t_{\text{next}} = \max(t_0, t_1) + t_{\text{coord}} + t_{\text{comm}}, \qquad \Delta t = 6.4 - 5.8 = 0.6\text{ ms}$$

| 推导项（示意时间线） | 算式 | 结果 |
| --- | --- | --- |
| 原路径下一段开始 | $\max(2, 5) + 0.8 + 0.6$ | **6.4 ms** |
| 卸载后下一段开始 | $\max(2, 5) + 0.2 + 0.6$ | **5.8 ms** |
| 本轮提前量 | $6.4 - 5.8$ | **0.6 ms** |
| 卡 0 等待另一份输入 | $5 - 2$ | **3.0 ms** |

实际通信可以按块流水执行，部分协调也能提前完成。这时沿各块真实依赖画[关键路径](inference-performance-analysis.md#时间线怎样告诉你应该先优化哪一段)，不能把已经重叠的区间再相加。这个小例子教的是分开记账：卸载改变了谁来干活，以及哪一段变短；它不改变后一段需要完整输入这件事。

从业者拿到一段“通信很慢”的记录，可以沿这次交接做三步对照。

1. **先对齐同一次工作。** 固定模型、输入形状、精度、通信组、数据量和端口路径，用同一轮的任务标识关联两卡的输入就绪、通信提交、通信完成与下一段开始。跨设备时间需要统一时基；软件提交时间也不能替代设备实际开始时间。
2. **再判断长区间包住了什么。** 如果卡 1 的输入就绪也变晚，先查它此前的计算与负载；如果两卡就绪时间稳定，而通信提交到完成变长，再继续拆队列、传输和归约。只有接口名和一个总耗时，还不足以判定链路带宽不足。
3. **做能区分原因的对照。** 保持通信量与路径不变，平衡两侧此前的工作，观察迟到差距是否缩小；或保持输入就绪条件相近，移走竞争流量，观察完成时间是否恢复。要比较卸载与原路径，则须先确认软件确有可比较的两条实现，并同时核对结果数值、端到端耗时和资源占用。

例如，卡 1 从 5 ms 提前到 3 ms，下一段随之提前，而后面的 0.6 ms 基本不变，证据更支持参与者迟到。两卡都准时、移走竞争流量后传输区间缩短，才更支持共享通路争用。调整流量优先级还会把等待移给其他工作，其代价见 [AI QoS](ai-qos.md)；该页的软件启用条件需按自己的硬件另核。

## 放回本站的 GLM 双机，该怎样使用这套分析

本站完整拆解的双机案例 [GLM-5.3-Flash（2×A2×8，TP8/DP2/EP16，W8A8）](glm-5-3-flash-two-node.md#部署前提) 代表了典型 **Atlas A2 两层互联分工**：每台机器内部 8 卡走机内 `HCCS` 做注意力侧高频 `TP8 All-Reduce`，两台机器共 16 卡跨越 `RoCE` 网卡共同持有完整路由专家并完成 `EP16` 跨机交换（4 token 示例请求 `R1` 的精确通信次数与字节推导见[一条请求的逐层前向](one-request.md#第-4-站-逐层前向每张卡上的形状通信和字节)）。

把本页的记账框架带回 A2 双机，再展望向 950（`A5`）超节点迁移时的差异：
- **分析公式完全同构**：不管底层是 A2 的 `HCCL`（见 [CANN 与 HCCL](cann-hccl.md)）还是 950 的 `STARS 2.0 + CCU + UB 2.0`，集合通信慢都遵循 $\max(t_0, t_1) + t_{\text{coord}} + t_{\text{comm}}$——必须先把“热门专家或长序列导致的慢卡迟到”与“协调下发 / 物理链路拥塞”剥离开，绝不盲目怪罪网卡带宽。
- **硬件卸载边界严禁混套**：A2 没有独立 `CCU` 与 `UB Memory`，集合通信仍走 A2 既有 HCCL / AIV / RoCE 路径；迁往 950 时，则需重新核查目标 CANN 与框架版本是否真正为 `All-Reduce`、`MoE Dispatch/Combine` 启用了 CCU 卸载或图级矩阵乘-通信融合（如 `GRAPH_MM_REDUCE_SCATTER_FUSION`），以及物理端口在 `UB Link` 与 `UBoE` 之间的实际切分。

此外，DeepInfer 公开快照虽将 Ascend 950（需 CANN 9.2）列为支持硬件，但文档中的引擎级“异步调度”指的是 Host CPU 组批与设备执行流水重叠，而本页的 STARS 2.0 指的是芯片内部的硬件任务流调度——两层一内一外可以协同，不能因同带“调度”二字混为一谈（其开源发布范围见 [DeepSeek 生产实践](deepseek-serving-case.md)）。

## 常见误解

- **设备任务流数量就是可并发服务的请求数？** 一条请求会产生多项设备工作，多请求也可能组成同一批。请求容量要结合批处理、内存和时延目标测量。
- **CCU 接手以后，通信就不占时间？** 专用单元承担组织与执行，数据仍要就绪、搬运和归约。应比较具体区间和端到端结果。
- **URMA 异步提交以后，就能立即使用收到的数据？** 可以先做无关工作；依赖收到的数据时，必须按所用操作的完成与可见性约定衔接。
- **UB Memory 是让两张卡自动共享同一份缓存？** 它提供远端访存语义；地址权限、顺序和数据何时可用仍需按接口处理。
- **UB 带宽与 UBoE 带宽可以全部相加？** 部分物理端口复用，先核对分配给各用途的实际链路。
- **把 CANN 换成一个新版本，就证明模型已经使用 CCU？** 还要确认选中的软件实现、任务下发与设备轨迹；硬件存在只说明有这项能力。

## 对照源码

### 怎么开

本页是白皮书机制解读，没有提供通用的“打开 STARS/CCU”命令。需要按实际框架和 CANN 组合核对通信实现、提交接口与设备执行证据。DeepInfer 固定 README 的 Ascend 构建入口使用 `DEEPINFER_ACCELERATOR=ascend`，前提为 CANN 9.2；此入口选择平台，不能单独证明某次集合通信命中了 CCU。[S2]

### 会报什么错

白皮书没有给出框架日志字符串。遇到提交失败、权限错误或任务不完成，保存操作类型、源/目的内存区域、通信参与者及首次异常；按实际库的错误码定位。URMA/UB Memory 路径均涉及地址转换与权限检查，因此调查地址和权限有机制依据，但具体错误必须对照软件版本，不能从一个超时反推一定是权限问题。

### 开销和什么时候别开

比较路径时至少记录输入就绪、提交、完成和后续使用四个边界。CCU 的算法组织、临时存储、同步和数据流量仍须计入；小消息可能更受固定开销影响，大消息还受实际链路与内存路径约束。不要为了名称新而切换生产实现；先在相同工作量下验证结果、长尾与吞吐，再决定是否采用。

950 的 URMA 还区分 RTP 与 CTP 传输服务。白皮书说明 RTP 支持端到端可靠重传，CTP 不提供同样的端到端可靠重传机制；支持的端口能力也不同。实际可靠性与恢复设计要按选中的服务核对，不能把其中一类的保证套到另一类。
