**昇腾 950 的设备调度和通信单元，负责把已经安排好的计算接起来：前一段产出数据，把需要的数据送齐，再让后一段继续。** 它们能减少安排和搬运工作的开销；数据还没算出、链路还在传输时，依赖这份数据的计算仍要等待。

## 两张卡各算了一半，为什么还不能继续

沿用[集合通信页](collective-communication.md)的两卡小例子：卡 0 已算出部分结果 [1, 2]，卡 1 已算出 [10, 20]。这里的“部分”指每个位置都只算了一部分贡献。两卡要按位置加齐，各自取得 [11, 22]，才能把完整结果交给下一段计算。这个“合并并让每卡拿到结果”的操作叫 **All-Reduce**；前页解释它为什么由矩阵拆分产生。

图中浅青格是各卡已有的部分结果，深青格是可以交给下一段的完整结果。紫色箭头代表跨卡传递；中间的加号代表按位置求和。图只表达依赖与数据变化，实际通信算法可以分块、分步执行。

这段工作出现在[请求主线的逐层前向](one-request.md#第-4-站-逐层前向每张卡上的形状通信和字节)：模型已经决定要做哪些运算，现在要让设备把它们做完。卡 0 先算完，只说明自己的 [1, 2] 就绪；卡 1 的 [10, 20] 还没准备好时，最终的 [11, 22] 就不可能就绪。

## 为什么还需要专门安排这些任务

一次“本地计算 → 交换求和 → 下一段计算”需要几种不同资源。本地矩阵和向量运算由计算核心执行；跨卡数据要经过通信引擎和端口；后一段还要确认前面的结果已经可用。若每一个细小步骤都反复由主机介入安排，就会增加下发和协调开销。

**STARS 2.0 是芯片内安排任务及其同步关系的硬件调度器。** 主机可以把任务流交到设备侧，STARS 按配置取得任务，安排计算与搬运资源，并向主机报告结果。任务流是有顺序和依赖的一组设备工作；同步关系说明哪件事完成后，另一件事才可以继续。

**CCU 是承担集合通信的专用处理单元。** 软件先提供通信算法程序，STARS 可以把集合通信任务交给它；CCU 再组织搬运、同步和求和，完成后报告任务状态。把这部分组织工作交给专用硬件，称为通信卸载。它的目标包括减少通用资源的参与和系统总线流量；收益取决于原来花在这些工作上的时间与资源。

这里要分清两种调度：**请求调度**决定本轮处理哪些用户请求、给多少计算预算；**设备调度**接住已经形成的计算任务，安排执行资源和先后关系。STARS 不负责判断哪个聊天请求应该先回答。请求阶段排了很久的队，应先回到[请求调度](vllm-scheduler.md)，而不是从 STARS 的任务流数量推断服务可接多少用户。

## STARS 和 CCU 怎样把这一轮接起来

继续追踪卡 0 的 [1, 2]。主机提交任务和所需的依赖；设备完成本地计算，写出部分结果并满足相应的同步条件。通信任务取得所需输入后，CCU 按软件预置的算法执行小步骤：有的步骤搬数据，有的步骤做求和，有的步骤等待其他参与者。得到完整结果并满足后续任务的依赖后，下一段计算才使用 [11, 22]。

白皮书把 CCU 分成管理和执行两部分。管理部分 **CCUM** 接收名为 Mission 的任务并解释指令；执行部分 **CCUA** 有临时存放通信数据的 MemorySlice 和负责求和等归约的 Reduce Unit。需要跨节点搬运时，CCU 调用 **URMA（Unified Remote Memory Access，统一远程内存访问）**，也就是通过异步请求搬运远端内存数据的接口。下一节再把这次搬运展开。

灰色虚线传的是任务与完成条件，紫色实线传的是跨卡数据，青色表示本地结果。右侧远端数据并不是一提交 Mission 就出现：它可能还在计算、排队或传输。图中只展开卡 0 一侧的职责，卡 1 也要按同一通信程序参与；All-Reduce 的完整拆分仍以[通信原语页](collective-communication.md#all-reduce)为准。

STARS 通过专用控制总线 **HSCB（硬件高速控制总线）**向矩阵、向量计算单元下发任务，让这类控制减少对普通数据访问通路的依赖。白皮书给出的 ns 级调度开销指这一局部交互，不能直接填进整次请求的延迟预算。任务自身的计算、传输和同步仍有各自的时间。

## 远端那份数据究竟怎样到手

卡 0 要使用卡 1 的 [10, 20]，需要说明两件事：如何发出访问，以及数据实际走哪条路。**Unified Bus**，简称 UB，是这里的互联技术与协议体系；950 支持 UB 2.0。它与[算子页](op-to-ai-core.md#host-tiling把张量任务划给设备)中的 Unified Buffer 恰好缩写相同：后者是向量计算使用的片上缓冲区。以下“UB”都指互联。

**URMA 采用异步提交。** 发起方把搬运工作交到名为 Jetty 的队列，再通过 Doorbell（门铃寄存器，用来唤醒硬件拉取队列任务）通知硬件处理。工作经过端口到达远端；UMMU（统一内存管理单元）负责把使用的虚拟地址翻译为实际地址，并检查访问权限。提交以后，发起方可以继续做与这份数据无关的工作；读取收到的结果之前，仍须按接口要求确认相应操作已经完成。

**UB Memory 提供直接读写远端内存的访问语义。** 核心发出的访问经过地址解码，找到目的节点与地址，再由远端进行地址翻译和权限校验。依赖这次读取结果的计算，要等数据返回。白皮书称它为同步访存语义：这里强调访问方式，不能据此推断整颗芯片都会停住，也不能把远端内存当作延迟等同于本地的内存。

下面用读取卡 1 的 [10, 20] 对比两条路径。上半部多了一份提交的工作与完成通知；下半部沿地址直接发出读取。两种方式都要经过端口和远端权限检查，差别不在于有没有网络。

```wiki-diagram

```

图中的完成通知只表达“使用数据以前需要取得相应完成依据”。具体操作的通知条件、内存可见性和顺序，必须遵守所用接口的约定。拿到远端地址本身，也不代表程序自动拥有访问权限或可以省略同步。

如果这次通信要经过以太网交换机，**UBoE（Unified Bus over Ethernet，以太网承载 UB）**让 UB 的相关通信功能承载在以太网上。它描述互联的承载方式，URMA 描述怎样提交访问，二者可以出现在同一条数据路径中。950 的以太端口和部分 UB Link 复用底层物理资源；把某个端口用于以太网，会减少相应的 UB Link 能力。因此评估带宽时，应按实际端口配置列账，不能把两种用途的峰值直接相加。

## 接入内存池以后，模型就能直接多留历史了吗

前面追踪的是两张卡交换结果。白皮书还画了另一类连接：计算卡经 UB 访问 CPU 内存池或存储资源池。**内存池**把其他机器的内存作为可访问资源；**存储资源池**则组织存储设备。它们扩大可使用的数据存放范围，但“硬件能访问”到“这条请求能复用历史”之间，还有软件工作。

例如某条请求的历史块还在远端池里，本机设备内存已满。引擎先要知道池中哪份数据对应这个前缀、采用什么格式、算到了哪个位置，再决定把哪些块取回，或是否有算子能够按支持的路径访问远端。若当前实现仍要求计算前把 KV 搬进本地设备内存，池再大也不能直接增加本轮可驻留的 KV；它减少的是丢弃后的重算。管理前缀、寻找块和取回的机制，复用 [KV Pool](kv-pool.md)，不由 UB 链路本身完成。

因此，观察“加了内存池仍然慢”时，先按[生产案例的三个完成点](deepseek-serving-case.md#再追问一句哪些历史能找回哪些还得准备)区分查到前缀、取到主机、进入设备；实现若走另一条路径，就记录其实际取数与可用边界。容量增加、命中增加与数据及时到达是不同结果，不能只用池容量解释首字延迟。

白皮书里的**超节点**是多张计算卡通过高速互联组织起来的系统。连接关系叫**拓扑**：Full Mesh 让节点彼此直接相连，Clos 通过多级交换组织通路；实际部署也可以混合。排查时要知道源和目的经过哪些端口、交换设备，与其他流量共享哪一段。支持较大规模的超节点，并不意味着一次模型计算应使用全部卡；并行组的大小和代价仍回到[大规模 EP](large-scale-ep.md)判断。

还有一种容易漏看的流量：某芯片只替别处转发数据。950 的 UB On Chip Switch 可在同一个通信晶粒（IO Die）的端口间转发，不经过计算晶粒和设备主存（DRAM）。因此，判断通信出口是否繁忙，还须计入替别处转发的流量；本卡计算和内存空闲不足以排除出口争用。接入以太网络时，还要区分经 UB Switch 转换与芯片直接采用 UBoE 两条连接方式，不能从同一个“以太网”标签推断路径相同。

## 通信卸载以后，为什么下一段仍然晚

回到最初两张卡，用一组**教学时间记录**做判断。两次试验执行相同的计算与通信，卡 0 都在 2 ms 产出 [1, 2]，卡 1 都在 5 ms 产出 [10, 20]。为单独观察协调开销，假设本例等两份完整输入就绪后，才进入剩余的协调、交换与求和，且这几段依次执行。

下表是按同一轮任务手工对齐的示意记录，不是某个分析工具的原生日志，也不是 950 实测。对照的变化是“剩余协调”从 0.8 ms 降到 0.2 ms；交换与求和仍花 0.6 ms。

| 同一轮的事件或区间 | 原路径 | 协调工作卸载后 |
| --- | ---: | ---: |
| 卡 0 的部分结果就绪 | 2 ms | 2 ms |
| 卡 1 的部分结果就绪 | 5 ms | 5 ms |
| 两份就绪以后剩余的协调 | 0.8 ms | 0.2 ms |
| 随后的交换与求和 | 0.6 ms | 0.6 ms |

从卡 0 看，2–5 ms 的等待来自另一张卡尚未算完。协调更快以后，这 3 ms 仍然存在。下一段开始时刻由较晚的输入，加上尚未完成的后续工作决定：

$$t_{\text{next}} = \max(t_0, t_1) + t_{\text{coord}} + t_{\text{comm}}, \qquad \Delta t = 6.4 - 5.8 = 0.6\text{ ms}$$

| 推导项（示意时间线） | 算式 | 结果 |
| --- | --- | --- |
| 原路径下一段开始 | $\max(2, 5) + 0.8 + 0.6$ | **6.4 ms** |
| 卸载后下一段开始 | $\max(2, 5) + 0.2 + 0.6$ | **5.8 ms** |
| 本轮提前量 | $6.4 - 5.8$ | **0.6 ms** |
| 卡 0 等待另一份输入 | $5 - 2$ | **3.0 ms** |

实际通信可以按块流水执行，部分协调也能提前完成。这时沿各块真实依赖画[关键路径](inference-performance-analysis.md#时间线怎样告诉你应该先优化哪一段)，不能把已经重叠的区间再相加。这个小例子教的是分开记账：卸载改变了谁来干活，以及哪一段变短；它不改变后一段需要完整输入这件事。

从业者拿到一段“通信很慢”的记录，可以沿这次交接做三步对照。

1. **先对齐同一次工作。** 固定模型、输入形状、精度、通信组、数据量和端口路径，用同一轮的任务标识关联两卡的输入就绪、通信提交、通信完成与下一段开始。跨设备时间需要统一时基；软件提交时间也不能替代设备实际开始时间。
2. **再判断长区间包住了什么。** 如果卡 1 的输入就绪也变晚，先查它此前的计算与负载；如果两卡就绪时间稳定，而通信提交到完成变长，再继续拆队列、传输和归约。只有接口名和一个总耗时，还不足以判定链路带宽不足。
3. **做能区分原因的对照。** 保持通信量与路径不变，平衡两侧此前的工作，观察迟到差距是否缩小；或保持输入就绪条件相近，移走竞争流量，观察完成时间是否恢复。要比较卸载与原路径，则须先确认软件确有可比较的两条实现，并同时核对结果数值、端到端耗时和资源占用。

例如，卡 1 从 5 ms 提前到 3 ms，下一段随之提前，而后面的 0.6 ms 基本不变，证据更支持参与者迟到。两卡都准时、移走竞争流量后传输区间缩短，才更支持共享通路争用。调整流量优先级还会把等待移给其他工作，其代价见 [AI QoS](ai-qos.md)；该页的软件启用条件需按自己的硬件另核。

## 放回本站的 GLM 双机，该怎样使用这套分析

本站固定部署是 GLM-5.3-Flash、两台 A2 共 16 卡，TP8/DP2/EP16、W8A8。R1 是 prompt 为 4 token 的示例请求；它在[逐层前向](one-request.md#第-4-站-逐层前向每张卡上的形状通信和字节)中的卡组、通信次数和张量字节，继续由主线统一推导。两台机器共同持有完整的路由专家集合，每台是一个 DP 执行组。

能直接复用的是分析方法：结果在哪里产生、谁在等待、何时交齐、下一段依赖什么。硬件实现则分别核对。A2 的固定软件路径由 [CANN 与 HCCL](cann-hccl.md)及算子页说明；950 白皮书列出的 STARS 2.0、CCU 与 UB 能力属于另一套硬件依据。把同一模型迁到 950 时，需要重新核实框架、通信库、算子和端口配置怎样实际使用这些能力。

DeepInfer 的固定公开版本把 Ascend 950 列为支持硬件，并列出 CANN 9.2 前提；这给出了调查软件入口的线索。它的“异步调度”说明 CPU 的批次安排可与设备执行重叠，而本页的 STARS 讨论芯片内任务调度。两者可以配合，但不能仅凭名称认定同一种机制。公开发布与完整生产服务的边界见 [DeepSeek 生产实践](deepseek-serving-case.md)。

## 常见误解

- **设备任务流数量就是可并发服务的请求数？** 一条请求会产生多项设备工作，多请求也可能组成同一批。请求容量要结合批处理、内存和时延目标测量。
- **CCU 接手以后，通信就不占时间？** 专用单元承担组织与执行，数据仍要就绪、搬运和归约。应比较具体区间和端到端结果。
- **URMA 异步提交以后，就能立即使用收到的数据？** 可以先做无关工作；依赖收到的数据时，必须按所用操作的完成与可见性约定衔接。
- **UB Memory 是让两张卡自动共享同一份缓存？** 它提供远端访存语义；地址权限、顺序和数据何时可用仍需按接口处理。
- **UB 带宽与 UBoE 带宽可以全部相加？** 部分物理端口复用，先核对分配给各用途的实际链路。
- **把 CANN 换成一个新版本，就证明模型已经使用 CCU？** 还要确认选中的软件实现、任务下发与设备轨迹；硬件存在只说明有这项能力。

## 对照源码

### 怎么开

本页是白皮书机制解读，没有提供通用的“打开 STARS/CCU”命令。需要按实际框架和 CANN 组合核对通信实现、提交接口与设备执行证据。DeepInfer 固定 README 的 Ascend 构建入口使用 `DEEPINFER_ACCELERATOR=ascend`，前提为 CANN 9.2；此入口选择平台，不能单独证明某次集合通信命中了 CCU。[S2]

### 会报什么错

白皮书没有给出框架日志字符串。遇到提交失败、权限错误或任务不完成，保存操作类型、源/目的内存区域、通信参与者及首次异常；按实际库的错误码定位。URMA/UB Memory 路径均涉及地址转换与权限检查，因此调查地址和权限有机制依据，但具体错误必须对照软件版本，不能从一个超时反推一定是权限问题。

### 开销和什么时候别开

比较路径时至少记录输入就绪、提交、完成和后续使用四个边界。CCU 的算法组织、临时存储、同步和数据流量仍须计入；小消息可能更受固定开销影响，大消息还受实际链路与内存路径约束。不要为了名称新而切换生产实现；先在相同工作量下验证结果、长尾与吞吐，再决定是否采用。

950 的 URMA 还区分 RTP 与 CTP 传输服务。白皮书说明 RTP 支持端到端可靠重传，CTP 不提供同样的端到端可靠重传机制；支持的端口能力也不同。实际可靠性与恢复设计要按选中的服务核对，不能把其中一类的保证套到另一类。
