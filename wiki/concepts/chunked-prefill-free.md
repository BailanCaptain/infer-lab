## 正在蹦字的屏幕，为什么突然冻住了？

想象一台正在跑在线对话的大模型服务器。

此刻，用户 **A** 和 **B** 正盯着屏幕看回答——字一个个往外蹦，丝滑流畅。对模型来说，这种逐字续写（**Decode**）极其轻量：每跑一步（一次前向传播），A 和 B 各自只需要送进 **1 个新 token**，几毫秒就能算完吐出下一个字。

就在这时，用户 **C** 贴进来一篇 **10,000 个 token** 的长报告，让模型总结全文。在吐出第一个回答字之前，模型必须先把这 10,000 个词通读一遍、把上下文信息算好存进显存——这一步叫 **Prefill（预填充）**。

服务器瞬间陷入了两难：

- **先停下 A、B，专心把 C 读完？** GPU 被这 10,000 个 token 独占几百毫秒，A 和 B 屏幕上的字当场冻住半秒钟。
- **把 A、B、C 拼进同一批一起算？** 同一步里的所有请求必须同进同出。A 和 B 明明只算 1 个词，也得陪着 C 这 10,000 个词的大矩阵全部算完才能拿到结果——照样冻住。

**Chunked Prefill（分块预填充）** 的解法干净利落：给每一步划一条**总 token 预算线**。

每一步开头，先给正在蹦字的 A 和 B 各留 1 个位置；预算还剩多少，就把 C 的长提示词切下多少塞进来。这一步吃不完？没关系，剩下的留到下一步接着切。

拿一组能一眼看清的小数字走一遍——设每步总预算为 **8 个 token**，A、B 各占 1 个，C 带着 **14 个 token**（编号 `0–13`）进场：

```wiki-diagram

```

原本一步硬吞 **16 个位置**的大雷，被拆成了三步平平稳稳的 `1 + 1 + 6`、`1 + 1 + 6`、`1 + 1 + 2`：

1. **A 和 B 全程无感**：每一步最多只算 8 个 token，她们的屏幕照常往外蹦字，没有被 C 拖下水。
2. **C 分三口吃完提示词**：前两步还在「读题」，算到第 5 和第 11 个词时句子都没读完，模型顺手预测出的词直接扔掉，不对外输出；直到**第 3 步读完最后一个词 `13`**，才真正吐出首个回答字 `y₀`。
3. **第 4 步回归日常**：C 把刚拿到的 `y₀` 送回去，和 A、B 一样变成每步只占 1 个位置的 Decode 请求。

## 把一句话劈成三截算，结果不会变味吗？

第一次听到「把提示词劈成几段算」，几乎所有人都会冒出同一个疑问：

> Transformer 的注意力机制不是要让前后的词互相看吗？切成 `0–5`、`6–11`、`12–13` 分三次送进模型，最后又没有一步叫「把三截结果拼起来」，算出来的数怎么可能和一次算完一模一样？

秘密在于生成式大模型的注意力是**单向因果**的——**后面的词要看前面的词，但前面的词永远看不见后面的词。**

不管你切不切块，第 `0–5` 个词在算自己的特征时，本来就只允许看 `0–5`。所以在第 1 步里，位置 `0–5` 算出来的键（K）和值（V）向量已经是**最终成品**，一个小数点都不会再变，直接写进显存的 **KV Cache** 存好就行。

到了第 2 步，真正精妙的配合发生了：

```wiki-diagram
file: chunked-prefill-free-kv
```

- **位置号接着往下编，绝不归零**：送进第 2 段词时，给它们标的位置号是 `6..11`，而不是重新标 `0..5`。
- **缓存只在原处往后追加**：模型算出 `6–11` 的 K、V，顺着写进缓存的后六个格子；做注意力打分时，把第 1 步留下的 `0–5` 和刚算出的 `6–11` **一块儿从显存里读出来**。

站在第 11 个词的视角看，它头顶的位置号是 `11`，脚下读到的历史是完整的 `0–11`。对数学公式来说，这 6 个词是和前面一起送进来的，还是隔了 10 毫秒才送进来的，**没有任何区别**。

哪怕遇到不存逐词 KV 的**线性注意力**（如 Mamba 或 KDA 层），道理也完全相通：它用一份固定大小的状态矩阵浓缩前文；第 1 步算完把状态矩阵存起来，第 2 步拿出来接着滚就行。

## 翻开 vLLM 源码：里面甚至没有「切块器」

如果让你去写这段调度代码，第一反应大概是建两个队列——一个管 Decode，一个管 Prefill，再写个切块函数专门切长句子。

但翻开 vLLM V1 调度器的核心循环，你会看到一个极简到漂亮的工程设计：**代码里压根不区分 Prefill 和 Decode，也没有任何专门的「切块模块」。**

在调度器眼里，天下所有请求都只有两个数字：

- `total_tokens`：到现在为止，这条请求**一共应该算到第几个词**；
- `computed_tokens`：在此之前，它**已经算完了几个词**。

两数一减，就是它此刻欠着的账。每一步调度，只是跑两轮完全一样的减法循环：

```python
budget = max_num_batched_tokens  # 例如每步预算 8

# 1. 先照顾已经在跑的请求（包括上一轮没读完提示词的 C）
for req in running:
    need = req.total_tokens - req.computed_tokens
    take = min(need, budget)
    schedule(req, take)
    req.computed_tokens += take
    budget -= take

# 2. 预算还有剩？去等待队列接新请求进来，剩多少喂多少
for req in waiting:
    need = req.total_tokens - req.computed_tokens
    take = min(need, budget)
    if take == 0:
        break
    schedule(req, take)
    req.computed_tokens += take
    running.append(req)
    budget -= take
```

盯着这十几行代码看三秒钟，所有现象全都自动涌现出来了：

- **正在蹦字的 A 和 B**：上一轮刚吐出 1 个新词，`total - computed == 1`，自然只拿走 `1` 个预算。
- **短提示词**：一共就 4 个词，剩余预算有 6，`min(4, 6) == 4`，一口气算完，当场转正。
- **14 个词的长提示词 C**：第 1 步在 `waiting` 里撞上只剩 `6` 的预算，`min(14, 6) == 6`，算完推进 `running`；第 2 步在 `running` 里再拿 `min(8, 6) == 6`；第 3 步拿走最后的 `min(2, 6) == 2`。

**Chunked Prefill 根本不是给调度器硬塞进去的特判补丁，而是当你把 Prefill 和 Decode 统一看成「每次按预算往前推一截进度条」之后，水到渠成的结果。**

## 意外之喜与真实代价：这笔买卖到底划不划算？

把长提示词切碎混进 Decode 批次里，最早由论文 **SARATHI** 系统提出。它之所以迅速成为现代推理引擎的默认标配，是因为它除了「防卡顿」，还白捡了一个硬件红利：

### 白捡的红利：Decode 搭上了 Prefill 的顺风车

纯跑 Decode 时，GPU 其实憋屈得要命。假设模型权重有 40 GB，为了给 A 和 B 各算 1 个新词，GPU 得花大力气把这 40 GB 权重从显存搬进计算核心一趟，结果只跟 **2 行向量**做完乘法就扔了——芯片完全卡在**搬运权重的显存带宽（Memory-bound）**上，昂贵的矩阵算力十成有九成在空转。

现在同一批里塞进了 C 的几百个 Prefill token。**权重还是只搬那一趟**，却顺手喂饱了矩阵乘法单元，把原本白白浪费掉的空闲算力榨成了实打实的吞吐量。

### 躲不开的三笔账单

当然，物理定律不会凭空变出免费午餐。切块换来丝滑的同时，你要付三笔账：

1. **长请求自己的首字变慢了（TTFT 上升）**：C 原本一步就能拿到第一个回答字，现在拆成三步，每一步还要带着别人的请求一起跑，等第一个字的时间自然拉长。
2. **前文的 KV Cache 要多从显存捞几趟**：注意力的总计算量一分没少（14 个词两两因果打分，切不切都是 `1 + 2 + … + 14 = 105` 次）；但拆成三段后，`0–5` 的缓存第 2 步要读一遍，第 3 步还得再读一遍。
3. **预算锁住的是 token 数，不是毫秒数**：同样一步跑 `8,192` 个 token，空上下文和背着十万字历史上下文的耗时天差地别。

所以工程调参时，`--max-num-batched-tokens` 本质上是一根**在「蹦字流畅度（ITL）」和「长文首字速度（TTFT）」之间拔河的滑杆**：

- 往小调（如 `2048`）：每步更轻，在线流式输出更稳，但超长文档要切很多刀；
- 往大调（如 `8192` 甚至 `16384`）：长文档几口就能吞完，首字更快，但同批正在蹦字的用户会感受到肉眼可见的顿挫；
- 如果线上业务严苛到「既要十万字秒回，又绝不允许流式生成抖动 10 毫秒」——单机混批就到头了，得上 **PD 分离（Prefill-Decode Disaggregation）**，干脆让两拨机器各干各的。

## 真实战场的彩蛋：一段 8,144 个词，引爆 15.9 GB 瞬时显存洪峰

纸面推演永远风平浪静，一上真实大模型就会撞见意想不到的连锁反应。拿本项目的双机 16 卡 **GLM-5.3-Flash** 部署（每台机器一个 DP 组，每步预算 `8,192`，开启 MTP 投机解码后每条 Decode 占 `1 + 3 = 4` 个位置）举个真实例子。

假设组里已有 12 条请求正在生成（共占 `12 × 4 = 48` 个位置），这时冲进来一条 **20,000 token** 的长提示词。按刚才的减法循环，它会被干脆地切成三步吞掉：

| 调度步 | 12 条在线 Decode | 长提示词切入量 | 本步总 token 数 | 这一步发生了什么 |
| :--- | :--- | :--- | :--- | :--- |
| **第 1 步** | `48` | `8,144` | **8,192（满载）** | 算完 `0–8,143`，末尾采样丢弃 |
| **第 2 步** | `48` | `8,144` | **8,192（满载）** | 算完 `8,144–16,287`，末尾采样丢弃 |
| **第 3 步** | `48` | `3,712` | **3,760** | 读完 `20,000` 全文，吐出首个回答字 |
| **第 4 步** | `52`（变 13 条） | — | **52** | 全员回到轻量纯 Decode |

表面看只是规规矩矩切了三刀，底层硬件却在这三步里连续发生了两次剧烈震荡：

1. **执行引擎当场「降挡」**：平时 12 条纯 Decode 只有 48 个位置，跑的是提前录制好的静态图（Graph Mode）和低延迟融合通信；一旦混入 `8,144` 个 Prefill 位置，静态图立刻失效退回 CPU 逐算子下发（Eager Mode），跨机专家层的通信也因为突破 `128` token 门槛，瞬间切换成全量广播收集（AllGather）。
2. **「零头缓存组」差点被一步撑爆**：按理说，GLM 的主注意力每 `640` 个位置才借 1 个缓存块，`8,144` 个位置只借 **13 块**，九牛一毛。偏偏它的稀疏注意力索引器配了一个「尾状态缓存组」，每 `4` 个新位置就要临时借 1 块存中间零头，等下一步滑出窗口才归还。于是第 1 步这 `8,144` 个位置一进来，尾状态组当场一口气借走了 **2,037 个块（约 15.9 GiB）**——**单靠这一段分块，一步就吞掉了整张卡 KV 显存池（3,855 块）的一半以上！** 直到第 4 步转入纯 Decode，它才像退潮一样瞬间缩回 **3 块**。

这就是为什么在真实的推理基础设施里，Chunked Prefill 从来不只是一个「切长句」的文本技巧——你切下去的每一刀有多宽，直接牵动着底层的图模式开关、跨机通信路径，甚至一整张加速卡的显存水位线。

## 附：工程师速查卡

平时调线上服务，记住这四个开关和边界就够用了：

| 参数 / 场景 | 行为与踩坑提示 |
| :--- | :--- |
| `enable_chunked_prefill` | 现代 vLLM（V1 架构）对绝大多数生成式模型**默认开启**（仅 encoder-decoder 等不支持的结构默认关闭）。 |
| `--max-num-batched-tokens` | 每步全批总预算（如 `2048` / `8192`）。调小保流式平稳（ITL），调大抢长文首字（TTFT）。切点平时无需对齐 KV 块大小，停在块中间下一轮接着写即可。 |
| `--long-prefill-token-threshold` | 单条请求每步最多拿多少位置（默认 `0` 不限制）。如果在预算 `8192` 下把它设成 `2048`，一条长请求每步最多只吃 `2048`，剩下的预算还能同时塞进别的等待请求，避免一条超长请求把本步余量独吞。 |
| **手动关掉分块会报什么错？** | 关掉分块意味着「任何长输入都必须一步吞完」。只要你的 `--max-num-batched-tokens` 设得比 `--max-model-len` 小（比如预算 `8192`、最大上下文 `133120`），引擎启动当场就会抛 `ValueError` 拒绝启动。 |
