## 一句话

在昇腾上建每个 HCCL 通信组时，vllm-ascend 会先问一句「这个组该给多大的通信缓冲区」，**答案不是全局一个数，而是按通信组的名字分派的**：`dp` 组按 `data_parallel_size` 现算，`dynamic_eplb` 组固定给一个较小的值，其余组一律吃同一个默认值，而名字里带 `mc2` 的组**干脆不给配置、退回环境变量 `HCCL_BUFFSIZE`**。

本页只依据一份维护者手工摘录的 `vllm_ascend/utils.py` 片段（摘录覆盖常量定义区与三个函数），**不是完整文件，也没有核对任何在册发布分支**，所以下面只陈述这段代码自身写了什么，不声称它在 v0.23 维护分支、v0.26 分支或 main 开发主线上成立 [A]。

## 那条请求走不到这里

[那条请求](one-request.md)是单卡昇腾、Qwen3-0.6B，没有 DP、没有 EP、也没有 MC2 融合通信，所以它一个通信组都不需要建，这段分派逻辑整段不执行 [D]。

要让它走到这里，最省事的改法是把并行度打开：设 `data_parallel_size = 4`，于是 `dp` 这个组名会命中下面那张表的第一行，缓冲区由 `calculate_dp_buffer_size()` 现算。按摘录里的公式算一遍——`(4 + 1) × 4 = 20` 字节，`math.ceil(20 / 1048576) = 1`，最后 `max(1, 50) = 50` [D]。也就是说这条改法下真正生效的不是算出来的 1，而是下限 `_MIN_DP_BUFFER_SIZE` [D]。

## 分派规则就是一张三行的表加一个例外

摘录里 `get_hccl_config_for_pg_options(group_name)` 的主体是一个字典查表加一个兜底 [D]：

| 传进来的 `group_name` | 拿到的 `hccl_buffer_size` | 意味着什么 |
|---|---|---|
| `"dp"` | `calculate_dp_buffer_size()` 的返回值 | 唯一一个随配置变化的组 |
| `"dynamic_eplb"` | `_DYNAMIC_EPLB_BUFFER_SIZE` = 100 | 写死的常量，只有默认值的一半 |
| 其他任何名字 | `get_default_buffer_config()`，即 `_DEFAULT_BUFFER_SIZE` = 200 | 兜底分支，绝大多数组落在这里 |
| 名字里含 `"mc2"` | **`None`** | 不是「给 0」，是根本不传 `pg_options` |

注意 MC2 那一行的判断写在查表之前、且用的是 `"mc2" in group_name` 的子串匹配，所以任何组名里只要出现 `mc2` 三个字母就会提前返回 [D]。另外三行是精确键匹配，`"dp"` 拼成别的写法就会掉进兜底的 200 [D]。

摘录里没有出现单位字样。判断依据只有 `calculate_dp_buffer_size()` 里那个 `/ (1024 * 1024)`——它把字节数换算成 MiB 之后才交给 `hccl_buffer_size`，所以这三个数（200 / 100 / 50）应当都是以 MiB 计的 [I]。这一点摘录没有明说，要确认得去读 torch_npu 侧对 `hccl_buffer_size` 的定义 [A]。

## DP 组那个公式算出来的数，几乎总是被下限顶掉

`calculate_dp_buffer_size()` 的四步很短 [D]：

1. 从 `get_current_vllm_config()` 取 `parallel_config.data_parallel_size`；
2. `int32_size = torch.iinfo(torch.int32).bits // 8`，即 4 字节；
3. `dp_buffer_size = math.ceil((dp_size + 1) * int32_size / (1024 * 1024))`；
4. `return max(dp_buffer_size, _MIN_DP_BUFFER_SIZE)`。

docstring 把 `+ 1` 解释为 `flags: with_prefill`——也就是这块缓冲区要装的是每个 DP rank 一个 int32，外加一个标志位 [D]。**这意味着它的真实需求量小到离谱**：要让第 3 步的结果超过下限 50 MiB，需要 `(dp_size + 1) × 4 > 50 × 1024 × 1024`，即 `dp_size` 超过一千三百万 [D]。任何现实规模下第 3 步都返回 1，最终值恒等于 50 [D]。

所以这个函数的实际语义是「DP 组固定 50 MiB」，公式部分是为了表达意图而非为了算出数 [I]。它比默认的 200 小，方向上是在给 DP 组**省**显存 [D]。

## MC2 组返回 None 是绕开一个已知缺陷，不是遗漏

摘录里这个分支上方挂着一条 `FIXME`，原文说：当前的 mc2 算子只依据 `HCCL_BUFFSIZE` 配置来划分通信空间（communication space partitioning），对 mc2 组使用 `pg_options` 会导致内存不对齐问题（memory misalignment problems）[D]。

这句话把两条配置通路的关系讲清楚了：`pg_options` 里的 `hccl_buffer_size` 是**建组时逐组下发**的，而 mc2 算子自己读的是**进程级环境变量** `HCCL_BUFFSIZE` [D]。两边同时生效时，算子按环境变量切分出的空间与建组时实际分配的大小对不上，就会踩到对不齐 [I]。返回 `None` 相当于主动放弃对这个组的逐组配置权，让它整个回落到 `HCCL_BUFFSIZE` 这一条通路上 [I]。

**读者该拿走的结论是：MC2 通信组的缓冲区只能通过环境变量 `HCCL_BUFFSIZE` 调，调它会同时影响所有依赖该环境变量的通信，而不是只影响 MC2** [I]。`FIXME` 这个标记本身也说明这是临时规避、上游认为该修 [D]。

## 这份摘录说不了的事

摘录只有常量区和三个函数，**调用方一行都没有**，所以下面这些都还是缺口，不要从本页推断：

- 谁在什么时候调用 `get_hccl_config_for_pg_options`、传进去的组名具体有哪些字符串 [A]；
- 返回 `None` 之后建组代码怎么处理（是省略 `pg_options` 参数，还是传 `None` 进去）[A]；
- `HCCL_BUFFSIZE` 在 vllm-ascend 里有没有被代码设过默认值，还是完全交给用户 [A]；
- 这段逻辑在三个在册版本上各是什么样、常量值有没有差异 [A]。

## 常见误解

- **「`HCCL_BUFFSIZE` 和 `hccl_buffer_size` 是同一个开关的两种写法」**——是两条通路。后者建组时逐组下发，前者是进程级环境变量；正因为两者会打架，MC2 组才被排除在前者之外。[D]
- **「MC2 组返回 `None` 表示不要缓冲区 / 给 0」**——返回的是「不提供 `pg_options`」，缓冲区仍然存在，只是改由 `HCCL_BUFFSIZE` 决定。[D]
- **「DP 组的缓冲区会随 DP 规模一起涨」**——公式算出的需求量只有几十字节级，恒被 50 的下限顶掉；要涨到超过下限得上千万个 DP rank。[D]
- **「200 就是全局默认，所有组都是 200」**——它只是查表兜底值；`dp` 与 `dynamic_eplb` 各有自己的数，`mc2` 连表都不查。[D]
- **「这几个数是 GB / 字节」**——摘录未标单位，从换算式看应是 MiB，但这是推断，未经 torch_npu 侧文档确认。[I]
