## HCCL buffer 是什么，为什么每个通信组都要先占一块显存？

**通信组（process group）**是一组要一起通信的卡：成员和组内编号在启动时定下来，[集合通信](collective-communication.md)的每一次操作都发生在某个组里。**HCCL buffer 是 HCCL（昇腾集合通信库）为一个通信组在每张成员卡上预留的一块设备内存：这个组以后每次收发，数据都先落进这块预留区，再由链路搬去对端，或者从这里取回来。** 大小在建组时按配置定下，服务活着就一直不还。

```wiki-diagram
file: hccl-buffer
```

图里这张卡参加了三个组，卡上就有三块缓冲，各留各的：只交换几十字节调度信息的组，和搬整批激活的组，不共用一块中转区。还要分清缓冲和通信的输入是两回事——输入是模型算出来的隐藏向量、专家激活或调度信息，它们各自住在自己的张量里，通信时才被搬进缓冲；缓冲是那个固定的中转区，留多大和这一次搬多少没有关系。

通信组按什么规则划分、走机内还是跨机的链路、争用时怎么排优先级，见 [CANN 与 HCCL](cann-hccl.md)；All-Reduce、All-to-All 这些操作各让每张卡得到什么，见[通信基础](collective-communication.md)。本页只管这块预留区：谁定它的大小，它占了谁的地方。

## 为什么要提前留，代价落在哪里？

两张卡交换数据，得有一块双方都认的中转区。vllm-ascend 的调优文档就是这样描述控制它的那个环境变量的：控制两个 NPU 之间共享数据的缓存大小。预留一次、反复使用，每次通信就不必临时申请内存、重新告诉通信库往哪里写；代价是这块内存从建组起就被占住，通信空闲时也不释放。

**这笔代价直接落在 KV cache 的预算上。** 昇腾的 worker 按这个顺序分账：先量一次显存快照，之后才建通信组、装权重、跑一遍试算；最后算出可用 KV = 预算 − （权重 + 激活峰值 + 非 torch 增量）。「非 torch 增量」的口径是「试算结束时的非 torch 占用 − 最初那次快照」，而 HCCL 的缓冲不经过 torch 的分配器，正好落进这一项。于是每一块缓冲都是从 KV 的额度里直接扣走的：组越多、每组留得越大，能切出来的 KV 块就越少。这份预算本身怎么来的，见[双机部署页](glm-5-3-flash-two-node.md#剩下的显存变成多少-kv-cache)。

反方向也有代价。留得太小，一次要搬的数据装不进中转区：普通集合通信会分多次搬，而 MoE 用的 MC2 算子在算 tiling（算子执行前定下的切分与搬运方案）的时候就直接判失败，后面单独讲。所以这个值既不是越大越好，也不是越小越好。

## 放到 GLM 双机：本部署建了哪些组，各留多大

固定部署是两台 Atlas 800 A2、每台 8 卡，TP8 / DP2 / EP16，完整前提见[部署前提](glm-5-3-flash-two-node.md#部署前提)。启动时每个 worker 都会建下面这几个 HCCL 组，成员的推导见[16 张卡怎样分组](glm-5-3-flash-two-node.md#16-张卡怎样分组)；缓冲值按组名从源码写死的三个常量里挑：

| 组 | 以 rank 0 为例的成员 | 这个组做什么 | 本卡为它留的值 |
|---|---|---|---|
| world | 全部 16 张卡 | 启动阶段的全局对齐 | 200 M |
| tp | 机内 8 张卡 | 每层 attention 输出和 MLP 之后的 All-Reduce | 200 M |
| ep | 全部 16 张卡 | MoE 走 All-Gather 路径时的收集与归约 | 200 M |
| mc2 | 全部 16 张卡 | MoE 走 MC2 路径时的 dispatch / combine | 不写这个字段，见下文 |
| dp | 跨机同号的 2 张卡 | 每步同步两台机器还有没有活干 | 50 M |
| pp、dcp、pcp | 只有本卡 | 这三种并行规模都是 1，组里只剩自己 | 各 200 M |

表里的 M 按源码的换算是 1,024 × 1,024 字节。两台机器之间那次 2 元素状态同步走的是 CPU 通道（gloo），不是 HCCL 组，不占这块缓冲。另外三个组只在开关打开时才建：EPLB 的负载均衡组（常量 100 M）、细粒度 TP 的四个组、FlashComm2 的组，本部署都没开——EPLB 的判定见 [expert-parallel](expert-parallel.md#这套部署有没有开-eplb)，另两项的规模配成 0 就不建组。

### DP 组为什么只留 50 M

dp 是唯一按规模算的组：公式取 DP 规模再加一个标记位，每项算一个 int32，换算成 M 之后取一个下限。

```calc
title: DP 组的 50 M 是怎么来的
按公式换算 = ceil((2 + 1) × 4 B ÷ 1 MiB) = ceil(12 ÷ 1,048,576) = 1 M
和下限比 = max(1 M, 50 M) = 50 M
> 公式里的 4 是 int32 的字节数，下限 50 写在源码常量里
```

DP=2 时换算项还不到 1 M，结果完全由下限决定。反过来不成立：50 M 不代表每步真的发 50 M。这一步同步的只是几个 int32 标记——本部署这条路径构造两组、每组 DP 个 int32，再归约成各 rank 的状态——消息布局由收发代码决定，不能从预算值反推。

### 这些组合起来，从 KV 里拿走多少

把上表的配置值加起来，再按一个 KV 块 7.969 MiB 折算。块大小和 3,855 块是[双机部署页](glm-5-3-flash-two-node.md#剩下的显存变成多少-kv-cache)推导好的，本页只引用：

```calc
title: 本卡上这些组的配置值合计
真要跨卡通信的四个组 = 200 M（world）+ 200 M（tp）+ 200 M（ep）+ 50 M（dp） = 650 M
只有本卡一个成员的三个组 = 3 × 200 M = 600 M
650 M 折合 KV 块 = 650 MiB ÷ 7.969 MiB = 81.6 ≈ 82 块
82 块折合缓存位置 = 82 × 640 = 52,480 token
```

四个真要跨卡的组合计 650 M，相当于 82 个 KV 块、5 万多个 token 的缓存位置，占那 3,855 块算例的 2.1%。三个只有本卡一个成员的组按配置也各写了 200 M，合起来 600 M；它们是否真的各占一块同样大的设备内存，取决于 HCCL 怎样处理单成员组，本页只有配置值、没有实机计量，这一条列在页末。

## 建组时怎么挑值，建完能不能复用？

昇腾把上游的建组入口整体换成了自己的版本：每建一个组，先按组名取一份配置，再构造一个 Options（交给建组函数的一组参数）传下去，中间还多了一道注册表。

```wiki-diagram
file: hccl-buffer-flow
```

四条分派里，`dp` 和 `dynamic_eplb` 是精确匹配组名，`mc2` 那条是「名字里含 mc2」，其余一律走 200 M。要注意四条分支都会构造 Options 并把组名写进去，`mc2` 那条省掉的只是缓冲字段，不是「不传配置」。

注册表按四件事算一个键：成员、后端、这份配置、复用域。复用域也按组名定：名字里带 eplb 的自成一域，`mc2` 自成一域，其余归同一个共用域。键相同就交出已经建好的那个组、只多记一次引用，不再真建；键算不出来就退回逐个新建——出现了不认识的非默认字段，或者传进来的成员和 Options 里记的成员对不上，都按这条走。所以进程里真正建了几个 HCCL 组，不等于代码里创建了几个通信组对象，「组数乘每组的值」也就不能直接当成实际占用。

还有一处细节值得记住：组名本身被有意排除在键之外，但那份配置里也写了组名，于是按本仓代码读，名字不同的组算出来的键就不同。注册表的单元测试用的配置只带缓冲大小，那种情况下同成员、同大小的组才会命中复用。这一条也列在页末。

## MC2 组为什么不按组配？

`mc2` 那条分支直接返回空配置，源码注释给了理由：MC2 算子是按环境变量 `HCCL_BUFFSIZE` 划分自己那块通信空间的，再单独给这个组覆盖一个缓冲大小，两边划分不一致就会踩到内存对不上的问题。

于是 MoE 这条最吃通信的路，缓冲改由那个环境变量统一决定。MC2 算子在算 tiling 时先取这个值，环境里没设就按 200 M 算，再拿这一批 dispatch 真要搬的量去比：按 token 行数、每个 token 选中的专家数和隐藏维算出三份 int8 数据，外加一块固定余量。装不下就直接判失败，不会自己降级成分多次搬。

这也说明两个层级不能混着看：环境变量管的是采用它的通信域和 MC2 算子的窗口，逐组配置管的是单个组的那个字段。一个组归哪一套管，由建组时挑到的那条分支决定。

## 常见误解

**「留了 200 M，就是这个组每次通信 200 M 数据。」** 不是。缓冲是中转区的容量上限，是启动时定下的配置；一次通信实际搬多少，由那次操作的张量形状决定。

**「dp 组留 50 M，说明每步同步 50 M 元数据。」** 不是。那一步同步的是几个 int32 标记，50 只是公式的下限；预算值和消息布局是两件事。

**「组数乘每组的值，就是这个进程的通信内存。」** 不成立。注册表会让键相同的组复用同一个底层组；只有本卡一个成员的组另算；收发缓冲之外通信库还有别的内部开销。配置值只是配置值，实际占用要在实机上量。

**「`HCCL_BUFFSIZE` 和 `hccl_buffer_size` 是一回事。」** 不是。前者是环境变量，管采用它的通信域和 MC2 算子的窗口；后者是逐组 Options 里的字段，只管那一个组。名字含 `mc2` 的组是被有意排除在后者之外的。

**「缓冲只在通信时占用显存。」** 不是。它在建组时就占住，服务期间不释放，KV cache 只能用剩下的部分。

## 对照源码

### 怎么开

逐组缓冲没有开关：只要建组就按组名挑值，三个常量（200 / 50 / 100）写死在源码里。[C2] 能调的是环境变量 `HCCL_BUFFSIZE`，单位是 M，作用于采用它的通信域和 MC2 算子的窗口。[S18] 本部署的启动命令和其他环境变量以官方教程为准，参数清单见[部署前提](glm-5-3-flash-two-node.md#部署前提)。要确认某个组最终用了多少，只能在实机上核：组名、成员、字段最终值和 torch_npu / CANN 版本一起记。

### 会报什么错

- 启动阶段空闲显存不足：`Free memory on device (…) on startup is less than desired GPU memory utilization`。缓冲这类非 torch 占用会把空闲显存压到 `gpu_memory_utilization` 要的额度以下。[C11]
- MC2 窗口装不下：`HCCL_BUFFSIZE is too SMALL, m = …, expected HCCL_BUFFSIZE is ((m * k * topK * sizeof(int8_t)) * 3 + 3MB)= %luMB, HCCL_BUFFSIZE=%luMB.`，tiling 直接返回失败。提示文案写的是 `+ 3MB`，实现按 `+ 10 * MB_SIZE` 判定，照提示估出来的门槛会偏小。[C15]
- 环境变量写了超过 uint16 的值：MC2 侧只记一条 warning，然后按默认 200 M 算；解析异常记一条 error。[C14]
- Options 里出现不认识的非默认字段，或成员与 Options 记录的成员不一致：注册表算不出键，退回逐个新建，不报错。[C7]

### 开销和什么时候别开

关不掉：通信组必须建，缓冲跟着建组一起占。量级上，本部署 8 个组的配置值合计 1,250 M，其中 600 M 来自三个只有本卡一个成员的组，折合 150 多个 KV 块。[D] 调大 `HCCL_BUFFSIZE` 能让 MC2 吃下更大的批，但吃掉的是同一份 KV 额度；调小先撞上面那条 tiling 检查。没有实机计量和通信耗时对照时，不要凭配置值推断收益，更不要把某次小消息的字节数当成调参结论。
