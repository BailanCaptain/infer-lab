**推理测量，是把“快不快”拆成几个有明确起点、终点和统计范围的问题。** 这样才能知道一次改动究竟改善了什么，又让谁多等了一会儿。

记录越细，越容易找到停顿发生在哪一步，也会增加客户端和服务端的采集、传输与保存成本；先留必要的时间与计数，再针对异常请求短时加深采集。

[上一例](inference-performance-walkthrough.md#同一组请求比较两种设置)已经找到了取舍：把新请求 N 的长输入分段，正在生成的请求 D 中途停顿缩短了，N 的首字却来得更晚。本页继续判断：把这种配置用于更多请求后，服务究竟有没有变好？

## 每秒回答更多，为什么用起来反而更慢

你把服务一次处理的请求数量调大，压测报告里的“每秒输出量”提高了，可试用的人却说回答更卡。这两份反馈可以同时成立：服务每轮照顾了更多人，每个人等这一轮结束的时间也变长了。

模型按 **token（词元）**处理文字，一个 token 不一定是一个汉字。**吞吐**数的是服务每秒完成多少工作；**延迟**问的是某个请求等了多久。把多条请求放进同一步计算叫一个**批次**。图里有四条已在生成的请求：左侧每步选两条，右侧把四条一起选入。右侧一步能交出更多 token，但每条请求仍要等这一步结束；多选两条以后，这一步可能也更长。


因此，只数“一步产出多少”还不够，还要量“这一步花多久”以及没被选入的请求等了多久。后台离线处理更在意多久做完整批任务；聊天服务还要照顾第一个字何时出现、后续输出会不会停顿。先约定目标，才有判断改动好坏的尺子。

## 先把一个请求的几种等待分开

请求从客户端发出，经过[入口、调度、计算和返回](one-request.md#一条请求要走过七站)，最后才变成屏幕上的文字。首字慢既能来自排队，也能来自输入处理或计算；只报一个首字时间，还没有定位到原因。

| 指标 | 本页采用的定义 | 能回答什么 |
| --- | --- | --- |
| TTFT，首个 token 等待 | 从客户端实际发送到收到第一个输出 token | 用户多久开始得到输出 |
| ITL，相邻 token 间隔 | 同一请求相邻两个输出 token 的到达时刻之差 | 输出是否有停顿 |
| 请求级 TPOT，平均后续 token 时间 | 首个到末个输出 token 的时间，除以输出 token 数减一 | 这条回答平均推进多快 |
| E2E，端到端时间 | 从发送到约定的请求完成事件 | 什么时候拿到完整结果 |

这张表先假定能看到逐 token 时间。实际客户端常收到的是 **SSE 片段**，即 HTTP 流里逐段发来的消息。一个片段能合并多个 token，声明角色的首个片段还能是空的。若只记录片段时间，应写“有效片段间隔”；若目标是首个可见答案，应另记首个非空答案文本，不能把角色消息、思考字段和答案混算。原因见[流式输出](streaming-output.md)。

一些压测工具用“请求延迟减 TTFT”作为 TPOT 的分子。若请求延迟结束于最后一个内容片段，它与上面的定义接近；若结束于最后的用量消息或连接结束，就多算了尾部等待。报告必须保留工具版本、接口和计时事件。输出不足两个 token 时没有后续间隔，不把它混入普通 TPOT 均值；工具若为达标判定填零，也要记录这个约定。

[停顿样例](inference-performance-walkthrough.md#这次到底停了多久)完整演算了这些指标。现场应同时留下原始时间序列和汇总值：平均值能描述整体，原始记录才能定位那一次停顿。

## 服务里的同名指标，和客户端在量同一段吗

客户端能回答“用户等了多久”，服务内部的记录帮助判断“时间花在哪一站”。两者的起点、终点不同。例如，模型已经交回一个 token，服务仍要把它变成文本、组装响应并发送；这段工作会影响客户端等待，却不都包含在引擎内部的 token 间隔里。

先看普通生成请求、单条输出序列的情况。引擎为进入等待队列、首次被调度和交回输出记录事件。**事件时间**是程序在那个位置读到的时钟，不是设备 kernel 的开始、结束时间。**EngineCore** 是负责调度和推动模型执行的引擎核心进程。以下时间线只采用同一 EngineCore 的相对时间，数值均为示意。请求在 120 ms 被抢占，也就是暂时退出运行集合；180 ms 恢复调度，200 ms 交回最后一组输出。

**prefill** 处理输入以产生首个输出，**decode** 利用已有历史继续生成。下面的监控把首次调度到首个输出作为 prefill 阶段，把首个到最后输出作为 decode 阶段；这两个统计时间段包含中途的等待。

```wiki-diagram
file: inference-metrics-events
```

这里首次输出含 1 个 token，第二次含 3 个 token，总共 4 个。一次能交回多个 token，以及几步怎样合成片段，见[流式输出](streaming-output.md#前端跟不上时几步的文字并成一段)。图中的抢占发生在首个输出以后，因此它落在 decode 的时间段里；首次调度时间仍保留 20 ms，恢复时不重新起算（以下均为同一组引擎事件的示意推导）：

$$\text{TPOT}_{\text{req}} = \frac{200 - 100}{4 - 1} \approx 33.33\text{ ms}, \qquad \Delta t_{\text{event}} = 200 - 100 = 100\text{ ms}$$

| 指标名称（同一份引擎事件·示意） | 计算式 | 结果 |
| --- | --- | --- |
| 首次排队时间 | $20 - 0$ | **20 ms** |
| prefill 阶段时间 | $100 - 20$ | **80 ms** |
| decode 阶段时间（含抢占等待） | $200 - 100$ | **100 ms** |
| inference 阶段时间 | $200 - 20$ | **180 ms** |
| 两次输出事件的间隔（inter-token 样本） | $200 - 100$ | **100 ms** |
| 请求级平均后续 token 时间 | $100 / (4 - 1)$ | **$\approx 33.33\text{ ms}$** |

读懂这张引擎计时表，需要守住三条容易踩坑的边界：

- **事件间隔 $\neq$ 请求均摊 TPOT**：100 ms 的输出事件间隔与 33.33 ms 的请求平均值可以同时正确。内部 inter-token 指标每遇到一次后续输出事件就记一个样本，没有按该次交回的 3 个 token 再平摊；请求级平均值才按输出数量计算。空文本、思考字段和合并发送会继续改变客户端看到的片段，三类样本不能互换。
- **排队指标只量首次入队到首次调度**：被抢占后的等待不会追加到排队指标里；首次输出前的抢占会延长 prefill 阶段，首次输出后的抢占会延长 decode 阶段。`inference` 是首次调度到最后输出的整段经过时间，包含这些等待，并非把设备计算时长加起来。输出不足两个 token 时，固定服务实现给请求平均后续 token 时间记 0；这与前文压测工具普通 TPOT 样本排除短输出的约定不同。
- **墙上时钟与单调时钟不能混减**：服务的 TTFT 用前端保存的请求到达时刻，到前端处理首个引擎输出批次的统计时刻；服务 E2E 使用同一到达时刻，到完成输出批次的统计时刻。这两个量使用前端墙上时钟，前面的阶段差值使用 EngineCore 的单调时钟。墙上时钟表示日历时间，单调时钟用于量间隔；不要把两套原始数直接相减，也不要把服务 TTFT 写成“客户端收到首个可见字”——内部统计更新还早于本轮文本解码与 HTTP 发送。

这些值会汇总成监控指标，却不保留每条请求的完整时间线。下一步在[性能分析的监控节](inference-performance-analysis.md#先读监控面板再选择一条慢请求)看怎样读取类型、标签和窗口；需要找某一条请求，再接请求级 trace。阶段定义只在本节保留。

## 吞吐提高了多少，要先说清数了什么

现在把停顿样例的 A（较大预算）、B（较小预算）放到同一份请求集上比较。这里扩大到 24 条请求，每条要求输出 100 个 token；保留长输入与短输入的混合，但不把前文 D 的五个 token 当作这次全部负载。以下是为演算构造的**教学结果，不是已运行的压测**。

**SLO（服务目标）**就是事先约定的可接受表现。本轮要求每条达标请求成功完成，TTFT 不超过 350 ms，最长 ITL 不超过 150 ms，且任务质量通过相同检查。假定客户端能记录逐 token 到达；只有 SSE 片段时应换成明确的片段指标。

| 同一 10 秒窗口的记录 | A | B |
| --- | --- | --- |
| 发出的请求 | 24 | 24 |
| 成功完成，每条输出 100 token | 20 | 20 |
| 已失败 / 窗口结束未完成 | 2 / 2 | 2 / 2 |
| 成功且满足上述目标 | 16 | 18 |

两种配置的交付总数一样，B 却让更多交付满足等待要求。我们要把“完成多少”和“其中多少可接受”分别统计，才不会漏掉这种收益。

我们采用“窗口内成功完成请求的完整输出”口径，失败请求的部分输出另记，未完成请求继续追踪最终结果。窗口开始时没有遗留请求。这样的口径能说明这段时间交付了多少完整回答，但不等于逐个数窗口内所有到达的 token（以下按 10 秒窗口、24 条请求的教学结果推导）：

$$\text{goodput}_A = \frac{16}{10} = 1.6\text{ 请求/秒}, \qquad \text{goodput}_B = \frac{18}{10} = 1.8\text{ 请求/秒}, \qquad \text{最高可能成功率} = \frac{20 + 2}{24} \approx 91.67\%$$

| 报告留存口径（10 秒窗口·示意） | 计算式 | 数值 |
| --- | --- | --- |
| 成功请求吞吐 | $20 / 10$ | **2 请求/秒** |
| 成功请求输出吞吐 | $(20 \times 100) / 10$ | **200 token/秒** |
| A / B 达标请求吞吐（goodput） | $16 / 10$ vs $18 / 10$ | **1.6 vs 1.8 请求/秒**（B 多交付 2 请求） |
| 窗口内已知失败比例 | $2 / 24 \times 100\%$ | **8.33%** |
| 窗口结束未完成数 | $24 - 20 - 2$ | **2 请求** |
| 本批最终成功率最高可能值 | $(20 + 2) / 24 \times 100\%$ | **$\approx 91.67\%$** |

本页的 **goodput（达标请求吞吐）**是单位时间内成功且满足约定目标的请求数，单位为请求/秒。这里 A、B 都是每秒 200 个成功输出 token，B 的达标吞吐却从 1.6 提高到 1.8 请求/秒。因此，“总吞吐没涨”不等于“改动没用”；它改善的是同一工作量下的可接受交付。


读实际报告时，还要确认压测工具是否启用了达标统计。有些零值表示没有配置达标阈值，不能直接解读为“所有请求都未达标”；本页核对的 vLLM 工具行为见[源码区](#源码位置)。上面的教学表已明确统计了达标请求，可以按给出的数量计算。

本批 A、B 已经各有两条失败。按发出的全部 24 条请求作分母，即使两条未完成请求最终都成功，成功率最高也只有约 91.67%，低于“至少 99%”的要求。因此可以说“B 在这个窗口里达标交付更多”，也能明确说“这批 A、B 都没有通过成功率门槛”。两项判断并不矛盾：局部指标改善与整体验收通过是两回事。20 条成功请求内部的达标比例，也不能替代所有请求的成功率。

未完成的两条没有最终延迟，也还不能判作成功。补测时可以等待排空，也可以在固定截止时间停止并单列未完成项，但 A、B 两组必须采用同一种方式。不能丢掉慢请求后宣布延迟变好。输入 token、输出 token、两者合计也应分别列出；缓存命中的输入长度与实际重算位置数是两种工作量。

## 平均不慢，为什么总有人等很久

把每条请求的延迟从小到大排列，**P95** 用接近第 95 百分位的值描述慢的那一端。用最近秩算法举例：20 条请求排序后，取第 19 条的延迟；若它是 800 ms，就表示这 20 条里至少有 19 条的延迟不超过 800 ms。常见工具也会在相邻样本之间插值，因此同一批数据的 P95 需要注明算法。这个值只描述纳入排序的样本，失败和未完成项仍要另报；样本很少时，也不能据此推断稳定的长尾表现。

比较前先按输入长度、输出长度和请求种类分组。一组全是短问答，另一组混入大量长文档，即使程序没变，整体 P95 也会变。报告至少保留各组样本数、失败数、长度分布、P50/P95/P99 和重复运行的波动。

还有一个容易忽略的差别。假设一条短回答只有一个后续间隔，长 100 ms；另一条长回答有九个后续间隔，每个都是 20 ms。这也是教学示意。先算每条请求的 TPOT，再取平均，每条请求各占一票；把所有间隔放在一起，长回答就贡献九票：

$$\overline{\text{TPOT}}_{\text{req}} = \frac{100 + 20}{2} = 60\text{ ms}, \qquad \overline{\text{ITL}}_{\text{all}} = \frac{100 + 9 \times 20}{10} = 28\text{ ms}$$

| 统计口径（两请求示意：短答 1×100 ms、长答 9×20 ms） | 权重与算式 | 结果 |
| --- | --- | --- |
| 请求级 TPOT 的平均值 | 每条请求一票：$(100 + 20) / 2$ | **60 ms** |
| 全部 ITL 的平均值 | 每个间隔一票：$(100 + 9 \times 20) / 10$ | **28 ms** |

两个结果都能算对，但回答的问题不同。报告出现差别时，先核对这种样本权重以及片段是否合并，再判断程序是否出错。

回到 A、B：总体多了两条达标请求以后，还要逐组检查。若短问答全部改善、长文请求的 TTFT 却越过目标，就需要按业务取舍重新选预算。用总平均掩盖这一组退化，会重复上一例“只看 D、不看 N”的错误。

## 怎样让两次压测真正可比

先固定同一批输入、请求到达方式和输出要求，再只改变要检验的配置。**负载生成器**是发送测试请求的程序；它自身的 CPU、连接池或并发上限不足，也会让服务看起来吃不满。

- **闭环负载（固定并发）**：保持固定数量的请求在运行，完成一条再补一条。它适合研究给定并发下的满载吞吐，但服务一慢，补入的请求也随之变少，容易掩盖真实线上流量下的队列积压与尾部延迟（协调遗漏）。
- **开环负载（按计划到达率）**：按预先确定的时间表（如 `request_rate` 与 `burstiness`）发请求，能直接暴露持续到达下的排队增长。若生成器因并发上限迟发，必须同时记录**计划发送、实际发送和服务收到**三个时刻，避免客户端里的等待从报告中消失。

可比性验收按以下三段边界隔离一次性开销与缓存污染：

1. **隔离预热与前缀缓存状态**：先预热再测能消化首次编译、图捕获等一次性工作，但必须明确**是否已存在可复用的提示词缓存**——第二遍用相同提示词命中历史时，收益就不全来自本次配置。比较正常重复访问时应保持两组同等命中条件；测冷请求时应走相同、可验证的冷缓存准备流程，不能只给其中一组换新提示词。
2. **完整留档与交错复测**：每轮可复查的结果应保存安装版本与启动日志、模型和分词器文件标识、输入与计划到达表、实际生效配置、原始响应时间及 token 数、失败/未完成记录与冷暖状态。先交错重复 A、B，确认达标请求的差别大于运行波动。
3. **基准与剖析分跑**：先得到未开调试采集的基准，再短时采 **profiler**（记录函数或设备任务执行时间的工具）解释慢在哪里，最后关闭采集复测；采集引入的额外开销绝不混入收益结论。

确认 A、B 的收益稳定后，逐级提高相同请求组合的到达速率，观察哪一档开始积压或违反 SLO——这个运行点才是[容量案例](inference-capacity-and-reliability.md#先说明够用是什么意思再测一个实例)需要的输入。要解释为什么 B 的单步更短，则继续读[性能分析](inference-performance-analysis.md)，两项工作分别回答“是否有效”和“为什么有效”。

## 读 DeepInfer 的性能图，先弄清哪些工作被计入

现在带着同一把尺子读 DeepInfer 的离线基准。**P（Prefill）处理输入，D（Decode）利用已有历史继续生成。** 示例分别测 P 处理未命中输入的速度、D 连续执行的步速；**步速**是一秒完成多少轮生成计算。一轮可能验证多个候选，候选也可能被拒绝，所以步数、验证数和实际输出数需要分开。

固定快照的示例把 D 的吞吐按“所有候选都被接受”换算。假设一张卡每轮处理两条请求，每条验证三个候选，测得每秒 100 轮；这是缩小的教学例子。按全部接受计数，每条这一轮产出三个接受的候选，再加一个新 token；若实际平均每条只交付两个，结果就不同：

$$\text{TPS}_{\text{全接受}} = 100 \times 2 \times (1 + 3) = 800\text{ token/秒}, \qquad \text{TPS}_{\text{实交付}} = 100 \times 2 \times 2 = 400\text{ token/秒}$$

| 计数口径（100 轮/秒 × 2 请求/轮·示意） | 算式 | 换算吞吐 |
| --- | --- | --- |
| 全部接受口径（1 新 + 3 候选） | $100 \times 2 \times (1 + 3)$ | **800 token/秒** |
| 平均实际交付口径（每条交付 2 token） | $100 \times 2 \times 2$ | **400 token/秒** |

800 描述一种计数口径；要回答用户得到多少，必须补上实际接受与交付记录。候选怎样变成输出，继续见 [DSpark](dspark.md)。在昇腾生产压测与精度基线验收中，把这些指标口径落到具体压测工具与数据集的实战步骤见[AISBench 与 EvalScope 实战](aisbench-and-evalscope.md)。

另一个陷阱在时间线。示例导出的 **trace** 是设备执行事件记录，但其中 P、D 分别采样，再首尾拼接到一张图里。中间的预热和性能测量没有放进去。因此，图上 P 的末尾紧挨 D 的开头，只表示两个采样片段被排在一起，无法据此计算在线请求的首字延迟，或认定真实服务没有交接等待。

可以把它用于“这一段调用了哪些 kernel、哪些操作相互等待”的分析；要量收益，则取未开采集时的计时记录。**Kernel** 是设备上执行某项运算的程序。采集工具自己也要消耗资源，固定示例甚至把 D 的采集放在测量之后，避免采集结束后的残留影响污染数字。

最后看报告主动排除了什么。该示例为研究稳定计算，会剔除与专家负载统计汇集重合的计时间隔。这有助于比较引擎执行能力；线上容量测试仍要保留真实发生的周期工作、排队、失败和长尾。读者可以据此问出三个具体问题：**输出是否实际接受、时间线是否连续、哪些成本被排除了？** 再漂亮的离线曲线，也要回到前面的客户端口径完成验收。

## 放到 GLM 双机，怎样安排这份记录

沿用[官方双机部署](glm-5-3-flash-two-node.md#部署前提)。**DP** 把请求分给两个执行组；**TP** 把矩阵计算分给机内多卡；**EP** 把专家网络分到两机多卡。两组要共同完成部分计算，不能把它们看成互不依赖的完整模型副本。

因此，既要记录整个服务的吞吐，也要记录请求进入哪个 DP 组以及各组输入长度、等待队列和实际工作量。只看总量，会漏掉一组集中接到长请求、另一组在等待的情况。

这套配置还有 **MTP**，即模型猜测后续 token 后再验证的路径，一轮能交回多个 token。记录客户端片段数、引擎接受的输出 token 数和设备执行步数时要分别命名。它们怎样对应，继续看[多请求主线](concurrent-requests.md)与[流式输出](streaming-output.md)。本页不提供这套设备的性能实测值。

测得同一负载与延迟目标下的能力以后，可继续用[容量与恢复案例](inference-capacity-and-reliability.md)估算故障余量、积压和恢复时间。

## 常见误解

- **“TTFT 就是处理提示词的时间。”** 客户端口径还包含传输、排队、前后处理；定位需要服务内的阶段记录。
- **“只有成功请求才值得统计。”** 只报成功样本会隐藏超时和拥塞；失败与未完成项必须一起交付。
- **“并发数相同就是负载相同。”** 到达方式、输入长度、实际生成长度和缓存状态都会改变工作量。
- **“吞吐最高的配置一定最好。”** 先满足服务目标和输出质量，再比较吞吐、资源占用与成本。

## 对照源码

### 怎么开

现场先用该安装版本的 `vllm bench serve --help` 核对接口、数据集、到达速率、并发上限、预热和保存逐请求结果的参数；昇腾侧工具化压测与精度基线对照流程（AISBench 压测模式、EvalScope 评测与指标对齐）见[AISBench 与 EvalScope 实战](aisbench-and-evalscope.md)。使用与部署一致的分词器；输出长度优先用可信的服务 token 计数，退回对返回文本重新分词时注明这一口径。

### 会报什么错

压测工具里的“没有收到有效片段”首先是响应与计时契约不满足；保留状态码、错误体、接口类型和原始流，确认请求是否到达生成阶段。HTTP 成功也要检查流内错误和正常结束标记。失败请求不能因为缺少 TTFT 就从分母中消失。

### 开销和什么时候别开

逐 token 日志、完整响应保存与 profiler 会占用 CPU、存储或改变时序。容量基准和定位采集分开运行；若客户端已经无法按时发压测请求，先解决生成器限制，再加服务负载。
