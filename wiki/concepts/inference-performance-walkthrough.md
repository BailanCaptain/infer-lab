**推理性能分析，是找出一次请求的时间花在哪里，再验证怎样让它更快。** 这篇从一次“回答到一半停住”的现象开始，走完记录、定位和验证的过程。

## 同一个问题，为什么人多时回答会卡住

你独自测试一个问答服务，回答不断出现在屏幕上，用起来很流畅。换成多人同时使用后，同样的问题却时不时停一下，然后才继续输出。

我们跟踪其中一条请求，叫它 **D**。D 已经开始回答时，另一条请求 **N** 带着很长的提示词加入。恰好从这时起，D 停顿了。最先想到的解释是：服务忙着处理 N，让 D 等久了。

这件事怎样发生？模型把文本拆成 **token（词元）**来处理，一个 token 不一定对应一个汉字。处理提示词的计算叫 **prefill**；利用已经算过的历史继续生成回答，叫 **decode**。此时，D 在 decode，N 刚要做 prefill。

服务可以把它们安排进同一步计算，这一组请求叫一个**批次**。图中每个小格代表一个待计算的位置：D 只需要继续一个位置，N 却带来一整排提示词位置。它们被放进同一批后，这一步要同时完成两部分工作。如果这一步变慢，D 也要等它完成，才能拿到新的结果。

```

D 自己的问题虽然没变，同批要做的工作却变了。服务每一步都会重新选择请求；N 的长提示词处理完后，这部分额外工作也就结束了，所以还要比较 N 加入前后的表现。

这是一个合理的解释，接下来要查记录来验证。设备早已算完、文本堵在返回途中，或者 D 当时没有被安排计算，也都能造成停顿。区分这些情况，才能知道该改哪里。

## 这次到底停了多久

先记下 D 在什么时候收到新内容。为了方便演算，下面假设能观察到每个输出 token 的到达时间；**本页所有毫秒数都是教学示意，不是设备实测。**

D 在 0 ms 发出请求，五个输出 token 依次在 **300、350、410、650、700 ms** 到达。前两个间隔分别是 50 ms 和 60 ms，第三个间隔却拉长到 240 ms。我们要解释的，就是 **410–650 ms 之间发生了什么**。

这些等待有各自的指标名称。**TTFT**（Time to First Token，首字等待）记录发出请求后，等多久收到第一个 token；**ITL**（Inter-Token Latency，相邻词间隔）记录相邻两个输出 token 相隔多久。把首个到末个 token 之间的时间平均分给后续 token，就得到这里使用的请求级 **TPOT**（Time Per Output Token，单输出词平均耗时）：

$$\text{TPOT} = \frac{t_{\text{last}} - t_{\text{first}}}{N_{\text{out}} - 1} = \frac{700 - 300}{5 - 1} = 100\text{ ms}$$

| 指标（D 的教学示意） | 算式 | 数值结果 |
| --- | --- | --- |
| 首个 token 等待（TTFT） | $300 - 0$ | **300 ms** |
| 相邻 token 间隔（ITL 序列） | $350 - 300,\; 410 - 350,\; 650 - 410,\; 700 - 650$ | **50、60、240、50 ms** |
| 请求级平均输出间隔（TPOT） | $(700 - 300) \div (5 - 1)$ | **100 ms** |
| 本次要调查的长停顿 | $650 - 410$ | **240 ms** |

只看“平均每 100 ms 收到一个 token”，很难知道第三个 token 后面曾停了 240 ms。保留每次到达时间，我们才能把这次停顿与服务里的计算对应起来。TTFT 也要留下：后面若用一种办法改善输出间隔，还要检查它会不会让第一个 token 等得更久。

## 这 240 ms，服务在做什么

如果要比较多次压测，指标的统一口径、分位数、失败请求和冷暖状态见[推理测量](inference-benchmarking.md)；本页继续沿 D 的这一次停顿取证。

客户端记录只告诉我们“没收到内容”。要知道原因，先找出这段停顿期间服务处理了哪些批次，看 D 有没有被安排进去。找到 D 所在的批次后，再追它何时算完、结果何时返回。

先查调度记录。**Scheduler（调度器）**决定每一步安排哪些请求、各自处理多少 token。如果 D 没有进入这一批，就要查它为什么没被安排；如果进入了，就继续看这一批何时开始、何时结束。

排好批次后，**ModelRunner** 负责整理输入、组织模型执行，**worker** 是管理设备执行的进程。设备算完，还要更新请求状态，把 token 转成文本并发送，客户端才会看到新内容。下图把这些环节放回[一条请求的七站](one-request.md#一条请求要走过七站)；具体函数之间的关系见[请求调用链](request-call-chain.md)。图里的“抢占”指缓存不足时先暂停一条请求、让出缓存，之后再恢复或重算。

```

继续这个示意例子，假设客户端和设备记录已换算到同一时间基准。调度记录证实，**D 和 N 确实在同一批中**；设备记录又显示，这一批从 **430 ms 算到 620 ms**。D 在 410 ms 收到上一次输出，在 650 ms 收到下一次输出。中间这段等待，大部分与这一批的执行时间重合。

把关联记录展开，就能看出每份证据补上了什么。下面的时刻仍是教学假设；N 在 400 ms 到达，带来 1200 个输入 token。先采用普通逐 token 生成，暂不引入后文 GLM 的候选验证。

| 记录 | 观察到什么 | 此时能判断什么 |
| --- | --- | --- |
| 请求与调度 | N 在 400 ms 到达；下一批包含 D 的 1 个位置和 N 的 1200 个位置 | D 已获调度，这一段不是一直没轮到 D |
| 设备执行 | 相邻纯 decode 步约 20 ms；混合步从 430 到 620 ms | 停顿中出现了明显更长的一步 |
| 返回 | D 在 650 ms 收到这一批的输出 | 执行结束到收到输出还有 30 ms；不能把全部 240 ms 都算成模型计算 |

现在可以提出一个更具体的解释：**N 的输入集中在同一步，使 D 这次必须等待的一步变长了。** 这些记录把方向缩小到了混合步，但还没有证明它为何变长，也没证明分块一定值得做。接下来才用实验检验。

换一份记录，分析方向也会改变。假如这一批在 **450 ms 就算完了**，D 却到 650 ms 才收到内容，那么主要等待出现在设备执行之后。此时应该继续追结果处理、代理是否缓冲了文本，以及客户端有没有及时读取，而不是先去优化模型计算。

## 怎样验证是长提示词拖慢了回答

现在假设我们看到的是前一种情况：D 和 N 同批，计算这一批也确实花了较长时间。一个可以检验的办法是，**每一步少处理一些 N 的提示词，看 D 能不能更快拿到后续结果。**

这就是 **chunked prefill** 要解决的问题：当提示词装不下当前一步的计算预算时，先处理其中一段，其余留到后续步骤。已经算好的历史状态会保留，下一段从断开的地方继续。这样，仍被安排在同批的 D 有机会随着较短的计算步骤继续生成；N 则要等自己的提示词全部处理完，才有第一个输出 token。

这里的“预算”限制的是每步处理的 token 位置数，可以理解为这一步允许放进多少个待计算的输入。它不直接规定执行时间。打开 chunked prefill 后，一条提示词如果仍能整个装进预算，就不会被切开；实验要确认 N 实际分成了几步。分块的计算过程和参数限制见 [chunked prefill](chunked-prefill.md)。

### 同一组请求，比较两种设置

把上述配置记为 **A**：chunked prefill 已开启，但预算仍容得下 N 的全部输入。**B** 只缩小每步 token 预算，使 N 实际分成三段，每段 400 个位置。这里的 400 是 N 获得的份额；同批 D 的位置也要占预算，不能据此把总预算填成 400。现场参数还须满足模型和版本约束。

A、B 使用相同的模型、版本、输入、采样设置和请求到达安排，也保持相同的分流方式与预热条件。启动后检查实际生效的配置，再查 N 每一步分到了多少输入。这样比较的是预算变化带来的影响。

下面是这组对照的**示意结果**。A、B 中 D 都生成五个 token；N 的输入和目标输出不变，表中只展示它到首个输出为止的阶段。D 前三个 token 的到达时刻相同。

| 观察项 | A：N 一次处理 | B：N 分三段处理 |
| --- | --- | --- |
| N 的输入份额 | 一步 1200 | 三步各 400 |
| 这段设备时间线 | 430–620：D 与 N；随后一小步完成 D | 430–500：D 与 N；510–580：D 与 N；590–660：只剩 N |
| D 五个输出的到达时刻 | 300、350、410、650、700 ms | 300、350、410、530、610 ms |
| N 首个输出到达时刻 | 650 ms | 690 ms |

D 在 B 的第二个混合步后已经生成完，所以第三步只有 N。每个混合步只处理较短的一段，D 有机会在段间交回结果；N 则必须等三段都处理完。

```wiki-diagram

```

图中条形是设备工作，圆点是客户端收到输出，两者之间还隔着结果处理与传输。A 中 D 在 410 ms 收到一个输出后，一直等到 650 ms；B 把下一次到达提前到 530 ms。N 的首字则从 650 ms 推迟到 690 ms。设 $\Delta \text{ITL}_{\max}$ 与 $\Delta \text{TTFT}_N$ 分别表示 D 的最长输出间隔缩减量与 N 的首字等待增量：

$$\Delta \text{ITL}_{\max} = 240 - \max(50, 60, 120, 80) = 120\text{ ms}, \qquad \Delta \text{TTFT}_N = (690 - 400) - (650 - 400) = 40\text{ ms}$$

| 分块前后等待变化（示意） | 算式 | 数值结果 |
| --- | --- | --- |
| B 中 D 最长输出间隔 | $\max(50, 60, 120, 80)$ | **120 ms** |
| D 的最长间隔减少量 | $240 - 120$ | **减少 120 ms** |
| A 中 N 的首字等待（TTFT） | $650 - 400$ | **250 ms** |
| B 中 N 的首字等待（TTFT） | $690 - 400$ | **290 ms** |
| N 多等的首字时间 | $290 - 250$ | **增加 40 ms** |

三项证据连上了：N 每步处理的内容变少，D 所在步变短，D 的长停顿也缩短。这支持采用 B 缓解**这类负载下**的中途停顿。它没有说明“输入减到三分之一，任何设备就会快三倍”：算子利用率、主机准备次数和通信路径都会随之改变，[性能分析](inference-performance-analysis.md)会接着拆解这笔成本。

实际记录不符合这张表时，判断也要随之改变：

| 实验中看到什么 | 接下来怎样判断 |
| --- | --- |
| 三件事都发生了 | 支持“减少每步 prefill 工作量能缓解这类停顿”；继续检查新请求和整机吞吐的代价 |
| N 分块了，设备每步也更快，D 仍然卡住 | 先看 D 是否持续被安排计算、批次之间是否有空档；若结果早已产生，再查处理和发送 |
| 改了预算，N 仍然整段计算 | 先查配置是否生效、调度条件是否满足；这次实验还没有检验到分块的影响 |

一次结果容易受缓存、预热和其他负载影响。按预先约定的次数交错运行 A、B，每轮都记录缓存命中、预热情况和样本数。如果各轮差别很大，先找出波动的来源，再讨论改善幅度。

### D 不停了，是否就算优化成功

还要看 N 和其他请求付出了什么代价。N 的提示词分成更多步骤以后，首个 token 往往更晚出现；调度和输入准备要多做几次，需要访问前面各段的注意力计算还会重复读取那些历史数据。每步工作变少，单步硬件利用率却未必更高。

**吞吐**衡量一段时间内服务完成的总工作量，例如每秒输出多少 token。它与单个用户的等待不同：同一步多处理一些请求，整机总产出会更高，单条请求却要等得更久。因此，实验开始前就要定目标，例如“减少回答中途的长停顿，同时让新请求的首字等待保持在可接受范围”。

在这个例子里，假如约定一份 **SLO（服务等级目标）**：“首字不超过 350 ms，单次输出间隔不超过 150 ms”，D 从不达标变成达标，N 的首字也仍在限制内，B 值得进入更大负载的验证。若业务要求 N 在 270 ms 内出首字，B 就违反了目标：不能只拿 D 的改善宣布成功。

**这次实验的结论是有条件地选择 B，而不是分块越小越好。** 两条请求还不能给出整机容量和长尾保证；下一篇[推理测量](inference-benchmarking.md#吞吐提高了多少要先说清数了什么)会用 **goodput（达标请求吞吐，即每秒成功且满足全部 SLO 的请求数）**继续对 A、B 做一组请求的验收。

判断 A、B 时，至少保留下面几类结果。长输入和短输入分别统计，才能看出改善落在谁身上、代价又由谁承担。

表中的“有效输入数”只数真实要处理的位置，“实际执行尺寸”还会包含为对齐图档位而额外补入的空位。执行图模式需要匹配预先捕获好的计算形状，就会把输入补大；因此同样的有效输入数不一定对应同样的执行量。补齐的具体过程复用[多请求中的图尺寸示例](concurrent-requests.md#先补到自己这组的图尺寸)。

| 要判断的问题 | A、B 都要留下的数据 |
| --- | --- |
| 执行是否真的改变了 | 生效配置、N 的分块情况、每步有效输入数与实际执行尺寸、使用的执行方式 |
| 用户是否等得更少 | TTFT、ITL 或有效文本消息间隔、请求级 TPOT，以及样本数和统计方法 |
| 服务能否承接原来的工作量 | 同一统计时段内的成功请求数、输出 token 数、失败数、未完成数和队列积压 |
| 结果和资源有没有退化 | 实际输出长度、任务正确性、各卡内存、历史缓存使用量和抢占次数 |

平均值之外还可以看 **P95**，即按约定算法计算的第 95 百分位，用来观察较慢的那部分请求。它需要足够的样本；几条请求不足以证明大多数负载下的长尾表现。失败和未完成的请求也要计入报告，否则排除慢请求、减少实际生成量造成的数字改善，就会被误当成优化收益。

输出正确性要按任务检查。如果还要求 A、B 逐 token 完全一致，就需要另外约定随机采样、随机种子及执行确定性等条件，相关机制见[采样](sampling.md)和[批次一致性](batch-invariance.md)。

## 如果记录不符合这个例子，该从哪里查

前面走完的是“长输入加入同批”这一条分析路径。现场查到的记录不同，接下来的检查也应随之改变。比如，D 没有被安排执行时，就要先找调度没选它的原因。

其中一种原因是 **KV cache** 不够用。这是为后续生成保留历史计算结果或状态的缓存。请求开始或继续计算时需要获得相应空间；如果调度器因此让请求等待或抢占了它的缓存，就应核对相应事件。可以从[块分配](vllm-kv-block-allocation.md)和[多请求中的抢占](concurrent-requests.md)继续追。

下面这张表把本例和其他常见情况放在一起。每行都从已经看到的现象出发，给出下一项检查。

| 已经看到的现象 | 优先检查的原因 | 下一步查什么，结果说明什么 |
| --- | --- | --- |
| N 很晚才开始计算，首个 token 也很晚 | 请求来得太快，或者某个执行组接得太多 | 保留请求长度、降低到达速率；若排队缩短而单步时间基本不变，支持排队解释。若只在一个组积压，查[请求路由](dp-request-routing.md) |
| D 和 N 同批，停顿与长 prefill 重合 | 这一步要处理太多输入 | 比较相邻的纯 decode 批次，再做前面的分块实验；仅凭时间重合，还不足以确认原因 |
| D 没被安排执行，同时发生缓存分配失败或抢占 | 历史缓存空间 | 对照同一请求的分配、回收和抢占记录，查看相同负载下可用块数怎样变化 |
| 设备两次执行之间空了很久，CPU 还在准备或提交输入 | 主机还没把下一批工作交给设备 | 把主机和设备的记录按批次对应起来，找出迟交的环节，再查[输入准备](prepare-inputs-flow.md)、[CPU 绑定](cpu-binding.md)或[异步调度](async-scheduling.md) |
| 多卡通信持续很久 | 某张卡还没赶上，或者数据传输本身慢 | 比较同一次通信在各卡上的执行记录；先看前面的计算是否完成，再查数据量、链路与通信实现 |
| 服务已产生结果，客户端还没收到 | 输出处理、传输缓冲或客户端读取 | 比较服务端发送与客户端接收的时间，沿[流式输出](streaming-output.md)查出延迟发生在哪一段 |

通信尤其容易误判。如果另一张卡还没完成前面的计算，先到的卡就要等它，这段时间也会被算进通信耗时。各张卡的 CPU 几乎同时提交任务，也不代表设备已经执行到同一个地方：任务还需要等待前面的工作完成。要区分“有卡迟到”和“传输慢”，需要设备侧的执行记录；缺少这份记录时，两种解释都要保留。

设备利用率同样只能提示忙闲。它不能独自说明时间花在计算、读取显存还是通信上。看到耗时最长的算子以后，还要检查 D 的结果是否真的在等它完成。

可以用一个变式检验自己是否读懂：**B 的设备已经在 500 ms 算完，D 却仍在 650 ms 才收到第四个 token，你还会继续缩小预算吗？** 此时计算已经提前结束，新的证据指向执行之后的等待。先找结果何时被处理、发送、接收；只有确认 D 的下一次输出仍在等待某段长计算完成，进一步缩小预算才有依据。

## 现场怎样拿到这些记录

前面的分支给出方向；现场已经定位到排队、长步、主机空隙、缓存、通信或返回时，可以接着用[性能排障](inference-performance-troubleshooting.md)选择实验。启动、输出异常或长运行问题从[通用入口](inference-troubleshooting.md)分流。

第一次排查的目标，是把停顿缩小到**没轮到计算、计算这一批很久，或算完后迟迟没送到**中的一段。先从已有请求日志和监控里选定一条 D、一次明确停顿，保留当时的输入输出长度和实际负载；这些是比较条件，不需要逐层转储模型。

接着只补能区分当前两个解释的记录。例如，已知 D 进入了某一批，却不知道是计算慢还是返回慢，就先补这一批的设备完成时刻。若已有可靠记录证明设备早已完成，下一步只追结果处理、发送与客户端接收。查到哪个交接解释不了等待，再往那里补一项，而不是默认从头采到尾。

**trace** 是按时间记录的一串事件，例如某批开始执行、某个结果发送；**profiler** 是采集执行时间和算子活动的工具。它们帮助我们回答“那段时间正在做什么”，但还需要知道事件属于谁。

实际开始/停止采集、找到设备轨迹和服务批次表的方法统一见[性能分析的采集入口](inference-performance-analysis.md#怎么开)，包括 PD 两端分别采集的要求。拿到产物后，再按下面的请求、步骤与 rank 把事件接起来。

### 用请求和批次把三处记录接起来

客户端与服务之间，用 **request_id（请求编号）**找到同一条 D；调度与执行之间，用 **step（调度或执行步骤编号）**等关联信息找到同一批；多卡之间，用 **rank（并行进程编号，常对应一张卡）**分清是谁在执行。各层的编号若不直接相同，就需要保存它们之间的对应关系。

| 现在还分不清什么 | 先补哪份记录 | 看到结果后怎样继续 |
| --- | --- | --- |
| 停顿发生在哪一次输出 | 客户端的请求编号、发送与各段接收时刻、状态码与错误 | 圈定停顿窗口；只有流式消息时先按消息计时，方法见下一小节 |
| D 当时有没有轮到计算 | 调度记录中 D 所在的执行组、等待时长、选入的步骤 | 未选入就查等待原因；选入后才把该步与执行记录相连 |
| 这一批慢，还是结果返回慢 | 相关批次的设备开始、完成时刻，以及已知的客户端接收时刻 | 设备区间长就查本批工作；设备已完成就查结果处理、发送和接收 |
| 确定执行期间有空档，但不知卡在哪里 | 同一步的主机准备、提交、设备活动及依赖 | 主机迟交就查准备；已经提交仍在等就查前序工作或通信参与者 |

只有命中具体分支，才增加详细字段：**调度等缓存**时补分配、回收、抢占与可用块；**已定位到长批次**时补实际预算、每请求位置数、有效输入数、补齐后的执行尺寸和执行路径；**多卡等待**时再按 rank 对齐各参与者。客户端输入与实际输出 token 数继续用于保证工作量可比。这样，字段各自服务于一个判断，不是一张必须一次填满的采集清单。

把前面的 D/N 记录整理后，可以用 `request_id`、`step`、`rank` 三个主键把客户端 SSE、调度交接与 NPU `trace_view.json` 对齐到同一根水平时间轴上。图中 `430–620 ms` 是已确认的设备混合步区间，而 `620–650 ms` 在补采发送/代理/读取时刻前保持为“待细分区间”，避免把尚未拆分的返回等待笼统归给单个模块：

下面是用同一份 D/N 数据整理出的关联表。**这是人工整理的示意格式，不是 vLLM 默认日志；42 只是本例给混合步起的编号。** 此处先看一个 rank，其他参与者也要以相同执行步关联起来。

读这份表时，先用 D 找到调度步 42，再用 42 找到设备区间，而不是在所有算子里挑一个最长的。这样才知道 430–620 ms 的执行确实与 D 有关。反过来，如果慢算子属于另一步，它即使与停顿同时发生，也还不能解释 D 为什么在等。

默认日志未必包含这些关联字段；缺了哪一段，就先在那一段补受控记录。进程和函数位置沿[请求调用链](request-call-chain.md)寻找。这里的返回记录只证实设备结束后到客户端接收还有 30 ms；若要继续拆这 30 ms，还必须补服务发送、代理转发与客户端读取的时刻。

如果手里只有默认日志，从本页[最小取证步骤](#怎么开)开始：先保留客户端原始片段，再检查请求与批次的对应，最后按缺口采一个短窗口。表里的每一列不必一次拿齐，但不能把尚未采到的时间补成猜测。

比较时间前也要检查时钟。同一进程内用不会随系统校时跳变的单调计时计算耗时；跨机器或客户端与服务器之间，先核对时钟偏移和采集工具的时间基准。异步执行允许 CPU 在设备计算上一批时准备下一批。这时，两条记录的时间即使很接近，处理的也不是同一批请求。

### 只有流式消息，没有逐 token 时间怎么办

真实接口常用 **SSE**（Server-Sent Events，服务端逐段推送的流式消息）把输出发给客户端。有的消息带多个 token，有的只带角色等信息，没有新文本。此时可以统计“包含有效文本的消息之间隔了多久”，并注明这是消息间隔。

使用一次验证多个候选的生成方式时，模型一步还能产出多个 token。因此，设备执行一步的耗时、相邻 token 的间隔、相邻文本消息的间隔，测的是不同过程。保留实际能采集到的量，才能正确比较前后两次实验；具体返回过程见[流式输出](streaming-output.md)。

### 怎样让别人重现同一个问题

除了时间，还要保存产生这些记录的条件：模型和权重版本、分词器、聊天模板、框架与插件的提交或镜像、设备、并行方式、完整启动参数和实际配置；输入长度、输出长度、采样设置、预热状态和缓存命中也都影响结果。

采集期间的初始化、抢占和错误都要标出。**图捕获**，即把执行流程记录下来供后续重放，也要单独记录，以便识别额外的准备开销。

请求怎样到达同样重要。如果十个客户端都等上一条完成才发下一条，服务变慢后，发新请求的速度也会下降。如果客户端按预定时刻持续发请求，服务跟不上时，队列会继续增长。两种实验都可以做，但 A、B 必须采用相同方式，并记录实际到达情况。

现场记录可以从下面的提纲开始。暂时拿不到的数据写“未采集”，这样下一位排查者也能知道结论还缺什么。

```text
问题与目标：哪类请求在何时变慢，希望改善什么，哪些指标必须满足？
环境与负载：模型/权重/分词器/模板、框架版本、设备、实际配置、到达安排。
这次停顿：请求编号、执行组、起止时间；测到的是 token 还是消息间隔？
已有记录：客户端、调度、设备、结果返回分别发生了什么？
怀疑的原因：哪些记录支持它，看到什么结果就需要换一个解释？
对照 A/B：主动改了哪一项，实际执行怎样变化，有哪些伴随变化？
测量结果：样本数、等待、吞吐、失败/未完成、内存和输出正确性。
下一步：现在能确认什么，还需要在哪里补记录？
```

## 一组长输入怎样拖长另一组的计算步

前面的 D/N 1200 token 是独立于具体模型的通用教学示意；下面切换至本站例外 B 绑定的 [GLM-5.3-Flash 双机部署](glm-5-3-flash-two-node.md#部署前提)（2×A2×8，TP8/DP2/EP16，沿用原审定镜像口径），看看一组长提示词怎样跨组拉长另一组的计算步。

两台机器各有一个 **DP 执行组**，分别接收和调度请求；模型的 **MoE（混合专家）**部分会为每个输入选择要使用的专家网络。**EP** 把这些专家分布到 16 张卡上，两台机器合起来才持有完整的专家集合。因此，两组虽然各自调度，执行专家计算时仍要跨机协作。

沿用[多请求页的场景 M](concurrent-requests.md#示例场景-m-与变体-m)：DP0 有 12 条正在生成的请求 D₁…D₁₂，N 带着 6000 个提示词 token 加入；DP1 有 7 条正在生成的请求。前面跟踪的 D 对应这里的 D₁。场景 M 给出本例的跨组路由前提与调度数字，前面用到的毫秒数仍只是教学示意。

### N 为什么进入已经更忙的 DP0

这是复现实验前要确认的第一件事。按场景 M 的负载，默认路由本来倾向 DP1。请求直接指定 DP0，或者前端使用滞后的负载信息，都能解释 N 为什么到了 DP0。实验要记录实际路由条件；详细选择过程见[DP 请求路由](dp-request-routing.md)。

### 只多一条请求，为什么这一步会大很多

因为调度器安排的是本步要计算多少输入，而不仅是请求条数。这个部署还使用 **MTP**：模型通过额外预测层先猜后续 token，再验证这些候选。每条 decode 请求通常安排 1 个已确定的 token 和 3 个候选 token（共 4 个位置）。

于是场景 M 第 2 步里，DP0 混合步的有效输入数为 $12 \times 4 + 6000 = \mathbf{6048}$，另一组 DP1 为 $7 \times 4 = \mathbf{28}$。13 条请求并不意味着只算 13 个输入。完整计算仍见[多请求调度](concurrent-requests.md#第-2-站-调度一步-8192-个-token-怎样分给-13-条请求)。

这个场景已经启用 chunked prefill，但 N 的 6000 个 token 能装进当前 **8192** 预算，所以仍然一次处理。这也解释了为什么排查时要看“这次实际切开了吗”，而不能只看功能开关。把两组放上同一根 `0 → 6048` 宽度尺，就能直观看出 DP0 如何把仅有 28 个真实 token 的 DP1 一并拉宽、压回 eager 并推过 **128** 的通信门槛：

### 把预算调小后，除了输入数量还变了什么

首先要分三步核对执行方式（**graph mode** 先捕获后重放，**eager** 按当前步骤逐算子下发）：第一看**模式资格**，即本批请求构成是否满足整图或分段图条件；第二看**尺寸补齐**，各组先向上补到本组图档位，再跨 DP 对齐最大宽度，因此有效输入数不等于算子实际处理的宽度；第三看**设备记录**，结合 ModelRunner 日志与底层运行时轨迹确认实际命中的选图与流执行记录（主机下发、选图与通信证据见[昇腾运行时与调优](ascend-runtime-and-tuning.md)）。

其次要看具体的 MoE 专家分发／合并路径。在本例固定部署中，单步超过 **128** 个 token 的容量门槛后，专家分发与合并会从面向小批的 **MC2**（设备侧融合的专家 `Dispatch` / `Combine` 分发合并路径）切到 **AllGather**（先跨卡汇总输入分片、算完专家再归并）路径；门槛出处见[一条请求](one-request.md#moe-通信走-mc2-还是-allgather)，补齐与跨组协作过程见[多请求页](concurrent-requests.md)。DP1 即使只有 28 个真实输入，也要对齐参与这次跨机协作；它出现等待时，应先查另一组的进度，再判断是否有网络问题。

因此，A、B 虽然只主动改变每步预算，但批次变小后，一旦跨过图选择或通信方案的门槛，执行路径也会跟着改变。如果 D₁ 的停顿缩短了，可以得出“这项配置对这类负载有效”的结论。要进一步确认收益来自哪一段计算或通信，还需要比较对应的执行记录。

## 常见误解

- **“并发一高就慢，肯定要加卡。”** 先区分排队、单步变长、主机供给、通信和返回等待。增加卡数还会改变并行和通信，并非每一段都会加速。
- **“打开分块就不会有长步。”** 场景 M 里的长输入仍装得下预算。要看这一批分了多少位置，不能只看开关。
- **“调参后快了，所以证明了唯一根因。”** 调整预算会牵动图选择、通信路径和缓存行为。配置层面的改善与机制层面的归因，需要不同证据。
- **“临时关闭图、打开同步和转储后测一次，就能比较性能。”** 这些动作改变执行路径和开销，适合定位问题；收益验收应回到正常运行配置，并单独保留调试实验。
- **“知识库能直接从‘卡顿’给出根因。”** 本例提供候选、证据位置和区分实验；缺现场记录时，可用的答案是下一步采什么、如何判别。

只有默认日志时，按下面的顺序做一轮最小取证。先在隔离复现环境确认问题，再开启会改变时序的细粒度采集。

1. **先留住一次真实停顿。** 在发起请求的程序中保存请求标识、原始 SSE 片段、每次读取的单调时刻，以及状态码、结束原因。分别标出有文本的片段和角色、心跳等无文本消息；不能把一个含多个 token 的片段拆成虚构的逐 token 时刻。已有汇总监控用于找异常时段，不能单独证明 D 属于哪一步。
2. **检查关联是否齐全，再补缺的边界。** 下面是固定源码中的取证位置；字段存在于内部对象，不等于默认日志已经打印。需要补日志时，给调度输出附一个仅用于诊断的关联号，并让它跟随对应执行任务和结果；不能用两条 CPU 日志的时间接近来猜同一批。[C2][C8][C9][C10]

| 固定边界 | 读取或关联什么 | 现成记录的边界 |
| --- | --- | --- |
| `Scheduler.schedule` 返回的 `SchedulerOutput` | `num_scheduled_tokens` 给出请求编号到本步位置数的映射；保留执行组和自加的批次关联号 | 是内部字段；`scheduled_spec_decode_tokens` 中的候选不等于已交付的新输出 |
| `EngineCore` 的批次队列 | 调度输出与执行 future 的配对；取回结果时保留同一个关联号 | future 表示尚待取得的执行结果；提交时刻不能当作设备完成时刻 |
| Ascend `ModelRunner` 准备执行 | 关联 rank、有效输入数、补齐后尺寸和实际图模式 | 固定版有 `Running batch with cudagraph_mode` 的 DEBUG 日志，能辅助核对执行形状；它不给完整请求映射或设备完成时刻 |
| `OutputProcessor` 接到引擎结果 | `engine_core_output.request_id`、`new_token_ids` 与输出队列交接；继续关联前端发送和客户端接收 | 解码、入队、生成 SSE、客户端收到是不同事件；入队不能写成客户端收到 |

3. **设备执行仍有疑点时，才采短窗口。** 若已有证据把等待定位在排队或返回，沿那一段继续查；需要补设备执行证据时，才用下面的采集入口。服务函数级路径用服务 profiler，设备算子时间用 Ascend PyTorch Profiler；两者配置不同。在 `v0.30.0` 主基线及当前官方指南中，Torch 路径在启动时传入 `--profiler-config '{"profiler": "torch", "torch_profiler_dir": "./prof_out"}'`（以隔离环境的 `vllm serve Qwen/Qwen3-8B` 为例，同时须设 `VLLM_SERVER_DEV_MODE=1` 开放管理端点），再通过下面的 HTTP 端点控制采集窗口。先在现场安装版的帮助与同版文档中确认支持，不能把这套入口直接当作固定 GLM 镜像的已验证能力。[S7]

```bash
# 仅供已按对应版本指南启用 profiler 的隔离服务使用；替换为实际地址。
curl -X POST http://127.0.0.1:8000/start_profile
# 用保存的输入和到达安排复现目标停顿，覆盖它前后相邻的几步。
curl -X POST http://127.0.0.1:8000/stop_profile
```

当前指南说明，未配置 profiler 时这些端点返回 404；这只能说明采集入口不可用，不能说明推理路径有故障。按同版指南解析导出文件，在 `trace_view.json` 看主机、设备活动和依赖，在 `kernel_details.csv` 对照算子信息；先确认目标 rank 与事件确实被采到。另一套 MS Service Profiler 的 `request.csv`、`batch.csv`、`kvcache.csv` 可补服务记录，但符号配置须匹配安装版本，不能把两套工具的开关混用。[S7]

4. **把记录接回 D，再作判断。** 从请求编号找到调度批次，再找相关设备步骤和输出片段。跨进程、跨设备须核对采集时钟；缺少对应关系或设备事件时，就保留该段为“未采集”。确认等待所在后才选择 A/B 变量。结束采集并恢复正常日志配置后，按原负载复测效果，不能拿 profiler 模式的时间直接当优化收益。

### 会报什么错

本例的输出停顿可以发生在全部请求最终成功的情况下，因此没有专属报错字符串。若现场同时出现超时、内存不足或 worker 退出，保留第一处原始异常、请求编号和各 rank 的上下文，先沿[调用链的报错定位](request-call-chain.md#会报什么错)找到失败阶段；失败请求仍计入基准结果，不能删掉以后只比较成功请求的速度。

### 开销和什么时候别开

profiler、细粒度日志和数值转储都会增加工作或改变时序。先用正常模式得到基准，再单独采集解释问题的 trace，最后关闭调试采集复测。trace 用来解释路径；它自身的耗时不直接替代无采集时的服务指标。

如果主要等待发生在排队或客户端返回，优先采那一段；全程采集每个算子通常只会增加数据量。需要比较输出时，继续查[采样](sampling.md)、[批次一致性](batch-invariance.md)和[流式输出](streaming-output.md)。

### 版本差异

按知识库四版本正式钉点核对：`v0.23.0`（`2c59ff10` / `0fc695fc`）、`v0.26.0rc`（`2ed6cbba` / `568afb3a`）、`v0.30.0` 主基线（`c09d3e20` / `ced6857a`）与 `main`（`8d6180e2` / `ba15685a`）；**本文 D/N 240 ms 与场景 M 走读沿用例外 B 专用镜像钉点 `db701c1f`（配套 `vllm@0fc695fc`），与四版社区分支分别核对。**

**`v0.30.0` 及 `main` 的时间线分析须区分客户端计时口径与 Runner 入口变化。** 配套 ChatCompletion/audio 压测由带非空 `choices` 的块推进计时，尾部仅含 `usage` 的块不推进结束时间；`choices` 块的 `content` 仍可为空，因此该统计也不等于“有效文本消息间隔”（`endpoint_request_func.py`）。Worker 侧 profiler 须显式启用、首次 `start` 惰性创建对象并沿用首次 `trace_name`，跨 rank 的请求与批次关联仍须保留外部记录；只有消息事件时，应明确自己数的是上述 `choices` 块还是另行筛选的有效文本消息。
