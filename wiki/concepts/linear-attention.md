## 话越长，全注意力每一步越贵

先回忆一下[贯穿例子](one-request.md)那一页算过的账。模型每生成一个新 token，全注意力层都要做两件事：

- **回头翻一遍。** 新 token 要跟前面的每一个 token 都算一个分数——看自己跟那个 token 有多相关，再按分数把前面的信息取过来。前面有 100 个 token，就要算 100 个分数；前面有 1000 个，就要算 1000 个。
- **给自己留笔记。** 为了下一步不用把前面全部重算，每个 token 算出来的两份数据要存下来备查，这份存下来的东西全库叫「笔记」（正式名字是 [KV Cache](kv-cache.md)）。回答越长，笔记越多。

两件事都跟着话的长度走：话越长，每一步要翻的越多，要存的也越多。回答第 200 个 token 时，要回头看前面 236 个；如果回答写到 2000 个 token，每一步要看的就是两千多个。

全注意力具体怎么打分、怎么取信息，在[注意力](attention-qkv.md)那一页。这里只需要记住一件事：**全注意力每一步都要把前面全部翻一遍，而且前面的全部都得存着。**

那么，有没有不用回头翻全部的办法？

## 线性注意力：不留笔记，只记一份小抄

线性注意力的办法是：**不给每个 token 留笔记，手里只保一份固定大小的「状态」**——可以把它想成一张小抄。

它的工作方式是这样的：

1. 每看完一个 token，就把这个 token 带来的信息揉进小抄里，改写小抄上的内容。
2. 揉完，这个 token 本身就扔了，不单独存。
3. 下一个新 token 来了，不再跟前面每个 token 逐个算分数，只跟这张小抄打交道：从小抄里取它需要的东西，再把自己也揉进去。

关键在于小抄的大小是**固定的**。不管前面已经有 10 个 token 还是 10000 个，小抄都是那么大。所以每一步要做的事也一样多——话再长，每一步的开销都不变；显存里要为它留的地方也不变。

## 小抄大小是死的，所以不全换

省是真省，但代价也来自同一个地方：**小抄的大小是死的。**

全注意力手里有前面每个 token 的原始笔记，想精确回看第 5 个 token 说了什么，翻出来就是。线性注意力手里只有一张揉过无数遍的小抄，新东西不断揉进来，装不下的细节就会被挤掉。离得远、又没有被反复强调过的信息，可能就记不牢了。

所以实际的模型往往不是整个换掉，而是**混着用**。贯穿例子里的模型就是这样：40 层里，每 4 层一组，前 3 层用线性注意力（省），第 4 层用全注意力（保底）。一共 30 层线性注意力、10 层全注意力——那 10 层全注意力负责需要精确回看的时候，把前面的原话翻出来。

这个混搭比例是模型出厂时就定好的，写在模型的配置里，是训练时就定下的结构，不是部署时可以随手调的开关。

## 名字里的「线性」，说的是开销怎么随长度长

「线性」这个名字说的是：**总开销随话的长度只按一次方长**——话长一倍，总开销也大约长一倍。

全注意力是按平方长的：话长一倍，每一步要翻的多一倍，要走的步数也多一倍，两者相乘，总开销大约变成四倍。线性注意力每一步的开销固定，步数多一倍，总开销就只多一倍。

还会碰到几个具体的名字，比如 Mamba、GDN。它们都是线性注意力这个思路下的具体结构，各自把小抄怎么揉、怎么取做得不一样。本页讲的是共同的思路，具体结构不展开；以后讲到某一种具体实现时，才会直接用它的名字。

## 落到这个例子：30 层的小抄，跟回答多长无关

回到贯穿例子，Qwen3.6-35B-A3B 跑在两颗 NPU 上，这次提问 37 个 token、回答 200 个 token。那 30 层线性注意力的小抄，[贯穿例子](one-request.md)那一页已经算过：

- 每层的状态约 1 MiB，30 层合起来约 **30.7 MiB**——这是一条请求在每颗 NPU 上占的。
- 这个数**跟回答 200 个 token 还是 2000 个 token 无关**，从这条请求一开始就是这么大，一直不变。
- 不过显存里实际占掉的比这更多：每层的状态要补齐到和一整块笔记一样大才好放，于是 30 层实际占掉约 **60.7 MiB**，其中差不多一半是补出来的空白。为什么要补齐、怎么补，在[贯穿例子](one-request.md)那一页。

对比一下同一次提问里那 10 层全注意力的笔记：237 个 token 一共才 2.3 MiB。这个例子里，占地方的大头反而是那份一开始就固定的小抄，而不是越答越多的笔记——话很短的时候就是这样；话越长，笔记越多，而小抄始终不变。
