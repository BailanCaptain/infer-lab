## 话越长，全注意力每一步越贵

先回忆一下[贯穿例子](one-request.md)那一页算过的账。模型每生成一个新 token，全注意力层都要做两件事：

- **回头翻一遍。** 新 token 要跟前面的每一个 token 都算一个分数——看自己跟那个 token 有多相关，再按分数把前面的信息取过来。前面有 100 个 token，就要算 100 个分数；前面有 1000 个，就要算 1000 个。
- **给自己留笔记。** 为了下一步不用把前面全部重算，每个 token 算出来的两份数据要存下来备查，这份存下来的东西全库叫「笔记」（正式名字是 [KV Cache](kv-cache.md)）。回答越长，笔记越多。

两件事都跟着话的长度走：话越长，每一步要翻的越多，要存的也越多。回答第 200 个 token 时，要回头看前面 236 个；如果回答写到 2000 个 token，每一步要看的就是两千多个。

全注意力具体怎么打分、怎么取信息，在[注意力](attention-qkv.md)那一页。这里只需要记住一件事：**全注意力每一步都要把前面全部翻一遍，而且前面的全部都得存着。**

那么，有没有不用回头翻全部的办法？

## 线性注意力：不留笔记，只记一份小抄

线性注意力的办法是：**不给每个 token 留笔记，手里只保一份固定大小的「状态」**——可以把它想成一张小抄。

它的工作方式是这样的：

1. 每看完一个 token，就把这个 token 带来的信息揉进小抄里，改写小抄上的内容。
2. 揉完，这个 token 本身就扔了，不单独存。
3. 下一个新 token 来了，不再跟前面每个 token 逐个算分数，只跟这张小抄打交道：从小抄里取它需要的东西，再把自己也揉进去。

关键在于小抄的大小是**固定的**。不管前面已经有 10 个 token 还是 10000 个，小抄都是那么大。对固定模型的一条序列，递推状态的形状不随长度增长；单 token 更新的算术量也不随历史长度增长。但实际耗时受实现影响，整个服务还可能保存前缀状态快照、临时缓冲和其他请求，不能据此说总显存永远不变。

## 小抄大小是死的，所以不全换

省是真省，但代价也来自同一个地方：**小抄的大小是死的。**

全注意力保留每个位置变换后的 K、V，可以按位置分别参与计算；K、V 不是原文副本，也不保证能精确复述第 5 个 token。线性注意力手里只有一张揉过无数遍的小抄，新东西不断揉进来，装不下的细节就会被挤掉。离得远、又没有被反复强调过的信息，可能就记不牢了。

所以实际的模型往往不是整个换掉，而是**混着用**。贯穿例子里的模型就是这样：40 层里，每 4 层一组，前 3 层用线性注意力（省），第 4 层用全注意力（保底）。一共 30 层线性注意力、10 层全注意力——全注意力层保留逐位置交互的通路；这不等于模型保证能找回前面的原话。

这个混搭比例是模型出厂时就定好的，写在模型的配置里，是训练时就定下的结构，不是部署时可以随手调的开关。

## 名字里的「线性」，说的是开销怎么随长度长

「线性」这个名字说的是：**总开销随话的长度只按一次方长**——话长一倍，总开销也大约长一倍。

全注意力是按平方长的：话长一倍，每一步要翻的多一倍，要走的步数也多一倍，两者相乘，总开销大约变成四倍。线性注意力每一步的开销固定，步数多一倍，总开销就只多一倍。

还会碰到几个具体的名字，比如 Mamba、GDN。GDN（Gated DeltaNet）是本例采用的结构；Mamba 属于选择性状态空间模型，不能当成线性注意力的同义词。它们都可以用递推状态处理序列，但状态更新公式不同。本页讲的是共同的思路，具体结构不展开；以后讲到某一种具体实现时，才会直接用它的名字。

## 落到这个例子：30 层的小抄，跟回答多长无关

回到贯穿例子，Qwen3.6-35B-A3B 跑在两颗 NPU 上，这次提问 37 个 token、回答 200 个 token。那 30 层线性注意力的小抄，[贯穿例子](one-request.md)那一页已经算过：

- 每层的状态约 1 MiB，30 层合起来约 **30.7 MiB**——这是 TP=2、SSM 状态为 float32 时，一条请求在每个 NPU 上的状态有效数据。
- 这个数**跟回答 200 个 token 还是 2000 个 token 无关**，从这条请求一开始就是这么大，一直不变。
- 不过显存里实际占掉的比这更多：每层的状态要补齐到和一整块笔记一样大才好放，于是 30 层实际占掉约 **60.7 MiB**，其中差不多一半是补出来的空白。为什么要补齐、怎么补，在[贯穿例子](one-request.md)那一页。

对比有效数据：按 237 个位置估算，那 10 层全注意力的 K、V 约 2.3 MiB，而递推状态有效数据约 30.7 MiB。前者还没计整块分配带来的空位，不能拿 2.3 MiB 直接和补齐后的 60.7 MiB 当作两边的实占比较。状态也不一定更小：短序列尤其如此。

## 小抄怎么存，去哪里看

这份状态在显存里具体怎么放，以及为什么这个模型的笔记块因此变成了 2048 个位置那么大，都在[贯穿例子](one-request.md)的下半和 [KV Cache](kv-cache.md) 那一组页里。本页只讲思路，不展开存法。

## 对照源码

### 开销和什么时候别开

本页的线性复杂度只讨论固定模型宽度下随序列长度变化的算术量。固定大小的递推状态，不代表整个引擎的总显存固定；前缀复用、状态快照、并发数和工作区仍需单独计入。

### 版本差异

本页代码核对范围是 vLLM v0.23.0（配套 Ascend releases/v0.23.0）。30.7 MiB 有效状态与 60.7 MiB 补齐占用只沿用[贯穿例子](one-request.md)的 TP=2、SSM float32 设定；其他 TP 或类型需重新计算。块大小、前缀缓存的跨版本差异以该页为准。

### 源码位置

- 配置的 `layer_types` 将 40 层排成 30 层线性注意力、10 层全注意力 [S1]。
- `linear_attention` 对应 `QwenGatedDeltaNetAttention` [C1]。框架沿用 mamba 相关缓存名称，并不意味着这里运行的模型就是 Mamba。
- Mamba 原论文明确使用选择性状态空间模型；它与 Gated DeltaNet 共享递推处理的直觉，不是同一个算法 [S2]。
