## 一行输入怎样用权重算出一行输出？

**矩阵乘把一行输入与权重的每一列分别逐项相乘、再求和，依次填出一行输出；权重是训练得到、推理时反复使用的数。** 矩阵就是按行列排成的数表。一行输入表示一个 token 位置：token 是分词得到、用编号表示的文本单位，经嵌入查表后才变成这行数。

这里位于[一条请求的 A4 逐层前向](one-request.md#第-4-站-逐层前向每张卡上的形状通信和字节)。主机 CPU 组织执行，NPU 是实际计算的设备；权重和输入张量在设备内存中参与运算。主机内存另记账。[平台接口](vllm-platform-interface.md)约定由后端提供设备实现，矩阵的数学含义保持不变。

图中亮起的输入行先与亮起的权重列配对，得到亮起的输出格；换一列权重，就填下一个输出格。**输入行不换、权重列逐列换，最后得到完整输出行。** 其余输入行沿相同规则计算，共用这片权重。

## 为什么要这样变换，代价是什么？

**矩阵乘让模型用学到的规则重新组合特征，既要做乘加，也要把参与计算的数搬到计算单元。** 例如 GLM 前 3 层的稠密前馈网络会把每个位置的表示从 4096 维扩到 12288 维，做非线性变换后再缩回去。前馈网络也叫 MLP 或 FFN，它对各位置分别处理；注意力负责从上下文中提取信息。**稠密**指每个 token 都经过同一组完整的前馈权重；后面的层改用 MoE（混合专家），每个 token 只走其中挑出的几个小前馈网络，见[下文](#moe嵌入和残差混合也按同一规则算吗)。向量在层间持续变化，到某个投影前的输入已不再是最初查表的数值。

**参数量、计算量、容量和访存量是四笔不同的账。** 参数量数的是训练得到多少个标量；配置项则控制服务行为，不属于模型权重。但有些配置会改变实际参与计算的权重：[量化](quantization.md)选项决定权重以什么格式和精度加载、参与乘法（本部署是 W8A8，下文详述）；[LoRA](lora.md) 这类适配器保留原权重，在旁边再挂一对小矩阵，把它们算出的增量加到输出上。继续训练或更新模型则是另外的操作，不属于这里的普通推理。下表把容易混用的量分开：

| 量 | 它回答什么 | 增加输入行数会怎样 |
|---|---|---|
| 参数量 | 这一片权重有多少个数 | 权重形状不变，个数不变 |
| 计算量 | 所有输出需要多少次乘加 | 随本轮行数增加 |
| 容量 | 权重、输入、输出各占多少空间 | 权重不变，输入和输出变大 |
| 访存量 | 这次执行实际读写多少字节 | 取决于分块、缓存和复用，需单独测量 |

单卡的矩阵乘只依赖本地输入与权重。权重太大或计算太多时，可以用 **TP（tensor parallel，张量并行）**把同一矩阵切给多张卡合算：GLM 的稠密 MLP 先按输出列切，门控（把升维得到的两路结果逐元素组合的非线性步骤，见[下文 SwiGLU](#gate-与-up-扩宽down-再缩回去)）在各卡本地完成，再由按输入行切的降维投影算部分和；末尾通过 **All-Reduce** 将各卡对应位置相加，让每卡获得完整结果。下一段计算需要合齐后的数值，因此要在这里等通信。

**稠密 MLP 每层归约一次；连同 attention（注意力）输出投影，一整个 decoder 层归约两次。** decoder 层就是依次处理注意力和前馈计算的模型层。单个矩阵乘不等于一次通信，两路升维投影之间也没有额外归约；成对切分和非线性前不能随意交换顺序的原因见 [TP 页](tensor-parallel.md#一张卡算不动一层时怎么办)。

## 输入行、权重列和输出元素怎样对应？

**输入宽度必须等于权重的行数，输出宽度由权重的列数决定。** 记输入 X 为 [T,H]，权重 W 为 [H,F]，则输出 Y = XW 为 [T,F]。T 是本轮参与这个投影的输入位置数，H 是输入宽度，F 是输出宽度。这里说的是数学形状，存储方向在页末对照源码。

输出第 i 行、第 j 列满足：

```text
Y[i,j] = X[i,0] × W[0,j] + … + X[i,H−1] × W[H−1,j]
```

这一格只使用第 i 行的 H 个数；同列输出的其他格使用其他输入行。因而这个投影保持 T 不变，改变每行的表示宽度，本身不会混合不同 token 的行。若线性层另有偏置，就是对每行输出加同一个偏置向量；下文 GLM 稠密前馈网络的三个投影均不带偏置。

W 含 HF 个参数；输出共有 TF 个元素，各需 H 次乘法和 H−1 次加法。通常把一次乘和一次加各记一个操作，近似写为 2THF；以浮点运算表示时称为 **FLOPs**。这个数描述算术规模，本部署的 8 位整数乘法不能直接当成设备执行了同样次数的浮点指令。

## 到 GLM 双机：一个 token 怎样走过前馈投影？

采用[官方双机前提](glm-5-3-flash-two-node.md#部署前提)：两台 Atlas 800 A2 各 8 张 NPU，机内 TP8 合算矩阵；两组分别承接请求，**路由专家**（MoE 层里可供路由网络挑选的全部专家，每层 288 个，不是某个 token 选中的那几个）跨全部 16 卡分布。

**W8A8** 指权重和参与乘法的激活都用 8 位整数（INT8）：权重离线存成 INT8，每个输出通道另配缩放系数；激活在乘法前按 token 动态量化成 INT8；乘完再用两组缩放系数换回 **BF16**（一种每个数占 2 字节的浮点格式）输出，层间表示和 All-Reduce 载荷都是 BF16。它按层生效：加载时逐层查量化描述，标成浮点的层改用不量化的实现，所以并非每个矩阵都是 INT8。本部署的划分如下，其中一部分由模型代码直接证实，其余按上游模型配置的不量化清单推断：

| 加载后精度 | 哪些矩阵 |
|---|---|
| INT8（W8A8） | 前 3 层稠密 MLP 的 gate、up、down；MoE 层的路由专家和共享专家；稀疏 MLA 的三个大投影（Q 与 KV 的压缩投影合并成一个、Q 的展开投影、输出投影） |
| BF16（源码证实） | KDA 层的九个投影（Q、K、V、两组门控投影、b 投影、输出投影）；索引器的 K 与打分合并投影；嵌入表 |
| BF16（推断） | 稀疏 MLA 的 KV 展开投影；索引器的 Q 展开投影；词表投影 |
| FP32 | router 的打分矩阵、mHC 的混合参数、KDA 的短卷积等小参数 |

KDA 与稀疏 MLA 是 GLM 的两种注意力层，分别占 34 层和 11 层；索引器是稀疏 MLA 里给历史位置打分、挑出要看哪些位置的小网络；router 是 MoE 层里给专家打分的路由网络。

两行 BF16 的结论强度不一样。标「源码证实」的那一批，模型代码建层时传的就是 `quant_config=None`：KDA 的九个投影在 `glm5_next.py` 的 1541–1680 行，索引器那个把 K 投影与打分合并成一层的 `wk_weights_proj` 在 1235–1300 行，嵌入表在 2263–2268 行。描述文件写什么都不会让它们变成 INT8。标「推断」的那一批建层时接了 `quant_config`，实际精度由量化包里的描述文件决定，本页按上游配置的不量化清单推断——索引器的 Q 展开投影 `wq_b` 就在这一批里，和它同层的 `wk_weights_proj` 反而是证实的。INT8 那一行同理是推断。描述文件到手后若与上游清单不同，变的是字节数，形状和切法不变。精度划分的依据分级以[量化](quantization.md#哪些矩阵是-8-位哪些保持-bf16)页为准。逐部件的存法见[模型页的权重精度](glm-5-3-flash.md#权重精度文件里怎么存加载后变成什么)，每卡字节见[每张卡上放了什么](glm-5-3-flash-two-node.md#每张卡上放了什么)。

**R1 是主线中[提示词含 4 个 token 的示例请求](one-request.md#示例请求-r1-与官方双机部署)。** 先跟其中一个位置走过前三层的稠密 MLP，再看四行共同执行的账。

### 从嵌入向量到 MLP 输入

**这个位置进入 MLP 时是一行 4096 维表示。** 嵌入先按 token 编号查出向量；GLM 的 mHC（在子层前后混合多条残差流的连接机制）在层间保存四路表示，但进入一个注意力或 MLP 子层前，会将四路混合为一路，再归一化。因此 MLP 的输入宽度仍是 4096，不能直接把四路展开宽度当作它的输入宽度。

R1 嵌入后的形状是 [4,4096]，四路残差是 [4,4,4096]；后者的 BF16 载荷为 128 KiB。这些形状和字节的推导保留在[主线的词嵌入与四路残差](one-request.md#词嵌入与四路残差)。到 MLP 前，注意力已经改变了数值，四行只是形状相同。

### gate 与 up 扩宽，down 再缩回去

**一行输入经过三个逻辑投影，中间穿插非线性门控，最后回到 4096 维。** gate 和 up 都将输入扩到 12288 维：up 提供中间数值，gate 经过 SiLU 非线性函数后与 up 对应元素相乘，这种门控叫 **SwiGLU**。固定实现先把 gate 的上限设为 10、up 限制在 −10 到 10，再计算 SiLU(gate) × up；限制的是门控输入。随后 down 投影缩回隐藏宽度。非线性使这组计算不能合成一个固定矩阵乘。

TP8 后，本卡持有 gate 和 up 各 1536 个输出通道，合并投影共输出 3072 列。门控后留下 1536 列，down 用这段输入计算 [T,4096] 的部分和，最后归约合齐。**输出形状完整与数值完整是两回事。** R1 的每卡路径为 [4,4096] → [4,3072] → [4,1536] → [4,4096]；末尾一次归约的逻辑载荷为 32,768 B，原始形状与通信账见[主线稠密 MLP](one-request.md#前-3-层的稠密-mlp)。

为看清参数量与运算量的区别，单独取**未分片的 up 逻辑矩阵**：[4096,12288]，四行输入产生 [4,12288] 输出。它是整个 TP 组共同完成的规模，不是单卡实际驻留布局。

```calc
title: R1 的单个 up 逻辑投影有多少参数和运算
参数个数 = 4096 × 12288 = 50,331,648
乘法次数 = 4 × 4096 × 12288 = 201,326,592
乘加近似规模 = 2 × 4 × 4096 × 12288 = 402,653,184 次 ≈ 4.03 亿次
```

这只覆盖 up。完整 FFN 还有 gate、门控与 down；整个模型还有注意力、归一化、残差混合和词表投影。量化、融合和并行决定实际执行方式，所以这份算术量须与设备运行记录一起使用，才能解释时延。

## 同一片权重，为什么能处理多行输入？

**固定模型的普通推理复用同一组权重；变的是每轮输入的行数和数值。** prefill 是首次处理提示词，普通 decode 是根据已有历史继续计算新位置。下图用 R1 的四行 prefill，对照关闭[投机解码](speculative-decoding.md)（先草拟几个候选 token，再让模型一轮验证它们）时单请求的一行普通 decode；两轮共用未分片的 up 逻辑权重。

```wiki-diagram
file: matmul-weights-share
```

本部署实际启用了 **MTP**：模型先草拟后续 token，再由主干验证。主线示例的 decode 输入是 1 个已确定位置加 3 个候选，仍为 4 行；因此图中的单行分支是普通 decode 的对照条件，实际轮次见[主线第二圈](one-request.md#第二圈和第三圈decode-步一次验证-1--3-个-token)。有多条请求时，T 还包含同轮其他请求的新位置，不能把 T 直接当请求数或上下文总长度。

同一轮把更多行交给矩阵乘，可以让一个读入计算单元的权重块参与更多行的计算；这就是批内复用的机会。真实内核按小块读权重和输入，片上缓存容量、量化布局及计算分块共同决定一次从设备内存读入后能用多久。**逻辑上共用一份权重，不保证整片权重只读一次，也不要求每个 token 都重新读取整片权重。**

**反过来，行数少时，一块权重读进来只服务几行，读得多、算得少，瓶颈容易落在显存带宽上。** 本轮有 T 行输入经过这片权重，每个权重读入计算单元后就被复用 T 次，配 T 次乘法和 T 次加法；这个 T 就是权重复用次数。把权重从设备内存搬进来花访存时间，拿它做乘加花计算时间。设备每秒能做的运算数与每秒能读的字节数之比由硬件决定：每读 1 字节配的运算少于这个比值，乘加早早做完，计算单元等着下一块权重送到，叫**带宽受限**；多于这个比值，数据来得及、乘加做不完，叫**算力受限**。复用次数越大，每字节配的运算越多，越往算力受限那头走。

放到本部署，decode 每个请求一步只贡献很少的行：关闭投机时 1 行，开了 MTP 也只有 1 + 3 = 4 行。多条请求同轮 decode 会把行数叠起来，量级仍是几十行，例如在多请求示例[场景 M](concurrent-requests.md#示例场景-m-与变体-m) 里（两台机器各是一组，记作 DP0、DP1），DP0 上 12 条 decode 请求共 48 行，DP1 上 7 条共 28 行。prefill 一步能把一整段提示词交进来，上限是单步 token 预算 8,192：同一场景中 DP0 混入一条 6000 token 的新请求后，本步是 6,048 行。稠密 MLP 的 TP8 切的是权重，不切 token 行，所以同组每张卡的本地权重都要服务本组这一步的全部行。

```calc
title: 本卡合并 gate/up 权重每读 1 字节配几次运算
本卡权重字节 = 4096 × 3072 × 1 B = 12,582,912 B
R1 decode 一步（单请求 4 行） = 2 × 4 × 4096 × 3072 ÷ 12,582,912 B = 8 次/B
场景 M 的 DP0 纯 decode（48 行） = 2 × 48 × 4096 × 3072 ÷ 12,582,912 B = 96 次/B
场景 M 的 DP0 混入长 prefill（6,048 行） = 2 × 6,048 × 4096 × 3072 ÷ 12,582,912 B = 12,096 次/B
> 前一项是单请求的量级参照，后两项才是同一个 DP0 的两步
```

INT8 权重每个占 1 字节，所以每字节配的运算就是 2T，三项之间的差距全部来自行数。同口径的对照要在同一个 DP0 的两步之间做：纯 decode 96 次，混入一条 6000 token 的新请求后 12,096 次，相差 126 倍。R1 那一行是单请求的量级参照，它只有 4 行而不是一步的全部行，别拿它直接去除多请求混合的那一步。decode 这头同一片权重只被几行复用，读得多、算得少，更容易卡在显存带宽上；prefill 这头同一片权重被几千行复用，更偏向算力受限。decode 时 MoE 的路由专家复用更少：每个 token 只去 8 个专家，R1 的 4 行分到每张卡平均只有 2 行，一个被选中的专家读进来通常只服务一两行。MTP 把每请求的行数从 1 提到 4，也就让同一次读入的权重多服务 3 行；但遇到被拒的候选，后面位置算出的结果都作废，它的收益与代价见[投机解码](speculative-decoding.md#为什么也可能变慢)和[主线第二圈](one-request.md#第二圈和第三圈decode-步一次验证-1--3-个-token)。

这里只数了权重；输入输出本身、注意力读取的历史也要占带宽，另见[prefill 的性能分析](prefill.md#性能分析要结合输入规模)。分界值要拿设备的算力与带宽之比来定，主线底稿没有收录 Atlas 800 A2 的这两项规格，某一步实际受哪一头限制仍以设备测量为准。

## 权重容量、设备显存与主机内存怎样分开记？

**先注明精度和分片范围，再谈容量；主机 RAM 与 NPU 显存分别统计。** 模型文件存于磁盘，加载过程中主机可能持有文件页或暂存张量；推理中参与本卡矩阵乘的权重位于设备内存，计算还需要输入、输出和临时缓冲。主机加载峰值不能与设备权重容量混成“每卡显存”。

上面的 up 逻辑矩阵若全部以 BF16 保存，容量是一个明确的精度对照：

```calc
title: 未分片 up 权重的 BF16 容量对照
逻辑权重载荷 = 50,331,648 × 2 B = 100,663,296 B = 96 MiB
```

这 96 MiB 描述的是假定 BF16 的完整 up 权重。本部署的稠密 MLP 按 TP8 分片，并按 W8A8 存权重主体；下面列实际口径的结论，完整推导回链 [TP 每卡权重账](tensor-parallel.md#稠密-mlp-与共享专家每卡各留一段通道)。数学形状按 [输入维,输出维] 书写。

| 统计对象 | 每卡数学形状／范围 | 设备侧权重主体 |
|---|---|---|
| 合并 gate/up | [4096,3072]，INT8 | 12 MiB／稠密层 |
| down | [1536,4096]，INT8 | 6 MiB／稠密层 |
| 三个稠密 MLP | 每层 18 MiB，三层合计 | 54 MiB／卡 |

这些值只数权重主体；量化还保存恢复数值范围所需的缩放系数等辅助参数，加载后可能改变布局、产生运行时副本。输入输出、计算临时空间和缓存也另占显存。全模型每卡容量统一见[部署页的每张卡上放了什么](glm-5-3-flash-two-node.md#每张卡上放了什么)，主机加载与设备预算见[设备内存](device-memory.md)。某轮实际从显存读取的字节数则属于访存账，需要测量。

## MoE、嵌入和残差混合也按同一规则算吗？

**矩阵乘的行列规则不变，但参与计算的权重集合、输入来源和切分方式会变。** 前三层的 MLP 是稠密前馈，后续 **MoE（混合专家）**将前馈工作交给多个可选择的小网络，每个小网络称为专家。GLM 每个 MoE 层有 288 个路由专家，即整个可供 router（负责打分选择的路由网络）选择的集合；每个 token 从中选 8 个，另走所有 token 都使用的共享专家。

专家的中间宽度是 2048，区别于稠密 MLP 的 12288。不同 token 选择不同专家集合时，整轮参与的专家要按并集统计，数量可以超过 8 个。总参数量包含全部权重，单 token 的激活参数只包含实际经过的部分；注意力、共享专家、路由器和输出层各有权重，因此不能将总参数直接乘 8/288 当成整模型激活参数量。结构与统计边界见[模型的 MoE 小节](glm-5-3-flash.md#moe288-个专家里每次挑-8-个)。

**EP（expert parallel，专家并行）**把完整路由专家分到不同卡，输入行按选中的专家重排后送去计算；共享专家仍按 TP 切矩阵。它们各自的容量与通信见 [EP](expert-parallel.md) 和 [TP](tensor-parallel.md#共享专家切法仍是列接行归约由外层安排)。同一专家内多行共用权重，不同专家之间用的是不同权重。

嵌入是拿 token 编号查词表的某一行，不是让整数编号直接乘所有权重列；最终词表投影才把隐藏向量变成各 token 的分数。mHC 则用四路展开表示生成混合系数，其输入宽度与 MLP 不同。这几类矩阵各自有作用，详见[嵌入](embedding.md)与[模型的四路残差](glm-5-3-flash.md#一层有两段计算四条-residual-流贯穿两段)。

## 常见误解

- **“参数量越大，每个 token 就一定计算全部参数。”** 稠密投影使用这片矩阵的全部权重，MoE 则只执行选中的专家及共享路径；整模型要按路径统计。
- **“输入变成四行，权重也复制四份。”** 四行共用一片权重，增大的是输入输出和算术工作；并行部署的副本与分片另有约定。
- **“矩阵乘会直接把各 token 混在一起。”** 这里的前馈投影逐行处理，跨位置的信息交互由注意力等结构完成。
- **“输出已有全部列，所有卡就都算完了。”** 本部署稠密 MLP 的 down 在归约前输出部分和，归约后才有完整数值。
- **“96 MiB 就是本卡的权重占用或一次读取量。”** 它是未分片 BF16 up 的容量对照；实际设备驻留要按量化与 TP 分片记账，访存另测。
- **“FLOPs 除以标称算力就是请求耗时。”** 还要考虑访存、整数与浮点精度、通信、内核效率和其他算子；没有运行测量只能说明算术规模。

### 会报什么错

输入末维须与本卡权重的输入维匹配。遇到形状错误，先区分数学方向、加载后的存储方向和 TP 分片，核对输入属于完整向量还是本卡切片，再定位到对应后端算子；错误文字取决于具体内核。

固定 Ascend 的 `AscendRowParallelLinear` 还显式禁止一种偏置组合：关闭结果归约，同时直接加偏置且不将偏置留给调用方，会抛出 `ValueError`。这是为了避免分片结果之后相加时把偏置重复加多次；本页 GLM MLP 的 `bias=False` 不走这条错误分支。

### 开销和什么时候别开

调批大小、量化或并行方式之前，先确认当前成本落在乘加、访存还是通信。这里没有可单独关闭的数学步骤；去掉 gate/up 或 down 就改变了模型本身。改变批大小则仍用同样的权重，但会改变输入输出容量、权重复用机会和通信载荷。

图中的线性投影采用数学形状 [H,F]。[PyTorch Linear](https://docs.pytorch.org/docs/2.14/generated/torch.nn.Linear.html) 的参数通常按 [F,H] 保存，计算形式是输入乘权重转置再加偏置。固定 Ascend W8A8 的加载逻辑先建立 [输出维,输入维] 的 INT8 权重，随后 `process_weights_after_loading` 将它转置并按条件转成设备分块格式。查运行时张量必须同时说明查看的是加载前、加载后还是数学形状。

`AscendW8A8DynamicLinearMethod.apply` 对输入逐 token 动态量化，调用 `npu_quant_matmul`，用权重与输入的 scale 恢复输出范围，并将输出类型设为输入类型。源码另有一条大维度拆块分支，但它只在某个超大投影权重并开启对应特性时才生效，本页的稠密 MLP 不走它。[C7]

即便不走拆块分支，也不能从三个逻辑矩阵断言底层只有三个 kernel。原因有两条，彼此独立，要分开看：

- **gate/up 合并：矩阵乘反而少一次。** 模型把 gate 和 up 建成一个合并的列切 Linear，前向只调用一次；W8A8 下每次调用是「一次逐 token 动态量化 + 一次 `npu_quant_matmul`」。所以一层稠密 MLP 在一张卡上是 2 次量化矩阵乘（gate/up 一次、down 一次），各带 1 次动态量化，不是 3 次矩阵乘。[C3][C7]
- **门控：没有用上融合算子。** Ascend 写了一个「限幅后调 NPU SwiGLU 融合算子」的版本，但按静态读码，它的注册键和 vLLM 查表用的类名对不上，没有生效；GLM 实际走上游的 PyTorch 写法，两次截断、一次 SiLU、一次相乘，是 4 个逐元素算子。[C22] 推理过程、影响范围和缺的 profiling 见 [MLP、residual 与 RMSNorm 的开销一节](mlp-residual-norm.md#开销和什么时候别开)。

按源码调用数，一张卡上一层稠密 MLP 是 2 次动态量化、2 次量化矩阵乘、4 个逐元素算子，再加 down 之后的一次 TP8 All-Reduce。图编译会不会再合并其中的逐元素算子，实际 kernel 个数和耗时是多少，都要对照运行记录。
