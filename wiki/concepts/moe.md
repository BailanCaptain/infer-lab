## 350 亿个参数，为什么每次只算 30 亿

全库跟的例子是 Qwen3.6-35B-A3B（完整设定见[贯穿全库的例子](one-request.md)）。名字里的两个数，读起来有点奇怪：

- **35B**：模型一共存着约 350 亿个参数，也就是约 350 亿个训练好的数字（参数、权重是什么，见[矩阵乘与权重](matmul-and-weights.md)）。
- **A3B**：每个 token 走一遍模型，实际拿来乘的只有约 30 亿个。A 是 activated，「被用上的」。

也就是说，每处理一个 token（模型处理文字的最小单位，见 [token](token.md)），模型存着的数字里有九成这次根本没碰。那它们存着干什么？既然不用，为什么不删掉？

答案就在这页的主题 MoE 里：那九成不是没用，而是**这次轮不到**。下一个 token 也许就轮到它们了。

## MoE：把一份大的换成很多份小的，每次只用几份

先回忆一层里有什么（见[层与隐藏向量](layers-and-hidden.md)）：每层先是一段注意力，让 token 之间互相看一眼；然后是一段每个 token 各算各的计算，叫 [MLP](mlp-residual-norm.md)。MLP 说白了就是拿这个 token 的那串数字去乘几块权重，再变回同样长的一串数字。

普通的做法是每层放**一份** MLP，所有 token 都过这一份。MoE（Mixture of Experts，「混合专家」）换了个办法：

- 把这一份 MLP 换成**很多份小的**。每一份叫一个**专家**，长得和 MLP 一样，只是小得多。这个模型每层有 256 个专家。
- 每个 token 走到这一层时，**不是 256 个都过**，只挑其中 8 个来算，其余 248 个这次不动。

这样模型就可以「存得多、算得少」：存着的专家越多，模型能学到、能装下的东西就越多；而每个 token 真正要乘的，只有被挑中的那几个。35B 是它的「见识」，3B 是它每次的「出力」。

算一笔账就能看出那九成去哪了（每个专家多大，下面会讲）：一个专家约 315 万个参数，一层 256 个，40 层下来是约 322 亿——350 亿里的绝大部分都是专家。而每个 token 每层只用 8 个专家，40 层合起来约 10 亿。剩下二三十亿是注意力、共享专家（下面讲）这些每次都要用的部分，加起来就是那约 30 亿。

## 路由器：看一眼这个 token，给 256 个专家打分

「挑 8 个」由谁来挑？每层有一个很小的网络，叫**路由器**。

一个 token 到了这一层，手里是一串 2048 个数字，叫它的**隐藏向量**（层与层之间传的就是它）。路由器看一眼这串数字，给 256 个专家各打一个分，意思是「这个 token 交给这位专家处理有多合适」。然后：

1. **挑人**：取分数最高的 8 个。挑出来的这 8 个编号，连同各自的分数，叫这个 token 在这一层的**路由结果**。
2. **各算各的**：这 8 个专家各自拿这个 token 的隐藏向量去算，各交出一串 2048 个数字。
3. **加权合起来**：8 份结果不是简单相加，而是按路由器打的分加权——分高的专家说话分量重，分低的轻一些。

图里那一大片淡色格子，就是这一层的 256 个专家；亮起来的 8 个是这次被挑中的。多数专家都闲着，只有被点到的干活——这就是「35B 存着、3B 在算」在一层里的样子。

有两点值得记住：

- **每个 token 分别选择，结果可以相同，也可以不同。** 路由器看的是这个 token 自己的隐藏向量，所以「的」和「矩阵」很可能挑到完全不同的 8 个专家。同一个问题里的 37 个 token，每一个都各自挑一遍。
- **每一层也各挑各的。** 40 层每层都有自己的路由器和自己的 256 个专家，一个 token 在第 1 层挑了谁，和它在第 2 层挑谁没有关系。

还有一个容易混的词：给 token 挑专家的叫「路由器」，它在模型**里面**、每层一个。把一整条请求分给某一份模型副本的，叫「前端路由」，那是模型**外面**的调度，跟这页不是一回事。

## 共享专家：有一份谁都要过

除了挑出来的 8 个，这个模型每层还有 **1 个共享专家**。它不用路由器挑，每个 token 都要过它；它的结果还会经过共享专家门控，再和那 8 份加权结果加在一起，才是这一层 MoE 的输出。

可以这么直觉地理解分工：共享专家负责谁都用得上的那部分通用处理，256 个里挑出来的那些各管各的专长。不过这只是帮助记忆的比喻，每个专家实际学到了什么，是训练出来的，没法事先规定。

## 每个专家很小，靠数量凑出本事

一个专家有多大？它和 MLP 一样，先把 2048 个数的隐藏向量乘成一串中间数字，再乘回 2048 个。这个模型里，这串中间数字只有 **512 个**，只是隐藏向量长度的四分之一。

一个专家由三块权重组成，每块 2048 × 512 个数：

```
3 × 2048 × 512 ≈ 315 万个参数     一个专家
315 万 × 256   ≈ 8 亿             一层的 256 个专家
8 亿 × 40 层   ≈ 322 亿           整个模型的专家
```

换个角度看：256 个专家的中间宽度相加是 256 × 512 = 131072，而每个 token 只激活其中 8 份，也就是 8 × 512 = 4096。这只比较中间通道数量，不表示路由加权在数学上等价于一个同宽度的普通 MLP。单个专家很小，本事是靠数量凑出来的。

## 一颗 NPU 装不下，token 得被送到专家那里去

落回贯穿例子：模型跑在两个 Atlas A3 NPU 设备上；这里按软件可见设备计数，板卡与设备的区别见[硬件计数](hardware-devices.md)。专家权重约 60 GiB，还要加注意力等权重、KV Cache 和临时空间；本例按每个设备 64 GB 的容量预算，需要把模型分开存。

本例采用专家权重常驻显存的部署：路由器下一个 token 会挑谁事先不知道，需要让各专家随时可用。其他系统可以设计卸载和按需加载，但那会增加搬运，不是这里采用的设定。

办法是把每层的 256 个专家按编号分成两堆，0 到 127 号放在一颗 NPU 上，128 到 255 号放在另一颗上。于是一个 token 挑中的专家，可能有几个不在它所在的那颗 NPU 上——这时就得**把这个 token 送过去**，在那边算完再送回来。

专家怎么分、token 怎么送出去又收回来、来回一趟要付出多少代价，是[专家并行](expert-parallel.md)那一页的主题。这里只要知道：**MoE 让每个 token 只用几个专家，但也因此必须把 token 送到专家所在的地方。**

最后一个延伸问题：路由器挑谁由数据决定，有的专家特别受欢迎，放它的那颗 NPU 就会比另一颗忙。怎么缓解这种忙闲不均，见 [EPLB](eplb.md)。

## 对照源码

### 开销和什么时候别开

专家个数、top-k、共享专家属于训练得到的模型结构，不能为了省显存随意删专家或把 top-k 改小而仍声称行为等价。专家并行是部署方式，和是否采用 MoE 是两件事。

### 版本差异

本页的 256 选 8、共享专家 1 个、40 层均来自所引模型配置；其他 MoE 模型不一定如此 [S1]。代码只核对 vLLM v0.23.0（配套 Ascend releases/v0.23.0）。

### 源码位置

- `Qwen3NextSparseMoeBlock` 创建路由器、共享专家门控，并将 `num_experts`、`num_experts_per_tok` 传入 `FusedMoE` [C1]。
- 共享专家计算后乘以其门控的 sigmoid 值，再与路由专家路径合并；不是无条件以固定系数加一份结果 [C1][C2]。
