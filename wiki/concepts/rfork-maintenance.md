## 同事又发来一份补丁，现在跑的到底是哪版代码

假设同事发来第八份 RFork 补丁，让你「在现在的版本上打上去」。第一个问题就是：「现在的版本」指的是哪一份代码？是社区最新版？是前面七份补丁依次叠上去的结果？还是别的什么？

**版本维护要做的，就是任何时候都说得清「现在运行的是哪一份完整代码」，并让原补丁、这份代码和知识页三样东西彼此对得上。** RFork 本身是什么见[总览](rfork.md)；这里要记住的是，本章讲的 RFork 是用户的工作版，**独立于社区演进**。判断当前行为只认一样东西：**用户确认过的、补丁全部应用之后的完整源码**。原来那几份补丁文件是历史材料，用来追溯「谁在什么时候改了什么」，不能拿来直接说明现在的代码怎么跑。

下图是这七份补丁真实的前后关系，后面几节都会回到这张图：

```wiki-diagram
file: rfork-patch-history
```

右下角那一格就是「现在的版本」。具体来说，有三样东西各自钉在一个固定的提交上：

- **当前完整实现**：图里的补丁 7 那一格，用户确认的基线，本章所有机制页都按它来讲；
- **前六份补丁的原件**：用来下载和追溯；
- **第七份补丁的原件**：同样用来下载和追溯。

后两样所在的提交，只是在补丁 6、补丁 7 那两格的代码之上多存了补丁原件（前者 6 个、后者 1 个），代码本身没有再变；所以「存原件的提交」和「补丁做出来的代码」是两个不同的提交号（三个提交号见文末[版本差异](#版本差异)）。

当前钉的是哪一个提交，全项目只在一处定义；本页记的是这次基线的历史说明，不是会自动跟着变的第二份配置。本章各页标的「已核」只表示核对过这个工作版，**不代表社区的同名分支也成立**。

所以收到新补丁时，代码快照、版本钉点、机制页和排错页要一起核对、一起更新。

## 七份补丁不是一条链

直觉上，前六份补丁依次打完，再打第七份，就该得到当前代码。实际不是这样。

看上图：补丁 1 到 3 是两路共有的，**从补丁 3 之后，历史分成了两路**。上面一路是原来的补丁 4、5、6；下面一路先有另外三次提交，再往后才是补丁 7。按这三次提交自己的说明，它们和补丁 4–6 主题相近，但实现和覆盖范围不同：重构传输和会话、适配 v0.26 的接口并在回退时放掉 MoE 的旧权重、回退之前摘掉编译留下的钩子。补丁 7 是对着下面这一路写的。

于是第七份补丁改到的一部分测试文件，在补丁 6 的终点上根本不存在；一个管张量布局的文件，前后文也对不上。图上标着「直接打不上」的那条虚线就是这个意思。

2026-09-21 做过一次核对：在补丁 6 终点的干净工作区上先「试打」第七份补丁，确实打不上去。随后从两路终点的两个确切提交之间，单独导出一份**衔接差异**（图上从补丁 6 拐下来的那条虚线），并验证了「基线 → 原六份补丁 → 衔接差异 → 原第七份补丁」这样一步步重建出来的整棵代码树，和当前完整实现一模一样。

这份衔接差异不小：18 个文件，增 3080 行、删 185 行。大头是测试和一份租约生命周期的设计文档；落在源码上的只有六个文件、合计约 300 行增删，涉及 Planner 客户端、加载器、会话和张量布局等。所以下面那一路三次提交带来的变化，既不能算在补丁 4–6 头上，也不能算在补丁 7 头上。

原始补丁没有被悄悄改写；衔接差异单独存放，并明确标成「从版本历史另外生成的材料」，不冒充用户给的补丁内容。

## 每份补丁管什么，读的时候边界在哪

每份补丁具体改了什么、社区各版本有没有合进去，只在[总览的版本对照](rfork.md#版本差异)里写一份。这里只讲**拿着补丁原件读的时候，能说明什么、不能据此断言什么**：

| 材料 | 原件管的事 | 读的时候的边界 |
|---|---|---|
| 第一份补丁 | 布局传输、NPU 同步与回退相关处理 | 不能据此断言已经覆盖后面所有清理问题 |
| 第二份补丁 | 保留登记过的张量的所有者 | 当前实现还额外保留了原始存储，应看最终代码 |
| 第三份补丁 | 投机解码的 draft 模型和主模型重复登记的问题 | 什么时候算共享、全部共享时怎么走，仍以最终代码为准 |
| 第四到第六份补丁 | 传输与会话层重构、v0.26 接口适配、清理与并发处理 | 走的是图上面那一路，和补丁 7 的底不同，不能把这里的实现细节平移到当前代码 |
| 衔接差异 | 两路终点之间的差：租约、回退、清理、张量安全和测试 | 单独记录，不算进「第七份补丁的内容」 |
| 第七份补丁本身 | 来源服务的 HTTP 端口可以按 rank 固定下来；采集时跳过本机的 top-k 下标缓冲区 | 不负责固定传输引擎的端口；跳过名单里只有这一个缓冲区，不是所有临时缓冲区 |

第七份补丁的端口怎么配见[配置](rfork-config.md#四类端口谁监听谁来连由什么决定)，那个缓冲区为什么不从来源搬见[布局](rfork-layout.md#本机的工作区不从-a-搬)。当前代码里另外一些行为——晚一点才去申请租约（见[启动](rfork-startup.md)）、有次数上限的后台归还租约（见[生命周期](rfork-lifecycle.md)）、回退时清理全局编译与 MoE 引用——都要看最终的加载器和会话代码；第七份补丁本身能直接对上的，只有端口和 top-k 采集这两处变化。

表里「v0.26 接口适配」在当前代码里留下的一个痕迹，是一个**兼容垫片**：在还没有「硬件档案」这个接口的 Ascend 版本上，它按是不是 310P 现造一个只带权重布局策略的替身对象，让 RFork 照样能起来；身份指纹和布局判断都从这个入口取值。跨版本读代码时，先找这类垫片，别假设两边接口一样。

## 代码放在哪：一份快照用来读，一份完整仓库用来改

项目里存了两份代码，用途不同：

- **项目里的快照**：从审定过的提交导出的 RFork 那部分代码，连同随版本保存的测试、示例 Planner、原版自带文档、七份原始补丁、衔接差异，以及一份登记了来源和哈希的清单。它带着许可证和集成入口，但只是抽出来的范围，**离开 vLLM / Ascend 的安装环境跑不起来**。
- **完整的独立仓库**：用来打新补丁、构建、按行号审计。换机器要重新建。

开发只在完整仓库里做，再从审定的提交导出快照——这样不会出现两份代码各自被手改、慢慢对不上的情况。

换机器时能不能把完整仓库找回来，现在**还没有保障**。2026-10-02 核过：钉点提交和补丁 7 的归档提交，都不在同事仓库的任何一个分支上（62 个分支头逐个检查，没有一个包含它们；补丁 1–6 的归档提交倒是其中一个分支的头）。普通克隆只带下分支上的提交，所以克隆完直接检出钉点会失败。当天实测，按完整提交号单独拉取这一个提交能取到，取到后再检出即可。不在分支上的提交 GitHub 会保留多久，待核：缺同事仓库的保留约定。要把它保住，二选一：请同事给这个提交留一个分支；或者现在就按「未公开的提交」处理，交付时连同一个 Git bundle 一起保存，换机先恢复 bundle 再检出钉点。

知识页上的源码链接指向同事仓库里的固定提交，这两个提交的页面当天都能打开。以后出现还没公开的本地提交时，不能假装同名链接已经存在，也不能为了让链接点得开就擅自推送代码。

读快照时几条边界：看到有测试，不等于这一轮跑过；示例 Planner 只证明示例协议，代替不了现场的生产 Planner；原版文档和代码冲突时要明说，以实际运行的那条路径为准。

| 权重采集、布局、量化方法 | [布局](rfork-layout.md)、[传输](rfork-transfer.md)、[输出一致性验收](rfork.md#成功至少有四种不能压成一个开关) |
| 传输内存的登记、注销、收尾 | [传输](rfork-transfer.md)、[生命周期](rfork-lifecycle.md)、[排错](rfork-troubleshooting.md)里清理失败的那部分 |
| 会话、租约、Planner 协议 | [启动](rfork-startup.md)、[生命周期](rfork-lifecycle.md)、[配置](rfork-config.md)、[排错](rfork-troubleshooting.md)里 400/404 的那部分 |
| 回退、全局模型引用 | [启动](rfork-startup.md)、[传输](rfork-transfer.md)、[排错](rfork-troubleshooting.md)里 OOM 的那部分 |

完整的操作规程只写在一处（位置见下半），按顺序是：保存原件、确认基线、先试打再正式打、核对行为变化、跑当前环境能跑的测试、改钉点并重新导出快照和哈希、同步知识页、最后统一校验。知识页不再抄第二套维护步骤。

改好的代码要上线时，还有一个容易踩的坑。新实例是拿一把「钥匙」去找能借权重的来源的，钥匙由部署指纹算出来；指纹里有部署策略名和模型权重的版本号，**却没有 RFork 代码本身的版本**（指纹的全部内容见[身份](rfork-identity.md#部署指纹里写了什么)）。也就是说，代码升级了、模型没换，钥匙不会跟着变，不能指望靠钥匙变化把旧来源自动隔开。

反过来，部署策略名在指纹里，换一个名字钥匙就变了。所以新旧版本应当用各自独立的部署策略名；切换前要核对 Planner 给的候选、旧的登记信息和还在进行的传输，再安排实例和 Planner 一起切。**不能用清空 Planner 账本来代替「等正在读的实例读完」或「确认底层内存已清理」。** 官方材料的核读与差异见[官网对照页](../sources/rfork-official-guide.md)。

## 哪些已经核过，哪些要到现场

本地能核的有：快照和补丁的字节有没有变；原件能不能重放出完整代码树；知识页引用的行号是否存在；页面格式和链接是否正确。**这些都证明不了真实 NPU 上已经把权重传完。**

这一轮没有 NPU、CANN、YuanRong 以及 RFork 的 Python 运行依赖，所以不声称跑过原版 RFork 单测或设备集成测试。以下几项要在实际部署里核：传输内存的登记与清理约定、MTP 全部共享时的保护、输出一致性、并发扩容，以及来源实例的推理是否受影响。

## 常见误解

- **「社区升级了，RFork 也一起重钉」**——只有用户工作版的更新才会改这个钉点；社区版本继续各走各的。
- **「补丁能打上去就能上线」**——还要核行为、协议兼容、回退和真实设备上的结果。
- **「指纹里有版本号，RFork 一升级钥匙自然就变了」**——那个版本号是模型的，不是 RFork 代码的；要隔开新旧版本，得换部署策略名。
- **「补丁 7 的说明里没写的行为，就是补丁 1–6 带来的」**——下面那一路另外三次提交和衔接差异也带来了变化，不能只按补丁编号去归因。
- **「当前版本修了某个问题，旧日志里一定也有这段保护」**——旧事故要回到当时的完整源码去看，不能拿后来的行为倒推。

## 对照源码

### 怎么开

- 当前钉点唯一定义在 `wiki/seeds/rfork.yaml`，登记为 rfork 仓库的 main 技术键；`rfork:main` 的 verified 只指这个工作版。
- 完整维护规程在项目根 `rfork/README.md`（保存原件、确认基线、先 `git apply --check` 再 apply、导出快照、重算哈希、同步来源）。
- 核验命令：`pnpm rfork:verify` 核本地源码和补丁的字节完整性；加 `--git` 还核原始 blob，并用临时 index 重放出完整代码树。`pnpm wiki:audit` 核引用行号存在，`pnpm wiki:lint` 核格式和链接。
- 新旧版本切换用独立的 `model_deploy_strategy_name`。
- 换机取回钉点：先 `git fetch origin <完整提交号>`，再 `git checkout --detach <完整提交号>`（2026-10-02 在空仓库里实测能取到 `3284850b`）。`pnpm wiki:clone --seeds wiki/seeds/rfork.yaml` 只拉分支头和标签（`scripts/wiki/clone.ts` 的 fetch 计划），按这个逻辑拿不到不在分支上的钉点；全新机器上未实测。

### 会报什么错

2026-09-21 在干净的 `7ddcfca9`（原 patch1–6 终点）工作树上执行 `git apply --check` 应用 patch7，复现了不适用；报错原文见 `rfork/VERSION-NOTE.md`。原因：patch7 的父提交是 `09b8eeae`，与 `7ddcfca9` 在 patch3 之后分叉；patch7 修改的部分测试文件在 `7ddcfca9` 不存在，`tensor_layout.py` 的上下文也不匹配。随后从两个确切提交导出衔接 diff，验证「基线 → 原六份补丁 → 衔接 diff → 原 patch7」重建的整个 Git tree 与 `3284850b` 一致。[D]

### 开销和什么时候别开

- 配置 fingerprint 不包含 RFork 代码 commit，代码升级不能依赖 seed key 必然变化来隔离旧 seed；新旧版本应使用独立 `model_deploy_strategy_name`，并核对 Planner 候选、旧元数据和活动传输后再切换；不能用清空账本替代 reader 排空或 native 清理确认。
- `rfork:verify`、`wiki:audit`、`wiki:lint` 都不证明实际 NPU 已完成权重传输。本轮未运行原 RFork 单测或设备集成测试；待现场核验：Ex 注册/清理契约、MTP 全共享保护、输出一致性、并发扩容、source 推理影响。

### 版本差异

社区 v0.23 / v0.26 / main 各拿到了哪些补丁、行为差在哪，全章只在[总览的版本对照](rfork.md#版本差异)里写，本页不另列。本页只管工作版自己的版本身份。

三个固定身份（提交号、每份补丁的 SHA256 与快照文件清单登记在 `rfork/manifest.json` 的 `patches[].sourceCommit` / `patchCommit`；核对过程与命令输出在 `rfork/VERSION-NOTE.md`；本页 `sources` 只钉源码行号，版本身份不在其中）：

| 名称 | 固定身份 | 用途 |
|---|---|---|
| 当前完整实现 | `3284850b42f94934dfe6909ed6f1c4c145a7f69c` | 用户确认的基线；seeds 中登记为 rfork 仓库的 main 技术键 |
