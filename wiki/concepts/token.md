## 一句话怎样变成模型能处理的编号？

**Token 是模型用整数编号表示的文本单元；分词器（tokenizer）按配套规则把文本切成这些单元，再查词表得到 token ID。** 词表是单元与编号的对应表。聊天消息还要先经过对话模板，把角色、正文和消息边界组织成模型约定的格式。

```wiki-diagram

```

图中的句子只演示流向，p₀…pₙ₋₁ 代表最终得到的整数编号。切分位置和 n 都由实际分词决定。Token 可以是词、子词、标点、空白或字节片段；采用字节表示时，一个汉字也会被拆成多个 token。

本页挂靠 [A1 入口](one-request.md#第-1-站-入口从-http-到-node0-的引擎)。模板与分词在**主机的 CPU 和内存**上处理；NPU 是执行模型计算的[设备](hardware-devices.md)，使用自己的[设备内存](device-memory.md)。编号稍后经[嵌入](embedding.md)查表成为向量，再参与[矩阵乘](matmul-and-weights.md)；[平台契约](vllm-platform-interface.md)约定引擎如何选择设备实现，这与词表规定“编号代表什么”是两层约定。

## 为什么要分词，代价花在哪里？

**分词在词表大小与序列长度之间取舍，也让模型能用已知单元表示少见词。** 把每个自然语言词都收成一个条目，词表会很大，仍会遇到新词；把所有文字拆得很细，序列又会变长。GLM-5.3-Flash 的文本词表维度为 **154880**，因此输入嵌入和输出打分都围绕这个有限维度组织。

子词是小于完整词的片段。常见的 BPE、WordPiece、Unigram 都能做子词切分，但学习和选取片段的规则不同：BPE 从小单元逐步合并，WordPiece 使用不同的合并准则，Unigram 从候选词表中筛选并给切分打分。Sennrich 等人的原始论文用 BPE 子词表示处理机器翻译中的稀有词。遇到未知字符时，是退回字节、使用未知标记还是采用其他处理，取决于具体分词器配置。

代价分两处。入口要用 CPU 时间套模板、编码文本，用主机内存保存消息、编号和请求记录；调度以后，更多 token 意味着更多待处理的位置，会影响模型计算与历史状态占用。**Token 数只是长度单位，不能直接当成设备内存字节数。** 设备上的权重、临时向量和历史状态怎样计费，见[设备内存](device-memory.md)与[单请求第 2 站](one-request.md#第-2-站-调度4-个-token-的预算和-15-个块号)。分词完成后才向引擎交接；模型各层之间的通信属于后续计算，并非每切出一个 token 就通信一次。

三个容易混淆的对象要分开：

| 对象 | 回答什么问题 | 会怎样变化 |
| --- | --- | --- |
| Token ID | 这是词表中的哪个单元？ | 同一编号可以在一条序列中反复出现 |
| 序列位置 | 这个单元出现在第几处？ | 每次出现占据自己的位置 |
| 嵌入向量 | 模型从哪些数值开始算？ | 用编号查嵌入表得到；后续各层继续变换 |

编号相近不代表含义相近，也不代表相邻位置。序列中的同一个编号能查到相同的初始嵌入，而位置和上下文会影响后续计算。

## 放到 GLM 双机：R1 在入口拿到了什么？

**R1 是[主线的示例请求](one-request.md#示例请求-r1-与官方双机部署)，约定套完模板并分词后，提示词有 4 个 token。** 这是教学设定；首图那句中文没有被指定为 R1，也没有指定实际编号。部署条件统一见[官方双机前提](glm-5-3-flash-two-node.md#部署前提)。

### 先把完整上下文变成编号

**输入长度要数最终序列，包含历史消息和模板带入的内容。** 系统说明、旧的用户问题、旧回答和当前问题，都会按模板组织起来；角色边界和回答起始标记按模板设置进入序列，也要计数。只给当前聊天气泡分词，无法复现服务收到的完整输入。

R1 的最终输入写成 p₀、p₁、p₂、p₃，列表长度为 4，位置是 0、1、2、3。这里的 p₀ 是“第一个输入编号”的符号名称，既不等于编号 0，也不保证与其他 p 不同。词表的 154880 是可供模型查表、打分的维度，与这条请求只有 4 个位置是两回事。

模板和分词是两个逻辑步骤，实际接口可以一次完成。手动复现时，如果先得到带特殊标记的模板文本、再单独编码，应避免编码器重复补起始或结束标记。比较两次 token 数，要同时固定消息内容、tokenizer 文件版本、特殊 token 设置、模板与模板选项。

### 再交给某一个引擎等待调度

**主机上传的是编号和请求设置，设备输入张量要到后面才准备。** API server 是接收 HTTP 的前端进程；EngineCore 是持有调度器的引擎进程；DP 把不同请求分给不同执行组。这套部署有两个 DP 组，R1 先进入其中一个引擎。

图中的模板或输入校验失败会返回入口错误；成功才建立请求。前端先登记输出队列和反分词状态，再按显式指定或负载选组。两边初始空闲、从第一个组开始比较时，R1 进入 DP0；具体打分和跨进程函数链见[调用链的入口一站](request-call-chain.md#七站逐站从哪个函数进往下调谁)。ZMQ 是这里传送请求对象的进程间消息库。

入口请求携带 4 个提示词编号、采样设置，以及可选的目标组编号；采样设置决定怎样选输出编号及何时停止。前端的输出记录负责之后把生成编号还原为文本，引擎里的请求记录负责等待和推进。到了 A3，worker（负责一张设备的执行进程）才按调度结果准备本步编号、位置等张量；A4 再做模型计算。

**这两笔内存账不可相加后统称显存。** 主机账包括字符串、整数列表、请求对象及输出队列，实际字节还取决于对象与传输表示；设备账包括后续输入张量、嵌入结果、权重和保存历史的 KV cache。KV cache 是模型为复用过去计算而保留的状态，GLM 各类层的存法不同。本页的“4 个整数”不等于“4 个字节”，也不是 R1 的总设备占用；每卡的形状与字节统一看[主线第 3 站](one-request.md#第-3-站-准备输入一份计划发给-8-个-worker)。

## 生成的编号怎样变回文字？

**模型产生候选分数，采样选出编号，反分词把累积编号还原为可见文本。** 这里的采样泛指选取输出编号，既包括取最高分，也包括按概率抽取。Token ID 接回已有序列后，才成为下一轮生成所依据的上下文。

一个输出 token 可以贡献多个字符，也可以只提供尚未拼成完整字符的字节片段。结束等特殊 token 具有控制用途，通常不会显示为普通文字；为匹配停止字符串，输出端还会按配置暂留一部分文本。因此，流式接口的一次文本增量与一个 token、一个汉字都没有固定的一一对应关系。

输入长度是已经有的 token 数；输出上限约束最多新增多少 token；上下文容量约束服务允许处理的总序列范围。请求也会因结束编号、停止字符串等条件提前结束。GLM 部署中的 MTP 是先猜候选、再由主模型验证的多 token 预测机制，草拟几个不等于最终输出上限；它如何推进 R1，见[主线第 5 站](one-request.md#第-5-站-采样与-mtp-草拟选出-y₀再猜-3-个)。

## 常见误解

- **“Token 就是一个字或一个词。”** 要看实际分词；中英文、空白、标点和少见字符的切法都受词表与规则影响，字数没有固定的 token 换算系数。
- **“词表大小就是可输入的长度。”** 词表描述可选编号的空间，输入长度数的是这次序列里的位置；重复编号也要逐次计数。
- **“两套分词器输出的整数可以直接互换。”** 编号的含义来自配套词表。两套词表若把同一个数分给不同单元，互换后就会查到错误的嵌入；模型权重也要与编号映射配套。
- **“只数最新问题，就知道请求长度。”** 模板格式化后的全部上下文才是计数对象，额外重复添加特殊标记还会改变结果。
- **“4 个 token 就只占很少显存。”** 入口只确定长度；权重常驻、历史状态的块分配和本步中间结果属于另外的设备账。
- **“流式收到三段，就生成了三个 token。”** 文本增量受字节拼接、反分词和判停影响；应使用生成编号的计数。

## 对照源码

### 怎么开

普通文本与聊天生成会初始化配套分词器，无须给 token 概念开启一个额外特性。`tokenizer` 未指定时使用模型名称或路径，`tokenizer_mode="auto"` 选择相应实现；三版的准确默认值与差异列在下表。

复现聊天输入时，Hugging Face 的 `apply_chat_template(..., tokenize=True)` 可以直接得到编号。若使用 `tokenize=False` 先渲染文本，再调用编码器，通常应设置 `add_special_tokens=False`，防止重复加入模板已有的标记。服务实际采用的模板、生成起始标记等选项也要一致。

### 会报什么错

固定控制流在解析不到可用模板时抛出 `ChatTemplateResolutionError`，先核模型文件和服务模板配置。启用长度校验时，输入处理会拒绝空的 decoder prompt、超出上下文容量的 prompt；生成任务中，prompt 恰好占满容量也会被拒绝，因为至少要留一个输出位置。带分词器校验编号时，若最大输入编号超过分词器最大编号与模型词表上界二者的较大值，会报 `Token id … is out of vocabulary`；这项检查只检查上界。这些都应从模板、编号或长度条件定位，不先归因于 NPU 计算。

### 开销和什么时候别开

入口的模板渲染、编码和出口的增量反分词使用主机资源；每个位置后续的计算与缓存另记设备账。`skip_tokenizer_init=True` 会跳过 tokenizer 和 detokenizer 初始化，要求调用方提供合法 `prompt_token_ids`，输出也只含编号。只在调用方已经负责正确编码和解码的接口路径使用；普通聊天消息仍需要完成模板与分词。

### 版本差异

这里核的是 vLLM 的文本分词契约与 HF 模板包装层；GLM 双机数值和流程图固定在控制流 `0fc695fc`、执行侧 `db701c1f`。下表中的 main 是仓库约定的 `84030bbe`，不是浮动分支，也不意味着三版都支持同一 GLM 部署。

| 核对项 | v0.23（0fc695fc） | v0.26（568afb3a） | main（84030bbe） | 对使用者意味着什么 |
| --- | --- | --- | --- | --- |
| 文本分词与 HF 模板处理 | 有 | 有 | 有 | 都将消息转为编号；具体切分由配套文件决定 |
