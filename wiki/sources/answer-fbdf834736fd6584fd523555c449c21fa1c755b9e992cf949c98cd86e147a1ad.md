## 一句话

提问是「Block Table 里的块是什么时候分配、什么时候回收的？」。**这个问题的前提本身要先纠正：块表里既不分配也不回收。** 分配与回收都发生在上游 EngineCore 进程的 `KVCacheManager` / `BlockPool`，块表只是事后把分出来的块号抄进格子 [I]。

本页是那次回答的归档。回答当时站内的示例请求还是一个旧算例：Qwen3-0.6B、单卡、37 个 token 的问题、200 个 token 的回答、一块 128 个 token。回答引用的三页后来都改写成了 GLM 双机主线，旧算例的数字现在只留在本页和归档原文里。**下面的步数、格数、块号都属于这个单卡旧算例，不是 GLM 双机的实测**；双机上同一件事怎么发生，见[换到 GLM 双机](#换到-glm-双机哪些说法还成立)。

## 什么时候分

调度器每挑中一条请求就调一次 `allocate_slots`，但只有「当前块装不下新 token」时才真正要块：还差的块数 = 向上取整（要存的 token 数 ÷ 块大小）− 手里已有的块数，不大于 0 就一块都不借 [C2]。落到回答当时的单卡旧算例上，一块 128 个 token。这也是钉住版本上普通模型在默认参数下的块大小：vLLM 构造配置时先把没指定的块大小填成 16 [C15]，配置收尾时调平台钩子 [C16]，Ascend 在钩子里调块大小刷新 [C18]，对非混合模型只要前缀缓存或 chunked prefill 任一开着、块大小又不是 128，就改成 128 [C3]；而这两项在用户没指定时按模型是否支持默认打开，Qwen3 这类普通模型都支持 [C17]。

| 时刻 | 要不要块 | 发生了什么 |
|---|---|---|
| 第 1 步 prefill | 要 1 块 | 37 个 token 需 `ceil(37/128) = 1` 块，`BlockPool.get_new_blocks(1)` 从空闲队列队头取走一块，`ref_cnt` 由 0 加到 1 [C4] |
| 第 1–91 步 decode | 不要 | 每步都调 `allocate_slots`，但第 0 块还有空格 |
| 第 92 步 decode | 要 1 块 | 第 0 块 128 格填满，第二次 `get_new_blocks(1)` |

**199 步 decode 一共只分了 1 次块**，这是最容易记错的地方 [I]。这条结论只属于单卡旧算例：GLM 双机上有一个缓存组每 1–4 步就借一次块。借块的一般规则见 [KV 块分配](../concepts/vllm-kv-block-allocation.md#请求要存-kv-时块从哪里来用完去哪里)。

## 什么时候回收

请求结束时 `free(request)` 把块**按逆序**交回 BlockPool：先交序列尾部的块，再交开头的块 [C5]。v0.23 上全注意力组的块按这个顺序排到空闲队列队尾，于是尾部那块先被别人取走，开头那块——最可能被下一条请求当作前缀复用的那块——留得最久 [C6]。v0.26 起排队规则变了，见下面[版本差异](#版本差异)。

回收只做两件事：减 `ref_cnt`、把计数归零的块排回队列。**它不清空内容**，块里的 KV 和登记过的哈希一直留着；等这块被别的请求取走时，`get_new_blocks` 才把它从登记表里摘掉，旧内容就此失效 [C4]。

## 拿到块不等于能被别人复用

这是问答里追加的一点：v0.23 上只有**写满**的块才会经 `cache_full_blocks` 登记进哈希表，成为可复用的缓存块；登记几块按「已算 token 数 ÷ 块大小」向下取整 [C8]。旧算例的第 1 块到请求结束都没写满，所以从没进过缓存表。

回答说第 1 块「用了 109 格」，这是按整条序列 37 + 200 = 237 个 token 数的。按真正写进 KV 的位置数是 108 格：37 个 prompt 位置加 199 步 decode 各写 1 个，共 236 个；最后一个输出 token 采样出来请求就结束了，没有再算它的 KV [D]。两种数法都不满 128，结论不变。

v0.26 起 BlockPool 多了 `cache_partial_block`，可以给没写满的块挂一条「部分」前缀缓存条目，main 上也有 [C10][C12]；什么条件下会用到见 [KV 块分配的版本差异](../concepts/vllm-kv-block-allocation.md#版本差异)。所以「写满才登记」是 v0.23 的规则，不是三版通用。

## 版本差异

钉点：v0.23 = vLLM 0fc695fc，v0.26 = vLLM 568afb3a，main = vLLM 84030bbe，与 [KV 块分配](../concepts/vllm-kv-block-allocation.md#版本差异)一致。原回答只比了 v0.23 和 v0.26 两列，没有核源码；main 一列和本节角标是归档后按钉住源码补核的。

| 项 | v0.23 | v0.26 | main | 意味着什么 |
|---|---|---|---|---|
| 请求结束时还回的块排在哪一头 | 全注意力组还块走 `free_blocks` 的默认分支，一律排队尾 [C6]；插队头的开关只给窗口外被跳过的块和滑动窗口组还块用 [C7][C14] | 按有没有哈希分两拨：没登记的插队头，登记过的排队尾，开关参数取消 [C9] | 同 v0.26；另外前缀缓存关着时一律插队头，按后进先出复用 [C11] | [!] 旧算例的第 1 块从没进过缓存表：在 v0.26 和 main 上会被下一条请求立刻取走，在 v0.23 上还得排在整条空闲队列后面 |
| 没写满的块能不能登记 | 不能 [C8] | 新增部分登记 [C10] | 有部分登记 [C12] | 「写满才登记」只在 v0.23 上是绝对的 |

## 块表侧只剩记账

同一条请求在[块表](../concepts/block-table.md)上的全部动作：第 1 步 `add_row([5])`，第 92 步 `append_row([42])`，结束时 `clear_row(0)` 把用过的格子填回 0 [C13]。表里每格是 int32，回答说「整整 200 步只改了 8 个字节」，指的是这两次写进去的两个块号格，各 4 字节；结束时这两格又被写回 0，每行的块数计数也跟着变 [C13]。表在每步的其他开销见 [Block Table 每步花多少](../concepts/block-table.md#表本身占多少每步花多少)。

## 换到 GLM 双机：哪些说法还成立

部署前提见[双机部署页的「部署前提」](../concepts/glm-5-3-flash-two-node.md#部署前提)。双机主线的示例请求 R1 只有 4 个 token 的 prompt，这是教学设定，定义见[一条请求](../concepts/one-request.md#示例请求-r1-与官方双机部署)。下表左列是本页的单卡旧算例，右列是同一件事在双机上的样子；右列的数字都在链接页里推导，这里不重算。

| 说法 | 单卡旧算例（本页） | GLM 双机 R1 |
|---|---|---|
| 分配、回收在哪发生 | 引擎进程的 KVCacheManager / BlockPool | 仍然如此；R1 落在 DP0，只从 node0 引擎的池子借块，见 [R1 从借块到还块](../concepts/vllm-kv-block-allocation.md#放到-glm-双机r1-从借块到还块) |
| 一块覆盖几个 token | 128 | full 组一块 640，推导见[为什么一个逻辑块是 640 个 token](../concepts/glm-5-3-flash-two-node.md#为什么一个逻辑块是-640-个-token) |
| 第一步借几块 | 1 块 | 5 个缓存组一起借，共 15 块，见[第 2 站](../concepts/one-request.md#第-2-站-调度4-个-token-的预算和-15-个块号) |
| decode 步借不借 | 只在第 92 步借 1 次 | full 组和 KDA 组多数步不借；indexer 尾状态组块长 4，每 1–4 步借还各 1 块，见 [decode 每一步](../concepts/vllm-kv-block-allocation.md#decode-每一步full-组和-kda-组多数步不借尾状态组边借边还) |
| 结束还几块 | 2 块，逆序交回 | 16 或 17 块一次还清，见[结束](../concepts/vllm-kv-block-allocation.md#结束1617-块一次还清) |
| 写满才登记、逆序让开头块留得久 | 回答按前缀缓存开着讲，这两条决定哪块能被复用 | 前缀缓存关着，块从不登记；排在哪一头只影响下次拿到哪几个号，不影响复用，见 [GLM 双机上它开着吗](../concepts/prefix-caching.md#glm-双机上它开着吗) |
| 块表 | 一张表，这一行只写两格 | 5 个缓存组各一张表；full 组的 1 个块号在表里展开成 5 个 kernel 块号，见 [R1 的块号进了哪几张表](../concepts/block-table.md#放到-glm-双机r1-的-15-个块号进了哪几张表) |

GLM 专用镜像的分配代码用 vLLM 0fc695fc，排队规则按上面 v0.23 一列走。

## 这份记录不能证明什么

- 回答里出现的物理块号 5 和 42 是当时被引页明确标注的假设值，不是某次真实运行的观测结果 [I]。
- 原回答没有覆盖 main 上的回收顺序，也没有涉及抢占时的块释放路径。前者已在[版本差异](#版本差异)补上；后者见[池子不够时：宁可抢占，也不借一半](../concepts/vllm-kv-block-allocation.md#池子不够时宁可抢占也不借一半)。
