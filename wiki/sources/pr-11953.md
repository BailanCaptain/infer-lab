## 一句话

**PR #11953 的意图是把 `layer_sharding` 整条特性从 vllm-ascend 里拿掉**——配置项、`NPUPlatform` 里的合法性校验、专用文档页、发布说明里的条目、以及依赖它的单元测试与 e2e 配置。标题写的是 `[Refactor] remove layer sharding`，合并提交 `896012151dbaaa444e940f19106fde877d616dc9` [M1]。

本页的依据只有一份归档材料：PR 正文、若干评论以及**五个文件**的 diff 片段。材料明确列出另有四十多个被改动但**未提供差异正文**的文件（含 `vllm_ascend/ops/layer_shard_linear.py`、`vllm_ascend/ops/flashcomm2_oshard_manager.py`、`vllm_ascend/model_loader/rfork/rfork_loader.py` 等）[M1]。

单看这份材料，超出这五个文件的说法都只是 PR 描述的**自述** [I]。本次提交可在本地 `vllm-ascend` 仓库查到；归档后按钉住提交补核的几处（RFork 绕行与各分支状态），下文均单独标了源码角标。

## 作者自己怎么说的

PR 正文三段，逐条抄要点 [M1]：

- **Removal of Layer Sharding**：`layer_sharding` 特性及其实现，包括 `Flashcomm2OShardManager` 和相关 ops，已从代码库中完全移除。
- **Documentation Updates**：删除全部相关文档，包括专门的 guide、导航条目，以及 release notes 和 feature matrix 里的引用。
- **Cleanup of Test Infrastructure**：删除依赖该特性的单测与集成测试，并更新其余测试以去掉依赖。

用户可见变更那一栏，作者称该功能使用较少、价值有限，并认为删除不会带来功能风险；测试栏只填了 `No involvement.`。[M1][S12] **“使用较少”没有说明用户数为零，测试栏也没有给出具体方法或结果。** 归档还记录了 E2E 重跑，因而不能把这两句话解释成“没人使用，所以没有测试”。

审阅机器人给出的建议摘要与作者的说法在一处不同：机器人写的是 `Yes, the layer_sharding option is removed from --additional-config. Users can no longer enable layer sharding.`，即把它归为**有**用户可见变更 [M1]。这条分歧材料里没有后续结论 [I]。

## 五个文件里实际看到的删除点

下表五行全部出自那份归档材料的 diff 片段 [M1]：

| 文件 | 删掉了什么 |
|---|---|
| `vllm_ascend/ascend_config.py` | `AscendConfig` 里 `self.layer_sharding = additional_config.get("layer_sharding", None)` 及其后的 `logger.info_once` 提示（原提示说该特性在 FLASHCOMM2 与 DSA-CP 开启时效果最好，不带这两个特性用可能显著劣化） |
| `vllm_ascend/platform.py` | 类方法 `_validate_layer_sharding_config`，以及 `check_and_update_config` 流程里对它的调用；该校验原来要求 `kv_transfer_config.kv_role == "kv_producer"`，否则抛 `ValueError` |
| `docs/source/user_guide/configuration/additional_config.md` | 表格中那一行：`layer_sharding`，类型 `dict`，默认 `{}` |
| `docs/source/user_guide/feature_guide/layer_sharding.md` | 整个文件删除（80 行） |
| `docs/source/user_guide/release_notes.md` | 三条历史条目：DSV32 混合部署下 layer_sharding 报错的修复（#8717），以及两处 “Flashcomm2 now works with oshard generalized feature”（#4723） |

**注意 platform.py 的删除意味着约束一起消失了。** 原来在非 P 节点上配 `layer_sharding` 会在启动期直接报错；这个 `raise ValueError` 随校验方法一并删掉 [M1]。删除后 `--additional-config` 里再写这个键会走什么路径，五个片段里看不出来 [I]；在 v0.26 和 main 上的实际表现见 [layer_sharding 参数页的事实表](../params/layer-sharding.md#事实表)。

这里的报错条件还取决于配置值的真假：在仍保留校验的 `2c59ff10` 和 `db701c1f` 快照中，缺键或空列表等假值会直接返回；只有配置值为真时，才要求存在 `kv_transfer_config` 且角色为 `kv_producer`。该函数不检查元素类型，通过此项不代表配置内容有效（见已核来源 5、6 `platform.py#L338-L346`，为源码判断、未做启动实测）。

这条校验原来在启动期由平台插件 NPUPlatform 的配置检查调用 [C9]，也就是 vllm-ascend 接进 vLLM 的第一个口子，见[请求调用链](../concepts/request-call-chain.md#vllm-ascend-从六个口子接进-vllm)；所以配错时是服务起不来，而不是请求跑到一半出错。

## 被删的那份文档说过什么

`layer_sharding.md` 是这次一起删掉的，它是 PR 材料里关于该特性**唯一完整的官方描述**，值得留下摘要 [M1]：

- 做法：第 i 层的 linear 权重只存在设备 `i % K` 上（`K` 为通信组设备数），其余设备初始化时只持有一个轻量的 shared dummy tensor，前向时通过异步 broadcast 按需取真权重。
- 收益前提：算当前层（MLA 或 MOE）时在后台异步 broadcast 下一层权重；原文以 attention 计算能够覆盖搬运耗时为前提，描述 `o_proj` 传输被完全掩盖。具体负载是否满足这个前提，仍要比较实际计算与搬运时间。
- 适用场景：层数极深的架构（举例 DeepSeek-V3/R1 的 61 层；这是文档原文的例子，不是本站 GLM 的层数）、以及 DSA-CP 或 FlashComm2 这类要求整张 `O` 投影矩阵每层都驻留显存的情况。
- 两条限制：只能在 PD 分离的 **P 节点**开；**RFork 权重传输不支持它**——`--load-format rfork` 与 `layer_sharding` 同时给出时，RFork 传输被绕过，模型退回默认 loader 加载。
- 用法是列表而不是 dict：`--additional-config '{"layer_sharding": ["o_proj", "q_b_proj"]}'`。

最后这一点与同一 PR 删掉的配置表那一行对不上：表里写的类型是 `dict`、默认 `{}`，而 guide 和两份示例给的都是字符串列表 [M1]。删除之前文档内部就不一致 [I]。

## 版本边界：材料证不了，钉住提交上查得到

材料里能确定的版本信息只有两行：`vLLM version: v0.23.0`，以及一个上游 vLLM main 的提交链接 [M1]。这是 PR 的 CI 环境标注，**不是 vllm-ascend 的分支归属** [I]。

所以：

- 单靠这份材料，**不能**断言 v0.23 维护分支、v0.26 分支或 `main` 开发主线上 `layer_sharding` 已经不存在。按固定提交核对：v0.23（`2c59ff10`）与本站 GLM（`db701c1f`）均保留配置读取与启动校验 [C4][C5][C8][C6]；v0.26（`2ed6cbba`）、v0.30.0rc2（`7d825229`）与 `main`（`baa023ad`）均包含此合并，`vllm_ascend/` 下已无 `layer_sharding` 标识。已核标签中最早包含它的是 `v0.24.0rc1`（发布说明未列此项，`baa023ad` 将其记在 `v0.26.0rc1` 的「Deprecation and Breaking Changes」下 [S7]）。版本状态的真相源仍是 [layer_sharding 参数页的版本谱系](../params/layer-sharding.md#版本谱系)。
- 本站 GLM 双机用不到它：`db701c1f` 上这个键还认，但双机是混部、没有 `kv_transfer_config`，配上会在启动期被上面那条校验拒绝，详见[参数页「开了的代价」](../params/layer-sharding.md#开了的代价)。
- 材料记录了冲突提醒、随后一次 E2E 重跑，以及最终合并事件 [M1]。这些事件能说明审阅过程，但每次提交具体怎样变化，仍要看对应提交差异。
- 差异依据是 `2b115d02dd219d1278ffea1b5dc67ae61bba422f → 896012151dbaaa444e940f19106fde877d616dc9` 的第一父提交差异 [M1]，反映的是「这次合并往主线加了什么」，而非作者分支的逐次提交。本地仓库中该合并提交只有 `2b115d02` 一个父提交（整条 PR 压成一个提交合入，共改 51 个文件），与材料「5 个有正文、40 多个只有名字」吻合。

## 影响面：材料给出的是文件名清单，不是调用关系

材料列出的未提供差异正文的文件里，有几类值得单独点出来，因为它们说明这次删除的波及范围远超五个片段 [M1]：

- **算子实现**：`vllm_ascend/ops/layer_shard_linear.py`、`vllm_ascend/ops/flashcomm2_oshard_manager.py`、`vllm_ascend/ops/linear_op.py`。
- **注意力与并行**：`vllm_ascend/attention/mla_v1.py`、`sfa_v1.py`、`attention_v1.py`、`vllm_ascend/distributed/parallel_state.py`。
- **量化与加载**：`vllm_ascend/quantization/method_adapters.py`、`vllm_ascend/model_loader/rfork/rfork_loader.py`。
- **多机 e2e 配置**：若干 `DeepSeek-V3.2` / `DeepSeek_V3.2T_MTP*_PD` 的 yaml。

**但这只是“文件被改过”。** 每个文件改了几行、是否连带改变默认行为，材料没有给出。`rfork_loader.py` 曾被删掉的文档点名（与 `layer_sharding` 互斥并绕过 RFork）[M1]。按本地提交补核可确定：删掉的正是这条绕行——原来检查 `layer_sharding` 是否为真，满足时记理由、打 warning 并退默认 loader；删后该处只剩动态 EPLB 一条 [C2][C3][C11]。两个算子文件 `layer_shard_linear.py` 与 `flashcomm2_oshard_manager.py` 整文件删除，其余文件本页未逐个核对。

这里「有没有」的判断是配置值是否为真，而非键是否存在：`2b115d02` 的 RFork 辅助函数返回 `bool(additional_config.get("layer_sharding"))`，空列表不会触发绕行。该快照先判 `layer_sharding`，再用 `elif` 判动态 EPLB，两者同开时记录理由为 `layer_sharding`（见来源 2、3 `rfork_loader.py#L110-L112`、`#L234-L246`，不推广至删后行为，也未做加载实测）。

## 常见误解

- **「这个 PR 合了，所以我手上的 vllm-ascend 里已经没有 `layer_sharding` 了」**——材料只能证明主线上有这么一次合并。v0.23 维护分支就没跟着删，它的配置读取还在；看自己手上那版的结论，以参数页版本谱系为准。
- **「作者说 no functional risk，所以配了这个键也不会有事」**——在还没删的版本上，非 P 节点把它设为非空列表等真值，会在启动期 `raise ValueError` [C5]；删除后这个校验一起消失，材料里看不出删后的行为，参数页事实表写了 v0.26 和 main 上分别会怎样。
- **「五个 diff 片段就是这个 PR 的全部改动」**——材料自己写明另有四十余个文件被改动但未提供差异正文，并明确要求不得把所选片段当作全 PR 或完整运行时行为。
- **「`layer_sharding` 是个 dict，按文档表格填」**——被删的 guide 和两处示例给的都是字符串列表（`["o_proj"]`），与配置表里标的 `dict` / `{}` 不一致。
